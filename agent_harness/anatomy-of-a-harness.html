Anatomy of a harness — the parts that turn a model into an agent

Every harness has the same skeleton: a loop, a set of tools, context management, and guardrails — plus the extras that make it pleasant: memory, subagents, skills, hooks, and a plug-in protocol for more tools. We'll tour each part using Claude Code as the worked example, because it's a harness you've already lived inside. Nothing here is Claude-specific — it's the generic anatomy, with real names attached.

2 · The agentic loop

The harness repeatedly: takes the current context, asks the model what to do next, and — if the model requests a tool — executes it and feeds the result back. It ends when the model signals completion, a limit trips (max iterations, max tokens), or a guardrail intervenes.

  • Stop conditions matter more than people think. A good harness distinguishes "I'm done" from "I'm stuck" and can hand control back to a human instead of spinning.
  • Workflows as harnesses: newer systems let the harness dynamically spin up a small multi-agent fleet per task (a "dynamic workflow" is really a harness the harness wrote for one job — splitting a big task across sub-agents, each with isolated context).

3 · Tools — the agent-computer interface

The harness decides what the model can touch, then describes each tool well enough that the model calls it correctly. Anthropic calls this the agent-computer interface (ACI): the quality of your tool names, descriptions, and schemas is a bigger lever on agent reliability than the model choice. Claude Code's built-ins are the classic set:

Capability Claude Code tool Why the harness exposes it
Read the world Read, Glob, Grep Model sees the actual repo, not a guess
Change the world Write / Edit Precise, reviewable file edits
Run the world Bash Tests, builds, scripts — the verification loop
See the web WebFetch, WebSearch Docs, current events, external state
Do work in parallel Task (subagents) Fan-out research while the main thread keeps focus
Run packaged procedures Skill Invoke a documented, reusable workflow on demand

4 · Context management

The model can only "see" what's in its context window — so context is the scarcest resource, and the harness is its curator. This is increasingly its own discipline, often called context engineering.

  • What goes in: the system prompt (identity, rules), project instructions, tool definitions, the relevant files and command output, conversation history.
  • What's kept out: irrelevance. The best harnesses don't dump your whole repo in; they read on demand and let the model search.
  • What happens when it overflows: compaction — the harness summarises the conversation so far and continues on a shorter thread, keeping the task alive across tens of thousands of tokens.
  • Persistence: memories that survive the session live in files — e.g. a project CLAUDE.md, memory directories, per-agent memory JSON — re-injected at session start.

5 · Guardrails: permissions, modes, hooks

A harness is only as trustworthy as its brakes. This is where "agent" diverges from "autonomous script".

  • Permission modes — read-only (plan), ask-on-every-action (default), or auto-run for trusted actions. The user stays in control of anything irreversible.
  • Hooks — the harness fires events around its own behaviour (before a tool runs, after a tool runs, on user prompt, on stop, before compaction, at session start). Hooks let you inject policy: block a dangerous command, run a formatter after every edit, enforce that no file outside a path is touched. Hooks are executed by the harness, not the model — that's what makes them trustworthy policy.
  • Sandboxing — run tools in a container/worktree so a mistake can't nuke the real repo.
  • Stopping rules & iteration caps — budget for how long the loop may run.

6 · Memory & continuity

Between turns and between sessions, the harness is what remembers:

Mechanism Scope Used for
CLAUDE.md / AGENTS.md Project Standing instructions, conventions, do/don't
Global user memory Across projects Your preferences, workflow, identity
Memory folders Agent-scoped Facts the agent accumulated about the work
Session logs / transcripts Ephemeral → auditable Resume, review, learn from past runs

7 · Subagents, skills, and MCP — the extensibility layer

  • Subagents: smaller, purpose-built agents with their own system prompt and a trimmed toolset, spawned by the main agent for parallel or isolated work. Isolation of context is the superpower — subagent A's mess doesn't pollute subagent B.
  • Skills: a folder + SKILL.md that packages a reusable procedure (with assets and scripts) the model can load on demand. Skills make the harness teachable.
  • MCP (Model Context Protocol): the open standard that lets any harness connect to external tools/servers — databases, browsers, internal APIs — with one protocol instead of bespoke integrations. MCP is the harness's USB port.

8 · "You've been inside a harness all along"

If this tour feels like a description of a house you already live in, that's the correct reaction — it is. Every Claude Code session you've run exercised all of these parts: the loop that kept going after a test failed, the permission prompt that stopped a risky command, the compaction when the conversation got long, the CLAUDE.md that shaped the answers, the subagents and skills you've wired in. You weren't using "an AI" — you were operating a harness. Once you see it, you can't unsee it, and that's the point of this page.
