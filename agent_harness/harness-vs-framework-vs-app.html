Harness vs framework vs application — where does each layer end?

Half the confusion around "harness" is that people use it for three different layers of the same stack. This page draws the boundaries: the model reasons, the harness owns the loop and the tools, the framework/library gives you reusable building blocks to assemble your own orchestration, and the application is what your user actually touches. Once the layers are clean, "build vs buy" answers itself.

Two facts make the picture confusing: (a) a product like Claude Code spans layers 1 (it is a harness) and 3 (it is an application you run), and (b) frameworks are often mislabelled "harnesses". Naming aside, what matters is who owns the loop and the tools — that owner is the de-facto harness.

2 · The ownership test

Ask one question of any tool: "does it own the agentic loop — deciding when to call the model, execute its tool calls, and feed observations back — or does it just give me pieces to assemble?"

Layer Owns the loop? You supply Archetypes
Harness Yes — end to end Goals, policy, config Claude Code, Codex CLI, Gemini CLI, Cursor, Docker Agent coding harness
Framework / SDK No — it's a toolkit you wire into a loop The loop, state, model wiring LangGraph, OpenAI Agents SDK, Claude Agent SDK, AutoGen, CrewAI
Application Uses one above it Your domain, UI, users Support bots, review agents, your in-house tools

This is why you'll hear both "LangGraph is my harness" and "I use Claude Code as my harness" — and both speakers are right in their own stack. The first person assembled a loop from framework parts; the second is using a pre-built loop. Same goal, different altitude.

3 · Frameworks are the Lego; the harness is the build instructions + motor

A framework gives you primitives — graph nodes, agents, handoffs, guardrails, memory stores — but no one runs a "LangGraph" that does work by itself. Someone has to write the loop, connect a model, expose tools, and decide the stopping rules. When you ship that, you've written a harness (a bespoke one). Conversely a ready-made harness like Claude Code hands you a finished loop with first-class tools and lets you configure, not construct.

Use a ready-made harness when
  • The domain matches (code, general agent work)
  • You want tools, hooks, and memory for free
  • You'd rather configure policy than write loops
Assemble from a framework when
  • You need bespoke orchestration/state machines
  • The loop must live inside your product's codebase
  • You need fine-grained control over model/tool routing
Write from scratch only when
  • You're learning (see page 5)
  • You have unusual constraints (offline, custom protocol)
  • You accept owning retries, safety, and context forever

4 · Workflows vs agents — the policy half of the picture

Anthropic's building agents guidance adds the other axis. A workflow is predetermined code paths (chaining, routing, orchestrator-workers, evaluator-optimiser) — the shape is fixed. An agent lets the model decide its own path, dynamically using tools. The harness is what executes whichever you pick: a workflow is a harness whose loop has been partially hard-coded; a full agent is a harness whose loop is mostly delegated to the model.

Rule of thumb from Anthropic: reach for the simplest thing that works. Start with a workflow; only use an autonomous agent where you need flexibility at scale and can afford the verification. A harness makes both cheap to swap — which is the real argument for "buying" one.

5 · The "harness as orchestrator" pattern

One more zoom level that shows up in production (and in your industry_standards reading): an outer harness that delegates real work to a coding CLI as a sub-process. A CI system spawns Claude Code with a persona, policy hooks, and a spec file, then inspects the result and either ships it or loops back for a fix. Here the inner agent is a harness and a tool of an outer orchestrator — evidence that "harness" is a relative label: whatever owns the loop at your altitude.

6 · Deciding for yourself

  1. Map the layer you're actually in. Building a product feature? You're at layer 3 and will call a harness or SDK, not build one.
  2. Prefer the ready-made harness for coding tasks. You already have one; configuring it (CLAUDE.md, skills, hooks, permissions) beats re-implementing it.
  3. Choose a framework only where your product needs the bespoke loop. Then you're writing a small harness — see page 5 for the minimal shape.
  4. Keep the layers honest. When someone says "just a wrapper", ask which layer they mean — usually they've mistaken the harness for the model.
