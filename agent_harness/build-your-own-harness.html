Build your own harness — the agentic loop is just code

Pages 1–4 are theory; here's the payoff. A harness is not magic — at its core it's a while loop that asks the model "what next?", executes the tool it names, feeds the result back, and repeats. Below is a ~100-line harness you can actually run (no API key needed: it drives a scripted "model" so you can watch the loop). Then we show the one swap that turns it into a real agent, and where to stop hand-rolling.

1 · The five pieces, and nothing else

Strip away the marketing and a harness is:

  1. A model interface — something that returns text or a tool call.
  2. A tool registry — name → (description, function).
  3. A message store — the running context fed back to the model.
  4. An executor — runs the requested tool, catching errors.
  5. Guardrails — permission gate, iteration cap, stop conditions.

Everything fancy — subagents, skills, compaction, hooks — is an upgrade to one of these five. Build the five and you understand every harness ever made.

2 · The runnable harness

Copy this to mini_harness.py and run it with Python 3.10+:

"""mini_harness.py — a ~100-line agent harness you can run today.

Runs OFFLINE: "call_model" is a scripted stand-in for a frontier model, so you can
see the agentic loop (reason -> act -> observe -> repeat) without an API key.
Swap in a real model call at the marker at the bottom to make it live.
"""
from __future__ import annotations
import json
import re
import sys

MAX_ITERATIONS = 10

# ----------------------------------------------------------------------------
# 2. TOOL REGISTRY: name -> (description, function)
#    The harness never hard-codes what a tool does — the MODEL decides via these.
# ----------------------------------------------------------------------------
TOOLS = {
    "add": {
        "description": "Add two integers. args: {'a': int, 'b': int}",
        "fn": lambda a, b: a + b,
    },
    "grep": {
        "description": "Search files for a term. args: {'pattern': str}",
        "fn": lambda pattern: f"hits: {len(re.findall(pattern, 'apple banana cherry'))} for {pattern!r}",
    },
    "read_file": {
        "description": "Read a file. args: {'path': str}",
        "fn": lambda path: f"(contents of {path}, 3 lines)" if path else "ERROR: no path",
    },
}

# A fake "smart enough" model: it looks at the GOAL and the LAST tool result,
# then decides the next step. Real models do the same — just with far more
# sophistication. Each branch is one "reason" step of the loop.
def call_model(messages: list[dict]) -> dict:
    """Return EITHER {'kind': 'final', 'text': str} OR {'kind': 'tool', ...}."""
    last = messages[-1]["content"]
    s = messages[0]["content"].lower()

    if "total" in s and last.startswith("tool-result add"):
        total = int(last.split("=")[1])
        return {"kind": "final", "text": f"Total is {total}. Done."}

    if "read a file" in s:
        m = re.search(r"hits: (\d+)", last)
        if m:  # grep answered -> we have everything, wrap up
            n = int(m.group(1))
            return {"kind": "final", "text": f"Found {n} hit{'s' if n != 1 else ''}. Done."}
        if last.startswith("tool-result read_file"):
            return {"kind": "tool", "name": "grep", "args": {"pattern": "apple"}}
        return {"kind": "tool", "name": "read_file", "args": {"path": "notes.txt"}}

    if "total" in s:  # fresh goal, first step of the loop
        return {"kind": "tool", "name": "add", "args": {"a": 6, "b": 7}}

    # Unknown request -> admit defeat instead of spinning forever.
    return {"kind": "final", "text": "I don't know how to do that yet."}


# ----------------------------------------------------------------------------
# 5. GUARDRAILS (minimal): permission gate + iteration cap.
# ----------------------------------------------------------------------------
def human_approves(action: str) -> bool:
    """Ask the operator. `input()` is the world's simplest permission prompt.

    If there is no terminal (piped / CI), deny by default — fail closed.
    """
    if not sys.stdin.isatty():
        return False
    return input(f"  [allow] {action}? [y/N] ").strip().lower() == "y"


# ----------------------------------------------------------------------------
# 3 + 4. MESSAGE STORE + EXECUTOR live inside the loop below.
# ----------------------------------------------------------------------------
def run_agent(goal: str, *, ask_every_tool: bool = False) -> None:
    messages = [{"role": "system", "content": f"goal: {goal}"}]
    print(f"\n>>> Task: {goal}")

    for step in range(1, MAX_ITERATIONS + 1):
        decision = call_model(messages)          # 1. model proposes
        if decision["kind"] == "final":
            print(f"  [done] {decision['text']}")
            return

        name, args = decision["name"], decision["args"]
        action = f"{name}({json.dumps(args)})"
        if ask_every_tool and not human_approves(action):   # guardrail
            print(f"  [blocked by user] {action}")
            return

        tool = TOOLS.get(name)
        if tool is None:
            result = f"ERROR: unknown tool {name}"
        else:
            try:
                result = str(tool["fn"](**args))             # 2. harness executes
            except Exception as e:                           #    errors -> observations
                result = f"ERROR: {type(e).__name__}: {e}"

        messages.append({"role": "assistant", "content": action})
        messages.append({"role": "user", "content": f"tool-result {name}={result}"})
        print(f"  step {step:2d}: {action} -> {result}")

    print(f"  [cap] hit {MAX_ITERATIONS} steps without finishing.")


if __name__ == "__main__":
    # --- Try the default demo ------------------------------------------------
    run_agent("Add 6 and 7 and give me the total.")

    # --- Try a different goal (read_file -> grep path) -----------------------
    run_agent("Read a file, then tell me what you found.")

    # --- Now the SAME harness with guardrails ON ------------------------------
    run_agent("Add 6 and 7 and give me the total.", ask_every_tool=True)

    # === MARKER: make it live =================================================
    # Replace call_model's body with a real provider call, e.g. Claude:
    #   import anthropic
    #   client = anthropic.Anthropic()
    #   tool_specs = [{"name": n, "description": t["description"]} for n, t in TOOLS.items()]
    #   ...send messages + tool_specs via client.messages.create(...),
    #   then:  stop == "tool_use"  -> return {"kind":"tool", ...} from the block
    #   else:  return {"kind":"final","text": text}
    # The loop above is unchanged. THAT is the whole point of a harness.

Run it and watch: each step N line is one trip around the agentic loop from page 1. The third run shows the permission gate stopping the exact same task.

3 · The anatomy, mapped onto the code

Anatomy (page 2) Where it is in mini_harness.py
Agentic loop run_agent's for step loop: propose → execute → append → repeat
Tools / ACI TOOLS registry — descriptions are the whole interface the "model" sees
Context management messages list grows and is passed whole to call_model (real harnesses compact it when it overflows)
Guardrails human_approves permission gate + MAX_ITERATIONS cap + error capture in the executor
Model interface call_model(messages) -> decision — swap the body at the MARKER to go live

4 · Graduating from hand-rolled to production

Your mini harness nails the concept, but going live exposes the hard 20% that real harnesses exist to save you from:

  • Reliable tool-call parsing — real providers return structured tool_use blocks; hand-parsing free text is fragile.
  • Context compaction — long tasks overflow the window; summarising correctly is hard.
  • Sandboxing & audit — a real Bash tool needs permissions, containers, and logs; your input() gate doesn't scale to unattended runs.
  • Subagents & parallelism — isolated contexts for fan-out work.
  • Skills & memory — teachable, persistent behaviour across sessions.
So when do you hand-roll? When you're learning (now), or when your product genuinely needs a loop that lives inside your codebase with bespoke state. Otherwise reach for an existing harness or the SDK layer — building your own from scratch is how you appreciate the machinery, not how you ship a product.
