Agent harness · page 1 of 5

What is an agent harness? The brain is the model. The body is the harness.

A language model, on its own, produces text. An agent does things: it reads your repo, edits a file, runs a test, browses a page, and — crucially — keeps going based on what happened. That gap — between "produces text" and "does things" — is filled by a piece of software called an agent harness.

1 · The one-sentence definition

An agent harness is the software scaffold around a model — the loop, the tools, the context management, and the guardrails — that turn raw model intelligence into a working agent. Anthropic has used exactly this framing when describing Claude Code: the harness is what organises how the model reads a project, edits code, runs commands, and adjusts based on results. When people say "X runs in a harness", they mean "X is being driven by an LLM inside a controlled loop with tools, not by the raw API alone."

Useful analogy from the earliest days of the term: a horse needs a harness before it can pull a cart. The intelligence (horse) is nothing without the rig that connects its strength to a useful job — and constrains where it can go. A test harness runs software through assertions; a prompt/agent harness runs an LLM through a loop of perception and action.

2 · What the raw API gives you — and what it can't

Call a chat API and you get back one thing: text. That text can describe edits, but nothing changes on disk. It can propose a command, but nothing executes. The model has no hands, no eyes on your system, and no memory of yesterday unless you supply it. All of those — capability, perception, memory, control — are the harness's job.

A raw model (the brain)
  • Reason, plan, and write
  • Understand language & code
  • Generate the intent of an action
What the model can't do alone
  • Read your actual files or run code
  • Act on the world or change state
  • Remember anything between calls
  • Know when to stop or ask permission
  • Be interrupted, sandboxed, or audited
The harness (the body)
  • Runs the loop that keeps the model going
  • Gives it tools and executes them
  • Manages the context window
  • Enforces permissions & guardrails
  • Persists memory across sessions

This is why "just a wrapper around an API" is usually said by people who haven't tried to make a model do real work. The wrapper — the loop, tools, and constraints — is most of the engineering.

3 · The agentic loop: the heart of every harness

The single most important idea is that an agent is not one call — it's a loop. The model proposes an action (usually a tool call), the harness executes it, feeds the result back, and the model decides the next step. It repeats until the model says it's done, the harness hits a safety or iteration limit, or a human interrupts.

flowchart LR
  U[You give a goal] --> H[Harness]
  H --> M[Model reasons]
  M -->|tool call: read/edit/run/search| H2[Harness executes the tool]
  H2 -->|observation: result + errors| M
  M -->|done / needs help| H3[Harness returns / asks permission]
  H3 --> U
  H2 -.->|guardrail blocks or prompts| U

Each arrow back into the model is one "turn". A long coding task can be dozens of turns. Everything that makes this loop safe, fast, and effective — tool selection, context packing, stopping rules — is harness engineering.

4 · Where the word actually shows up

You'll hear "harness" in several real places, and they're all this same idea at different zoom levels:

Context What it means Example
Coding agents The CLI/app that drives a model through your repo Claude Code, OpenAI Codex CLI, Gemini CLI — each is a harness
SDK harness The library you use to build your own agent loop Claude Agent SDK, OpenAI Agents SDK, LangGraph
Custom harness on a CLI Outer orchestration that delegates real work to a coding agent A CI "harness agent" that invokes Claude Code with policy & hooks
"Dynamic" harness A harness that writes its own multi-agent orchestration at runtime Claude Code dynamic workflows (see anatomy, page 2)

Notice the thread: every sense is the machinery that lets a model act in a controlled way. The product names differ; the skeleton is the same.

5 · Why the harness — not the model — is the product

Models converge: the frontier labs are all within striking distance of each other on raw reasoning. But harnesses diverge wildly. Whether an agent can recover from a failed test, whether it will ask before doing something destructive, whether it remembers your preferences next week, whether a junior engineer can safely run it unattended — these are harness properties, and they're where products win or lose.

  • Safety lives in the harness: permission prompts, sandboxes, read-only modes.
  • Reliability lives in the harness: retries, verification loops, stopping rules.
  • Capability is granted by the harness: which tools exist and how well they're described.
  • Continuity comes from the harness: memory files, session logs, context compaction.

That's why Anthropic talks about "harness design patterns" for balancing intelligence, latency, and cost — and why the best use of an LLM increasingly means choosing and configuring a great harness, not shopping for a slightly smarter model.
