A richer server: tools, resources & prompts

Real MCP servers expose more than tools. Add resources (read-only data by URI) and prompts (reusable templates), and learn exactly how each one surfaces in LangGraph.

The three primitives, and who controls them

flowchart TD
    S["FastMCP server"] --> T["🛠️ Tools
model-controlled
the LLM decides to call"]
    S --> R["📄 Resources
app-controlled
the app loads into context"]
    S --> P["💬 Prompts
user-controlled
the user invokes a template"]

Same server, three kinds of capability — each meant for a different decision-maker.

The code — kb_server.py (a tiny knowledge base)

from fastmcp import FastMCP

mcp = FastMCP("Knowledge Base")

NOTES = {
    "onboarding": "Welcome! Step 1: clone the repo. Step 2: run setup.sh.",
    "release":    "Releases ship every other Thursday after QA sign-off.",
}

# ---- TOOL: the model can CALL this to take an action ----
@mcp.tool
def search_notes(query: str) -> list[str]:
    """Search internal notes for a keyword and return matching titles."""
    return [k for k, v in NOTES.items() if query.lower() in v.lower()]

# ---- RESOURCE: read-only data addressed by a URI ----
@mcp.resource("notes://{title}")
def get_note(title: str) -> str:
    """Return the full text of a note by its title."""
    return NOTES.get(title, "Not found.")

# ---- PROMPT: a reusable, parameterised template ----
@mcp.prompt
def summarize_note(title: str) -> str:
    """Build a prompt that asks the model to summarise a note."""
    return f"Summarise the note titled '{title}' in one sentence."

if __name__ == "__main__":
    mcp.run()

How each primitive maps into LangGraph

Primitive Adapter call What you get
Tool client.get_tools() LangChain tools the agent calls autonomously.
Resource client.get_resources(server) Blobs/text you load into state or context yourself.
Prompt client.get_prompt(server, name, args) A ready-made message list to seed the conversation.
Key distinction: the agent chooses tools on its own, but you decide when to inject resources and prompts. Resources/prompts are app logic, not autonomous actions.

Loading a resource into the agent

from langchain_mcp_adapters.client import MultiServerMCPClient

client = MultiServerMCPClient({
    "kb": {"command": "python", "args": ["kb_server.py"], "transport": "stdio"},
})

# Pull a specific resource by URI and add it to context.
docs = await client.get_resources("kb", uris=["notes://onboarding"])
context = "\n".join(d.data for d in docs)

tools = await client.get_tools()
agent = create_react_agent("openai:gpt-4o", tools)

await agent.ainvoke({"messages": [
    {"role": "system", "content": f"Reference docs:\n{context}"},
    {"role": "user", "content": "How do I get started?"},
]})

Using a server-provided prompt

# Fetch the prompt template, already rendered with args, as messages.
messages = await client.get_prompt("kb", "summarize_note", arguments={"title": "release"})
result = await agent.ainvoke({"messages": messages})

Prompts let the server own best-practice wording (the team that built the tool knows how to ask), while your agent just invokes them by name.

Tool vs Resource — choosing correctly

Make it a Tool when…

…the model should decide to run it, it takes action or computes, or its result depends on arguments the LLM chooses (search, create, send).

Make it a Resource when…

…it's just data to read into context, identified by a stable URI, and the app (not the model) decides when to load it (a file, a config, a doc).

Best practices

  • Don't expose data as a tool just to load it — use a resource; it keeps the tool list lean and the model focused.
  • Use URI templates (notes://{title}) for parameterised resources.
  • Put canonical wording in prompts so every client asks the same, tested way.
  • Keep tool counts modest. Too many tools degrades selection accuracy — split into multiple servers if needed (build 04).
