Fixtures and parametrize — write less, cover more

In P1 every test set up its own data. That gets old fast. Here you meet the two pytest features that remove most of that repetition: fixtures for shared setup and parametrize for running the same test with many inputs.

The story

Your shopping cart needs to be tested with many products, many quantities, many discount values, and a few invalid inputs. If you wrote one function per case, you would end up with hundreds of nearly identical tests. Instead, you write a few smart tests and let pytest do the multiplication.

Files in this project

File Purpose
cart.py A small ShoppingCart class with add, remove, total, and discount.
conftest.py Shared fixtures (catalog, empty cart, pre-loaded cart). Auto-discovered by pytest.
test_cart.py Tests that consume the fixtures and use parametrize.

Mental model — fixtures are dependency injection for tests

You declare what a test needs by adding it as a function parameter. Pytest looks up a fixture with that name and builds it for you.

Fixture catalog
->
Fixture empty_cart
->
Fixture cart_with_items
->
Test asks for one of these

Fixtures can depend on other fixtures, so you build up complex objects in tiny reusable pieces.

Core code — the fixtures

@pytest.fixture
def catalog():
    return {
        "A1": Product("A1", "Notebook", 5.00),
        "B2": Product("B2", "Pen", 1.50),
        "C3": Product("C3", "Backpack", 49.99),
    }

@pytest.fixture
def empty_cart(catalog):
    return ShoppingCart(catalog=catalog)

@pytest.fixture
def cart_with_items(empty_cart):
    empty_cart.add("A1", 2)
    empty_cart.add("B2", 4)
    return empty_cart

Any test that asks for empty_cart gets a brand new cart. Tests cannot accidentally pollute each other because each fixture call is independent by default.

Core code — parametrize replaces copy-paste

@pytest.mark.parametrize(
    "sku,quantity,expected_total",
    [
        ("A1", 1, 5.00),
        ("A1", 3, 15.00),
        ("B2", 10, 15.00),
        ("C3", 1, 49.99),
    ],
)
def test_total_for_single_product(empty_cart, sku, quantity, expected_total):
    empty_cart.add(sku, quantity)
    assert empty_cart.total() == expected_total

This single function generates four tests. Pytest reports each one independently, so when a case fails, you know exactly which input broke.

conftest.py — fixtures shared across files

If a fixture lives in conftest.py, every test file in that folder (and child folders) can use it without any import. This is how real teams keep test data DRY.

Tip: if you find yourself importing setup helpers everywhere, move them into a fixture in conftest.py. The test file becomes pure intent.

Fixture scopes — control how often setup runs

Scope Fresh instance per… Use when
function (default) Each test Most cases. Maximum isolation.
class Test class Tests in a class share state on purpose.
module Each file Expensive setup shared by a file.
session Whole test run One-time setup like a Docker container or a temp DB.

How to run it

cd 06_side_projects/testing_projects/p2_fixtures_parametrize
pip install -r requirements.txt

pytest -v
# Run only the parametrized total test, all cases:
pytest -v -k test_total_for_single_product
# Run only the case with sku=A1 and quantity=3:
pytest -v -k "A1-3"

The bracketed labels you see in pytest output (for example test_total_for_single_product[A1-3-15.00]) come from the parametrize values.

What you should take away from P2

  • Fixtures remove repeated setup. Tests stay short and focused.
  • Parametrize turns one test into many. Bug fixes become a one-line addition.
  • conftest.py shares fixtures without imports.
  • Scopes let you control how often setup runs, but default to function scope.
Interview-ready answer: "Pytest fixtures are dependency injection for tests. I declare them in conftest.py and any test in the package can request them by name. For repeated input cases I use @pytest.mark.parametrize, which expands one function into N independently reported tests."
