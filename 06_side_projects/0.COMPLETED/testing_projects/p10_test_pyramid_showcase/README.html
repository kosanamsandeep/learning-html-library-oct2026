Project 10 · Capstone

The full test pyramid in one small e-commerce app

Everything from P1 to P9 comes together here. The same tiny shop is tested at four levels: pure unit tests for the pricing rules, unit-with-mocks for the service, integration tests for the database and the API, and one end-to-end test for the user journey. You will see exactly which kind of test catches which kind of bug — and why the pyramid shape is the right shape.

The story

You are shipping a checkout API. Bugs in pricing cost money. Bugs in stock cost trust. Bugs in the HTTP layer make the frontend crash. Bugs in the boot path bring the whole site down. No single test style catches all of those. The test pyramid says: many cheap tests at the base, fewer expensive tests at the top, and the right shape lets you sleep at night.

The pyramid in this project

1 E2E test

The user journey. Slowest, most realistic.

2 integration files

Service+DB and API layer.

2 unit files, many cases

Pricing rules and service logic. Fast.

Bug Caught fastest by
Discount of 50% returns 0.6 instead of 0.5 test_pricing_unit.py
Service decrements stock before validating test_service_unit.py
SQL forgets to COMMIT test_integration.py
API returns 200 instead of 409 on out-of-stock test_api.py

The takeaway: each layer catches a different kind of bug. If you only had one layer, you would miss most of them.

Coverage — what it tells you and what it does not

Use pytest-cov to measure what fraction of your code is exercised by tests.

pytest --cov=. --cov-report=term-missing

Coverage is a great signal for finding untested branches. It is a bad target on its own.

What 100% coverage proves

  • Every line ran at least once during the test run.
  • You touched every if/else branch.

What 100% coverage does NOT prove

  • The assertions were meaningful. You could "cover" a function with assert True.
  • Edge cases were considered.
  • Integration between modules works.

Pragmatic targets: 80-90% line coverage on business logic, 60-70% overall, plus the four lenses (happy / edge / error / side effects) reviewed in code review.

How to ideate tests for a new feature

  1. What rule is it? Write that as a pure function and a parametrized unit test.
  2. What collaborators does it need? Inject them; mock them in unit tests.
  3. What real I/O does it perform? Add an integration test for that boundary.
  4. What HTTP contract changes? Add an API integration test (status, JSON).
  5. Is this on a critical user journey? If yes, add or update one E2E test.

Follow that list and you end up with the pyramid shape automatically.

How to run it

cd 06_side_projects/testing_projects/p10_test_pyramid_showcase
pip install -r requirements.txt

# Run everything
pytest -v

# Run only the fast layers (skip E2E)
pytest -v --ignore=test_e2e.py

# Coverage report
pytest --cov=. --cov-report=term-missing

What you should take away from P10

  • The pyramid is many fast unit tests, some integration tests, a few E2E tests.
  • Each layer catches a different family of bugs. Skipping a layer creates a blind spot.
  • Coverage is a tool, not a goal.
  • When you add a feature, walk the five-step ideation list to decide what tests to write.
Interview-ready answer: "I follow the test pyramid: most of my tests are fast unit tests on pure logic, a smaller layer of integration tests cover the database and HTTP route, and one or two E2E tests cover the critical user journey. I use pytest with fixtures, parametrize, mocks, FastAPI TestClient for integration, and a uvicorn subprocess for true end-to-end. Coverage gives me a signal, not a goal."
