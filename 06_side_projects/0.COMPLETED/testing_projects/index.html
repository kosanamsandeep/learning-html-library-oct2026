Side Projects · Testing track

Python testing, beginner to advanced — ten small projects, one big story

Software without tests is software you cannot change safely. This track teaches Python testing the way a real team learns it: small examples, real failure modes, and one library that does 90% of the work in production Python projects today: pytest.

Why testing matters

Tests are not extra work. They are a safety net that lets you change code without breaking other code. The bigger the codebase, the more tests pay for themselves.

What happens without tests

  • You change one function and three unrelated features break.
  • You fear refactoring, so the codebase rots over time.
  • Bugs are caught by users instead of by your CI.
  • Onboarding new developers is painful because nobody is sure what works.
  • Releases are stressful events instead of routine.

What changes with tests

  • You can refactor with confidence, because tests catch regressions.
  • Tests act as live documentation of intended behavior.
  • Bugs are caught seconds after you save the file, not days later.
  • Code reviews focus on design, not "did you break anything?"
  • Deployments become small and frequent.

What if you simply skip testing?

Below is the typical timeline of a project without tests. Most teams know this story.

  1. Week 1: feature ships fast. No tests, no problem.
  2. Week 4: a small fix breaks an old feature. Customer complains.
  3. Month 3: developers add if branches instead of refactoring, because nobody trusts the code.
  4. Month 6: most bugs are reported by users. Developers spend more time fixing than building.
  5. Year 1: every release needs full manual testing, takes days, and still misses bugs.
The lesson: the cost of not testing is paid later, with interest. Tests are how you keep development speed high as the project grows.

Why pytest is the framework we use here

Python has built-in unittest, but the modern community standard is pytest. Every project in this track uses it.

Pytest advantage What it means in practice
Plain assert No need for self.assertEqual. You write assert x == 5 and pytest prints a rich failure diff.
Auto-discovery Files named test_*.py and functions named test_* are found automatically. No registration code.
Fixtures Reusable setup with dependency injection. A test simply declares def test_x(client): and pytest builds client for it.
Parametrize Run the same test with many inputs without copy-pasting code.
Plugins Huge ecosystem: pytest-cov, pytest-mock, pytest-asyncio, pytest-xdist, hypothesis.
Clean output Failures show actual vs expected values, not cryptic stack traces.
Compatible Pytest can run existing unittest tests too. Adopting it is not all-or-nothing.

Industry signals: most large open-source Python projects (FastAPI, Pydantic, requests, Django apps, scikit-learn ecosystems, data platforms) test with pytest or pytest-compatible runners.

The test pyramid — and how to remember it

You will hear about unit, integration, and end-to-end tests. The classic shape is a pyramid.

End-to-End (few)
Integration (some)
Unit (many)
Type Simple meaning How fast When to use it
Unit test Test one small function or class in isolation. Fake everything else. Milliseconds For pure logic: calculations, validation, rules, parsing, branching.
Integration test Test that two or more components work together. Database, repository, queue, API client. Tens of milliseconds to seconds For boundaries: DB queries, file I/O, internal service calls, FastAPI route + service.
End-to-end test Start the full app and behave like a real user or client. Seconds For critical user journeys: login, checkout, payment, signup.
How to remember when to use which: ask "what am I trying to trust?"
  • Trust a piece of logic → unit test.
  • Trust that pieces glue together → integration test.
  • Trust the whole flow from outside → end-to-end test.

Should you write the test first or the code first?

This is one of the most common questions for new developers. There are two famous styles. Both work.

TDD — test first

Workflow: Red → Green → Refactor.

  1. Red: write a test for behavior that does not exist yet. It fails.
  2. Green: write the smallest code that makes the test pass.
  3. Refactor: clean the code while keeping the test green.

Best for: clear logic, well-defined inputs/outputs, bug fixes (write a failing test that reproduces the bug first), critical pure functions.

Test-after — code first

Workflow: Build → Test → Stabilize.

  1. Write the implementation while you explore the design.
  2. Once it works, add tests that lock in the behavior.
  3. Refactor with the safety of the new tests.

Best for: exploratory work, prototypes, learning a new library, UI tweaks.

A practical answer: for bug fixes and core logic, write the test first. For exploratory features, write the code first but never ship it without tests. The goal is the same in both: critical behavior is covered before code reaches production.

How to ideate test cases — the four lenses

When you stare at code and wonder "what should I test?", run it through these four lenses.

Lens Question to ask Example
Happy path What is the normal use case? Calculator add(2, 3) == 5
Edge cases What about empty, zero, max, min, negative, unicode, very long? add(0, 0), add(-1, 1)
Error paths What should happen when input is invalid? divide(1, 0) raises ZeroDivisionError
Side effects What changes outside the function? DB, file, network, time? A handler writes to DB and sends email

The AAA pattern for writing tests

Every test in this track follows the same shape so it is easy to read.

def test_add_two_numbers():
    # Arrange: prepare data and dependencies
    a, b = 2, 3

    # Act: do the thing under test
    result = add(a, b)

    # Assert: check the outcome
    assert result == 5

Arrange. Act. Assert. If a test is hard to write in that shape, the code being tested probably needs to be split.

How to set up and run any project

cd 06_side_projects/testing_projects/p1_hello_pytest   # or any other project
python -m venv .venv
.venv\Scripts\activate                                 # Windows
pip install -r requirements.txt

# Run tests
pytest -v

Useful pytest flags you will see in this track:

Flag What it does
-v Verbose output (one line per test).
-k name Run only tests whose name matches.
-x Stop after the first failure.
-s Show print() output.
--cov=mypkg Measure coverage (requires pytest-cov).
-m slow Run only tests marked as @pytest.mark.slow.

Suggested learning order

  1. Read this hub end to end.
  2. Do P1 and P2 in one sitting to internalize fixtures and parametrize.
  3. Do P3 and P4 to learn exception and mock patterns.
  4. Do P5 in TDD mode — really write the test first.
  5. Do P6 and P7 to see integration tests with real databases and FastAPI.
  6. Do P8 to feel the difference between integration and true end-to-end tests.
  7. Do P9 and P10 once you are comfortable; they will reshape how you think about coverage.
