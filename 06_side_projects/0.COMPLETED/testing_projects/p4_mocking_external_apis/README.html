Project 4 · Intermediate

Mocking external APIs — never let your tests touch the internet

A test that calls a real weather API is slow, flaky, and broken every time the API changes. The fix is mocking: replace the parts that talk to the outside world with fake stand-ins that behave however the test needs. Here you will learn three different ways to do it.

The story

You build a small service: "if there is more than a 60% chance of rain tomorrow, send the user a notification". Two things in this story you do not control — the weather API and the email service. If your tests use the real ones, your CI will fail at 3 a.m. for reasons that have nothing to do with your code. Mocks let you pretend those collaborators returned exactly what you want.

The middle piece is what we actually care about. By accepting the two collaborators as constructor arguments, the service is testable by design — you can pass fakes in tests and the real ones in production. This is also the entire idea behind dependency injection.

Approach 1 — inject a MagicMock (preferred)

client = MagicMock(spec=WeatherClient)
client.get_forecast.return_value = Forecast("Bengaluru", 0.8, 27.0)
notifier = MagicMock()
service = WeatherService(client, notifier)

service.notify_if_rain_expected("Bengaluru", "asha@example.com")

notifier.send.assert_called_once()

This is the cleanest. The test reads top-to-bottom: build fakes, call the service, assert the side effect happened. spec=WeatherClient means the mock will reject any attribute that the real class does not have, which catches typos.

Approach 2 — patch the third-party call site

@patch("weather_service.requests.get")
def test_weather_client_parses_api_response(mock_get):
    mock_get.return_value.json.return_value = {"rain_chance": 0.75, "temperature_c": 22.5}
    mock_get.return_value.raise_for_status.return_value = None

    forecast = WeatherClient().get_forecast("Pune")

    assert forecast.rain_chance == 0.75

Use this when the code under test calls a library directly. The golden rule: patch where the name is looked up, not where it is defined. We patch weather_service.requests.get because that is where WeatherClient looks for it.

Approach 3 — pytest-mock (`mocker` fixture)

def test_service_calls_notifier_with_pytest_mock(mocker):
    client = mocker.Mock(spec=WeatherClient)
    client.get_forecast.return_value = Forecast("Chennai", 0.9, 30.0)
    notifier = mocker.Mock()

    WeatherService(client, notifier).notify_if_rain_expected("Chennai", "ravi@x.com")

    notifier.send.assert_called_once()

pytest-mock is a thin wrapper that auto-cleans up patches at the end of each test. Same power as unittest.mock, less boilerplate.

Mock vs Stub vs Fake — the practical difference

Term Meaning Example
Stub Returns canned data, that is all. client.get_forecast.return_value = Forecast(...)
Mock Returns data and records calls so you can assert how it was used. notifier.send.assert_called_once_with(...)
Fake A simple working implementation, for testing only. class InMemoryNotifier: def send(self, r, m): self.sent.append((r, m))

All three count as "test doubles". Pick the lightest one that proves what you need.

What you should and should NOT assert with mocks

Do assert

  • That the collaborator was called when it should be.
  • That it was called once when uniqueness matters.
  • That the arguments it was called with are correct.

Don't over-assert

  • Don't lock in internal call order if the order is not part of the contract.
  • Don't mock the thing under test. Then you are testing the mock.
  • Don't mock value objects (dataclasses, dicts). Just construct them.

How to run it

cd 06_side_projects/testing_projects/p4_mocking_external_apis
pip install -r requirements.txt
pytest -v

Note the tests run in milliseconds even though the real client would talk to example-weather.test which does not even exist. That is the win.

What you should take away from P4

  • Mocks let unit tests stay fast, deterministic, and offline.
  • Inject collaborators when you can; patch when you must.
  • "Patch where it is used, not where it is defined."
  • Assert behavior (the call happened with the right args), not implementation details.
Interview-ready answer: "I prefer constructor injection so my service accepts a real client in production and a mock in tests. When that is not possible I patch the dependency at the call site with unittest.mock.patch or the mocker fixture from pytest-mock. I assert that the right collaborator was called with the right arguments, not the internal implementation steps."
