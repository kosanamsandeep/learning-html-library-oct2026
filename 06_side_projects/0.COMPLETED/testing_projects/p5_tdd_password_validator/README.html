Project 5 · Intermediate

Test-Driven Development — build the test first, then make it pass

This project answers your question directly: should I write the test first or the code first? Both work, but writing the test first has a name (TDD) and a famous rhythm: Red, Green, Refactor. Here we build a password validator one failing test at a time.

The TDD loop

1. Red

Write a test for behavior that does not exist yet. Run it. It fails because the code is not there. That failure is good — it proves the test can detect the bug it claims to detect.

2. Green

Write the smallest, ugliest code that makes the test pass. No extra features. No future-proofing. Just turn the red bar green.

3. Refactor

Clean the code while every test stays green. Extract functions, rename variables, remove duplication. Tests act as your safety net.

Then repeat for the next rule. Each loop is a few minutes. The code grows together with its tests.

TDD vs Test-After — the honest comparison

TDD (test first)

  • Forces a tiny, well-defined design step before coding.
  • Tests really do drive the API of the function (what arguments, what return).
  • You never have untested code, because code only exists to satisfy a test.
  • Great for bug fixes: write a failing test that reproduces the bug, then fix it.
  • Forces small, composable functions.

Test-After (code first)

  • Faster when you are exploring an unfamiliar library.
  • Easier when the requirements are still fuzzy.
  • Risk: tests get written to match existing code, even if the code is wrong.
  • Risk: some branches never get a test.
Pragmatic rule: use TDD for bug fixes and for any code you can describe in input/output terms. Use test-after for exploratory work, but never ship a feature without tests. Both styles land in the same place: behavior is locked in by tests.

The narrative — building the validator one test at a time

Below is the order we would actually type things. After each step we run pytest and expect the new test to fail, then pass.

Step 1 — minimum length

# RED — write the test first
def test_short_password_is_rejected():
    result = validate_password("Ab1!")
    assert result.ok is False
    assert any("at least 8" in e for e in result.errors)

# GREEN — smallest code that passes
def validate_password(password):
    errors = []
    if len(password) < 8:
        errors.append("must be at least 8 characters")
    return ValidationResult(ok=not errors, errors=errors)

Step 2 — must contain uppercase

# RED
def test_password_without_uppercase_is_rejected():
    result = validate_password("abcdefg1!")
    assert any("uppercase" in e for e in result.errors)

# GREEN — add ONE line of logic
if not any(c.isupper() for c in password):
    errors.append("must contain at least one uppercase letter")

Steps 3-5 — digit, special, no spaces

Same loop, three more times. After each rule the code has exactly the logic the tests demand and nothing else.

Step 6 — happy path

def test_strong_password_is_accepted():
    assert validate_password("Strong1!").ok is True

This is the test that proves "all the rules combined do not over-reject".

Step 7 — refactor

Once all tests are green, look at the code. Notice that every rule is "check a condition, append a message". The current implementation is already clean enough. If the rules grow to twenty, refactor each rule into a small function and iterate. Tests stay green throughout, so refactoring is safe.

Why we return a list of errors instead of raising

A subtle TDD lesson: tests shape the API.

If we had decided "raise an exception on the first failure", we would never have written test_all_failures_are_collected_at_once. Returning a structured ValidationResult with all errors is friendlier for forms (the user sees every problem, not just the first one). TDD revealed that requirement because the test "tell me everything wrong at once" was easy to imagine and easy to write.

What you should take away from P5

  • TDD has three steps: Red, Green, Refactor.
  • Writing the test first forces a real design decision before code.
  • For bug fixes, always start with a failing test that reproduces the bug.
  • For exploratory work, code first is fine — but never ship without tests.
  • Tests shape the API. A different test would have produced a different function signature.
Interview-ready answer: "I use TDD for any code with a clear input/output contract and for every bug fix — I reproduce the bug with a failing test first. For exploratory work I write code first and add tests before merging. The non-negotiable is that behavior is covered by tests before it reaches production."
