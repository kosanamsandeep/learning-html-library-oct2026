Project 6 · Intermediate

Integration tests — let your code touch a real database

Unit tests are fast because they fake the world. Integration tests are honest because they do not. In this project a tiny TodoRepository talks to a real SQLite database that lives on disk, and pytest gives each test a fresh copy of it.

The story

You wrote a repository class with a clean API: add, get, list_all, mark_done, delete. The tests pass in isolation — but the moment you point the code at a real database, things break: wrong column name, missing commit, type mismatch on the done column. Integration tests catch those bugs because they exercise the SQL itself.

Files in this project

File Purpose
repository.py TodoRepository backed by SQLite. Real schema, real queries.
conftest.py Fixture that gives each test a brand-new SQLite file via tmp_path.
test_repository.py Integration tests that round-trip data through the database.

Unit test vs integration test — the line

Unit test (P4) Integration test (P6)
Touches the network or disk? No Yes (a real file on disk)
What is being verified? Pure rule (rain >= threshold) Code + database glue together correctly
Speed Milliseconds Tens of milliseconds
Failure points Logic bugs SQL syntax, missing commit, schema drift, type coercion
Rule of thumb: if you mocked the repository in a higher test, you still need at least one integration test of the repository itself, so that mock stays believable.

The tmp_path fixture — pytest's gift to integration tests

@pytest.fixture
def repo(tmp_path):
    db_file = tmp_path / "todos.sqlite"
    repository = TodoRepository(db_file)
    yield repository
    repository.close()

tmp_path is a built-in pytest fixture that hands you a unique temporary directory per test, auto-deleted afterwards. Each test gets a brand-new database, so no test can pollute another.

The yield pattern is how a fixture does setup and teardown in one place: code before yield runs before the test, code after yield runs after.

What an integration test looks like

def test_added_todo_can_be_retrieved(repo):
    saved = repo.add("Buy milk")
    fetched = repo.get(saved.id)

    assert fetched == saved

def test_persistence_survives_repository_instance(tmp_path):
    first = TodoRepository(tmp_path / "db.sqlite")
    first.add("survive me")
    first.close()

    second = TodoRepository(tmp_path / "db.sqlite")
    assert [t.title for t in second.list_all()] == ["survive me"]
    second.close()

The second test in particular cannot be faked with a mock — it proves that the row was actually written to the file. That is the kind of confidence integration tests buy you.

How to ideate integration tests

  1. Round-trip: write a row, read it back, assert equality.
  2. Update isolation: change row A, verify row B is unaffected.
  3. Not found: query a missing id, verify a clean "no result" instead of a crash.
  4. Constraints: insert invalid data (empty title, oversized field) and assert the correct error.
  5. Persistence: open a new connection and confirm the data is still there.

Why SQLite for integration tests

  • Zero install. It is part of the Python standard library.
  • One file. tmp_path makes each test database disposable.
  • Fast enough. A whole test suite usually runs in under a second.
  • Real SQL. Your queries actually run against an SQL engine.

For Postgres-specific features, the same pattern works with testcontainers or a dedicated test database. The structure of the fixture stays the same: setup, yield, teardown.

How to run it

cd 06_side_projects/testing_projects/p6_database_integration
pip install -r requirements.txt
pytest -v

To break it on purpose: remove the self._connection.commit() line in add. test_persistence_survives_repository_instance will fail, because the row never reached the file. That single test would have caught a real production bug.

What you should take away from P6

  • Integration tests verify that your code and a real dependency work together.
  • tmp_path gives each test an isolated workspace.
  • yield fixtures handle setup and teardown in one block.
  • The kinds of bugs integration tests catch (missing commit, bad SQL) cannot be caught by mocks.
Interview-ready answer: "I use SQLite plus pytest's tmp_path fixture to spin up a clean database per test. That gives me real integration coverage — schema, SQL, commit boundaries — without the overhead of a containerized database. For Postgres-specific work I swap SQLite for testcontainers with the same fixture shape."
