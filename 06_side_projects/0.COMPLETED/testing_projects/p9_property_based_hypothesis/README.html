Project 9 · Advanced

Property-based testing — let the computer invent the inputs

Example-based tests check that your chosen inputs produce your expected outputs. Property-based testing flips the question: describe a rule that must hold for any input, and let Hypothesis throw hundreds of inputs at it — including the weird ones you never would have thought of.

The story

You write merge_sorted. You write tests with neat inputs like [1,3,5] and [2,4,6]. Everything passes. In production a user passes [] and your code explodes. Or [2_147_483_648]. Or a list with duplicates. Hypothesis tries those for you automatically, including the smallest input that breaks your code.

Files in this project

File Purpose
math_utils.py Four small functions: reverse, base64 round-trip, merge_sorted, safe_average.
test_properties.py Example-based tests on top, property-based tests below.

Example vs property — side by side

Example-based

def test_reverse_known_string():
    assert reverse("hello") == "olleh"

You picked the input. You picked the output. Useful, but blind to anything you did not pick.

Property-based

@given(st.text())
def test_reverse_is_an_involution(s):
    assert reverse(reverse(s)) == s

Hypothesis generates strings: empty, unicode, very long, special characters, surrogate pairs. Your rule must hold for every one of them.

How to ideate properties — the four families

Family Shape Example from this project
Round-trip decode(encode(x)) == x base64 round-trip
Invariant Some property is always preserved len(reverse(s)) == len(s)
Equivalence Two implementations should agree merge_sorted(a, b) == sorted(a + b)
Bounds The result always sits in a known range min(xs) <= avg(xs) <= max(xs)

If you can describe one of these about your function, you have a property-based test.

The Hypothesis vocabulary you need

Piece What it does
@given(...) Decorator that generates inputs for the test.
st.integers() Strategy that produces ints (positive, negative, big, small).
st.text() Strategy for strings, including unicode edge cases.
st.lists(strategy, max_size=...) Lists of values from another strategy.
st.binary() Random byte strings.
@settings(max_examples=200) Increase the search budget for tricky properties.

Shrinking — the killer feature

When Hypothesis finds a failing input it does not just report it. It shrinks it. If [7, -3, 1_000_000, 0, 0] breaks your code, Hypothesis will try simpler variants until it finds the smallest input that still fails, often something like [0, 0] or []. That tiny counterexample is what you commit as a regression test.

Why this matters: debugging is much easier when the failing input is one element instead of fifty.

When to use property-based tests

Great fit

  • Encoders/decoders, serializers, parsers.
  • Sorters, mergers, collection utilities.
  • Pure math: rounding, averages, bounds.
  • Functions with clean mathematical properties.

Not the best fit

  • Code that depends on time, randomness, or external services.
  • UI flows. Use E2E (P8) instead.
  • Functions whose contract is just "produce HTTP 200".

You will still write example-based tests. Property-based tests complement them; they rarely replace them.

How to run it

cd 06_side_projects/testing_projects/p9_property_based_hypothesis
pip install -r requirements.txt
pytest -v

Try to break it: introduce a bug in merge_sorted by changing <= to <. Hypothesis will report the failing input, often something simple like [0] and [0].

What you should take away from P9

  • Properties describe what must always be true, regardless of input.
  • Hypothesis searches the input space and shrinks counterexamples to the smallest failing one.
  • The four families — round-trip, invariant, equivalence, bounds — cover most useful properties.
  • Use property-based tests for parsers, encoders, math, and data structures.
Interview-ready answer: "Hypothesis lets me describe properties like 'reversing twice gives the original' or 'encoder + decoder is the identity', and then it generates inputs to try to falsify them. When it finds a counterexample it shrinks it, so I get the smallest input that breaks my code — which I add as a regression test."
