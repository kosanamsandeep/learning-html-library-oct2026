Project 7 · Advanced

FastAPI — unit tests for the rule, integration tests for the route

Most teams write only integration tests for their APIs. That works, but it is slow and couples every assertion to JSON. Here you will see the two-layer approach: pure unit tests on the ItemService and HTTP integration tests on the FastAPI route, glued together with app.dependency_overrides.

The story

Your API has a rule: prices must be positive, names cannot be blank. You could test that rule by POSTing JSON and checking the response. But the rule has nothing to do with HTTP — testing it through the network is twenty times slower and ten times harder to read. Split the code into a service layer and a route layer, and the tests split naturally too.

This split is the single most useful pattern in real-world API testing.

FastAPI TestClient in one line

from fastapi.testclient import TestClient
from main import app

client = TestClient(app)
response = client.post("/items", json={"name": "Pen", "price": 1.50})
assert response.status_code == 201

No server is started. TestClient calls the app in-process via the ASGI interface. It is fast enough that you can run thousands of these per test suite.

Dependency overrides — the secret of clean API tests

@pytest.fixture
def client(service):
    app.dependency_overrides[get_service] = lambda: service
    with TestClient(app) as test_client:
        yield test_client
    app.dependency_overrides.clear()

FastAPI's app.dependency_overrides lets you swap any dependency at test time. In this project we override get_service so every test gets a fresh, empty ItemStore. Tests never share state, even though they all hit the same global app.

Why this matters: in production the dependency could return a service wired to Postgres. In tests it returns one wired to an in-memory store. Same routes, two wirings, zero changes to main.py.

Compare a unit test and an integration test side by side

Unit test

def test_create_rejects_negative_price(service):
    with pytest.raises(ValueError):
        service.create("Pen", -0.01)

Reads as plain Python. Runs in microseconds. Easy to add new cases.

Integration test

def test_create_with_negative_price_returns_422(client):
    response = client.post("/items", json={"name": "x", "price": -1})
    assert response.status_code == 422

Proves the route plus Pydantic validation plus HTTP status all line up.

How to ideate API integration tests

  1. Status code for each path: 201 on create, 200 on get, 404 on missing, 204 on delete.
  2. Response shape: the JSON has exactly the keys the frontend expects.
  3. Validation errors: a bad payload returns 422 with the Pydantic detail.
  4. Domain errors: a business rule violation returns 400/409 with the right detail.
  5. Isolation: each test starts with an empty store (proves the fixture works).

How to run it

cd 06_side_projects/testing_projects/p7_fastapi_unit_vs_integration
pip install -r requirements.txt
pytest -v

# Run only unit tests:
pytest -v test_service_unit.py

# Run only integration tests:
pytest -v test_api_integration.py

Notice how the unit tests finish almost instantly. The integration tests are still very fast because no real server starts.

What you should take away from P7

  • Split rule code from transport code, and your tests split too.
  • Unit-test the service. Integration-test the route. Do not mix.
  • TestClient calls the app in-process — fast and deterministic.
  • app.dependency_overrides is how you swap real deps for test ones cleanly.
Interview-ready answer: "I structure FastAPI apps so the business rules live in a service class and the routes are thin wrappers. Unit tests target the service directly. Integration tests use FastAPI's TestClient together with app.dependency_overrides to inject a fresh in-memory store per test, asserting only on HTTP behavior — status codes and JSON shape."
