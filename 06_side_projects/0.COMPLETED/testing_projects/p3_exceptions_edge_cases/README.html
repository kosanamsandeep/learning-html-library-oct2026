Project 3 · Beginner

Exceptions and edge cases — testing what is supposed to break

Most production bugs do not live in the happy path. They live at the boundaries: zero, one, max, frozen, expired. This project teaches you to test those boundaries deliberately, using a small bank account with overdraft and freeze rules.

The story

Money software cannot have surprises. If a user has $100 and an overdraft of $50, withdrawing $150 must succeed and withdrawing $150.01 must fail with a clear error. Withdrawing zero or a negative amount must fail. A frozen account must reject everything. Those rules turn into tests, and the tests are what stop a bad refactor from breaking a real customer.

Custom exceptions — why they matter for testing

Three small classes, one base:

class BankError(Exception): pass
class InsufficientFundsError(BankError): pass
class InvalidAmountError(BankError): pass
class AccountFrozenError(BankError): pass

Custom exceptions let tests assert on the meaning of the failure, not just on a generic ValueError. That is the difference between "something went wrong" and "the user tried to overdraw their account by one cent".

The four lenses applied to this project

Lens Tests we wrote
Happy path Deposit, withdraw, history records.
Edge cases Withdraw exact balance, withdraw exactly to overdraft limit, then one cent more.
Error paths Negative amounts, zero, beyond overdraft.
State transitions Freeze blocks both operations; unfreeze restores them.

Core pattern — asserting on exceptions

def test_overdraft_boundary_one_cent_too_far(account):
    with pytest.raises(InsufficientFundsError):
        account.withdraw(150.01)

def test_withdraw_beyond_overdraft_raises(account):
    with pytest.raises(InsufficientFundsError) as exc_info:
        account.withdraw(1000)
    assert "overdraft" in str(exc_info.value).lower()

Two levels of strictness:

  • Just the type — enough when the type uniquely identifies the failure.
  • Type and message — when the message carries information users rely on.

Boundary checklist you can reuse

For any numeric input, ask:

  • What about zero?
  • What about negative?
  • What about the exact maximum allowed?
  • What about one unit beyond the maximum?
  • What about a very large value?

For any object with state, ask:

  • What happens in each state (active, frozen, closed)?
  • What happens at the transition itself?
  • Can the transition be reversed?
Common mistake: writing only happy-path tests. They pass forever and miss every real bug. Always add at least one edge case and one error case per behavior.

How to run it

cd 06_side_projects/testing_projects/p3_exceptions_edge_cases
pip install -r requirements.txt
pytest -v

To break it on purpose: change self.balance - amount < -self.overdraft_limit to <=. One specific test will fail and tell you exactly what assumption you broke.

What you should take away from P3

  • Custom exceptions make tests precise about the kind of failure.
  • The boundary checklist catches most numeric bugs.
  • State machines deserve tests for each state and each transition.
  • pytest.raises can also inspect the exception object.
Interview-ready answer: "I always test the happy path, edge cases at the boundaries, the explicit error path with the right exception type, and the state transitions of any object that has more than one state. pytest.raises is how I assert errors and inspect their messages."
