Project 8 · Advanced

True end-to-end testing — boot a real server, hit it like a user

P7's TestClient is fast but calls the app in-process. Real users do not. In this project we start uvicorn in a subprocess on a random port and hit it with httpx over a real socket. That is what "end-to-end" actually means.

The story

A URL shortener has one job: take a long URL, return a short one, and redirect on click. Two services talk: the shortener itself, and the browser that follows the redirect. The only way to verify the entire flow — JSON in, 302 redirect out, real Location header — is to run the server for real and watch what comes back over the wire.

Files in this project

File Purpose
main.py Tiny URL shortener. POST /links, GET /{code} (302 redirect), GET /stats.
conftest.py Session fixture starts uvicorn in a subprocess on a free port and waits for it to be ready.
test_e2e.py Tests use real httpx over a real socket.

Integration vs end-to-end — the real difference

Integration (P7) End-to-end (P8)
How the app is called FastAPI TestClient (in-process ASGI) uvicorn subprocess + real HTTP socket
What is covered App code, dependency wiring, routes App + uvicorn + the network stack + how the client interprets redirects
Speed Tens of milliseconds A few hundred milliseconds (boot + sockets)
Failure modes caught Bugs in routes/dependencies Bugs in startup, port binding, response headers, content negotiation
Cost vs value: E2E tests are slower and slightly flakier because they involve sockets. Reserve them for critical user journeys (signup, checkout, login, redirect). Do not E2E every endpoint.

Booting the server from inside pytest

@pytest.fixture(scope="session")
def base_url():
    port = _free_port()
    proc = subprocess.Popen(
        [sys.executable, "-m", "uvicorn", "main:app", "--port", str(port), "--log-level", "warning"],
        cwd=str(Path(__file__).parent),
    )
    url = f"http://127.0.0.1:{port}"
    try:
        _wait_until_ready(f"{url}/stats")
        yield url
    finally:
        proc.terminate()
        proc.wait(timeout=5)

Three details matter:

  1. Random free port. Two test runs on the same machine should not conflict.
  2. Wait until ready. Poll a known endpoint until it answers, so tests do not race the boot sequence.
  3. Always terminate in finally. Otherwise CI accumulates zombie processes.

What an E2E test looks like

def test_full_user_journey(client):
    # 1) User creates a short link
    code = client.post("/links", json={"url": "https://example.com/article"}).json()["code"]

    # 2) User shares it; somebody opens it
    follow = client.get(f"/{code}")
    assert follow.status_code == 302
    assert follow.headers["location"] == "https://example.com/article"

    # 3) Owner checks stats
    assert client.get("/stats").json()["total"] == 1

This reads like a sentence in plain English: "user creates link, someone follows it, owner sees the stats". That is the right shape for E2E tests — describe a user journey, not implementation steps.

Test isolation when there is real shared state

The subprocess keeps its memory between tests. To avoid one test polluting another, the client fixture POSTs to a small /_admin/reset endpoint before each test: 

@pytest.fixture
def client(base_url):
    with httpx.Client(base_url=base_url, follow_redirects=False) as c:
        c.post("/_admin/reset")
        yield c

In a real product this endpoint would never ship. Two safer alternatives: (a) start a fresh process per test (slow), or (b) wire the app to a database that the fixture truncates between tests.

Why httpx instead of requests

  • Same ergonomics as requests, plus async support.
  • FastAPI's TestClient is built on top of httpx, so you stay in one library.
  • follow_redirects=False lets us assert on the actual 302 response — crucial for redirect-heavy tests.

How to run it

cd 06_side_projects/testing_projects/p8_e2e_with_httpx
pip install -r requirements.txt
pytest -v

You will see a one-second pause at the start (the server is booting), then the tests run quickly.

Heads-up: on locked-down corporate machines, you may need to allow Python through the local firewall the first time. The server only binds to 127.0.0.1.

What you should take away from P8

  • True E2E means a real process and a real network call.
  • Use a session fixture to boot once and reuse the server.
  • Always wait until the server answers before running tests.
  • Reset state between tests deliberately. Do not rely on order.
  • E2E is expensive — use it for journeys, not for every line of code.
Interview-ready answer: "I treat integration and end-to-end as different layers. Integration uses FastAPI's TestClient in-process for speed. E2E uses a real uvicorn subprocess on a random port and an httpx client, so it covers boot, sockets, and redirect handling. E2E tests are reserved for critical user journeys."
