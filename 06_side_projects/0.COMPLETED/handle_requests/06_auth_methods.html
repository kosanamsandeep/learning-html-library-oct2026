Authentication — what each method means for a developer

Every auth scheme answers two questions: "how does the client prove identity?" and "where does the secret live?". Pick the wrong answer and you'll either be hacked or lock your users out.

Big picture Cookies (session) Authorization header JWT Basic OAuth 2.0 Client certs (mTLS) Why OAuth wins

The cheat sheet

Method Where the secret lives Sent how Stateless? Best for Big risk
Basic Username + password, every call Authorization: Basic base64(u:p) Yes Internal tools, quick scripts Password on the wire (always over HTTPS!)
Cookies (session) Random session ID; data on the server Cookie: sid=abc123 (auto by browser) No (server keeps state) Server-rendered web apps, login forms CSRF, session hijacking
JWT (bearer) Signed token; data inside the token Authorization: Bearer eyJ... Yes APIs, microservices, SPAs Token theft = full access until expiry; hard to revoke
OAuth 2.0 Token issued by an authorization server Authorization: Bearer ... (usually a JWT) Yes Third-party access, "Sign in with Google" Complex; misconfigured scopes / redirect URIs
Client certificate (mTLS) Private key on the client device TLS handshake (no header) Yes Service-to-service, IoT, zero-trust Cert distribution + rotation operationally heavy

🍪 Cookies (session login)

The browser logs in once; the server creates a session row and gives the browser a small string in a Set-Cookie header. The browser sends that string back on every subsequent request to the same domain — automatically.

sequenceDiagram
    participant B as Browser
    participant S as Server
    B->>S: POST /login (email + password)
    S->>S: Validate, create session row (sid=abc123)
    S-->>B: 200 OK
Set-Cookie: sid=abc123; HttpOnly; Secure; SameSite=Lax
    Note over B: Cookie stored
    B->>S: GET /dashboard
Cookie: sid=abc123
    S->>S: Look up session abc123 -> user 42
    S-->>B: 200 OK (HTML for user 42)

What a developer must set

Cookie flag Why
HttpOnly JS can't read it → defeats XSS-stealing.
Secure Only sent over HTTPS → no leaks on Wi-Fi.
SameSite=Lax or Strict Browser won't attach it to cross-site POSTs → defeats CSRF.
Max-Age / Expires Bounded lifetime.
Security stance: session cookies are server-controlled — invalidate one row and that user is logged out everywhere. Easiest to revoke of all the methods.

🪪 Authorization header (the "show me your badge" pattern)

An HTTP header named Authorization carries the credential. The first word is the scheme: 

Authorization: Basic ZGVtbzpwYXNz       # Basic auth
Authorization: Bearer eyJhbGciOiJIUzI1NiIs...   # JWT or OAuth token
Authorization: Digest ...                # rare
Authorization: AWS4-HMAC-SHA256 ...      # AWS request signing

Unlike cookies, the header is not attached automatically. The client decides to send it. That's why APIs prefer it: explicit, scriptable, immune to CSRF (browser won't auto-attach it on a cross-site request).

🎟️ JWT — the self-contained token

A JWT is three base64 chunks separated by dots:

eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9    .   eyJzdWIiOiI0MiIsImV4cCI6MTcwMH0   .   3xS9...sig
   ^^^ header (algo, type)                    ^^^ payload (claims)              ^^^ signature

The server signs the payload with a secret. When you send the token back, the server verifies the signature — no database lookup needed. That's why JWT is called stateless.

Strengths

  • No session table → easy to scale horizontally.
  • Contains claims (user id, roles, expiry) — services downstream can trust them without a callback.
  • Works across domains and mobile apps.

Weak spots a dev must guard

  • Theft = total compromise until the token expires. Keep lifetime short (5–15 min) and refresh.
  • Storing in localStorage exposes it to XSS. Prefer HttpOnly cookies for browser apps.
  • Revocation is hard — you must maintain a blacklist or accept short windows.
  • Never use the none algorithm; always verify signatures.
  • Don't put secrets in the payload — it's base64, not encrypted.
The pattern that actually works: short-lived access JWT (15 min) + long-lived refresh token stored server-side. You get statelessness for most calls and revocability when it matters.

🔓 Basic auth

Authorization: Basic base64("alice:hunter2")
# == Authorization: Basic YWxpY2U6aHVudGVyMg==
  • Trivial to use; supported everywhere.
  • The password is sent on every request. If TLS breaks, the password leaks.
  • No expiry, no scopes, no revocation short of changing the password.
  • No SSO — every service needs its own copy of the password.

Useful for: internal scripts, prototype admin panels, mTLS-protected internal endpoints. Not for public APIs.

🛂 OAuth 2.0 — delegated authorization

OAuth answers a different question. Basic/JWT/Cookies say "is this the user?". OAuth says "has this user authorized this third-party app to act on their behalf, and to what extent?".

sequenceDiagram
    participant U as User
    participant App as Your app
    participant AS as Auth server (e.g. Google)
    participant API as Resource API

    U->>App: Click "Sign in with Google"
    App->>AS: Redirect — client_id, scope=email, state
    AS->>U: Show consent screen
    U->>AS: Approve
    AS->>App: Redirect back with one-time CODE
    App->>AS: POST /token (code + client_secret)
    AS-->>App: access_token + refresh_token
    App->>API: GET /me
Authorization: Bearer access_token
    API-->>App: User data

The Authorization Code + PKCE flow — the modern default for web and mobile apps.

Key concepts a developer must internalize

Client ID / Secret Identifies your app to the auth server.
Scope What you're asking permission for (read:email, write:repo). Smallest possible.
State Random value you echo back — defeats CSRF on the redirect.
PKCE Extra random verifier — protects mobile/SPA where there's no secure secret.
Access token Short-lived, sent on each API call. Often a JWT.
Refresh token Long-lived, used to get new access tokens; stored carefully.

🔐 Client certificates (mTLS)

"Mutual TLS" — both sides present X.509 certificates during the TLS handshake. There's no Authorization header at all; the network connection itself proves identity.

  • Strength: phishing-proof. The private key never leaves the machine.
  • Use cases: service-to-service inside zero-trust networks, banks, payment rails, IoT fleets.
  • Pain: issuing, distributing, rotating, and revoking certificates is operational work — usually done with an internal CA or service mesh (Istio, Linkerd).
# requests with a client cert
requests.get(
    "https://payments.internal/charge",
    cert=("client.crt", "client.key"),
    verify="ca-bundle.pem",
)

Why people prefer OAuth over JWT or Basic

It's a common confusion: "JWT vs OAuth" is not apples-to-apples. OAuth is a protocol; JWT is a token format. Most modern OAuth servers issue JWTs. The real comparison is:

Concern Basic Raw JWT (you mint it) OAuth 2.0 (issued by an AS)
Who holds the password Every app Your app does Only the auth server
Third-party access ("sign in with X") ❌ ❌ ✅ first-class
Scoped permissions ❌ Possible, manual ✅ built-in
Short-lived access + refresh tokens ❌ You build it ✅ standardized
Centralized revocation / audit ❌ Hard ✅ at the AS
Single sign-on across many apps ❌ ❌ ✅
Battle-tested flows (PKCE, device, client_credentials) — You invent ✅ off-the-shelf
The short answer: OAuth is preferred because it solves the operational problems (key custody, scopes, revocation, SSO, third-party delegation) that Basic and raw JWT leave to each developer to reinvent. Inside one trusted boundary, plain JWT is fine. Across trust boundaries or with users, OAuth.

Security responsibilities, summarized

You're using… What you must own as a developer
Cookies Set HttpOnly, Secure, SameSite. CSRF tokens for state-changing forms. Rotate session ID after login.
Basic TLS-only. Don't log the header. Rotate creds. Use only for internal tools.
JWT Short expiry. Validate alg, iss, aud, exp. Keep secrets out of the payload. Have a refresh + revocation story.
OAuth Use Authorization Code + PKCE. Verify state. Smallest scope. Never expose client_secret in a browser/mobile build.
mTLS Automate cert issuance + rotation. Pin a CA. Plan for revocation (CRL/OCSP) and key loss.
