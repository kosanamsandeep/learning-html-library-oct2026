Chapter 03 · Architecture choice

HTTP/REST vs gRPC — when to use which

REST over HTTP is the universal lingua franca: anything can call it. gRPC is faster, typed, and bi-directional, but harder to consume from a browser. Both run on top of HTTP — the difference is what you put inside.

The one-line answer

Default to REST/HTTP+JSON for anything a browser, partner, or human will touch. Reach for gRPC for internal service-to-service traffic where you control both sides and care about latency, schema strictness, and streaming.

Side-by-side comparison

Topic REST over HTTP/JSON gRPC
Transport HTTP/1.1 or HTTP/2 HTTP/2 only
Payload format JSON (text, human-readable) Protobuf (binary, compact)
Schema Optional (OpenAPI, JSON Schema) Mandatory (.proto file, code-gen)
Type safety None by default End-to-end, generated client + server stubs
Streaming Server-Sent Events, WebSockets (bolted on) Native: unary, server-stream, client-stream, bi-di
Browser support Native Needs gRPC-Web proxy (Envoy)
Discoverability URLs are self-describing Needs the .proto file
Wire size (typical) ~3× larger than gRPC ~3× smaller (binary)
Latency (typical) 5–15 ms overhead 1–5 ms overhead
Debug with curl Trivial Needs grpcurl
Caching (HTTP caches, CDNs) Easy Hard (binary, POST-like)
Best at Public APIs, web apps, partners Internal microservices, low-latency, streaming

Same "GetUser" — side by side

REST + requests

# Server: GET /users/{id} → JSON
import requests
r = requests.get(
    "https://api.com/users/42",
    headers={"Authorization": "Bearer abc"},
    timeout=5,
)
r.raise_for_status()
user = r.json()  # dict — fields not validated

gRPC

# 1. Define schema in users.proto
# service Users {
#   rpc GetUser(GetUserReq) returns (User);
# }

# 2. Compile → generates users_pb2.py + users_pb2_grpc.py

import grpc
import users_pb2, users_pb2_grpc

channel = grpc.secure_channel("api.com:443",
                              grpc.ssl_channel_credentials())
stub = users_pb2_grpc.UsersStub(channel)
user = stub.GetUser(users_pb2.GetUserReq(id=42))
# `user` is a typed object — user.email, user.name, etc.

REST gives you a free-form dict; gRPC gives you a class with fields the compiler checks.

JSON is text you can read in a terminal. Protobuf is compact bytes you can't read without the schema.

Streaming — gRPC's real superpower

Pattern Example REST gRPC
Unary (req → res) Get one user Easy Easy
Server stream Tail logs, stock ticks SSE / chunked (clunky) First-class
Client stream Upload many sensor readings Multipart or many POSTs First-class
Bi-directional stream Chat, live collaboration WebSocket needed First-class

Decision flow

flowchart TD
    A[I'm designing an API] --> B{Browser/public consumers?}
    B -- yes --> R1[Use REST + JSON]
    B -- no --> C{Internal microservice you fully control?}
    C -- no --> R1
    C -- yes --> D{Need low latency
or streaming?}
    D -- no --> R1
    D -- yes --> R2[Use gRPC]

Real-world pattern: gRPC behind the firewall, REST at the edge. A REST gateway exposes the public surface; gRPC carries internal traffic between services.

Trade-offs in plain words

REST wins on

  • Universal — browser, curl, Postman, mobile, anything.
  • Human-readable when debugging.
  • No code generation step in the build.
  • Caches and CDNs understand it.

gRPC wins on

  • 3× smaller payloads, 2–5× lower latency.
  • Schema is contract — breaking changes caught at compile time.
  • Native streaming (server, client, bi-di).
  • Generated typed clients for many languages.
