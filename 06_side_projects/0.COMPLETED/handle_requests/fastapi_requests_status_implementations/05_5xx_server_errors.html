Chapter 05 · 5xx Server errors

5xx — "the request was fine, I failed"

5xx means the server couldn't fulfil a valid request. The art here is failing safely: never leak stack traces, always log with a trace id, and signal the right flavour — crashed (500), not implemented (501), or upstream/overloaded (502/503/504).

The 5xx you'll deal with

Code Meaning Typical cause
500 Internal Server Error Unhandled exception A bug — uncaught error in your code
501 Not Implemented Feature not built yet Stub endpoint / unsupported method
502 Bad Gateway Bad response from upstream A dependency returned garbage
503 Service Unavailable Temporarily down/overloaded Maintenance, DB down, shedding load
504 Gateway Timeout Upstream too slow A dependency didn't answer in time

500 — catch everything with a global handler

An uncaught exception already produces a 500, but the default body can leak details in some setups. Add a global handler that logs the real error server-side and returns a clean, trace-able envelope to the client.

from fastapi import FastAPI, Request, status
from fastapi.responses import JSONResponse
import logging, uuid

app = FastAPI()
log = logging.getLogger("app")

@app.exception_handler(Exception)
async def unhandled_handler(request: Request, exc: Exception):
    trace_id = str(uuid.uuid4())
    # Full detail to the logs (private); only a correlation id to the client.
    log.exception("unhandled error", extra={"trace_id": trace_id,
                                             "path": request.url.path})
    return JSONResponse(
        status_code=status.HTTP_500_INTERNAL_SERVER_ERROR,
        content={"error": "internal_error", "trace_id": trace_id},
    )

@app.get("/boom")
def boom():
    raise ValueError("something broke internally")   # -> clean 500 + trace_id
Never return raw exception text or stack traces to clients (info disclosure). Keep debug=False in production and log details privately.

501 Not Implemented — honest stubs

For endpoints you've declared but not built yet, return 501 so callers know it's coming, not broken.

from fastapi import FastAPI, HTTPException, status

app = FastAPI()

@app.post("/export/pdf")
def export_pdf():
    raise HTTPException(
        status_code=status.HTTP_501_NOT_IMPLEMENTED,
        detail="PDF export is not available yet",
    )

502 / 504 — when an upstream call fails or times out

If your service calls another API (with httpx/requests) and that call fails or times out, translate it into the right 5xx so clients can react sensibly. A timeout upstream → 504; a bad/garbled response → 502.

from fastapi import FastAPI, HTTPException, status
import httpx

app = FastAPI()

@app.get("/profile/{user_id}")
async def profile(user_id: int):
    try:
        async with httpx.AsyncClient(timeout=5.0) as client:
            r = await client.get(f"https://upstream.example/users/{user_id}")
    except httpx.TimeoutException:
        # upstream too slow
        raise HTTPException(status.HTTP_504_GATEWAY_TIMEOUT,
                            "profile service timed out")
    except httpx.RequestError:
        # couldn't reach / bad connection to upstream
        raise HTTPException(status.HTTP_502_BAD_GATEWAY,
                            "profile service unavailable")

    if r.status_code >= 500:
        # upstream itself errored -> we are a bad gateway to the client
        raise HTTPException(status.HTTP_502_BAD_GATEWAY,
                            "profile service returned an error")
    return r.json()
Pattern: your service is a "gateway" to its dependencies. Upstream slow → 504. Upstream unreachable or returns nonsense → 502.

503 Service Unavailable — maintenance & health-based shedding

503 says "try again later." Always pair it with Retry-After. Two common uses: a maintenance flag, and a readiness/health check that fails when a dependency (DB) is down.

from fastapi import FastAPI, Response, status

app = FastAPI()
MAINTENANCE = False

@app.middleware("http")
async def maintenance_gate(request, call_next):
    if MAINTENANCE and not request.url.path.startswith("/health"):
        return Response(
            content='{"error":"under maintenance"}',
            media_type="application/json",
            status_code=status.HTTP_503_SERVICE_UNAVAILABLE,
            headers={"Retry-After": "120"},       # come back in 2 minutes
        )
    return await call_next(request)

@app.get("/health")
async def health(response: Response):
    if not await db_is_up():
        response.status_code = status.HTTP_503_SERVICE_UNAVAILABLE
        return {"status": "degraded", "db": "down"}
    return {"status": "ok"}
Load balancers love 503 on /health: a readiness probe that returns 503 when the DB is down lets the orchestrator stop routing traffic to a sick instance.

Client-side: how callers should react to 5xx

Closing the loop with the theory page — 5xx are usually retryable with backoff, 4xx are not.

import time, httpx

def get_with_retry(url, attempts=4):
    for i in range(attempts):
        r = httpx.get(url, timeout=5)
        if r.status_code < 500:
            return r                       # 2xx/3xx/4xx: don't retry 4xx
        wait = min(2 ** i, 10)             # exponential backoff: 1,2,4,8...
        retry_after = r.headers.get("Retry-After")
        time.sleep(int(retry_after) if retry_after else wait)
    r.raise_for_status()

Summary

  • 500 — global Exception handler + trace id, no leaks.
  • 501 — honest stub for unbuilt features.
  • 502 — upstream unreachable / bad response.
  • 503 — maintenance / unhealthy, always + Retry-After.
  • 504 — upstream timed out.
