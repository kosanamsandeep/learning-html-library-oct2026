Chapter 02 · 2xx Success

2xx — "it worked", but pick the right success

Returning 200 for everything is a smell. The right 2xx tells the client exactly what happened: created, accepted-for-later, or done-with-nothing-to-return. Here's each one in FastAPI.

The 2xx you'll actually use

Code Return when… FastAPI mechanism
200 OK A normal read/update succeeded Default — just return data
201 Created A POST created a new resource status_code=201 + Location
202 Accepted Work was queued, not done yet status_code=202 + BackgroundTasks
204 No Content Success with nothing to return (delete) status_code=204 + empty Response
206 Partial Content You served a byte range / stream chunk Explicit Response + Content-Range

200 OK — the default

Return a dict or a Pydantic model. Use response_model to control exactly what the client sees (and to strip internal fields).

from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI()

class ItemOut(BaseModel):
    id: int
    name: str

@app.get("/items/{item_id}", response_model=ItemOut)   # 200 implicitly
def read_item(item_id: int):
    return {"id": item_id, "name": "widget", "secret": "hidden"}  # 'secret' is dropped

201 Created — return the new resource + Location

Best practice for a successful POST: respond 201, include the new resource's URL in the Location header, and return the created object. 

from fastapi import FastAPI, Response, HTTPException, status
from pydantic import BaseModel

app = FastAPI()

class Item(BaseModel):
    id: int
    name: str

DB: dict[int, Item] = {}

@app.post("/items", status_code=status.HTTP_201_CREATED, response_model=Item)
def create_item(item: Item, response: Response):
    if item.id in DB:
        raise HTTPException(status.HTTP_409_CONFLICT, "id already exists")
    DB[item.id] = item
    response.headers["Location"] = f"/items/{item.id}"   # where to find it
    return item
Why Location? It lets the client (and REST tooling) follow up with a GET on the exact resource it just created — the hallmark of a well-behaved REST API.

202 Accepted — "I took it, I'll do it later"

For long-running work (emails, report generation, video processing) you accept the request, kick off background work, and return 202 with a way to check progress.

from fastapi import FastAPI, BackgroundTasks, status
import uuid

app = FastAPI()
JOBS: dict[str, str] = {}

def run_report(job_id: str):
    # ...heavy work...
    JOBS[job_id] = "done"

@app.post("/reports", status_code=status.HTTP_202_ACCEPTED)
def start_report(bg: BackgroundTasks):
    job_id = str(uuid.uuid4())
    JOBS[job_id] = "processing"
    bg.add_task(run_report, job_id)
    # Tell the client where to poll for the result.
    return {"job_id": job_id, "status_url": f"/reports/{job_id}"}

@app.get("/reports/{job_id}")
def report_status(job_id: str):
    return {"job_id": job_id, "status": JOBS.get(job_id, "unknown")}
202 vs 201: 201 means "it exists now." 202 means "I accepted your request but it isn't finished" — always pair it with a status/polling endpoint.

204 No Content — success, empty body

Perfect for DELETE or a fire-and-forget update. A 204 response must have no body — return an empty Response.

from fastapi import FastAPI, Response, status

app = FastAPI()
DB: dict[int, dict] = {1: {"name": "widget"}}

@app.delete("/items/{item_id}", status_code=status.HTTP_204_NO_CONTENT)
def delete_item(item_id: int):
    DB.pop(item_id, None)
    return Response(status_code=status.HTTP_204_NO_CONTENT)   # no JSON body
Common bug: returning a dict with status_code=204 makes FastAPI try to write a body, which violates the spec and can warn/err. Always return an empty Response.

206 Partial Content — ranges & streaming

Used when the client asks for part of a file via the Range header (video seeking, resumable downloads). You return 206 with a Content-Range header describing the slice you sent.

from fastapi import FastAPI, Request, Response, status

app = FastAPI()
DATA = b"0123456789" * 1000   # pretend this is a file in memory

@app.get("/download")
def download(request: Request):
    range_header = request.headers.get("range")        # e.g. "bytes=0-99"
    if not range_header:
        return Response(DATA, media_type="application/octet-stream")  # 200 full

    units, _, rng = range_header.partition("=")
    start_s, _, end_s = rng.partition("-")
    start = int(start_s)
    end = int(end_s) if end_s else len(DATA) - 1
    chunk = DATA[start:end + 1]

    return Response(
        content=chunk,
        status_code=status.HTTP_206_PARTIAL_CONTENT,
        headers={
            "Content-Range": f"bytes {start}-{end}/{len(DATA)}",
            "Accept-Ranges": "bytes",
        },
        media_type="application/octet-stream",
    )
Tip: for real files, FastAPI's FileResponse already handles Range requests and 206 automatically — reach for it before hand-rolling byte math.

Summary

  • 200 read/update — just return data (+ response_model).
  • 201 create — status_code=201 + Location.
  • 202 queued — BackgroundTasks + polling URL.
  • 204 deleted — empty Response(status_code=204).
  • 206 partial — Content-Range or FileResponse.
