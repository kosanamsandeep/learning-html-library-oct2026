Chapter 07 · Real-time

Real-time protocols & WebRTC — how voice "talk-back" apps work

REST is request→response. But chat, live notifications, and especially two-way voice (ChatGPT voice mode, Google Meet, Discord) need data flowing continuously, both directions, with the lowest possible latency. This page compares the real-time options and answers the real question: how hard is WebRTC to implement vs the others?

The real-time family at a glance

Protocol Typical use Real-time? Direction Transport
REST (HTTP) CRUD APIs ❌ Request → Response TCP
SSE (Server-Sent Events) Notifications, token streaming (LLM text) ✅ One-way (server → client) TCP (HTTP)
WebSocket Chat, live dashboards, collaboration ✅ Two-way (full duplex) TCP
gRPC Backend-to-backend, streaming RPC ✅ (streaming) Two-way TCP (HTTP/2)
WebRTC Voice/video, screen share, P2P data ✅✅ ultra low-latency Two-way (media + data) UDP (SRTP/DTLS), TCP fallback
The key insight: the first four ride on TCP (reliable, ordered, but head-of-line blocking adds delay). WebRTC rides on UDP — it tolerates a lost audio packet rather than waiting for it, which is exactly what live voice needs. A 150 ms stall is unacceptable on a call but invisible in a chat.

Why voice "talk-back" apps pick WebRTC

What voice needs

  • Ultra-low latency (<200 ms mouth-to-ear) for natural turn-taking.
  • Loss tolerance — drop a packet, don't stall the stream.
  • Built-in media — mic capture, echo cancellation, noise suppression, jitter buffers.
  • Adaptive bitrate when the network degrades.

Why the others fall short

  • WebSocket is TCP — a lost packet blocks everything behind it (head-of-line blocking → audio glitches).
  • SSE is one-way text only.
  • REST/gRPC aren't designed to carry live mic audio with echo cancellation.
  • None of them give you codecs, NAT traversal, or jitter buffers for free.
How a voice assistant like ChatGPT voice mode is wired (conceptually): the browser opens a WebRTC connection to stream your mic audio up with minimal latency; the server runs speech-to-text → the model → text-to-speech and streams the spoken reply back over the same connection. (Public clients also expose a WebSocket variant of the Realtime API; WebRTC is the recommended path for browsers because of its media stack and latency.)

Note: exact internals of commercial products aren't public — this is the standard architecture such "speech-to-speech" systems use.

So… how hard is WebRTC to implement? (the honest answer)

WebRTC is significantly harder than the others — not because the API is huge, but because a working call needs several moving parts that the simpler protocols don't:

Protocol Effort to a working demo What you must stand up Ops burden
REST 🟢 Minutes One endpoint Trivial
SSE 🟢 Minutes One streaming endpoint Trivial
WebSocket 🟢 ~An hour WS route + connection handling Low (sticky sessions/scale-out)
gRPC 🟡 A few hours .proto + codegen + typed clients Medium (HTTP/2, tooling)
WebRTC 🔴 Days (and a real call: weeks) Signaling + STUN + TURN + ICE + SDP + media/codecs High (TURN servers, NAT, scaling via SFU)
The catch: WebRTC is peer-to-peer, but peers sit behind NATs/firewalls and can't reach each other directly. You still need a server for two jobs: a signaling channel (to exchange connection info) and STUN/TURN servers (to find a network path / relay media when direct fails). That infrastructure is the real cost.

The pieces that make WebRTC hard

Signaling

WebRTC does not define how peers first find each other. You build this yourself — usually a WebSocket that relays "offer/answer" (SDP) and ICE candidates between the two sides.

SDP (offer/answer)

A text blob describing codecs, media tracks, and parameters. One peer creates an offer, the other replies with an answer.

ICE + STUN

STUN tells a peer its public IP:port behind NAT. ICE gathers all candidate paths and picks one that works.

TURN (the expensive one)

When direct P2P is blocked (strict/symmetric NAT, corporate firewalls), a TURN server relays all media. It costs real bandwidth/money and you must run it (e.g. coturn).

DTLS-SRTP

Media is always encrypted. The handshake and key exchange are built in — good for security, more to understand when debugging.

SFU (to scale)

P2P mesh works for 2 people. For group calls you add a Selective Forwarding Unit server (mediasoup, Janus, LiveKit) to fan media out efficiently.

The WebRTC connection dance

    participant S as Signaling server
(your WebSocket)

    A->>T: Ask "what's my public IP?" (STUN)
    A->>A: createOffer() → local SDP

    B->>S: send ANSWER (SDP)

    A-->>S: ICE candidates
    B-->>S: ICE candidates
    S-->>A: relay candidates
    S-->>B: relay candidates

(direct, or via TURN relay)
    A-)B: 🔊 encrypted media flows DIRECTLY (UDP/SRTP)
    B-)A: 🔊 (signaling server is no longer in the media path)

Your server is only needed to set up the call. Once connected, audio flows peer-to-peer (or via TURN) — not back through your app.

Compare the code: a streaming endpoint in each protocol

To feel the difference, here is "send live data to a client" at its simplest in each. Notice how the first three are a handful of lines, while WebRTC needs a whole signaling + peer setup.

SSE — one-way stream (great for LLM text tokens)

from fastapi import FastAPI
from fastapi.responses import StreamingResponse
import asyncio

app = FastAPI()

async def token_stream():
    for word in ["Hello", "from", "the", "model"]:
        yield f"data: {word}\n\n"          # SSE frame
        await asyncio.sleep(0.2)

@app.get("/stream")
def stream():
    return StreamingResponse(token_stream(), media_type="text/event-stream")

WebSocket — two-way text/binary (chat, live UI)

from fastapi import FastAPI, WebSocket, WebSocketDisconnect

app = FastAPI()

@app.websocket("/ws")
async def ws(ws: WebSocket):
    await ws.accept()
    try:
        while True:
            msg = await ws.receive_text()
            await ws.send_text(f"echo: {msg}")
    except WebSocketDisconnect:
        pass

WebRTC — you first need a signaling relay…

Even the "simple" part — relaying offer/answer/ICE between two peers — is its own WebSocket server:

from fastapi import FastAPI, WebSocket, WebSocketDisconnect

app = FastAPI()
rooms: dict[str, list[WebSocket]] = {}

@app.websocket("/signal/{room}")
async def signal(ws: WebSocket, room: str):
    await ws.accept()
    rooms.setdefault(room, []).append(ws)
    try:
        while True:
            # Blindly relay SDP offers/answers and ICE candidates to the other peer(s).
            msg = await ws.receive_text()
            for peer in rooms[room]:
                if peer is not ws:
                    await peer.send_text(msg)
    except WebSocketDisconnect:
        rooms[room].remove(ws)
That's only the matchmaking. The browser still runs the real WebRTC API (RTCPeerConnection, getUserMedia) and you still need STUN/TURN. The signaling server above never touches the audio.

…and a server that actually speaks WebRTC (Python: aiortc)

If your server is a peer (e.g. a voice bot that receives mic audio and sends audio back), use aiortc. This handles SDP, ICE, DTLS-SRTP, and Opus for you — but you can see there's a lot more ceremony than a WebSocket.

# pip install aiortc
from fastapi import FastAPI, Request
from aiortc import RTCPeerConnection, RTCSessionDescription, MediaStreamTrack

app = FastAPI()
pcs: set[RTCPeerConnection] = set()

class EchoAudioTrack(MediaStreamTrack):
    """Receives the caller's mic frames and echoes them straight back."""
    kind = "audio"
    def __init__(self, source): 
        super().__init__()
        self.source = source
    async def recv(self):
        return await self.source.recv()      # here you'd run STT → LLM → TTS

@app.post("/offer")
async def offer(request: Request):
    body = await request.json()              # {sdp, type} from the browser
    pc = RTCPeerConnection()                 # ICE/DTLS handled internally
    pcs.add(pc)

    @pc.on("track")
    def on_track(track):
        if track.kind == "audio":
            pc.addTrack(EchoAudioTrack(track))   # pipe audio back

    await pc.setRemoteDescription(RTCSessionDescription(**body))
    answer = await pc.createAnswer()
    await pc.setLocalDescription(answer)
    # Return our SDP answer; the browser sets it as its remote description.
    return {"sdp": pc.localDescription.sdp, "type": pc.localDescription.type}
Still missing for production: a public TURN server (e.g. coturn) for clients behind strict NATs, reconnection logic, codec/bitrate tuning, and load-aware scaling. This is why most teams reach for a managed stack (LiveKit, Daily, Twilio, Agora) instead of hand-rolling.

Decision guide — which real-time protocol?

    A[Do I need real-time?] -- No --> REST[REST / gRPC]
    A -- Yes --> B{What am I moving?}
    B -- "Live audio/video" --> WRTC[WebRTC
+ STUN/TURN/SFU]
    B -- "Text/JSON, both ways" --> WS[WebSocket]

e.g. LLM text tokens" --> SSE[SSE]
    B -- "Service ↔ service streaming" --> GRPC[gRPC streaming]
If you want… Use Why
Stream LLM text to a browser SSE One-way, dead simple, auto-reconnect
Chat / live cursors / dashboards WebSocket Two-way text, easy, ubiquitous
Two-way voice/video WebRTC UDP, low latency, media stack built in
Internal streaming RPC gRPC Typed, fast, bi-di over HTTP/2
Pragmatic rule: reach for WebRTC only when you're moving live media. For everything else, WebSocket or SSE gets you 90% of "real-time" at 10% of the effort. And for real voice products, stand on a managed WebRTC platform rather than rebuilding STUN/TURN/SFU yourself.
