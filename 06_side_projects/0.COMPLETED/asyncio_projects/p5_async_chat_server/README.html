Async TCP chat server — many clients, one event loop

This capstone turns the earlier ideas into a real network program. The server accepts many TCP clients, gives each client its own coroutine, and broadcasts messages without creating one operating-system thread per user.

The story

A chat room is mostly waiting: waiting for a new connection, waiting for a line of text, waiting for a socket to accept bytes. Asyncio is excellent here because the event loop can serve one idle client while another client is typing and a third client is receiving a broadcast.

Files

File Purpose
server.py Async TCP server using asyncio.start_server, streams, broadcast, lock, and graceful client cleanup.
client.py Async client that reads from the server while also accepting terminal input.
requirements.txt No external dependencies.

Network mental model

Client connects
->
Server creates handler coroutine
->
Handler awaits incoming lines
->
Room broadcasts to all writers

Each client is handled by handle_client. The event loop switches between clients whenever a handler awaits socket input or socket drain.

Core server code

server = await asyncio.start_server(
    lambda reader, writer: handle_client(reader, writer, room),
    host,
    port,
)

async with server:
    await server.serve_forever()

StreamReader reads bytes from the client. StreamWriter writes bytes back. await writer.drain() is important because it respects TCP backpressure if a client is slow.

Why the chat room uses a lock

The chat room has a shared dictionary of connected clients. Even though asyncio usually runs one task at a time, tasks can interleave at await points. The lock makes joins, leaves, and snapshots of connected clients safe and easy to reason about.

async with self._lock:
    self._clients[client.writer] = client

How to run

cd 06_side_projects/asyncio_projects/p5_async_chat_server
python server.py

# Open another terminal:
python client.py

# Open a third terminal for a second user:
python client.py

Type a name, then messages. Type /quit to leave.

What to remember

  • Async servers are ideal for many mostly-idle connections.
  • asyncio.start_server creates a coroutine per connection.
  • reader.readline waits for network input without blocking all clients.
  • writer.drain handles network backpressure.
  • Shared state still needs careful coordination, often with asyncio.Lock.
Interview answer: An asyncio TCP server scales well for many idle or I/O-bound clients because each connection is a coroutine. The event loop resumes whichever connection has data ready, so the server avoids one thread per client while still handling many clients concurrently.
