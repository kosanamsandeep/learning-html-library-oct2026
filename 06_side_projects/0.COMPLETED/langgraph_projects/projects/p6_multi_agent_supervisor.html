Project 6 · Advanced

Orchestrate specialists: the supervisor pattern

One giant agent with 30 tools gets confused. The production answer is a team: a supervisor that routes each step to the right specialist agent, using Command handoffs and subgraphs. This is how serious systems scale.

What this project does

A supervisor LLM reads the conversation and decides which worker should act next — say a researcher (web/RAG) or a coder (runs Python). The chosen worker does its job, returns control to the supervisor, which decides again, until the task is finished. Each worker is itself a full agent (often a ReAct agent from P2) wrapped as a node or subgraph.

Advanced supervisor Command(goto=) handoffs subgraphs

The architecture

flowchart TD
    START((START)) --> sup["supervisor
who should act next?"]
    sup -->|route| research["researcher agent
(ReAct + search/RAG)"]
    sup -->|route| coder["coder agent
(ReAct + python REPL)"]
    sup -->|done| END((END))
    research -->|report back| sup
    coder -->|report back| sup

A hub-and-spoke topology. The supervisor is the only node that decides routing; workers just do work and return.

Why not just one big agent?

❌ Monolith agent

  • Too many tools → the model picks the wrong one.
  • One bloated prompt mixing every concern.
  • Hard to test, trace, or improve one capability.

✅ Supervised team

  • Each agent has a focused prompt + few tools.
  • Specialists are independently testable and swappable.
  • The supervisor's only job is routing — easy to reason about.

The handoff mechanism — Command

A node returns a Command that does two things at once: update state and say where to go next (goto). That's how the supervisor routes and how a worker returns control.

from typing import Literal
from langgraph.types import Command
from langgraph.graph import StateGraph, MessagesState, START, END
from pydantic import BaseModel

WORKERS = ["researcher", "coder"]

class Route(BaseModel):
    next: Literal["researcher", "coder", "FINISH"]

router = llm.with_structured_output(Route)

def supervisor(state: MessagesState) -> Command:
    decision = router.invoke([
        {"role": "system", "content": "Route to the best worker, or FINISH."},
        *state["messages"],
    ])
    if decision.next == "FINISH":
        return Command(goto=END)
    return Command(goto=decision.next)     # hand off to a worker

Workers as subgraph agents

Each worker is a self-contained agent (reuse P2's create_react_agent). After it runs, it hands control back to the supervisor with another Command.

from langgraph.prebuilt import create_react_agent

research_agent = create_react_agent(llm, tools=[web_search, rag_lookup],
    prompt="You are a research specialist.")
coder_agent = create_react_agent(llm, tools=[python_repl],
    prompt="You are a coding specialist.")

def researcher(state: MessagesState) -> Command[Literal["supervisor"]]:
    result = research_agent.invoke(state)
    return Command(
        update={"messages": result["messages"][-1:]},
        goto="supervisor",                 # return control
    )

def coder(state: MessagesState) -> Command[Literal["supervisor"]]:
    result = coder_agent.invoke(state)
    return Command(update={"messages": result["messages"][-1:]}, goto="supervisor")

Assembling the team

builder = StateGraph(MessagesState)
builder.add_node("supervisor", supervisor)
builder.add_node("researcher", researcher)
builder.add_node("coder", coder)
builder.add_edge(START, "supervisor")
# No manual edges to workers needed — Command(goto=...) handles routing.

graph = builder.compile(checkpointer=InMemorySaver())   # memory + diagnostics from P3/P4

graph.invoke({"messages": [{"role": "user",
    "content": "Research 2024 EV sales, then plot the trend."}]},
    {"configurable": {"thread_id": "team-1"}})
The flow: supervisor → researcher (finds sales data) → supervisor → coder (writes the plot) → supervisor → FINISH. Each handoff is a Command; the shared messages state is the team's common memory.

Multi-agent topologies

Pattern Shape Use when
Supervisor Central router → workers Clear division of labor, one coordinator (this project)
Swarm Peers hand off directly to each other Fluid collaboration, no central boss
Hierarchical Supervisors of supervisors Large systems, teams of teams
Network Any node → any node Maximum flexibility, hardest to control

LangChain ships langgraph-supervisor and langgraph-swarm as prebuilt libraries for the first two — but knowing the Command mechanism lets you build any of them.

Best practices for multi-agent systems

  • Keep workers focused. 2–5 tools each. If a worker needs 15 tools, split it.
  • Control what's shared. Return only the final message from a worker (result["messages"][-1:]) so the supervisor isn't flooded with the worker's internal scratchpad.
  • Use subgraphs for isolation. A worker can have its own private state schema and only expose a clean interface to the parent graph.
  • Cap total steps. Set recursion_limit — multi-agent loops can ping-pong.
  • Trace everything (P4). With many agents, LangSmith is the only sane way to see who did what and why.
  • Persist (P3). Long multi-agent tasks should be resumable; a checkpointer makes a crash recoverable.
