Project 3 · Intermediate

Memory done efficiently: checkpoints, threads & a store

The state in P1–P2 vanished when the call ended. Here you make it durable. You'll learn the two kinds of memory LangGraph offers — short-term (thread checkpoints) and long-term (the cross-thread Store) — and how to keep both cheap.

What this project does

Add a checkpointer at compile time and pass a thread_id at runtime. Now every step is saved. Re-invoking with the same thread_id resumes the exact conversation — across requests, processes, even crashes. Then add a Store so the agent remembers facts about a user across different conversations.

Intermediate checkpointer thread_id SqliteSaver Store summarization

Two kinds of memory — don't confuse them

🧵 Short-term = thread state

The message history of one conversation. Stored by a checkpointer, keyed by thread_id. This is "what we said in this chat".

🗄️ Long-term = the Store

Facts that should outlive any single chat — "the user is vegetarian", "prefers metric units". Stored in a Store, keyed by a namespace like (user_id, "facts").

Two chats (threads) share one long-term memory (store namespace).

Short-term: add a checkpointer

from langgraph.graph import StateGraph, MessagesState, START
from langgraph.checkpoint.memory import InMemorySaver

def chatbot(state: MessagesState):
    return {"messages": [llm.invoke(state["messages"])]}

builder = StateGraph(MessagesState)
builder.add_node("chatbot", chatbot)
builder.add_edge(START, "chatbot")

# THE ONE LINE that turns on memory:
checkpointer = InMemorySaver()                 # dev only; swap for SqliteSaver/Postgres in prod
graph = builder.compile(checkpointer=checkpointer)

# thread_id = the conversation's identity
config = {"configurable": {"thread_id": "user-42-chat-A"}}

graph.invoke({"messages": [{"role": "user", "content": "My name is Aria."}]}, config)
# Later, SAME thread_id -> it remembers:
graph.invoke({"messages": [{"role": "user", "content": "What's my name?"}]}, config)
# -> "Your name is Aria."
That's the whole feature. compile(checkpointer=...) + thread_id. Every super-step is snapshotted, so you also get crash-recovery and time-travel (P4) for free.

Long-term: the Store (cross-thread memory)

Inject a Store at compile time. Any node can receive it and read/write namespaced facts that persist across every thread for that user.

from langgraph.store.memory import InMemoryStore
from langgraph.store.base import BaseStore
from langchain_core.runnables import RunnableConfig

store = InMemoryStore()        # prod: PostgresStore, optionally with embeddings for semantic recall

def chatbot(state: MessagesState, config: RunnableConfig, *, store: BaseStore):
    user_id = config["configurable"]["user_id"]
    namespace = (user_id, "facts")

    # 1) recall long-term facts
    facts = store.search(namespace)
    memory = "\n".join(f.value["text"] for f in facts)

    sys = {"role": "system", "content": f"Known about user:\n{memory}"}
    reply = llm.invoke([sys, *state["messages"]])

    # 2) optionally write a new fact
    store.put(namespace, "latest", {"text": "Prefers concise answers."})
    return {"messages": [reply]}

graph = builder.compile(checkpointer=checkpointer, store=store)
graph.invoke(state, {"configurable": {"thread_id": "chat-B", "user_id": "user-42"}})
Semantic memory: give the store an embeddings index and use store.search(namespace, query="dietary preferences") to retrieve only the relevant facts instead of dumping everything into the prompt.

Keeping memory efficient — the part people skip

A naive agent re-sends the entire history every turn. Tokens (and cost, and latency) grow without bound. Three standard fixes:

✂️ Trim

Keep only the last N messages (or last N tokens) before calling the model.

from langchain_core.messages import trim_messages
msgs = trim_messages(state["messages"], max_tokens=2000,
    strategy="last", token_counter=llm)

📝 Summarize

When history gets long, replace old turns with a running summary message. Bounded tokens, preserved context.

🎯 Selective recall

Pull only relevant long-term facts from the Store via semantic search — not the whole profile.

Rule of thumb: short-term memory should be bounded (trim/summarize), long-term memory should be retrieved (search, not dump). That combination keeps an agent fast and cheap even after thousands of turns.

snap = graph.get_state(config)          # current checkpoint
