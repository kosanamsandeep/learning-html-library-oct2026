Project 07 — Supply Chain Security

Container Signing Lab

Build a CI pipeline that builds a Docker image, signs it with Cosign (keyless mode), pushes it to a registry, and enforces that only signed images can be deployed — using Sigstore's Fulcio + Rekor for transparent, keyless signing.

Architecture & Flow

The signing flow binds an identity (your GitHub OIDC token) to an artifact (the container image) through a short-lived signing certificate issued by Fulcio. Rekor records the signature in a tamper-proof transparency log.

  1. Build — CI builds a container image and computes its digest (sha256 hash).
  2. Request certificate — Cosign presents the CI job's OIDC token (from GitHub Actions) to Fulcio, which issues a short-lived code-signing certificate binding the identity to a ephemeral key pair.
  3. Sign — Cosign signs the image digest with the private key and stores the signature as a separate manifest in the container registry alongside the image.
  4. Transparency log — Cosign records the signature in Rekor's immutable merkle tree. Rekor returns a Signed Entry Timestamp (SET) proving the record was included.
  5. Verify — During deployment, an admission controller (or CI step) runs cosign verify to check the signature, validate the certificate chain against Fulcio, and confirm the entry exists in Rekor.

How Keyless Signing Works (Fulcio + Rekor)

Traditional signing requires managing long-lived private keys — a security risk and operational burden. Sigstore's keyless signing eliminates this by using ephemeral keys tied to a software identity (not a person, but an OIDC identity like an email or GitHub repository).

Component Role How It Works
Fulcio Certificate Authority (CA) Receives an OIDC token from the CI provider (e.g., id-token: write in GitHub Actions). Validates the token, then issues a short-lived X.509 code-signing certificate. The certificate embeds the identity (e.g., https://github.com/my-org/my-repo/.github/workflows/build.yml@refs/heads/main) in the Subject Alternative Name (SAN) field.
Rekor Transparency Log An immutable, append-only merkle tree of signing events. Every signature is recorded, creating a public audit trail. This prevents attackers from signing malicious artifacts and then hiding their tracks. Rekor returns a Signed Entry Timestamp (SET) that can be verified offline.
Cosign Signing & Verification CLI Orchestrates the flow: generates an ephemeral key pair, requests the Fulcio certificate, signs the artifact, records in Rekor, and uploads the signature to the registry. On verify, it checks the certificate chain, the Rekor entry, and confirms the identity matches expected policies.
Key insight: There are no long-lived secrets to rotate. The signing key exists only for the duration of the cosign sign command and is immediately discarded. Trust is rooted in the OIDC identity — an attacker would need to compromise your CI provider (e.g., steal your GitHub Actions OIDC token) to sign a malicious image as your project.

GitHub Actions Workflow

This is a complete CI pipeline that builds, signs, and pushes a container image using Cosign keyless signing. The id-token: write permission is required to obtain the OIDC token from GitHub.

# .github/workflows/build-and-sign.yml
name: Build, Sign & Push Container

on:
  push:
    branches: [main]
    tags: ['v*']
  pull_request:
    branches: [main]

permissions:
  contents: read
  id-token: write    # needed for OIDC token (keyless signing)
  packages: write    # needed to push to GHCR

env:
  REGISTRY: ghcr.io
  IMAGE_NAME: ${{ github.repository }}

jobs:
  build-and-sign:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout repository
        uses: actions/checkout@v4

      - name: Log in to the Container registry
        uses: docker/login-action@v3
        with:
          registry: ${{ env.REGISTRY }}
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - name: Extract metadata for Docker
        id: meta
        uses: docker/metadata-action@v5
        with:
          images: ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}

      - name: Build and push Docker image
        uses: docker/build-push-action@v5
        id: build
        with:
          context: .
          push: true
          tags: ${{ steps.meta.outputs.tags }}
          labels: ${{ steps.meta.outputs.labels }}

      - name: Install Cosign
        uses: sigstore/cosign-installer@v3

      - name: Sign the image with Cosign keyless
        env:
          DIGEST: ${{ steps.build.outputs.digest }}
          TAGS: ${{ steps.meta.outputs.tags }}
        run: |
          image="${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}@${DIGEST}"
          cosign sign "$image" \
            --yes \
            --upload=true \
            --tlog-upload=true

      - name: Verify the signed image
        run: |
          image="${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}@${{ steps.build.outputs.digest }}"
          cosign verify "$image" \
            --certificate-identity-regexp "https://github.com/${{ github.repository }}/.*" \
            --certificate-oidc-issuer "https://token.actions.githubusercontent.com"

Admission Control: Refusing Unsigned Images

Signing is only half the battle — you must enforce that only signed images can run in production. In Kubernetes, this is done with an admission controller like Sigstore Policy Controller or Kyverno.

Example Kyverno policy:

# require-image-signature.yaml
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: require-cosign-signature
spec:
  validationFailureAction: Enforce
  rules:
    - name: verify-image
      match:
        any:
          - resources:
              kinds:
                - Pod
      verifyImages:
        - imageReferences:
            - "ghcr.io/my-org/*"
          attestors:
            - entries:
                - keyless:
                    issuer: "https://token.actions.githubusercontent.com"
                    subject: "https://github.com/my-org/my-repo/.github/workflows/build.yml@*"
          required: true
How it works: When a Kubernetes pod spec references an image, the admission controller intercepts the request, runs cosign verify against the image, and checks that the signing certificate's identity matches the expected OIDC issuer and subject. If verification fails, the pod is rejected with a clear error message. This prevents attackers from deploying a tampered image even if they have push access to the registry.

Running the Lab Locally

You can simulate the signing flow on your local machine without a full CI pipeline:

# Prerequisites
# Install Cosign: https://docs.sigstore.dev/cosign/installation/
# Install Docker

# 1. Build a test image
docker build -t my-app:latest .

# 2. Sign with keyless mode (opens browser for OIDC auth)
cosign sign docker.io/yourname/my-app:latest

# 3. Verify the signature
cosign verify docker.io/yourname/my-app:latest \
  --certificate-identity your@email.com \
  --certificate-oidc-issuer https://accounts.google.com

# 4. (Optional) Verify without network access using the Rekor SET
cosign verify docker.io/yourname/my-app:latest \
  --certificate-identity your@email.com \
  --certificate-oidc-issuer https://accounts.google.com \
  --rekor-public-key /path/to/rekor.pub

Commands reference:

Command Purpose
cosign sign Signs an image digest and uploads the signature to the registry
cosign verify Verifies a signature against Fulcio root certs and Rekor
cosign verify-attestation Verifies an in-toto attestation attached to the image
cosign triangulate Locates the signature manifest for a given image
rekor-cli get Retrieves a transparency log entry by UUID

Security Model & Limitations

Aspect Detail
Trust root The OIDC identity (GitHub repo, email, etc.) and the Fulcio CA public key. No long-lived secrets.
Key compromise Ephemeral keys exist only during signing. No key rotation needed.
Transparency All signatures are public in Rekor. Any auditor can verify that no hidden signatures exist.
Limitation Keyless signing requires network access to Fulcio and Rekor. For air-gapped environments, use Cosign with a private key or a self-hosted Sigstore deployment.
Limitation OIDC identity binding is only as strong as the CI provider's OIDC implementation. GitHub's OIDC tokens include the repository and workflow ref, making them strongly scoped.
