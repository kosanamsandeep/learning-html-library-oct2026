AI Governance Dashboard

A web dashboard that shows which agents are used by which teams, SBOM compliance per repository, and eval score trends over time. Governance metrics made visible—so you can measure adoption without micromanaging.

System Architecture

The dashboard aggregates data from three independent collectors and presents them in a unified static interface. While the data sources are real systems, this project focuses on the dashboard front-end; data is loaded from static JSON snapshots for demonstration purposes.

What Metrics Matter for AI Governance

Effective governance walks a tightrope: you need enough visibility to detect problems, but not so much overhead that teams circumvent the system. These are the metrics that matter most:

Adoption breadth

What fraction of teams use AI-assisted tools at least once a week? Track aggregate trends, not per-developer stats. If adoption plateaus below 50%, investigate barriers (access, training, trust) rather than mandating usage.

SBOM freshness

What percentage of repos have an SBOM generated within the last 7 days? A declining SBOM freshness rate reveals teams sidestepping the supply chain pipeline. Surface this as a trend line, not a pass/fail gate.

Eval score drift

Are model eval scores stable, improving, or regressing? A single point drop is noise; three consecutive drops trigger an investigation. Flag regressions automatically without requiring manual review of every run.

Cost per team

Agent API costs broken down by team. High cost without high adoption suggests inefficient usage patterns. Low cost with high adoption is the sweet spot. Share this data openly to encourage cost-conscious usage.

Measuring Adoption Without Micromanaging

The single most important governance principle: measure outcomes, not activity. A dashboard that shows "team X made 50K agent calls this week" invites gaming. A dashboard that shows "team X resolved 30% more PRs with the same headcount after adopting the code review assistant" builds trust.

Best practices for non-intrusive governance:

  • Aggregate by default, drill-down on demand. Show team-level aggregates first; individual usage is available via opt-in telemetry.
  • Trend lines over targets. Prefer month-over-month trends over hard targets. Trends reveal improvement; targets encourage metric-fixing.
  • Make data self-service. The dashboard should answer "how are we doing?" without requiring a data analyst. Each panel should be self-explanatory.
  • Separate insights from evaluation. The dashboard is for insight. Performance reviews should not use dashboard data punitively, or the data will become unreliable.

Extending to a Live Dashboard

To turn this static mockup into a live governance tool, you need three additions:

ComponentWhat it doesTechnology options
Data collector servicePolls APIs on a schedule, transforms data into the fixture schema, writes to storagePython cron job, GitHub Actions scheduled workflow, serverless function
Storage layerHolds snapshot history so the dashboard can show trend lines, not just point-in-time dataSQLite (single team), PostgreSQL (multi-team), or S3 + Athena
API gatewayServes the latest snapshots to the dashboard frontendFastAPI + uvicorn, Next.js API routes, or simply serve JSON from S3
AlertingFires notifications when metrics cross thresholds (e.g. SBOM compliance drops below 80%)Slack webhook, PagerDuty, or email via SendGrid
Final thought: A governance dashboard is only as good as the trust it builds. If the data is stale, incomplete, or used punitively, teams will find ways to evade it. Invest in data quality and a culture of transparency first; the dashboard UI is the easy part.
