Claude Code Lifecycle

Power of Hooks — Lifecycle Automation for Agentic Workflows

Hooks are shell commands that fire at specific lifecycle events in a Claude Code session. Inject custom behaviour before and after file operations, command execution, and session teardown — without modifying Claude Code itself.

What are Hooks?

If you have ever used Git hooks (pre-commit, post-merge, etc.), you already understand the concept. Claude Code hooks follow the same pattern: at specific points in the agent’s lifecycle, the hook system fires a shell script you provide. The script can inspect context, modify behaviour, log activity, or cancel the operation by returning a non-zero exit code.

The Hook Lifecycle in a Claude Code Session

The diagram below traces a typical session: reading a file, editing it, writing it back, running a command, and finally exiting. Each step has a before/after hook pair.

Key insight: Hooks are transparent to the LLM. Claude does not see the hook script or its output (unless you configure logging). They execute in the host shell before or after the corresponding event, giving you a clean separation between agent logic and system-level policy.

The 10 Hooks — When Each One Fires

Claude Code defines ten hook events. Five are file-related, two are command-related, one fires on every tool invocation, and one fires at session teardown.

Hook Trigger Common Use Case
beforeRead Before reading a file from disk Refresh a stale cache, check file permissions, inject dynamic content
afterRead After reading a file from disk Log file accesses, annotate content for downstream tools
beforeEdit Before applying an edit to a file Validate edit permissions, backup the original file, enforce lock checks
afterEdit After applying an edit to a file Lint the result, track change deltas, notify watchers
beforeWrite Before writing a file to disk Template injection, secret scanning, size limits
afterWrite After writing a file to disk Auto-format, compile, trigger rebuilds, run tests
beforeCommand Before executing a shell command Block dangerous commands, inject environment variables, enforce timeouts
afterCommand After executing a shell command Audit logging, collect metrics, parse output
preExit When the session is ending Stash WIP, clean temp files, send notifications, release resources
preToolUse Before any tool (read, write, bash, MCP, etc.) is invoked Rate limiting, telemetry, approval gates, context injection

Sequence: A File Edit Flowing Through Multiple Hooks

When Claude edits and saves a file, six hooks fire in sequence. This diagram traces the full journey of a single file modification.

    participant C as Claude
    participant H as Hook System
    participant FS as Filesystem

    C->>+H: Read file
    H->>H: beforeRead
    H->>+FS: Read file
    FS->>-H: File content
    H->>H: afterRead
    H->>-C: Content returned

    C->>+H: Edit file
    H->>H: beforeEdit
    H->>H: afterEdit
    H->>-C: Edit applied

    C->>+H: Write file
    H->>H: beforeWrite
    H->>+FS: Write file to disk
    FS->>-H: Write complete
    H->>H: afterWrite

    H->>-C: Write complete
Variable reference: Hooks receive context via arguments — {file} (file path), {command} (shell command), {exit_code} (last exit code), {tool_name} (tool name), and {tool_input} (tool input JSON). See the individual scripts for details.

Real Hook Scripts

Four production-ready hook scripts are included in this project. Each is fully functional with proper error handling, logging, and documentation.

01_format_on_write.sh afterWrite

Auto-formats Python files after they are saved. Detects ruff first, falls back to black, and logs every action to a dedicated log file. Non-.py files are skipped transparently.

#!/usr/bin/env bash # 01_format_on_write.sh — afterWrite Hook # Auto-format Python files when Claude Code saves them. set -euo pipefail LOG_FILE="${HOME}/.claude/hooks/format_on_write.log" detect_formatter() { if command -v ruff &/dev/null; then PYTHON_FORMATTER="ruff format" elif command -v black &/dev/null; then PYTHON_FORMATTER="black --quiet" else exit 0 # no formatter available — skip gracefully fi } format_file() { local file_path="$1" [[ "${file_path}" != *.py ]] && return 0 [[ ! -f "${file_path}" ]] && return 0 ${PYTHON_FORMATTER} "${file_path}" }

Install by adding to settings.local.json:

"afterWrite": ".claude/hooks/01_format_on_write.sh '{file}'"

02_audit_trail.sh afterCommand

Logs every shell command to a tab-separated audit file. Captures timestamp, session ID, exit code, working directory, and the command text. Automatically rotates when the log exceeds 50 MB.

#!/usr/bin/env bash # 02_audit_trail.sh — afterCommand Hook # Log every command Claude Code executes. AUDIT_FILE="${HOME}/.claude/hooks/audit_trail.log" log_entry() { local timestamp="$(date '+%Y-%m-%dT%H:%M:%S%z')" local session_id="${CLAUDE_CODE_SESSION_ID:-unknown}" local cwd="$(pwd)" # Tab-separated: timestamp | session | exit_code | cwd | command printf "%s\t%s\t%s\t%s\t%s\n" \ "${timestamp}" "${session_id}" \ "${exit_code}" "${cwd}" "${command_raw}" \ >> "${AUDIT_FILE}" }

Query examples:

# Recent commands tail -20 ~/.claude/hooks/audit_trail.log # Failed commands (exit code != 0) awk '$3 != 0' ~/.claude/hooks/audit_trail.log # Commands containing a keyword grep 'git push' ~/.claude/hooks/audit_trail.log

03_block_dangerous.sh beforeCommand

Blocks destructive commands before they execute. Returns a non-zero exit code to abort the command when dangerous patterns are detected. Covers rm -rf /, kubectl delete, DROP TABLE, git push --force, and many others.

#!/usr/bin/env bash # 03_block_dangerous.sh — beforeCommand Hook DANGEROUS_PATTERNS=( 'rm -rf /' 'kubectl delete' 'DROP TABLE' 'git push --force' 'chmod -R 777 /' 'mkfs\.' ) check_patterns() { local command_raw="$1" for pattern in "${DANGEROUS_PATTERNS[@]}"; do if echo "${command_raw}" | grep -iqE "${pattern}"; then echo "BLOCKED: matched pattern '${pattern}'" >&2 return 1 # non-zero cancels the command fi done return 0 }

04_wip_safety.sh preExit

Auto-stashes uncommitted work-in-progress changes when a Claude Code session exits. Only runs in git repositories with dirty working trees. Stashes are prefixed with WIP/CLAUDE_CODE and include a timestamp and branch name. The hook automatically cleans up old stashes (keeps the last 20).

#!/usr/bin/env bash # 04_wip_safety.sh — preExit Hook # Auto-stash WIP on session exit. STASH_PREFIX="WIP/CLAUDE_CODE" MAX_STASHES=20 has_uncommitted_changes() { git diff --quiet --cached && git diff --quiet && \ [[ -z "$(git ls-files --others --exclude-standard)" ]] && return 1 return 0 } do_stash() { local timestamp="$(date '+%Y-%m-%d %H:%M:%S')" local branch="$(git rev-parse --abbrev-ref HEAD)" git stash push --include-untracked \ --message "${STASH_PREFIX} ${timestamp} — ${branch}" }

Restore next session:

git stash list git stash pop # or: git stash apply stash@{0}

Complete Hook Configuration

Here is how all four hooks fit together in a settings.local.json file. Place this file in your project’s .claude/ directory.

{
"hooks": {
# afterWrite: format Python files on save
"afterWrite": ".claude/hooks/01_format_on_write.sh '{file}'",

# beforeCommand: block dangerous commands
"beforeCommand": ".claude/hooks/03_block_dangerous.sh '{command}'",

# afterCommand: audit every command
"afterCommand": ".claude/hooks/02_audit_trail.sh '{command}' {exit_code}",

# preExit: stash WIP when session ends
"preExit": ".claude/hooks/04_wip_safety.sh"
}
}

Installation Steps

  1. Copy the hooks/ directory into your project as .claude/hooks/.
  2. Make scripts executable: chmod +x .claude/hooks/*.sh.
  3. Create or edit .claude/settings.local.json with the configuration above.
  4. Start a Claude Code session — hooks fire automatically.
Tip: Use settings.local.json (not settings.json) for project-specific hooks. The local file is gitignored by default, so each team member can opt in independently.

Testing Your Hooks

The project includes test_hooks.sh, a test suite that validates each hook independently in an isolated temporary directory.

# Run the full test suite bash test_hooks.sh

What the tests cover

Test What it validates
test_format_on_write Creates a deliberately unformatted .py file, runs the hook, and checks that formatting was applied. Also verifies non-.py files are skipped and missing files are handled gracefully.
test_audit_trail Logs commands with exit codes 0 and 1, then checks the audit file for correct timestamp, session ID, working directory, command text, and exit code.
test_block_dangerous Runs six dangerous commands through the block hook and confirms each is rejected. Then runs four safe commands and confirms they pass through.
test_wip_safety Creates a temporary git repo, commits an initial file, verifies clean tree is skipped, dirties the tree, runs the hook, and checks a timestamped WIP stash was created with the correct prefix.
All tests pass when run on a system with a Python formatter (ruff or black) installed. Without a formatter, the format test degrades gracefully — it checks the log for the “No formatter found” message and still passes.

Hook Design Principles

Not every automation belongs in a hook. Here is a decision framework to help you choose the right mechanism.

Hooks vs Skills vs Workflows

Hooks Best for

  • Synchronous, blocking operations
  • Policy enforcement (security, formatting)
  • Audit and observability
  • Transparent automation (Claude is unaware)
  • < 200 lines of shell script

Skills Best for

  • Interactive slash commands (/deploy, /review)
  • Reusable prompt templates with parameters
  • Loops with /loop integration
  • Claude-visible workflows

Workflows Best for

  • Complex, multi-step orchestration
  • Long-running background processes
  • Cross-tool coordination (CI/CD, deployment)
  • State machines with branching logic
Rule of thumb: If the logic runs in under a second, blocks until done, and enforces a policy — make it a hook. If it needs user interaction or runs for minutes — make it a skill or workflow.
