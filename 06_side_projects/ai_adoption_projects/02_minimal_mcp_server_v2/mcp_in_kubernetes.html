How stdio Works (Local Dev)

CURRENT SETUP

In the demo you just ran, the MCP server runs as a child subprocess of the LangGraph agent. They share stdio pipes on the same machine.

Key characteristics:

  • Parent-child process — the client literally spawns the server with subprocess.Popen()
  • Same machine — they share memory, filesystem, and process space
  • 1:1 relationship — each client gets its own server instance
  • Zero config networking — no ports, no URLs, just pipes

✅ Great for local dev

Simple, fast, no network setup. This is why the demo uses stdio.

Why stdio Breaks in Kubernetes

3 PROBLEMS

Kubernetes doesn't have a "parent process spawns a child process" model. Each container is an isolated unit.

①

No cross-container subprocess

Each container is an isolated process. You can't call subprocess.spawn() on a different container — it's a different machine (or at least a different PID namespace).

②

Single point of failure

The server lives and dies with the client. If the LangGraph pod restarts, its MCP server is gone too. No separation of concerns.

③

Can't scale independently

Each LangGraph replica spawns its own MCP server — 10 replicas = 10 servers. You can't scale the MCP server up/down based on load, and you can't share it across agents.

✅

How it works:

  • The MCP server runs as a K8s Deployment with SSE transport
  • A K8s Service provides stable DNS + load balancing
  • LangGraph agents connect via HTTP instead of spawning a subprocess

MCP Server — SSE mode (unchanged logic, different transport):

# server/mcp_server.py — same tools, different transport if __name__ == "__main__": # Local dev: python mcp_server.py # K8s: python mcp_server.py --transport sse --port 8000 parser = argparse.ArgumentParser() parser.add_argument("--transport", choices=["stdio", "sse"], default="stdio") parser.add_argument("--port", type=int, default=8000) args = parser.parse_args() app.run(transport=args.transport) # ← same app, just flip the flag

MCP Client — connects via SSE instead of stdio:

# agent/mcp_client.py — SSE version from mcp.client.sse import sse_client from mcp import ClientSession class MCPClientSSE: def __init__(self, url: str): # ← URL instead of script path self.url = url self.session: ClientSession | None = None async def __aenter__(self): # Connect via HTTP/SSE instead of spawning a subprocess self._client = sse_client(self.url) read, write = await self._client.__aenter__() self.session = await ClientSession(read, write).__aenter__() await self.session.initialize() return self async def list_tools(self): result = await self.session.list_tools() return result.tools async def call_tool(self, tool_name, args=None): result = await self.session.call_tool(tool_name, args or {}) return result.content[0].text async def __aexit__(self, *args): await self.session.__aexit__(*args) await self._client.__aexit__(*args)

K8s Manifests:

# mcp-server-deployment.yaml apiVersion: apps/v1 kind: Deployment metadata: name: mcp-server spec: replicas: 3 selector: matchLabels: app: mcp-server template: metadata: labels: app: mcp-server spec: containers: - name: mcp-server image: my-mcp-server:latest args: ["python", "mcp_server.py", "--transport", "sse", "--port", "8000"] ports: - containerPort: 8000
# mcp-server-service.yaml apiVersion: v1 kind: Service metadata: name: mcp-server spec: selector: app: mcp-server ports: - port: 8000 targetPort: 8000

LangGraph agent connects to the service:

# main.py — K8s version async def main(): # Connect via Service DNS instead of spawning subprocess async with MCPClientSSE("http://mcp-server:8000/mcp") as mcp: tools = await mcp.list_tools() graph = create_review_graph(mcp) result = await graph.ainvoke({"file_path": file_path})

The Hybrid Pattern — Best of Both

Most teams use stdio locally and SSE/HTTP in K8s. The MCP server code stays exactly the same — just the transport flag changes.

🖥️ Local Development

Command: python main.py

Transport: stdio — server spawns as a subprocess, zero config

☸️ Production (K8s)

Command: python mcp_server.py --transport sse --port 8000

Transport: SSE — server runs as standalone Deployment behind a Service

Summary — The Rule of Thumb

✅ Use stdio when...

  • You're developing locally
  • Everything runs on one machine
  • You want zero network config
  • You're in a CI/CD pipeline (single job)

✅ Use SSE/HTTP when...

  • You're running in Kubernetes
  • Multiple clients need the same server
  • You need independent scaling
  • You want server HA (replicas)
Bottom line: Your MCP server doesn't care about the transport. Write it once, run it both ways.
