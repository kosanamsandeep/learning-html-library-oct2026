DIY SBOM Generator

Build a script that scans a Python project, resolves transitive dependencies from requirements.txt + pip freeze, and outputs a CycloneDX-format Software Bill of Materials (SBOM) as JSON.

Architecture & Data Flow

The generator follows a linear pipeline: capture the installed environment, resolve each package's dependencies recursively, then assemble the results into the CycloneDX schema.

  1. Read project state — Parse requirements.txt (or pyproject.toml) for top-level dependencies, then capture the exact installed versions via pip list --format=json.
  2. Resolve transitive deps — Use pip inspect or the pip_api library to enumerate each package's declared dependencies. Walk the tree recursively, avoiding cycles.
  3. Build dependency graph — For each package recorded, track which packages it depends on and whether those are required, optional, or development-only.
  4. Generate CycloneDX document — Assemble a JSON object conforming to the CycloneDX 1.5 schema with bomFormat, specVersion, metadata, components, and dependencies arrays.
  5. Write output — Serialize to sbom.json with deterministic ordering for reproducible diffs.

Understanding CycloneDX Fields

The CycloneDX standard defines a minimal but expressive schema. Every component in the SBOM carries these key fields:

Field Type Description
bomFormat string Always "CycloneDX". Identifies the document format.
specVersion string Schema version, e.g. "1.5". Controls which fields are valid.
metadata object Includes timestamp, tool info (the generator), and the root component (your project).
components[] array Every software artifact — each has a name, version, type (library/framework), purl, and optional licenses.
dependencies[] array Maps each component ref (its bom-ref or purl) to an array of dependsOn references, forming the dependency graph.
purl string Package URL — a universal identifier like pkg:pypi/requests@2.31.0. Enables tool-agnostic matching across ecosystems.
Why PURL matters: Package URLs (pkg:pypi/django@5.0#arch=linux) provide a universal naming scheme that works across package managers (pip, npm, Maven, etc.). SBOM consumers use PURLs to match components against vulnerability databases like the National Vulnerability Database (NVD) or GitHub Advisory Database.

Starter Code: Python SBOM Generator

This minimal implementation uses pip list for installed packages and pip inspect (available in pip 24+) to resolve dependencies. For older pip versions, you can substitute with pip_api.installed_distributions from the pip-api package.

#!/usr/bin/env python3
"""sbom_gen.py — Generate a CycloneDX 1.5 SBOM for the current Python environment."""

import json
import subprocess
import sys
from datetime import datetime, timezone


def get_installed_packages():
    """Return list of dicts with name, version from pip list."""
    result = subprocess.run(
        [sys.executable, "-m", "pip", "list", "--format=json"],
        capture_output=True, text=True, check=True
    )
    return json.loads(result.stdout)


def get_dependency_tree():
    """Use pip inspect (pip >= 24) to get the resolved dependency graph."""
    result = subprocess.run(
        [sys.executable, "-m", "pip", "inspect"],
        capture_output=True, text=True, check=True
    )
    data = json.loads(result.stdout)
    # data["installed"] is a dict keyed by package name
    return data.get("installed", {})


def build_cyclonedx(installed_pkgs, dep_tree):
    """Assemble a CycloneDX 1.5 document from pip data."""
    components = []
    dependencies = []
    bom_refs = {}  # name -> bom-ref

    # Build components list
    for pkg in installed_pkgs:
        name = pkg["name"]
        version = pkg["version"]
        ref = f"pkg:pypi/{name}@{version}".lower()
        bom_refs[name] = ref

        component = {
            "type": "library",
            "name": name,
            "version": version,
            "purl": ref,
            "bom-ref": ref,
        }
        components.append(component)

    # Build dependency graph
    for name, info in dep_tree.items():
        ref = bom_refs.get(name)
        if not ref:
            continue
        deps = info.get("dependencies", [])
        depends_on = []
        for dep_name in deps:
            dep_version = deps[dep_name].get("version", "")
            dep_ref = f"pkg:pypi/{dep_name}@{dep_version}".lower()
            depends_on.append(dep_ref)
        dependencies.append({
            "ref": ref,
            "dependsOn": depends_on,
        })

    return {
        "bomFormat": "CycloneDX",
        "specVersion": "1.5",
        "serialNumber": f"urn:uuid:{datetime.now(timezone.utc).strftime('%Y%m%d%H%M%S')}-sbom",
        "version": 1,
        "metadata": {
            "timestamp": datetime.now(timezone.utc).isoformat(),
            "tools": [{"vendor": "DIY", "name": "sbom_gen.py", "version": "0.1.0"}],
            "component": {
                "type": "application",
                "name": "my-project",
                "version": "0.1.0",
                "bom-ref": "pkg:pypi/my-project@0.1.0",
            },
        },
        "components": components,
        "dependencies": dependencies,
    }


def main():
    print("🔍 Scanning installed packages...", file=sys.stderr)
    installed = get_installed_packages()
    print(f"   Found {len(installed)} packages.", file=sys.stderr)

    print("🧬 Resolving dependency tree...", file=sys.stderr)
    dep_tree = get_dependency_tree()

    print("📦 Assembling CycloneDX document...", file=sys.stderr)
    sbom = build_cyclonedx(installed, dep_tree)

    output_path = "sbom.json"
    with open(output_path, "w") as f:
        json.dump(sbom, f, indent=2)
    print(f"✅ SBOM written to {output_path}", file=sys.stderr)


if __name__ == "__main__":
    main()

Transitive Dependencies & Resolution Strategy

Understanding transitive dependencies is critical for an accurate SBOM. A direct dependency (one you list in requirements.txt) pulls in its own dependencies, which pull in theirs, forming a tree.

Example: Your project depends on requests, which depends on urllib3, certifi, idna, and charset-normalizer. An SBOM that omits these transitive deps will miss vulnerabilities in urllib3 — defeating the purpose of the SBOM.

Resolution Approaches

Method Pros Cons
pip inspect (pip 24+) Official, accurate, includes dependency metadata Requires recent pip; not available in all environments
pip-api library Works with older pip; easy to integrate External dependency; may lag pip releases
Parse METADATA files directly Zero dependencies; full control Fragile; format changes between Python versions
pip freeze only (flat list) Simplest approach No dependency graph — flat list only, no parent-child relationships

Handling Cycles

Dependency cycles are rare in Python (pip resolves them) but can appear in edge cases. Always track visited nodes during resolution to avoid infinite loops:

Running & Extending

Quick start:

# Create a virtual environment and install some packages
python -m venv .venv && source .venv/bin/activate
pip install requests flask django

# Generate the SBOM
python sbom_gen.py

# Inspect the output
cat sbom.json | jq '.components | length'
cat sbom.json | jq '.dependencies[0]'

Ideas for extension:

  • License detection: Query pip show <package> and parse the License: field, or use the Classifier: License ... lines.
  • Vulnerability lookup: After generating the SBOM, pass it to pip-audit or the OSV API to cross-reference known CVEs.
  • CI/CD integration: Run this script in your build pipeline, upload the SBOM to Dependency-Track or GitHub Dependency Graph, and fail the build if critical vulnerabilities are found.
  • Multi-format output: Add SPDX format support alongside CycloneDX so the SBOM works with a wider range of tooling.
