What & Why

A known-bad corpus is a curated collection of code snippets that contain verifiable bugs. Each entry records the buggy code, the correct fix, metadata about the bug, and the annotation decisions that turned a raw diff into a structured evaluation example.

Key Concepts

Data Annotation

Every bug is labelled with its category (logic, security, concurrency, etc.), severity, and a human-readable description. This turns noisy real-world diffs into clean training or evaluation records.

Corpus Structure

A flat collection of JSON objects, each representing one bug. The schema is versioned, self-describing, and designed to be consumed by evaluation harnesses, not humans.

Ground Truth

The fixed code is the ground-truth answer. An evaluator compares a model’s output against the known fix, or checks whether the model can identify the bug location and root cause.

Inter-Rater Reliability

When multiple annotators label the same bug, agreement metrics (Cohen’s κ, Krippendorff’s α) reveal how subjective the annotation scheme is. Low agreement signals that category definitions need refinement.

Corpus JSON Schema

Every entry in the corpus follows this structure. The schema is kept minimal so it is easy to validate, extend, and consume from any language. 

{
  "$schema": "https://example.com/kb-corpus-v1.schema.json",
  "corpus_version": "1.0",
  "entries": [

      "id": "KB-0042",
      "source": {
        "repo": "org/repo-name",
        "commit": "a1b2c3d4e5f6...",
        "file": "src/payments/validator.py",
        "line_start": 87,
        "line_end": 94,
        "pr_url": "https://github.com/org/repo/pull/142"
      },
      "buggy_code": "if user.role != 'admin':\n    return False\nreturn True",
      "fixed_code": "if user.role not in {'admin', 'moderator'}:\n    return False\nreturn True",
      "diff_summary": "Added moderator role to the access-control allowlist.",
      "annotation": {
        "category": "access-control",
        "subcategory": "missing-role",
        "severity": "high",
        "root_cause": "incomplete allowlist",
        "description": "The validator only checked for 'admin', missing the 'moderator' role that should also have access. Annotated as a logic-of-authorization bug.",
        "annotator": "human",
        "confidence": 0.98,
        "tags": ["auth", "rbac", "regression"]
      }
    }
  ]
}
Design rationale. Separating buggy_code, fixed_code, and annotation into distinct top-level keys allows evaluators to test different capabilities: bug localisation (find the fix location), explanation (describe the bug), or repair (produce the fix) — all from the same corpus entry.

Python Starter — Annotation Workflow

The script below shows how to load a known-bad corpus, inspect entries, compute basic corpus statistics, and prepare a sample for use with an eval harness. Use it as the foundation for your own annotation tooling. 

#!/usr/bin/env python3
"""
kb_corpus.py  —  Known-Bad Corpus utility

Usage:
    python kb_corpus.py corpus.json [--stats] [--sample N] [--category CAT]
"""

import json
import sys
import argparse
from collections import Counter
from pathlib import Path


def load_corpus(path: Path) -> list[dict]:
    """Load a known-bad corpus JSON file and return its entries."""
    with open(path, "r") as f:
        data = json.load(f)
    entries = data.get("entries", [])
    print(f"[OK] Loaded corpus v{data.get('corpus_version', '?')} "
          f"with {len(entries)} entries.")
    return entries


def compute_stats(entries: list[dict]) -> dict:
    """Aggregate annotation metadata into summary statistics."""
    cats = Counter()
    sevs = Counter()
    anns = Counter()
    confs = []

    for e in entries:
        ann = e.get("annotation", {})
        cats[ann.get("category", "unknown")] += 1
        sevs[ann.get("severity", "unknown")] += 1
        anns[ann.get("annotator", "unknown")] += 1
        if (c := ann.get("confidence")) is not None:
            confs.append(c)

    return {
        "categories": dict(cats.most_common()),
        "severities": dict(sevs.most_common()),
        "annotators": dict(anns.most_common()),
        "total": len(entries),
        "mean_confidence": round(sum(confs) / len(confs), 3) if confs else None,
    }


def filter_by_category(entries: list[dict], category: str) -> list[dict]:
    """Return only entries whose annotation category matches."""
    return [e for e in entries
            if e.get("annotation", {}).get("category") == category]


def sample_entries(entries: list[dict], n: int) -> list[dict]:
    """Return a random sample of n entries (deterministic seed for
    reproducibility)."""
    import random
    random.seed(42)
    return random.sample(entries, min(n, len(entries)))


# ── eval harness interface ─────────────────────────────────────

class KnownBadCorpus:
    """Thin wrapper so an evaluation harness can iterate over examples."""

    def __init__(self, entries: list[dict]):
        self._entries = entries

    def __len__(self) -> int:
        return len(self._entries)

    def __getitem__(self, idx: int) -> dict:
        return self._entries[idx]

    def as_qa_pairs(self) -> list[dict]:
        """Yield prompt / gold-answer dicts for an LLM eval harness."""
        pairs = []
        for e in self._entries:
            prompt = (
                f"The following code contains a bug.\n\n"
                f"```\n{e['buggy_code']}\n```\n\n"
                f"File: {e['source']['file']} (line {e['source']['line_start']})\n"
                f"Category: {e['annotation']['category']}\n\n"
                f"Describe the bug and provide the corrected code."
            )
            pairs.append({
                "id": e["id"],
                "prompt": prompt,
                "gold_answer": e["fixed_code"],
                "metadata": {
                    "category": e["annotation"]["category"],
                    "severity": e["annotation"]["severity"],
                },
            })
        return pairs


# ── CLI entry point ────────────────────────────────────────────

def main():
    parser = argparse.ArgumentParser(
        description="Known-Bad Corpus utilities")
    parser.add_argument("corpus", type=Path, help="path to corpus JSON")
    parser.add_argument("--stats", action="store_true",
                        help="print corpus statistics")
    parser.add_argument("--sample", type=int, default=0,
                        help="number of random entries to show")
    parser.add_argument("--category", type=str, default=None,
                        help="filter by annotation category")
    args = parser.parse_args()

    entries = load_corpus(args.corpus)

    if args.category:
        entries = filter_by_category(entries, args.category)
        print(f"[FILTER] Kept {len(entries)} entries for category "
              f"'{args.category}'.")

    if args.stats:
        stats = compute_stats(entries)
        print("\n── Corpus Statistics ──")
        print(f"  Total entries:       {stats['total']}")
        print(f"  Mean confidence:     {stats['mean_confidence']}")
        print(f"  Categories:          {stats['categories']}")
        print(f"  Severities:          {stats['severities']}")
        print(f"  Annotators:          {stats['annotators']}")

    if args.sample:
        sample = sample_entries(entries, args.sample)
        print(f"\n── Random Sample ({len(sample)} entries) ──")
        for e in sample:
            print(f"  [{e['id']}] {e['annotation']['category']}: "
                  f"{e['annotation']['description'][:60]}...")

    # Demonstrate the eval harness wrapper
    corpus = KnownBadCorpus(entries)
    qa = corpus.as_qa_pairs()
    print(f"\n[EVAL] Prepared {len(qa)} Q/A pairs for harness "
          f"(first prompt: {len(qa[0]['prompt'])} chars)")


if __name__ == "__main__":
    main()
Try it. After you have built a corpus JSON file, run python kb_corpus.py corpus.json --stats --sample 3 to verify your data. The KnownBadCorpus.as_qa_pairs() method produces prompts ready for any LLM evaluation harness.

Annotation Quality > Quantity

A large but noisy corpus erodes trust in evaluation results. Here is why investing in annotation quality pays off.

Dimension High-Quality Corpus Large-but-Noisy Corpus
Ground truth Every fix is verified (reviewed, tested, or confirmed by domain expert) Fixes are extracted automatically; many are partial or incidental refactors, not real bug fixes
Annotation labels Inter-rater agreement ≥ 0.8; disagreements are adjudicated Labels are noisy or inconsistent; no agreement measurement
Eval signal Small score differences (< 2%) are meaningful and reproducible Only large differences (> 10%) survive the noise floor
Debugging When a model fails, you can trace why (clean categories, explicit root cause) Failures are confounded; hard to tell if the model was wrong or the corpus entry is bad
Maintenance cost Low — each entry is curated, so removal or update is surgical High — noisy entries hide in the tail; bulk cleanup requires re-annotation
Rule of thumb. 200–500 high-quality, manually-curated examples outperform 5 000+ automatically-mined examples for eval purposes. Use a larger pool for training, but always evaluate on a clean, vetted set.

Practical Recommendations

  • Start small. Annotate 50–100 entries by hand to validate your category taxonomy before scaling.
  • Double-annotate 10 %. Randomly assign every tenth entry to a second annotator. Track agreement per category.
  • Version your corpus. Use the corpus_version field. When you fix an annotation error, bump the version so eval runs are traceable.
  • Keep a changelog. Record why an entry was added, modified, or removed. This turns your corpus into a living artefact rather than a snapshot.
