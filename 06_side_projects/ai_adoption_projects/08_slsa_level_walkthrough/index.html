Project 08 — Supply Chain Security

SLSA Level Walkthrough

Progressively harden a build pipeline through SLSA Levels 1 through 4. Each level adds concrete security guarantees: from basic build integrity at L1 to fully hermetic, reproducible builds with signed provenance at L4.

The SLSA Framework: A Security Staircase

SLSA (Supply-chain Levels for Software Artifacts, pronounced "salsa") is a security framework that defines a progression of increasing trust guarantees for software supply chains. Each level builds on the previous one, adding specific requirements that make it progressively harder for attackers to tamper with build outputs without detection.

Bottom line: Most real-world open source projects are at L1 or below. Reaching L3 is a strong security milestone. L4 is aspirational for all but the most critical infrastructure. The goal is not to hit L4 overnight but to make incremental progress that reduces risk.

SLSA L1 — Basic Build Integrity

What it provides: The build process is scripted and automated, with documented provenance. This prevents "works on my machine" issues and establishes a basic audit trail.

Requirements:

  • Build steps are defined in a script (not manual clicks).
  • Provenance is generated describing who built what and how.

Example: Basic GitHub Actions build with provenance

# .github/workflows/build.yml -- SLSA L1
name: Build
on: [push]

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: make build
      - run: make test
      - name: Generate provenance
        run: |
          cat <<EOF > provenance.json
          {
            "builder": {"id": "https://github.com/actions/virtual-environments"},
            "buildType": "https://example.com/makefile/v1",
            "invocation": {
              "configSource": {
                "uri": "git+https://github.com/${{ github.repository }}@${{ github.sha }}"
              }
            },
            "metadata": {
              "buildStartedOn": "${{ github.event.head_commit.timestamp }}"
            }
          }
          EOF
      - uses: actions/upload-artifact@v4
        with:
          name: provenance.json
          path: provenance.json
Cost: Low. Minimal changes to existing CI pipeline.
Benefit: Basic build traceability. You can answer "who built this and when?"
Gap: Provenance is not signed or verified. Anyone could craft a fake one.

SLSA L2 — Build Integrity with Signed Provenance

What it adds: Provenance is now signed by the build platform, making it non-repudiable. The build runs on dedicated infrastructure, not a developer's laptop.

New requirements over L1:

  • Provenance must be signed using an ephemeral key tied to the build platform.
  • The build runs on dedicated, hosted infrastructure (not a personal machine).
  • Build steps are version-controlled.

Example: Using the SLSA Generator (GitHub Actions)

# .github/workflows/build.yml -- SLSA L2
name: Build (L2)
on:
  push:
    branches: [main]

permissions:
  id-token: write   # needed for keyless signing
  contents: read

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: make build

  provenance:
    needs: [build]
    permissions:
      id-token: write
      contents: read
      actions: read
    uses: slsa-framework/slsa-github-generator/.github/workflows/generator_generic_slsa3.yml@v2.0.0
    with:
      base64-subjects: "${{ needs.build.outputs.digests }}"
      compile-generator: true

The SLSA Generator workflow produces an in-toto attestation signed by the GitHub Actions OIDC identity and uploads it as a build artifact. The attestation includes:

  • Subject: Digest of the built artifact (e.g., binary SHA256).
  • Builder: https://github.com/slsa-framework/slsa-github-generator.
  • Build Config: Link to the exact workflow file and commit that triggered the build.
  • Metadata: Timestamp, source repository, and invocation parameters.
Cost: Medium. Requires adopting the SLSA generator or integrating a signing step.
Benefit: Non-repudiable provenance. Consumers can verify that the artifact was built by your CI, not an attacker.
Gap: Build environment may still fetch dependencies from the internet with no pinning or verification.

SLSA L3 — Hardened Build Environment

What it adds: The build is isolated and hermetic. The build platform prevents tampering during the build, and the provenance proves the build was fully defined by source code.

New requirements over L2:

  • Build runs on a hosted platform with strong isolation between builds.
  • Build is "as-code" — no manual steps or parameters.
  • Provenance is non-falsifiable: the build platform signs it with a key that is inaccessible to build steps.

Example: Hermetic build with dependency pinning

# .github/workflows/build.yml -- SLSA L3 (hermetic)
name: Build (L3 Hermetic)
on:
  push:
    branches: [main]

permissions:
  id-token: write
  contents: read

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Build in isolated container
        # Use a pinned base image with all deps pre-installed
        run: |
          docker run --rm \
            -v $PWD:/workspace \
            -w /workspace \
            --network none \                    # 🔒 No network access during build
            "golang:1.22-alpine@sha256:abc123..." \
            sh -c "go build -o myapp . && go test ./..."

      - name: Generate non-falsifiable provenance
        uses: slsa-framework/slsa-github-generator/.github/workflows/generator_generic_slsa3.yml@v2.0.0
        with:
          base64-subjects: "${{ needs.build.outputs.digests }}"
          compile-generator: true

Key hermetic build practices:

Practice Why It Matters
--network none Prevents the build from fetching unversioned, unpinned dependencies. All deps must be pre-declared.
Pin base images by digest golang:1.22-alpine@sha256:abc ensures the same base image every time, even if the tag is updated.
Use lockfiles go.sum, package-lock.json, requirements.txt with hashes pin every transitive dependency.
Pre-install dependencies Use a pre-built builder image rather than apt-get install during the build.
Cost: High. Requires changing how dependencies are managed and enforcing network isolation.
Benefit: Strong supply chain guarantees. A compromised dependency server cannot inject malicious code during your build.
Gap: Different hermetic builds may produce different artifacts even from the same source (not reproducible).

SLSA L4 — Reproducible & Hermetic Builds

What it adds: Everything from L3, plus the build is reproducible — rebuilding the same source produces bit-for-bit identical output. This provides the strongest guarantee: you can detect backdoors inserted by the build platform itself.

New requirements over L3:

  • Build is fully hermetic (no external dependencies during build).
  • Build is reproducible: two independent builders produce identical output.
  • Two-person review is required for all changes affecting the build process.
  • All external dependencies are fully enumerated in the provenance.

Example: Reproducible Go build step

# Reproducible Go build snippet
# Achieved by: setting -trimpath, specifying GOFLAGS, and pinning toolchain version

name: Build (L4 Reproducible)
on:
  push:
    branches: [main]

permissions:
  id-token: write
  contents: read

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Reproducible Go build
        run: |
          # ✓ Pin Go version
          # ✓ Set -trimpath to remove filesystem-specific paths
          # ✓ Use -buildmode=default for consistent output
          # ✓ Set SOURCE_DATE_EPOCH for timestamp-independent binaries
          docker run --rm \
            -v $PWD:/workspace \
            -w /workspace \
            --network none \
            -e SOURCE_DATE_EPOCH=0 \
            -e GOFLAGS="-trimpath -ldflags=-buildid=" \
            "golang:1.22-alpine@sha256:abc123..." \
            go build -o myapp .

      - name: Verify reproducibility
        run: |
          # Build twice and compare checksums
          cp myapp myapp.first
          docker run --rm \
            -v $PWD:/workspace -w /workspace --network none \
            "golang:1.22-alpine@sha256:abc123..." \
            go build -o myapp .
          if ! cmp myapp.first myapp; then
            echo "❌ Build is NOT reproducible!"
            exit 1
          fi
          echo "✅ Build is reproducible"

      - name: Generate signed provenance (L4)
        uses: slsa-framework/slsa-github-generator/.github/workflows/generator_generic_slsa3.yml@v2.0.0
        with:
          base64-subjects: "${{ needs.build.outputs.digests }}"
          compile-generator: true

Making builds reproducible:

Challenge Solution
Timestamps embedded in binary Set SOURCE_DATE_EPOCH=0 (or another fixed timestamp).
Filesystem paths in debug info Use -trimpath (Go), -ffile-prefix-map (GCC), or equivalent.
Build IDs Use -ldflags=-buildid= (Go) or strip build IDs from the binary.
Randomness / ASLR Disable PIE if not needed, or accept the trade-off with documented caveats.
Locale-dependence Set LC_ALL=C.UTF-8 and TZ=UTC.
Cost: Very high. Requires deep build system expertise and significant tooling changes.
Benefit: Maximum supply chain integrity. Even a compromised build platform cannot hide tampering, because a separate builder would produce a different output.
Trade-off: Not all build systems or languages support reproducible builds. Some anti-virus scanners and signing tools intentionally inject non-reproducible data.

Cost-Benefit Summary

Level Key Requirement Implementation Effort Security Benefit Best For
L1 Scripted build + basic provenance Low (hours) Basic audit trail All projects
L2 Signed provenance + hosted CI Low-Medium (days) Non-repudiable builds Teams shipping artifacts
L3 Hermetic build + isolated env Medium-High (weeks) Tamper-proof build process Critical shared infrastructure
L4 Reproducible + two-party review High (months) Maximum integrity guarantees High-security / compliance contexts
Recommended path: Start at L1 for all projects (it's essentially free). Aim for L2 on any project that produces deployable artifacts. Target L3 for shared libraries, base images, and critical infrastructure. Pursue L4 only for projects where the cost of a compromised build is catastrophic (e.g., cryptographic libraries, OS packages, certificate authorities).

Verifying SLSA Provenance

Provenance is only useful if consumers verify it. The slsa-verifier tool checks that an artifact's provenance meets expected SLSA levels:

# Install slsa-verifier
go install github.com/slsa-framework/slsa-verifier/v2/cli/slsa-verifier@latest

# Verify an artifact was built at SLSA L3 or above
slsa-verifier verify-artifact \
  --provenance-path provenance.intoto.jsonl \
  --source-uri github.com/my-org/my-repo \
  --source-tag v1.2.3 \
  myapp.bin

# Verify against the SLSA attestation stored in a container registry
cosign verify-attestation \
  --type slsaprovenance \
  --certificate-identity-regexp "https://github.com/slsa-framework/.*" \
  ghcr.io/my-org/my-app@sha256:...
