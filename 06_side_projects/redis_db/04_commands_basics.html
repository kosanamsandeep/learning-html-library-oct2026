Chapter 04 · Commands

Core commands — keys, expiry & atomic ops

Now the everyday toolkit: managing keys, expiring data with TTLs, atomic counters, scanning safely, and the few commands you'll type a hundred times a day. Run every example against the dataset from chapter 03.

1 · Key management

EXISTS product:1        # → 1 if the key exists, else 0
TYPE product:1          # → hash (what structure is it?)
DEL product:99         # → delete a key
RENAME cart:1 cart:alice # → rename a key
RANDOMKEY                # → a random key name
DBSIZE                   # → number of keys in this DB

2 · Expiry & TTL — Redis's killer convenience

Any key can be told to self-destruct after a time. This is what makes Redis perfect for caches, sessions, OTPs, and rate-limit windows.

SET session:abc "user:42"
EXPIRE session:abc 3600   # expires in 1 hour
TTL session:abc           # → seconds left (-1 = no expiry, -2 = gone)
PERSIST session:abc       # → remove the expiry, make it permanent

# Set value AND expiry in one atomic command
SET otp:42 "839201" EX 120   # OTP valid 2 minutes
SET lock:job "1" NX EX 30  # set only if Not eXists (a lock)
Flag on SET Meaning
EX n / PX n Expire in n seconds / milliseconds
NX Only set if the key does not exist
XX Only set if the key already exists
KEEPTTL Keep the existing TTL when overwriting
One-line lock: SET lock:job 1 NX EX 30 returns OK only to the first caller and auto-releases after 30s. That's a distributed lock primitive in a single command.

3 · Atomic counters

INCR page:views        # +1, returns new value
INCRBY page:views 10   # +10
DECR product:1:stock  # -1
INCRBYFLOAT price 9.99 # works with floats too

These are atomic: thousands of clients can INCR the same key simultaneously and every increment is counted exactly once. No locks, no lost updates.

4 · Finding keys safely: SCAN, not KEYS

❌ KEYS pattern

Scans the entire keyspace in one blocking sweep. On a big production DB this can freeze the server. Use it only in dev/CLI on small data.

✅ SCAN cursor

Iterates in small batches without blocking. The safe, production-grade way to walk keys.

# Iterate keys matching a pattern, in batches
SCAN 0 MATCH "product:*" COUNT 100
# → returns a new cursor + a page of keys; repeat until cursor is 0

# Type-specific scans iterate inside one big key
HSCAN user:42 0      # walk hash fields
SSCAN tag:tech 0     # walk set members
ZSCAN bestsellers 0  # walk sorted-set members

5 · Key-naming conventions (design matters)

Redis has no tables, so your key names are your schema. Use a consistent colon:separated convention:

Pattern Example Holds
type:id user:42 a user hash
type:id:field user:42:cart that user's cart list
scope:metric sales:product:1 a counter
scope:window rate:ip:1.2.3.4:60 a rate-limit bucket
Two rules: (1) make keys predictable so you never need KEYS * to find them; (2) keep them short — every key name lives in RAM too.

6 · Inspecting & debugging

OBJECT ENCODING product:1  # internal encoding (listpack, hashtable…)
MEMORY USAGE product:1     # bytes this key uses
INFO memory                  # server memory overview
SLOWLOG GET 10                # 10 slowest recent commands
MONITOR                       # live-stream every command (dev only)

Try it yourself

easy Store a verification code for user 7 that expires in 5 minutes. 
SET otp:7 "123456" EX 300
easy Atomically reduce product:1 stock by one when it sells. 
HINCRBY product:1 stock -1
Hashes have their own atomic HINCRBY for a single field.
medium Grab a non-blocking lock named lock:report that auto-releases after 10 seconds. 
SET lock:report "1" NX EX 10
Returns OK to the first caller only; others get (nil) until it expires.
