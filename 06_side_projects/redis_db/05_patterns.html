Chapter 05 · Real patterns

The patterns that make teams adopt Redis

This is why Redis is everywhere. Six battle-tested patterns — caching, sessions, rate limiting, leaderboards, queues, and pub/sub — each just a few commands. Master these and you can drop Redis into almost any system.

1 · Cache-aside (the #1 use of Redis)

Put Redis in front of a slow database or API. Check the cache first; on a miss, fetch from the DB and store it with a TTL so it stays fresh.

sequenceDiagram
    participant App
    participant Redis
    participant DB
    App->>Redis: GET product:1
    alt cache hit
        Redis-->>App: value (microseconds) ⚡
    else cache miss
        Redis-->>App: (nil)
        App->>DB: SELECT … (slow)
        DB-->>App: row
        App->>Redis: SET product:1 value EX 300
    end

After the first miss, every later read is served from RAM until the TTL expires. This single pattern can cut database load by 90%+.

# Pseudocode for cache-aside
val = GET product:1
if val is nil:
    val = db.query("SELECT … WHERE id=1")
    SET product:1 val EX 300   # cache for 5 min
return val
Cache invalidation: when the underlying data changes, either DEL the key or overwrite it. A TTL is your safety net so stale data self-heals even if you forget.

2 · Sessions & tokens

Store per-user session state in a hash with an expiry; every request refreshes it. Logout = DEL. Idle timeout comes free from the TTL. 

HSET session:abc123 user_id 42 role "admin"
EXPIRE session:abc123 1800      # 30-min idle timeout

# On each request: read it and slide the window
HGETALL session:abc123
EXPIRE session:abc123 1800      # refresh TTL

DEL session:abc123             # logout

3 · Rate limiting (fixed window)

Allow N requests per time window per user/IP using an atomic counter that expires.

# Allow 100 requests per 60s per IP
INCR rate:ip:1.2.3.4            # returns the new count
# If the reply is 1, it's the first hit in this window → set the TTL
EXPIRE rate:ip:1.2.3.4 60 NX     # NX = only if no TTL yet
# If the count > 100 → reject the request (429)
Why Redis nails this: the counter is atomic and the key auto-expires, so the whole limiter is two commands and needs no cleanup job. (For burst-proof limits, use a sliding window with a sorted set or a small Lua script — see ch. 06.)

4 · Leaderboards & ranking

Sorted sets keep members ranked by score automatically — the canonical Redis showcase.

ZADD game:leaderboard 2500 "alice" 1800 "bob" 3100 "carol"

# Top 3 with scores
ZREVRANGE game:leaderboard 0 2 WITHSCORES

# A player scores 500 more — ranking updates instantly
ZINCRBY game:leaderboard 500 "bob"

# "What rank am I?" (0-based, highest first)
ZREVRANK game:leaderboard "alice"

# Players within a score band
ZRANGEBYSCORE game:leaderboard 2000 3000

5 · Job queues

A list is a ready-made queue. Producers push; workers block-pop and process. BRPOP waits efficiently instead of polling.

graph LR
    P1["Producer A"] -->|LPUSH| Q[("queue:jobs")]
    P2["Producer B"] -->|LPUSH| Q
    Q -->|BRPOP| W1["Worker 1"]
    Q -->|BRPOP| W2["Worker 2"]
    classDef p fill:#dbeafe,stroke:#2563eb,color:#1e3a8a;
    classDef q fill:#fde8e6,stroke:#dc382d,color:#7f1d1d;
    classDef w fill:#d1fae5,stroke:#047857,color:#064e3b;
    class P1,P2 p;
    class Q q;
    class W1,W2 w;

Many producers, many competing workers, one list. Each job is delivered to exactly one worker.

# Producer
LPUSH queue:jobs '{"type":"email","to":42}'

# Worker — blocks up to 5s waiting for a job
BRPOP queue:jobs 5

For durable, replayable queues with consumer groups and acknowledgements, use Streams (XADD/XREADGROUP) — covered in ch. 06.

6 · Pub/Sub (real-time fan-out)

Publish a message to a channel; every subscriber receives it instantly. Great for live notifications, chat, and cache-invalidation broadcasts.

# Terminal 1 — subscribe
SUBSCRIBE news

# Terminal 2 — publish
PUBLISH news "Redis 7.4 released!"
# → every subscriber to "news" gets the message immediately
Fire-and-forget: classic Pub/Sub doesn't store messages — a subscriber that's offline misses them. When you need persistence/replay, use Streams instead.

Pattern → type cheat sheet

Pattern Data type Key commands
Cache-aside String (+ TTL) GET / SET … EX
Sessions Hash (+ TTL) HSET / EXPIRE
Rate limiting String counter (+ TTL) INCR / EXPIRE
Leaderboard Sorted set ZADD / ZREVRANGE
Job queue List (or Stream) LPUSH / BRPOP
Real-time fan-out Pub/Sub (or Stream) PUBLISH / SUBSCRIBE
Unique counting Set / HyperLogLog SADD / PFADD

Try it yourself

easy Cache the string "home-html" under cache:home for 30 seconds. 
SET cache:home "home-html" EX 30
medium Add player "dave" with 2000 points to game:leaderboard and find his rank. 
ZADD game:leaderboard 2000 "dave"
ZREVRANK game:leaderboard "dave"
hard Sketch a per-user limit of 5 logins/min using one counter key. 
INCR rate:login:user:42
EXPIRE rate:login:user:42 60 NX
# reject if the INCR reply is > 5
The NX ensures the 60s window is anchored to the first request, not refreshed each time.
