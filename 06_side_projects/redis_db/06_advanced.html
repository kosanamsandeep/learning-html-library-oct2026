Chapter 06 · Going deep

Advanced Redis & making it production-ready

Persistence (so RAM data survives restarts), transactions & Lua for multi-step atomicity, pipelining for throughput, streams for durable events, eviction policies, and how Redis scales with replication and cluster. This is the "I run Redis in production" chapter.

1 · Persistence — is Redis durable?

Redis is in-memory, but it can write to disk so data survives restarts. Two mechanisms, often used together:

Mode How Trade-off
RDB (snapshot) Periodic point-in-time dump of the whole dataset Compact & fast restart, but you can lose the last few minutes on a crash
AOF (append-only file) Logs every write command; replays on restart More durable (down to ~1s), larger files, slightly slower
RDB + AOF Both enabled Recommended default: fast restart + good durability 
SAVE            # synchronous snapshot (blocks — avoid in prod)
BGSAVE          # background snapshot (preferred)
CONFIG SET appendonly yes   # enable AOF
LASTSAVE        # timestamp of last successful save
Mental model: treat Redis as a fast layer whose source of truth may be another DB. With persistence tuned it can be a primary store, but you must understand the durability window you've chosen.

2 · Transactions (MULTI / EXEC)

Queue several commands and run them as one atomic, isolated unit. WATCH adds optimistic locking (abort if a key changed).

WATCH product:1          # abort if this key changes before EXEC
MULTI                       # start queuing
HINCRBY product:1 stock -1
INCR sales:product:1
EXEC                        # run atomically (or nil if WATCH tripped)

Between MULTI and EXEC, commands are queued, not run. EXEC executes them with no other client interleaving.

3 · Lua scripts & Functions — true multi-step atomicity

A Lua script runs atomically on the server in a single step — ideal for read-then-write logic like a correct rate limiter or conditional update.

# Atomic "increment and return whether over limit"
EVAL "local n = redis.call('INCR', KEYS[1])
       if n == 1 then redis.call('EXPIRE', KEYS[1], ARGV[1]) end
       return n" 1 rate:ip:1.2.3.4 60
Why Lua beats MULTI here: the script can make decisions mid-way (the if), which a queued transaction can't. The whole thing is one atomic server step — no race between INCR and EXPIRE.

4 · Pipelining — fewer round-trips, more throughput

Network latency, not Redis, is usually the bottleneck. Pipelining sends many commands at once and reads all replies together.

graph TB
    subgraph Without["Without pipelining"]
        A1["cmd → wait → reply"] --> A2["cmd → wait → reply"] --> A3["cmd → wait → reply"]
    end
    subgraph With["With pipelining"]
        B1["cmd, cmd, cmd →"] --> B2["← reply, reply, reply"]
    end
    classDef slow fill:#fee2e2,stroke:#dc2626,color:#7f1d1d;
    classDef fast fill:#d1fae5,stroke:#047857,color:#064e3b;
    class A1,A2,A3 slow;
    class B1,B2 fast;

10,000 commands as 10,000 round-trips is slow; as one pipelined batch it's near instant. Most client libraries expose a pipeline() object.

5 · Streams — durable, replayable event logs

A Stream is an append-only log with consumer groups and acknowledgements — Redis's answer to Kafka for many workloads.

# Append an event (auto id with *)
XADD orders * user 42 total 1240

# Create a consumer group and read as a worker
XGROUP CREATE orders workers 0
XREADGROUP GROUP workers w1 COUNT 10 STREAMS orders >
XACK orders workers 1700000000000-0   # acknowledge processed

Unlike Pub/Sub, stream entries are stored: late or restarted consumers can replay, and unacknowledged messages can be reclaimed.

6 · Memory & eviction — staying inside RAM

When Redis hits maxmemory, an eviction policy decides what to drop. For a cache, evict least-recently-used keys; for a store, reject writes instead.

Policy Behavior
noeviction Reject writes when full (safest for a store)
allkeys-lru Evict least-recently-used key (classic cache)
allkeys-lfu Evict least-frequently-used key
volatile-ttl Evict keys with the nearest expiry first 
CONFIG SET maxmemory 512mb
CONFIG SET maxmemory-policy allkeys-lru

7 · Scaling — replication, Sentinel, Cluster

Replication
One primary, many read replicas. Spreads read load and gives a hot standby.
Sentinel
Monitors the primary and auto-promotes a replica on failure (high availability).
Cluster
Shards the keyspace across many nodes (16,384 hash slots) for datasets bigger than one machine's RAM.
Rule of thumb: start single-node. Add replication for HA/read-scaling. Reach for Cluster only when your data or throughput truly exceeds one node.

Performance checklist

✅ Pipeline bulk operations to cut round-trips
✅ Use SCAN, never KEYS, in production
✅ Set TTLs + an eviction policy so you never exceed RAM
✅ Use Lua for atomic read-then-write logic
❌ Storing huge values (multi-MB) under a single key
❌ Big O(N) commands (SMEMBERS on millions) on the hot path

Try it yourself

medium Decrement stock and increment sales for product 1 as one atomic unit. 
MULTI
HINCRBY product:1 stock -1
INCR sales:product:1
EXEC
hard Why use a Lua script instead of MULTI/EXEC for a rate limiter?
A rate limiter must conditionally set the TTL only on the first request (if n == 1). MULTI/EXEC queues commands blindly and can't branch on an intermediate result, but a Lua script runs the whole read-decide-write logic atomically on the server.
hard You're using Redis purely as a cache and it's full. Which eviction policy?
allkeys-lru (or allkeys-lfu) — evict the least useful keys to make room. noeviction would start rejecting writes, which you don't want for a cache.
