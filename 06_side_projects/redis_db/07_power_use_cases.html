Chapter 07 · Why Redis wins

The real power — and when NOT to use it

Redis isn't "a faster database for everything." It's a specialist that's unbeatable on latency and simple, high-frequency operations. Here's the proof, the killer use cases, and an honest list of when to reach for something else.

The core advantage: RAM + the right data structure

Two things make Redis extraordinary. First, data lives in memory, so latency is measured in microseconds, not milliseconds. Second, the server has purpose-built data structures, so operations like "rank this player" or "increment this counter" are single, atomic, O(1)/O(log n) commands — no read-modify-write round trips.

For data asked for constantly, the difference between milliseconds and microseconds — multiplied by millions of requests — is the difference between a slow app and an instant one.

Speed intuition

Operation Typical disk-based DB Redis (in-memory)
Single key lookup ~1–10 ms ~0.1 ms (often less)
Increment a counter Row lock / transaction One atomic INCR
Top-10 leaderboard ORDER BY … LIMIT + index One ZREVRANGE
Throughput (1 node) Thousands/sec 100k+ ops/sec

Exact numbers depend on hardware, payload, and config — but the order-of-magnitude gap on hot, simple operations is the whole point of Redis.

Killer use cases

⚡ Caching layer
Sit in front of a slow DB/API and serve hot data instantly. The single most common Redis deployment — cuts database load dramatically.
🔐 Sessions & tokens
Fast per-user state with automatic idle-timeout via TTL. Shared across all your app servers.
🚦 Rate limiting & counters
Atomic INCR with expiry — API quotas, "views", "likes", abuse protection.
🏆 Leaderboards & ranking
Sorted sets keep millions of scores ranked in real time. Games, trending, top-N feeds.
📨 Queues & background jobs
Lists and Streams decouple producers from workers — emails, image processing, webhooks.
📡 Real-time & pub/sub
Live notifications, chat fan-out, presence ("who's online"), and cache-invalidation broadcasts.
📍 Geospatial & search
Radius queries ("stores near me") with GEOADD/GEOSEARCH; full-text & vector search via Redis modules.
🤖 AI / LLM helper
Semantic caching of LLM responses and vector similarity search for RAG — fast retrieval beside your model.

Redis rarely replaces your database — it accelerates it. Postgres stays the durable source of truth; Redis absorbs the high-frequency reads, counters, sessions, and queues.

Choosing the right database

If you need… Best fit Why
Sub-ms reads, caching, counters, queues Redis In-memory + atomic structures
JOINs, transactions, ad-hoc SQL Relational (Postgres) Rich querying, durability
Flexible nested documents Document (MongoDB) Schema-light writes
Deep relationship traversal Graph (Neo4j) Index-free adjacency
Huge analytical scans Warehouse / OLAP Columnar aggregation
Semantic similarity search Vector DB (or Redis vectors) Embeddings / ANN
Rule of thumb: if a question is asked constantly, must return in milliseconds, or involves counters, queues, expiry, or rankings → Redis. If it involves JOINs, complex filters, or "the data must never be lost" as the primary store → reach for a relational DB (and put Redis in front of it).

When NOT to use Redis (be honest)

❌ Sole system of record without care. It's RAM-first; durability needs deliberate RDB/AOF config and you accept a small loss window.
❌ Complex queries / JOINs / reporting. There's no query planner — that's a relational/warehouse job.
❌ Data far bigger than RAM. RAM is the cost ceiling; a 100GB dataset on disk is cheap elsewhere, expensive here.
❌ Deep relationship traversal. Use a graph DB for "friends of friends to depth 5".
⚠️ Rarely-read cold data. Caching data that's almost never re-read just wastes memory.
⚠️ Strong cross-key transactions at scale. Possible with Lua/MULTI, but a relational DB is built for it.

Polyglot persistence is normal: the best systems combine Postgres (truth) + Redis (speed) + maybe a vector or graph DB. Pick the right tool per problem, not one DB for everything.

Remember it

RAM = microseconds. Redis wins where latency and frequency matter most.
Structures = simplicity. Counters, queues, rankings are one atomic command.
Speed layer, not replacement. Usually sits in front of a durable DB.
Mind the RAM & durability. TTLs, eviction, and persistence are the levers you must set.
