Chapter 02 · Mental model

Think in Redis — keys, structures, and RAM

Redis isn't "a faster SQL". It's a different shape of database: a single, giant dictionary in memory where each key points to a data structure. Internalize four ideas and the rest is easy.

The four ideas

1 · It lives in RAM

Data is held in memory, not on spinning disk per request. That's why reads and writes are microseconds. Disk is used only for optional persistence (snapshots / logs).

2 · Everything has a key

Redis is one flat keyspace: user:42, cart:42, rate:ip:1.2.3.4. You design key names the way you'd design tables.

3 · Values are data structures

A value isn't just text — it can be a hash, list, set, sorted set, stream… Pick the structure that matches the operation you need.

4 · One command at a time

Redis runs commands single-threaded, so each command is atomic — no half-updates, no locks needed for a single operation.

Anatomy of a key → value

    V --> F3["age → 30"]

    classDef val fill:#fde8e6,stroke:#dc382d,color:#7f1d1d;

A key (user:42) points to a value (here a hash with fields). Keys can carry a TTL so Redis deletes them automatically — perfect for caches, sessions, and tokens.

Why single-threaded is a feature, not a bug

Because Redis processes one command at a time, operations like "increment this counter" or "pop from this queue" are atomic by default — no race conditions, no locks. And since everything is in RAM, even single-threaded it handles 100k+ operations per second on a laptop.

Atomic example: 1,000 web servers all running INCR pageviews at once will never lose a count or collide — Redis serializes them. Doing the same safely in a relational DB needs transactions or row locks.

Redis trades rich querying for raw speed and simplicity: you fetch by key, and you get the answer in microseconds. There's no query planner — you decide the access path when you choose the key and structure.

Redis vs other databases at a glance

Model Stores data as Best at Weak at
Redis (in-memory KV) Key → data structure, in RAM Speed, caching, counters, queues, TTLs Ad-hoc queries, data > RAM, durability nuance
Relational (Postgres) Tables with rows & columns JOINs, transactions, ad-hoc SQL Raw per-key latency, simple scaling
Document (MongoDB) JSON-like documents Flexible schema, nested data Multi-document transactions, JOINs
Graph (Neo4j) Nodes + relationships Deep relationship traversal Simple key lookups, bulk aggregation
Wide-column (Cassandra) Partitioned column families Massive write volume, scale-out Low-latency single-key vs Redis, JOINs
The big idea: Redis is usually a complement, not a replacement. A typical stack is Postgres as the source of truth + Redis as the speed layer in front of it (cache, sessions, counters, queues).

Remember it (the whiteboard test)

Key = a label. Use colon:namespaces like user:42:cart so the keyspace reads like folders.
Value = pick the structure by the operation: need ranking? sorted set. Need fields? hash. Need a queue? list.
RAM = the budget. Set TTLs and an eviction policy so the dataset stays within memory.
Atomic by default. One command = one safe step. Need several together? Use transactions or Lua (ch. 06).
