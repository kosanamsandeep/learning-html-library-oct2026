Chapter 08 · Test yourself

Practice tests — prove you're an expert

Three graded rounds against the online-store dataset from chapter 03. Try each in redis-cli before revealing the answer. Aim to explain which data type and why, not just the command.

Setup: make sure the dataset from chapter 03 is loaded. If results look off, run FLUSHDB and re-paste it.

Round 1 Fundamentals & data types

easy Q1. Get the full hash for product:1. 
HGETALL product:1
Returns name, price, stock, category for the Laptop.
easy Q2. How many keys are in the current database? 
DBSIZE
easy Q3. Which data type would you use for a shopping cart, and why?
A list — it preserves insertion order and lets you push/pop items and allow duplicates (e.g. two of the same product). In our dataset cart:2 is a list.
easy Q4. Get the price field of product 2 without fetching the whole hash. 
HGET product:2 price
→ 800.
easy Q5. What's the difference between EXPIRE and PERSIST?
EXPIRE key seconds sets a TTL so the key auto-deletes; PERSIST key removes that TTL, making the key permanent again.

Round 2 Commands & structures

medium Q6. Sell one Laptop: atomically reduce its stock by 1 and bump its sales counter. 
MULTI
HINCRBY product:1 stock -1
INCR sales:product:1
EXEC
medium Q7. Which products are tagged tech AND bestseller? 
SINTER tag:tech tag:bestseller
→ {"1"} (the Laptop is in both sets).
medium Q8. Show the best-sellers ranked highest-first with their scores. 
ZREVRANGE bestsellers 0 -1 WITHSCORES
→ product:4 (61), product:2 (52), product:1 (37).
medium Q9. Add product 3 to Alice's cart (cart:1) at the end. 
RPUSH cart:1 3
Then LRANGE cart:1 0 -1 shows 1, 4, 3.
medium Q10. Cache the string "hot" under cache:product:1 for 60 seconds, only if it doesn't already exist. 
SET cache:product:1 "hot" NX EX 60

Round 3 Patterns, performance & judgment

hard Q11. Write a fixed-window rate limiter: max 10 hits per 60s for user:1. 
INCR rate:user:1
EXPIRE rate:user:1 60 NX
# reject the request if the INCR reply is > 10
NX anchors the 60s window to the first request so the limit can't be reset by later hits.
hard Q12. Why prefer a Lua script over MULTI/EXEC for that limiter?
The TTL should only be set on the first request (if count == 1). MULTI/EXEC can't branch on an intermediate result, but a Lua script runs the whole increment-check-expire atomically on the server with no race.
hard Q13. You need a leaderboard of 5 million players with instant top-10 and "my rank". Which type, and what's the cost?
A sorted set. ZADD/ZINCRBY are O(log n), ZREVRANGE 0 9 for top-10 is fast, and ZREVRANK member gives a rank directly — all without re-sorting or a separate index.
hard Q14. A teammate wants Redis as the only store for financial transactions that can never be lost. Good idea?
Risky as the sole store. Redis is RAM-first; durability needs careful AOF (appendfsync always/everysec) and you still accept a small loss window on crash. For money, keep a relational DB as the source of truth and use Redis as the speed/cache layer.
hard Q15. In production you must list all session:* keys. What do you run — and what do you avoid?
Use SCAN 0 MATCH "session:*" COUNT 100 and iterate the cursor. Avoid KEYS session:* — it blocks the single-threaded server while it sweeps the whole keyspace.
