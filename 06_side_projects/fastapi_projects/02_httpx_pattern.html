Why every modern FastAPI app pairs with httpx

FastAPI + httpx — the modern stack, explained

If FastAPI is "how clients call you", httpx is "how you call other services". The two were designed in the same era, both speak async natively, and together they let one Python worker hold hundreds of in-flight upstream calls without breaking a sweat.

requests — Python's most popular HTTP library since 2011 — is sync-only. Using requests in an async FastAPI app silently undoes everything async gave you. That's why httpx exists.

The story Why this matters

Story: a payments service called Stripe + a fraud-check service + an email service on every checkout. Using requests the three calls ran sequentially — 250 + 180 + 90 = ~520 ms per checkout. Switching to httpx.AsyncClient + asyncio.gather() the three calls ran concurrently — total wait ~250 ms (the slowest one). On Black Friday this difference was the gap between "scales fine" and "everything timed out".

What is httpx?

An HTTP client for Python that:

  • Has the same API as requests — easy migration.
  • Supports both sync (httpx.Client) and async (httpx.AsyncClient).
  • Supports HTTP/2.
  • Has first-class timeouts, retries (via tenacity or custom transports), and connection pooling.
  • Is what Starlette / FastAPI's own TestClient uses under the hood.

Side-by-side: requests vs httpx

requests (sync only)

import requests

@app.get("/aggregate")
def aggregate():
    # ⚠️ inside an async-capable framework, this blocks
    a = requests.get("https://api.a.com/data").json()
    b = requests.get("https://api.b.com/data").json()
    c = requests.get("https://api.c.com/data").json()
    return {"a": a, "b": b, "c": c}

httpx (async, concurrent)

import httpx, asyncio

@app.get("/aggregate")
async def aggregate():
    async with httpx.AsyncClient(timeout=2.0) as client:
        a, b, c = await asyncio.gather(
            client.get("https://api.a.com/data"),
            client.get("https://api.b.com/data"),
            client.get("https://api.c.com/data"),
        )
    return {"a": a.json(), "b": b.json(), "c": c.json()}

Same business logic. ~3x faster end-to-end. And one worker can now serve other requests while these three calls are in flight.

The AsyncClient lifecycle — do this once, not per request

Creating a new AsyncClient per request opens a new connection pool every time, which kills performance. Make one and reuse it for the app's lifetime.

from contextlib import asynccontextmanager
from fastapi import FastAPI
import httpx

@asynccontextmanager
async def lifespan(app: FastAPI):
    # startup: create one shared client
    app.state.http = httpx.AsyncClient(
        timeout=httpx.Timeout(5.0, connect=2.0),
        limits=httpx.Limits(max_connections=100, max_keepalive_connections=20),
    )
    yield
    # shutdown: close it cleanly
    await app.state.http.aclose()

app = FastAPI(lifespan=lifespan)

@app.get("/quote/{symbol}")
async def quote(symbol: str):
    r = await app.state.http.get(f"https://api.example.com/quote/{symbol}")
    r.raise_for_status()
    return r.json()
Rule: one AsyncClient per process, created on app startup, closed on shutdown. Reused for every request.

Timeouts — the #1 production lesson

Without timeouts, one slow upstream can hang every worker on every request and your service becomes "down" without anything actually being down.

# Configure separate timeouts for each phase
timeout = httpx.Timeout(
    connect=2.0,    # TCP / TLS handshake
    read=5.0,       # waiting for response body
    write=5.0,      # sending request body
    pool=1.0,       # waiting for a free connection from the pool
)
client = httpx.AsyncClient(timeout=timeout)
Never ship a service that calls an upstream without timeouts. The default of None means "wait forever".

Retries — done right

httpx doesn't ship a retry policy out of the box (deliberate). Use tenacity or write a small wrapper. Retry only idempotent verbs (GET, HEAD, PUT, DELETE) and only on transient errors (5xx, network failure, timeouts).

from tenacity import retry, stop_after_attempt, wait_exponential, retry_if_exception_type

@retry(
    stop=stop_after_attempt(3),
    wait=wait_exponential(multiplier=0.2, max=2),
    retry=retry_if_exception_type((httpx.ConnectError, httpx.ReadTimeout)),
    reraise=True,
)
async def safe_get(client: httpx.AsyncClient, url: str):
    r = await client.get(url)
    if r.status_code >= 500:
        raise httpx.HTTPStatusError("5xx", request=r.request, response=r)
    return r

When you actually want sync httpx

  • Inside a CLI script.
  • In a unit test where async machinery would be overkill.
  • Inside a sync FastAPI route (yes, those are valid — see concept 01).
with httpx.Client(timeout=5.0) as client:
    r = client.get("https://api.example.com")
    print(r.status_code)

The 5 rules of FastAPI + httpx

  1. One client per process. Created in lifespan, closed on shutdown.
  2. Always set timeouts. Never the default None.
  3. Use asyncio.gather when you have two or more independent upstream calls.
  4. Retry only idempotent verbs and only on transient failures.
  5. Wrap every external call with a circuit breaker in production (e.g. purgatory or pybreaker).
