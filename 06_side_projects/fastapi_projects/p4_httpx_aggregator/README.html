Project 4 · Intermediate · Where async earns its keep

FastAPI + httpx aggregator — the BFF pattern done right

Your front-end needs a user's profile, their last 5 repos, and their 5 latest followers — in one payload, in one round trip. The naive way calls GitHub three times sequentially. The right way fires all three in parallel with asyncio.gather, and the wall-clock time becomes whatever the slowest single call took.

This is the moment async stops being a buzzword and becomes a measurable speedup.

The problem we're solving

Modern UIs are composed of data from many services: a profile page needs user data + recent orders + recommendations + notifications. If the front-end makes 4 separate requests, each one pays a TLS handshake + latency tax. The BFF (Backend for Frontend) pattern says: have one server endpoint that fans out to the upstreams in parallel and merges the result.

Doing this well requires three things at once: async routes, an async HTTP client, and asyncio.gather.

How FastAPI + httpx solves it

1. One AsyncClient for the whole app

@asynccontextmanager
async def lifespan(app: FastAPI):
    app.state.http = httpx.AsyncClient(
        timeout=httpx.Timeout(5.0, connect=2.0),
        limits=httpx.Limits(max_connections=100, max_keepalive_connections=20),
    )
    yield
    await app.state.http.aclose()

Connection pool is reused. TLS handshake happens once per upstream host, not per request.

2. Concurrent calls with asyncio.gather

user, repos, followers = await asyncio.gather(
    safe_get(client, f"{GITHUB}/users/{username}"),
    safe_get(client, f"{GITHUB}/users/{username}/repos?per_page=5"),
    safe_get(client, f"{GITHUB}/users/{username}/followers?per_page=5"),
)

3. Graceful partial failure

If one upstream times out, the helper returns {"_error": "timeout"} instead of raising — the other two still come back. The client gets a partial answer rather than a 500.

What if you DIDN'T do this?

Using requests sequentially

Total = sum of all 3 upstream latencies (~3x slower). The worker is fully blocked during every wait, so it can't serve any other request meanwhile. Under load, queue backs up and everything times out.

Using httpx sequentially (no gather)

Async, but not concurrent. Still ~3x slower than necessary. People often miss this — async is necessary but not sufficient. You also have to schedule things in parallel.

New AsyncClient() per request

Every request opens a fresh TCP + TLS connection. Latency floor goes up by 100+ ms per upstream. Sockets pile up; eventually Too many open files.

No timeouts

One slow upstream hangs every worker. Your service appears "down" while perfectly healthy. Cardinal sin of distributed systems.

Measure it yourself

This project ships two endpoints that do the exact same work — one concurrent, one sequential. Hit them back-to-back and compare the elapsed_ms fields.

cd 06_side_projects/fastapi_projects/p4_httpx_aggregator
python -m venv .venv && .venv\Scripts\activate
pip install -r requirements.txt
uvicorn main:app --reload

curl http://127.0.0.1:8000/github/torvalds
# {"elapsed_ms_concurrent": 280, ...}

curl http://127.0.0.1:8000/github-sequential/torvalds
# {"elapsed_ms_sequential": 760, ...}

Same data, ~3x slower sequentially. That ratio scales with the number of upstreams: 5 upstreams of 200 ms each = 200 ms concurrent vs 1000 ms sequential. This is the speedup the user actually feels.

Things to try

  1. Hit a non-existent user (/github/this-user-doesnt-exist-12345) — see the 404 propagated cleanly.
  2. Drop the timeout to 0.05 and watch the partial failure mode — some sub-calls error out, the response still comes back.
  3. Add a fourth upstream (/users/{u}/starred). Add it to asyncio.gather. Total time barely changes.
  4. Try removing the shared client — create one inside the route. Re-measure. Notice latency goes up.

What you learned

  • The BFF for Frontend pattern.
  • One shared httpx.AsyncClient per process, via FastAPI lifespan.
  • asyncio.gather for true concurrency.
  • Strict timeouts and partial-failure handling — non-negotiable for production aggregators.
