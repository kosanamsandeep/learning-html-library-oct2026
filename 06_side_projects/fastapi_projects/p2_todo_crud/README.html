Todo CRUD — Pydantic models + Dependency Injection done right

A full Create/Read/Update/Delete REST API for todos. The point isn't todos — every tutorial does todos. The point is the shape: separate input/output models, a repository accessed via Depends(), and routes that are trivially testable because they don't know where the data lives.

The problem we're solving

Three things almost every real API needs that beginners get wrong:

  1. Different input vs output shapes. A TodoCreate doesn't have an id (the server makes it). A TodoUpdate has all-optional fields. A TodoOut always has an id. Using one model for all three leads to "user sent us an id, did we use it? did they get fields back they shouldn't?" bugs.
  2. Storage is going to change. Today it's an in-memory dict. Tomorrow Postgres. Next year Redis cache + Postgres. Your routes should never care.
  3. Tests should not touch the real DB. The route should accept a "repo" dependency that can be swapped for a fake.

How FastAPI solves it

Separate input / update / output models

class TodoBase(BaseModel):
    title: str = Field(min_length=1, max_length=200, examples=["Buy milk"])
    done: bool = False

class TodoCreate(TodoBase):
    pass

class TodoUpdate(BaseModel):
    title: str | None = Field(default=None, min_length=1, max_length=200)
    done: bool | None = None

class TodoOut(TodoBase):
    id: str

Now POST /todos takes a TodoCreate; PATCH /todos/{id} takes a TodoUpdate with everything optional; every response is locked to TodoOut via response_model=. Field leaks are impossible.

Dependency injection for the repository

def get_repo() -> InMemoryTodoRepo:
    return _repo_singleton

Repo = Annotated[InMemoryTodoRepo, Depends(get_repo)]

@app.get("/todos", response_model=list[TodoOut])
def list_todos(repo: Repo) -> list[TodoOut]:
    return repo.list()

The route declares "I need a repo". FastAPI injects it. In tests you write:

app.dependency_overrides[get_repo] = lambda: FakeRepo()

and every route in the test gets the fake. No monkey-patching, no globals.

What if you DIDN'T do this?

Without separate models

  • Users submit an id and it accidentally overwrites the server's.
  • Internal fields like created_by_admin get returned to consumers.
  • Every PATCH requires the full object — partial updates are awkward.

Without DI

  • Routes call a global db directly.
  • Tests have to patch globals or spin up a real DB.
  • You can't swap storage without rewriting routes.
  • Multi-tenancy / per-request context becomes impossible.
Real story: a team built a B2B SaaS where one WidgetModel was used for input, output, and DB rows. A junior dev added an internal_cost field for analytics. Two weeks later, customers saw internal_cost appear in every Widget API response and complained about the obvious markup. Cure: separate input/output models with explicit fields. Bug class disappeared.

# http://127.0.0.1:8000/docs

Things to try

  1. POST with {"title": ""} → see Pydantic's min_length=1 error.
  2. POST with no title at all → see the structured 422.
  3. PATCH with just {"done": true}. Title stays the same.
  4. GET a nonexistent id → see the custom 404 message.
  5. Add a created_at: datetime to TodoOut. Set it in the repository. Watch Swagger UI document the new field automatically.

What you learned

  • Pydantic input/output split — the safest pattern for REST APIs.
  • The repository pattern, injected via Depends().
  • Annotated[…, Depends(…)] — the modern, type-friendly DI syntax.
  • Custom 404s via HTTPException; 204 No Content on DELETE.
