Project 6 · Production · The finale

Production-grade service — everything you need before you ship

One service combining every pattern from P1–P5 plus the operational primitives that turn a demo into something you'd actually deploy: typed settings, structured logging, request-ID middleware, uniform error shape, health + readiness, background tasks, a concurrent DB + HTTP endpoint, and tests.

What's inside

Section What it teaches
1. Settings (pydantic-settings) Typed config from env vars / .env file. lru_cache'd so it's loaded once.
2. JsonFormatter Structured JSON logs — every line is one JSON object, easy to ingest in ELK / CloudWatch / Loki.
3. Async DB Engine + session factory created on startup, disposed on shutdown.
4. Custom exceptions + handlers One ErrorOut shape for every error response across the service.
5. lifespan Boots the DB engine AND the shared httpx.AsyncClient. Cleans both up on shutdown.
6. Request-ID middleware Generates or accepts X-Request-ID, includes it in every log line and every response header.
7. Access-log middleware Logs method, path, status, latency for every request.
8. /health + /ready Kubernetes-style liveness & readiness probes.
9. BackgroundTasks Fire-and-forget audit log after the response is sent.
10. Enrichment endpoint DB read + upstream HTTP call in one async handler — showcase end-to-end.
11. Tests Async pytest + httpx ASGITransport — fast, isolated, no server running.

The pre-launch checklist this project satisfies

  • ✅ All routes have response_model (or no body for 204).
  • ✅ All upstream HTTP calls have timeouts.
  • ✅ Settings come from env, not constants.
  • ✅ Errors have a uniform JSON shape with request_id.
  • ✅ Liveness + readiness endpoints exist.
  • ✅ Structured logs with request IDs.
  • ✅ Tests cover happy + error paths.

Run it

cd 06_side_projects/fastapi_projects/p6_production_app
python -m venv .venv && .venv\Scripts\activate
pip install -r requirements.txt
copy .env.example .env

uvicorn main:app --reload

# In another terminal:
curl http://127.0.0.1:8000/health
curl http://127.0.0.1:8000/ready

curl -X POST http://127.0.0.1:8000/widgets \
    -H "Content-Type: application/json" \
    -H "X-Request-ID: my-test-123" \
    -d "{\"name\": \"blue\"}"
# Server log will include  "request_id": "my-test-123"

# Note the response includes X-Request-ID header.
# Try the enrichment endpoint (uses upstream via httpx):
curl http://127.0.0.1:8000/widgets/<id-from-prev-call>/enriched

# Run the tests:
pytest -q

What if you DIDN'T do these things?

No request IDs

A customer reports "this call failed 3 minutes ago" → you have no way to find their request in the logs among thousands. Debugging time grows 10×.

Unstructured logs

You can grep. You can't jq. You can't build alerts on "any log line where level=ERROR and request_id=X". You also can't ship them into any modern log platform cleanly.

No /ready

Kubernetes routes traffic to you the instant the process starts — before DB connections are ready. First N requests fail.

No global exception handler

Different routes return different error shapes. Front-end has to special-case each. Stack traces leak to clients.

Settings via os.getenv scattered around

No types. No defaults. No central place to see what env vars the app needs. New engineer has to grep the whole repo to deploy.

No tests

Every refactor is terrifying. You ship slower. Bugs reach prod.

Things to try

  1. Send a request without X-Request-ID → see one is generated automatically and echoed back in the response header.
  2. Force an error (POST with {"name": ""}) → see Pydantic's structured 422.
  3. Stop your network → call /widgets/{id}/enriched. The DB call still works, the upstream returns the graceful fallback string. Partial degradation, not total failure.
  4. Add a new business endpoint that calls two upstreams concurrently with asyncio.gather. Try it inside this same project.
  5. Add prometheus-fastapi-instrumentator and expose /metrics.

What you learned

  • Typed settings with pydantic-settings and lru_cache.
  • Structured JSON logging — the foundation of any real observability stack.
  • Request-ID propagation through middleware, logs, and response headers.
  • Global exception handlers with a uniform error shape.
  • Lifespan orchestrating multiple long-lived resources.
  • Kubernetes-style health endpoints.
  • Background tasks for non-critical post-response work.
  • Async pytest with httpx's ASGITransport.
