Async database with SQLAlchemy 2.0

P2 stored todos in a Python dict. Restart and they're gone. P3 stores them in SQLite via async SQLAlchemy. Same API contract, but now: persistent, transactional, and built so it can scale to Postgres by changing one URL.

The problem we're solving

You need a real database. But you also want to keep async's throughput benefit. If you naively drop in the classic synchronous SQLAlchemy session inside an async def route, every DB call blocks the event loop and you've thrown away most of FastAPI's speed.

SQLAlchemy 2.0 ships first-class async support — AsyncSession, create_async_engine, await session.execute(). Use those and your routes stay genuinely non-blocking.

How FastAPI solves it

1. Async engine + session factory

engine = create_async_engine("sqlite+aiosqlite:///./todos.db")
SessionLocal = async_sessionmaker(engine, expire_on_commit=False)

async def get_db():
    async with SessionLocal() as session:
        yield session

DB = Annotated[AsyncSession, Depends(get_db)]

2. Lifespan creates tables on startup

@asynccontextmanager
async def lifespan(app: FastAPI):
    async with engine.begin() as conn:
        await conn.run_sync(Base.metadata.create_all)
    yield
    await engine.dispose()

app = FastAPI(lifespan=lifespan)

3. Routes are async + await every DB call

@app.get("/todos/{todo_id}", response_model=TodoOut)
async def get_todo(todo_id: str, db: DB):
    row = await db.get(TodoRow, todo_id)
    if not row: raise HTTPException(404)
    return TodoOut(id=row.id, title=row.title, done=row.done)

What if you DIDN'T do this?

Sync SQLAlchemy in async routes

Every DB call blocks the event loop. Other in-flight requests on the same worker are paused until your query returns. Under load: latency spikes, throughput collapses. The metric to watch is "event loop lag" — > 10 ms means you have a blocking call.

One engine per request

Creating create_engine(...) inside the route opens a new connection pool each time. Connections are expensive. After 30 seconds your DB will refuse connections.

Real story: a team built an internal reporting API. Started with sync SQLAlchemy inside async def routes "because async sounds fast". p99 latency was 9 seconds under modest load. They switched to async SQLAlchemy and the same code served 10x more requests with p99 of 200 ms. Lesson: async-the-keyword isn't async-the-behaviour. You have to actually await on a non-blocking driver.

Going to Postgres in 2 minutes

The whole switch is one URL change:

# requirements.txt — add asyncpg
asyncpg==0.30.0

# main.py
DATABASE_URL = "postgresql+asyncpg://user:pass@localhost:5432/mydb"

Nothing else in the code changes. Same async engine, same session, same routes. That's the SQLAlchemy promise.

Run it

cd 06_side_projects/fastapi_projects/p3_async_database
python -m venv .venv && .venv\Scripts\activate
pip install -r requirements.txt
uvicorn main:app --reload

# A SQLite file `todos.db` is created in the project folder.
# Restart the server — the data is still there.

curl -X POST http://127.0.0.1:8000/todos \
    -H "Content-Type: application/json" \
    -d "{\"title\": \"Pay rent\"}"
curl http://127.0.0.1:8000/todos
