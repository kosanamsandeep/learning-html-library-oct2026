A practical security track for the Python + FastAPI + requests stack you build with. Learn the concepts to be cautious of, the areas attackers probe, and the strategies that make your applications hard to break — all from a defender's point of view, with the attacker's mindset as a lens.

The one mental shift: assume hostile input

Every value crossing your application's boundary — query params, JSON bodies, headers, cookies, uploaded files, third-party API responses, even your own database rows — is untrusted until proven otherwise. Most breaches trace back to trusting input that shouldn't have been trusted.

Security is not a feature you bolt on at the end. It's a property of how you design every layer. The cheapest vulnerability to fix is the one you never wrote — so we build the habits in from the first line of code.

Seven principles to keep in mind on every build

① Least privilege

Every component gets the minimum access it needs — DB roles, tokens, file scopes, cloud IAM.

② Defense in depth

Never one control. If one layer fails, the next still protects you.

③ Fail closed

On error or doubt, deny. A crash should never default to "access granted".

④ Validate input, encode output

Check what comes in; escape what goes out (HTML, SQL, shell, logs).

⑤ Don't trust the client

Anything from the browser/app can be forged. Re-check everything server-side.

⑥ Secure defaults

The safe path should be the easy/default path. Make insecurity opt-in and loud.

⑦ Minimise attack surface

Fewer endpoints, fewer deps, fewer secrets, less exposed = less to attack.

How to use this track

Read it once end-to-end to build the mindset, then keep it open as a checklist while you build. Each page follows the same shape: the threat (what an attacker tries) → vulnerable vs hardened code → the strategy to adopt → a checklist you can paste into a PR review.

Ethics & scope. This material is for defending systems you own or are authorised to test. The attacker techniques are described at a conceptual level so you can close the gaps — never to target systems without explicit permission. Unauthorised testing is illegal.
