🔑 Secrets, transport & data protection

Even with perfect auth and validation, you lose if secrets leak, traffic is sniffable, or a stolen database dump is readable. This page covers keeping secrets out of code, encrypting in transit and at rest, and the headers/CORS config that harden the browser side.

Three states of data: in transit (TLS), at rest (encryption), and in use (least-privilege access). Protect all three.

Secrets management — never in source

Hardcoded keys, DB passwords, and tokens are the most common leak — they end up in Git history, logs, and error pages. Load them from the environment or a secrets manager, validate them at startup, and never commit them.

❌ Vulnerable — secret in code

STRIPE_KEY = "sk_live_51H...realkey..."   # committed to Git forever

✅ Hardened — typed settings from env, fail-fast

from pydantic import Field
from pydantic_settings import BaseSettings, SettingsConfigDict

class Settings(BaseSettings):
    model_config = SettingsConfigDict(env_file=".env", extra="forbid")

    jwt_secret: str = Field(min_length=32)
    database_url: str
    stripe_key: str

# Crashes at startup if a secret is missing/short — better than a 2am surprise.
settings = Settings()
Operational rules: add .env to .gitignore; use a secrets manager (Vault, AWS/GCP Secrets Manager, Doppler) in production; rotate any secret that was ever committed (assume it's burned); scan repos with tools like gitleaks / trufflehog in CI.

Encryption in transit — TLS everywhere

  • Terminate TLS 1.2+ (prefer 1.3) at your gateway/load balancer; redirect all HTTP → HTTPS.
  • Enable HSTS so browsers refuse to downgrade to HTTP.
  • For internal service-to-service calls, use TLS too (mTLS where possible) — the network is not a trust boundary.
  • Never disable certificate verification on outbound calls (see 05).

Encryption at rest & data minimization

Assume a database dump will leak someday. Reduce the blast radius:

Data Treatment
Passwords Argon2id/bcrypt hash (never reversible) — see 02
Secrets/tokens stored for users Encrypt (e.g. cryptography.Fernet) with a KMS-held key
PII (email, phone, address) Encrypt sensitive columns; consider tokenization
Card data (PAN) Don't store — delegate to a PCI-compliant processor
Anything you don't need Don't collect it. Least data = least liability. 
from cryptography.fernet import Fernet

fernet = Fernet(settings.field_key)            # 32-byte key from KMS / env
ciphertext = fernet.encrypt(api_token.encode())   # store this
plaintext = fernet.decrypt(ciphertext).decode()   # on read

Security headers — cheap, high-impact

A small middleware adds defense-in-depth for browser clients:

from fastapi import FastAPI, Request

app = FastAPI()

@app.middleware("http")
async def security_headers(request: Request, call_next):
    resp = await call_next(request)
    resp.headers["X-Content-Type-Options"] = "nosniff"
    resp.headers["X-Frame-Options"] = "DENY"           # anti-clickjacking
    resp.headers["Referrer-Policy"] = "no-referrer"
    resp.headers["Strict-Transport-Security"] = "max-age=63072000; includeSubDomains"
    resp.headers["Content-Security-Policy"] = "default-src 'self'"
    return resp
Header Defends against
Strict-Transport-Security Protocol downgrade / SSL strip
Content-Security-Policy XSS, data exfiltration, injected scripts
X-Content-Type-Options: nosniff MIME-sniffing attacks
X-Frame-Options: DENY Clickjacking
Referrer-Policy Leaking URLs/tokens via Referer

CORS — permissive config is a real vulnerability

CORS controls which browser origins may call your API. The frequent mistake is wildcarding it "to make things work," which can expose authenticated endpoints to any site.

❌ Vulnerable — wildcard + credentials

app.add_middleware(
    CORSMiddleware,
    allow_origins=["*"],          # any site can call you
    allow_credentials=True,      # ...and send cookies (invalid combo / dangerous)
    allow_methods=["*"], allow_headers=["*"],
)

✅ Hardened — explicit allow-list

from fastapi.middleware.cors import CORSMiddleware

app.add_middleware(
    CORSMiddleware,
    allow_origins=["https://app.example.com"],   # exact origins only
    allow_credentials=True,
    allow_methods=["GET", "POST"],
    allow_headers=["Authorization", "Content-Type"],
)
Remember: CORS is a browser protection, not a server authorization control. It does not stop non-browser clients (curl, scripts) — your auth checks still do all the real work.

Don't leak data through errors & logs

  • Return generic error messages to clients; log details server-side with a correlation ID.
  • Turn off stack traces / debug mode in production (debug=False).
  • Scrub secrets, tokens, passwords, and full PII from logs.
  • Disable or lock down auto-generated docs (/docs, /openapi.json) on sensitive deployments.

Data-protection checklist

  • No secret is in source or committed history; .env is gitignored.
  • Secrets loaded via typed settings, validated at startup, rotated if ever exposed.
  • TLS 1.2+/1.3 enforced end-to-end; HSTS enabled.
  • Sensitive columns encrypted at rest; PAN never stored.
  • Security headers middleware in place (HSTS, CSP, nosniff, frame-deny).
  • CORS uses an explicit origin allow-list, never * with credentials.
  • Debug off in prod; errors generic; logs scrubbed of secrets/PII.
