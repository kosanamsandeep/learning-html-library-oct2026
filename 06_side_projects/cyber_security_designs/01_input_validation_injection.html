🧪 Never trust input: stopping injection

Injection is consistently in the OWASP Top 10 because it's everywhere: any time untrusted data is mixed into a command, query, or template, an attacker can hijack the meaning. The fix is always the same idea — separate code from data.

The story: why injection happens

Your code builds a string. Part of it is your instruction ("SELECT this user"), part of it is their data (the user's name). If you glue them together with string formatting, the database can't tell where your intent ends and their data begins. A crafted value rewrites your query. That's injection — and it applies to SQL, shell commands, NoSQL, LDAP, XML, and even prompt-templates for LLMs.

What an attacker tries (conceptually)

  • SQL injection: appends boolean tautologies (OR 1=1), comments out the rest of your query, or stacks extra statements to read/alter data.
  • Command injection: slips shell metacharacters (;, &&, |, backticks) into anything passed to a shell.
  • NoSQL injection: sends an object where a string is expected (e.g. {"$ne": null}) to bypass filters.
  • Template / SSTI: injects template syntax into anything rendered by a template engine.
  • Mass over-posting: sends extra fields hoping your model trusts them (covered in 04).
The tell. Any place you build a string with f"...{user_input}..." and hand it to an interpreter (DB driver, shell, template, eval) is a potential injection point. Grep your codebase for f-strings near execute, os.system, subprocess, and eval.

SQL injection — vulnerable vs hardened

❌ Vulnerable — string-built query

# The username comes from the request. f-string mixes data into SQL.
def get_user(username: str):
    query = f"SELECT * FROM users WHERE name = '{username}'"
    return db.execute(query)   # attacker sends:  ' OR '1'='1

✅ Hardened — parameterised query (binding)

# The ? / :name placeholders keep the value as DATA, never parsed as SQL.
def get_user(username: str):
    query = "SELECT * FROM users WHERE name = :name"
    return db.execute(query, {"name": username})

✅ Even better — use an ORM / query builder

from sqlalchemy import select
from sqlalchemy.ext.asyncio import AsyncSession

async def get_user(session: AsyncSession, username: str):
    # SQLAlchemy binds parameters for you — no hand-built SQL strings.
    stmt = select(User).where(User.name == username)
    result = await session.execute(stmt)
    return result.scalar_one_or_none()
Rule: the column/table being queried may be code, but a value must always travel as a bound parameter. Never .format() or f-string a value into SQL — not even "trusted" internal ones.

Command injection — avoid the shell

❌ Vulnerable — shell=True with interpolated input

import os, subprocess

def ping(host: str):
    os.system(f"ping -c 1 {host}")            # host = "8.8.8.8; rm -rf /"
    subprocess.run(f"ping -c 1 {host}", shell=True)

✅ Hardened — argument list, no shell

import subprocess, ipaddress

def ping(host: str):
    # 1) Validate to a known-safe shape first.
    ipaddress.ip_address(host)             # raises ValueError if not an IP
    # 2) Pass args as a LIST — the OS does not invoke a shell, so
    #    metacharacters like ; && | are treated as literal text.
    subprocess.run(["ping", "-c", "1", host], shell=False, timeout=5, check=True)
Best of all: don't shell out. Most "run a command" needs have a pure-Python library equivalent. If you must, use an argument list, shell=False, an absolute binary path, and a timeout.

Validate at the boundary with Pydantic + FastAPI

FastAPI's biggest security win is that Pydantic validates and coerces every request body before your code runs. Lean into it: constrain types, lengths, ranges, and formats so malformed input is rejected with a clean 422 — never reaching your logic.

from fastapi import FastAPI
from pydantic import BaseModel, EmailStr, Field, field_validator

app = FastAPI()

class SignupRequest(BaseModel):
    # Tight constraints = smaller attack surface.
    username: str = Field(min_length=3, max_length=32, pattern=r"^[a-zA-Z0-9_]+$")
    email: EmailStr
    age: int = Field(ge=13, le=120)

    @field_validator("username")
    @classmethod
    def no_reserved(cls, v: str) -> str:
        if v.lower() in {"admin", "root", "system"}:
            raise ValueError("reserved username")
        return v

@app.post("/signup")
async def signup(body: SignupRequest):
    # By here, body is GUARANTEED valid & typed. No defensive re-checks needed.
    return {"ok": True, "user": body.username}
Constraint Pydantic tool Stops
Length bounds Field(min_length, max_length) Oversized payloads, buffer abuse
Numeric range Field(ge, le, gt, lt) Integer overflow / nonsense values
Allowed shape pattern= regex / Enum Unexpected characters, injection seeds
Known formats EmailStr, AnyUrl, UUID Malformed identifiers
Reject extras model_config = {"extra": "forbid"} Mass-assignment / over-posting
Set extra="forbid" on request models. By default Pydantic ignores unknown fields; forbidding them turns a silent over-post into a loud 422 — a free defence against mass-assignment.

Output encoding — the other half

Validation stops bad input coming in; encoding stops data being misread going out. The same value is dangerous in different contexts:

  • HTML context → escape < > & " ' (prevents stored XSS). Templating engines like Jinja2 auto-escape — keep it on.
  • SQL context → parameter binding (above).
  • Shell context → argument lists, never string concat.
  • Log context → strip newlines/control chars so attackers can't forge or split log lines (log injection).

Your injection-defence checklist

  • No value is ever f-stringed/`.format()`-ed into SQL, shell, or a template.
  • All DB access uses parameter binding or an ORM.
  • subprocess uses argument lists, shell=False, and a timeout.
  • Every request body is a Pydantic model with tight Field constraints.
  • Request models set extra="forbid".
  • Template auto-escaping is on; no eval/exec on user data.
  • User-controlled values are sanitised before being written to logs.
