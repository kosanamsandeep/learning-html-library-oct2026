02 · Core discipline · Identity & access

🔐 Authentication & authorization

Two questions you must answer on every protected request: "Who are you?" (authentication) and "Are you allowed to do this, to this object?" (authorization). Getting the second one wrong is the #1 API vulnerability today.

AuthN vs AuthZ — don't conflate them

sequenceDiagram
    participant C as Client
    participant A as FastAPI
    participant DB as DB
    C->>A: POST /login (email, password)
    A->>DB: fetch user by email
    A->>A: verify password hash (constant-time)
    A-->>C: short-lived access token (+ refresh)
    C->>A: GET /orders/42 (Bearer token)
    A->>A: AuthN: verify token signature & expiry
    A->>DB: load order 42
    A->>A: AuthZ: does order.owner == token.user?
    A-->>C: 200 only if owner, else 404/403

Authentication proves identity once; authorization must be re-checked on every request and every object.

Password storage — the non-negotiables

If you store passwords, store only a slow, salted hash — never plaintext, never fast hashes like MD5/SHA-256 alone. Use a memory-hard algorithm (Argon2id) or bcrypt.

❌ Vulnerable — fast/unsalted hash

import hashlib
digest = hashlib.sha256(password.encode()).hexdigest()  # crackable at billions/sec

✅ Hardened — Argon2id (or bcrypt) via passlib

from passlib.context import CryptContext

pwd = CryptContext(schemes=["argon2"], deprecated="auto")

def hash_password(raw: str) -> str:
    return pwd.hash(raw)            # salt + cost baked into the output

def verify_password(raw: str, stored: str) -> bool:
    return pwd.verify(raw, stored)  # constant-time comparison
Do Don't
Argon2id / bcrypt / scrypt MD5, SHA-1, plain SHA-256
Per-password random salt (automatic) Shared/global salt or none
Constant-time verify == string compare
Enforce length, check against breach lists Complexity rules that push reuse

Tokens & sessions — JWT done safely

FastAPI commonly uses OAuth2 password/bearer flow with JWTs. The pitfalls are subtle:

from datetime import datetime, timedelta, timezone
import jwt   # PyJWT

ALGO = "HS256"             # pin the algorithm explicitly

def make_token(user_id: str, secret: str) -> str:
    now = datetime.now(timezone.utc)
    payload = {
        "sub": user_id,
        "iat": now,
        "exp": now + timedelta(minutes=15),   # SHORT-lived
        "iss": "my-api",
    }
    return jwt.encode(payload, secret, algorithm=ALGO)

def read_token(token: str, secret: str) -> dict:
    # PIN algorithms — never trust the token's own "alg" header (alg=none attack).
    return jwt.decode(token, secret, algorithms=[ALGO], issuer="my-api",
                      options={"require": ["exp", "iat", "sub"]})
Classic JWT attacks & the fix:
  • alg=none / alg confusion → always pass an explicit algorithms=[...] allow-list to decode.
  • Long-lived tokens → keep access tokens short (5–15 min); use a revocable refresh token for longevity.
  • No revocation → maintain a server-side denylist / token version, so logout and "ban user" actually work.
  • Storing JWT in localStorage → exposed to XSS. Prefer HttpOnly, Secure, SameSite cookies for browser apps.

FastAPI dependency for the current user

from fastapi import Depends, HTTPException, status
from fastapi.security import OAuth2PasswordBearer

oauth2 = OAuth2PasswordBearer(tokenUrl="login")

async def current_user(token: str = Depends(oauth2)) -> User:
    try:
        claims = read_token(token, settings.jwt_secret)
    except jwt.PyJWTError:
        raise HTTPException(status.HTTP_401_UNAUTHORIZED, "invalid token")
    user = await users.get(claims["sub"])
    if user is None or not user.active:
        raise HTTPException(status.HTTP_401_UNAUTHORIZED, "invalid token")
    return user

The #1 API risk: Broken Object-Level Authorization (IDOR/BOLA)

You authenticated the user — but did you check they own the specific object they asked for? If GET /orders/42 returns order 42 to any logged-in user, attackers simply increment the ID and harvest everyone's data. This is IDOR (a.k.a. BOLA).

❌ Vulnerable — authenticated but not authorized

@app.get("/orders/{order_id}")
async def get_order(order_id: int, user: User = Depends(current_user)):
    return await orders.get(order_id)   # any user can read any order!

✅ Hardened — scope every query to the owner

@app.get("/orders/{order_id}")
async def get_order(order_id: int, user: User = Depends(current_user)):
    order = await orders.get_for_owner(order_id, owner_id=user.id)
    if order is None:
        # 404 (not 403) avoids leaking that the object exists.
        raise HTTPException(status.HTTP_404_NOT_FOUND)
    return order
Strategy: bake the owner filter into the data layer (WHERE owner_id = :me), not the route. Use unguessable IDs (UUIDs) as a defence in depth, but never rely on them — always enforce ownership in the query.

Authorization models — pick one and centralize it

Model Idea Good for
RBAC Roles → permissions (admin, editor, viewer) Most apps; simple, auditable
ABAC Rules over attributes (dept, region, time) Fine-grained, contextual access
ReBAC Relationships (owner, member-of) Sharing, multi-tenant graphs

Whatever you choose, put the decision in one place (a dependency or policy function), so it's testable and can't be forgotten on a new endpoint.

Login-flow hardening

  • Generic errors: "invalid email or password" — never reveal which was wrong (prevents user enumeration).
  • Rate-limit + lockout/backoff on login to blunt credential stuffing & brute force (see 04).
  • MFA for sensitive accounts; verify email before granting access.
  • Rotate & invalidate sessions on password change and logout.
  • CSRF protection for cookie-based auth (SameSite + anti-CSRF token).

Auth checklist

  • Passwords stored with Argon2id/bcrypt; verify is constant-time.
  • Access tokens short-lived; refresh tokens revocable.
  • jwt.decode always pins algorithms=[...] and validates exp/iss.
  • Every object read/write filters by the caller's identity (no IDOR).
  • Authorization logic lives in one central, tested place.
  • Login uses generic errors + rate limiting; MFA on sensitive roles.
  • Cookie auth uses HttpOnly + Secure + SameSite and CSRF protection.
