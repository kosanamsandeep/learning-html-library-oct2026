🕵️ The ethical hacker's playbook (and how you shut it down)

To defend well, think like the person testing you. An ethical hacker follows a repeatable method — recon → map → probe → exploit → report. Knowing each phase tells you exactly where to put your defenses. This page is conceptual and defensive: it's about hardening systems you own or are authorised to test.

Each phase has a matching defense. Raise the cost at every step and most attackers move on to an easier target.

What they look for at each phase — and your counter

Phase What an ethical hacker looks for Your defense
Recon Exposed /docs, .git, leaked keys in repos, verbose errors, subdomains, version banners Lock down docs in prod, scan for secret leaks, strip version banners, generic errors
Map All endpoints, params, hidden fields, ID patterns, auth flows Minimize surface, unguessable IDs, consistent auth on every route
Probe — input Injection (SQL/cmd), XSS, unvalidated params, weird types Parameterized queries, Pydantic validation, output encoding (01)
Probe — auth IDOR/BOLA, weak JWT, missing authz, user enumeration Per-object ownership checks, pinned JWT algs, generic login errors (02)
Probe — config Open CORS, missing headers, weak TLS, default creds Strict CORS, security headers, TLS 1.2+, no defaults (03)
Probe — abuse No rate limits, unbounded inputs, mass assignment, SSRF Rate limit, bound sizes, allow-list URLs (04, 05)
Exploit Chain small flaws into data theft / account takeover Defense in depth — no single failure is catastrophic

The tools defenders should also run

Run the same scanners attackers do — on your own systems, before they do. Find it first, fix it first.

Category Tool Use
SAST (code) bandit, semgrep Insecure patterns in your source
SCA (deps) pip-audit, Dependabot Known CVEs in dependencies
DAST (running app) OWASP ZAP Probe a live test instance for vulns
Secret scanning gitleaks, trufflehog Leaked keys in repo/history
Container/image trivy, grype Vulnerable OS/lib layers
TLS config testssl.sh, SSL Labs Weak ciphers/protocols
Authorization first. Only scan or test systems you own or have explicit, written permission to assess. Use intentionally-vulnerable practice apps (OWASP Juice Shop, DVWA) to learn techniques legally.

Threat modeling — design out the bugs (STRIDE)

The cheapest fix is a design that never has the flaw. Before building a feature, ask the STRIDE questions:

Threat Question Control
Spoofing Can someone fake an identity? Strong AuthN, MFA
Tampering Can data be altered in transit/at rest? TLS, signing, integrity checks
Repudiation Can they deny an action? Tamper-evident audit logs
Info disclosure Can data leak? Encryption, authz, least data
Denial of service Can it be exhausted? Rate limits, quotas, timeouts
Elevation Can someone gain more rights? Least privilege, authz checks

Six strategies to learn & institutionalize

① Shift security left

Add SAST/SCA/secret-scans to CI so issues are caught at PR time, not in prod.

② Threat model features

Run a quick STRIDE pass on every new design before you write code.

③ Secure code review

Make the checklists from pages 01–05 part of every PR review.

④ Least privilege by default

Scope tokens, DB roles, and cloud IAM to the minimum; review regularly.

⑤ Monitor & respond

Log security events, alert on anomalies, and rehearse an incident plan.

⑥ Patch & rotate

Keep deps current, rotate secrets, and re-test after changes.

Security isn't a gate at the end — it's a thread through design, code, build, test, release, and operations.

Master pre-deploy checklist

  • All inputs validated (Pydantic); all queries parameterized; no shell=True.
  • Auth on every route; object-level ownership enforced; JWT algs pinned.
  • Secrets out of code; TLS enforced; security headers + strict CORS set.
  • Rate limits, body-size caps, pagination, and timeouts in place.
  • Deps hash-locked & scanned; outbound URLs allow-listed (SSRF-safe).
  • Debug off; generic errors; security events logged & alerted.
  • SAST/SCA/secret-scan green in CI; DAST run against staging.
  • Incident response plan & backups tested; least-privilege IAM reviewed.
The mindset to carry forward: you will never make an app "100% secure" — aim to make attacks expensive, noisy, and low-reward. Defense in depth + early detection beats any single perfect control.
