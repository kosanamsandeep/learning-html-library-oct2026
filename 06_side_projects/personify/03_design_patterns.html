1 · Repository

Intent: hide how data is stored behind a collection-like interface (add, get, get_by_key, update, remove). Services speak this vocabulary and never see SQL or BSON. 

# infra/data/repositories/mongo_repository.py
class MongoRepository(BaseRepository[TEntityModel]):
    def add(self, data):
        return self.context.insert_one(
            db_name=self.database, collection_name=self.collection,
            data=self._model_type().dump(obj=data))

    def get_by_key(self, key):
        _result = self.context.find_one(... key=key)
        return self._model_type().load(data=_result) if _result else None

The Postgres twin (postgres_repository.py) exposes the same method names but uses SQLAlchemy sessions and binary expressions. Identical interface, different engine — that's the power of Repository.

Tell-tale sign

Two classes with matching method signatures (add/get/remove…) over different databases = Repository pattern. Swap one for the other and callers don't change.

2 · Unit of Work

Intent: treat a set of changes as a single transaction. The UoW is a context manager that owns the session, hands out a repository, and decides commit vs. rollback when the block ends. 

# infra/data/unit_of_work/base_unit_of_work.py
class BaseUnitOfWork(Generic[T]):
    def __exit__(self, exc_type, exc_val, exc_tb):
        if exc_type is None:
            self.commit()       # clean exit -> persist
        else:
            self._logger.exception(exc_val)
            self.rollback()     # error -> undo everything
# infra/data/unit_of_work/postgres_unit_of_work.py
class PostgresUnitOfWork(BaseUnitOfWork[TSQLEntityModel]):
    def __init__(self, logger, db_adapter, model_type, scope):
        super().__init__(logger=logger, model_type=model_type)
        self._session = sessionmaker(db_adapter.engine)()  # fresh session per request
        self._repository = PostgresRepository(... session=self.session ...)

    def commit(self):   self.session.commit()
    def rollback(self): self.session.rollback()

Recall from Chapter 2 how the service uses it:

with self.unit_of_work as _uow:
    return _uow.repository.add(data=data)
# commit happens here, automatically, on a clean exit
A nuance worth noticing

The Mongo UoW's commit() / rollback() are intentionally no-ops — a single document write in MongoDB is atomic on its own, so there's no multi-statement transaction to manage here. The pattern is still applied for a uniform service interface.

3 · Factory

Intent: centralise the messy construction of an object graph. A UserServiceFactory knows how to build a fully-wired UserService — which UoW, which model, which logger — so handlers don't. 

# app/factory/build_user_service.py
class UserServiceFactory(BaseServiceFactory):
    def build(self, scope: str) -> UserService:
        _uow = PostgresUnitOfWorkFactory(bootstrap=self._bootstrap)\
                  .build(model_type=UserModel, scope=scope)
        return UserService(
            logger=self._bootstrap.logger,
            uow=_uow,
            model_type=UserModel)

There are two tiers of factory — one builds services, one builds units of work — so the wiring is composable. The handler just calls service_factory.build(scope=request_id).

4 · Adapter

Intent: wrap a third-party library behind your own interface so the rest of the app depends on your contract, not the vendor's. PyMongoAdapter wraps PyMongo; PostgresAdapter wraps SQLAlchemy; MinIO adapters wrap the S3 client. 

# infra/adapters/base_adapter.py
class BaseAdapter(ABC):
    '''Base Adapter for resources'''
    def __init__(self, logger): self._logger = logger
Adapter vs. Repository — what's the difference?

The adapter wraps the driver (raw connection, low-level calls). The repository wraps the adapter and speaks in domain models. Two layers of insulation: vendor → adapter → repository → service.

5 · Dependency Injection

Intent: objects receive their collaborators instead of creating them. Look at any constructor or handler initialize() — everything comes in as an argument. 

# interfaces/.../base_user_handler.py — DI via Tornado's initialize()
def initialize(self, logger, schema_method_validators,
               service_factory, query_argument_validator=None):
    self.logger = logger
    self.schema_method_validators = schema_method_validators
    self._service = service_factory.build(scope=self.request_id)

The route table in tornado_app.py is the place where the concrete dependencies are chosen. Everywhere else just consumes abstractions — which is exactly what makes the code unit testable with fakes.

6 · Generics / type parameters

Intent: write a base once, reuse it for every model. BaseGenericService[T], BaseRepository[T], and BaseUnitOfWork[T] are all parameterised over the entity type. 

# app/base_generic_service.py
T = TypeVar('T')
class BaseGenericService(Generic[T]):
    def _add(self, data):
        with self.unit_of_work as _uow:
            return _uow.repository.add(data=data)
    # _get, _get_by_key, _update, _remove ... all generic

UserService and ContactService inherit all five CRUD helpers for free — they only add the business methods (loginUserWithCredentials, getUserContacts, …).

7 · Template Method

Intent: the base class fixes the skeleton of an algorithm and lets subclasses fill in the blanks. BaseRequestHandler.prepare() always runs "set context → parse → validate"; each concrete handler only implements get/post. 

# the skeleton lives in the base; subclasses supply the verb method
def prepare(self):
    self._set_log_context()
    self._set_authentication_context()   # user handlers only
    self._parse_json_body()
    return super().prepare()

And the queryable variant adds one more abstract hook subclasses must implement:

class BaseUserQueryableRequestHandler(BaseUserRequestHandler):
    @abstractmethod
    def _process_query_arguments(self): raise NotImplementedError

8 · Strategy (schema-per-method)

Intent: pick an algorithm at runtime from a lookup. Each handler is given a schema_method_validators dict — {"POST": SignUpSchema, ...} — and prepare() selects the right validator for the current HTTP verb. 

def __get_method_schema(self):
    selected = self.schema_method_validators.get(self.request.method)
    if selected is None:
        raise HTTPError(status_code=HTTPStatus.INTERNAL_SERVER_ERROR, ...)
    return selected

Adding a PUT to an endpoint is just adding a key to the dict — no if/elif ladder to edit.

Check yourself

What's the difference between an Adapter and a Repository here?
The adapter wraps the raw driver (pymongo/sqlalchemy). The repository wraps the adapter and exposes domain-model CRUD. Repository depends on adapter, not the other way round.
Why is the Mongo Unit of Work's commit() empty?
A single-document Mongo write is atomic by itself, so there's no multi-statement transaction to commit/rollback. The pattern is still implemented to keep one uniform service interface across both stores.
You need to support a new entity, NoteModel, in Postgres. What do you write?
A NoteModel (domain), a NoteService extending BaseGenericService[NoteModel] for any custom rules, and a NoteServiceFactory. The generic repository + Postgres UoW are reused — minimal new code.
Which pattern lets you add a PUT handler without an if/elif chain?
Strategy via the schema_method_validators dict — you add a "PUT" key mapping to its schema, and prepare() picks it automatically.
