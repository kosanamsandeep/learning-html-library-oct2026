Chapter 1 · The Mental Model

The Architecture

Before reading a single handler, understand the shape of the building. Personify-Service uses Domain-Driven Design arranged as four concentric layers. Get this picture in your head and every file suddenly has an obvious "home".

In this chapter

1 · The four layers

Everything lives under src/ split into four packages. Each has one job and talks only to its neighbours through clear contracts.

interfaces/

Delivery layer

The only layer that knows about HTTP and Tornado. Handlers, marshmallow schemas, and Swagger docs. It translates the outside world into plain Python calls.

app/

Application layer

The use-cases: UserService, ContactService. They orchestrate domain + infrastructure but contain no framework or database code.

domain/

Domain layer

The models — UserModel, ContactModel — and their base classes. Pure data + validation. The heart that everything else serves.

infra/

Infrastructure layer

The "how": database adapters, repositories, unit-of-work, token/hash generators, parsers, validators, logging, constants. All the messy real-world details.

Four layers, four responsibilities. Notice that domain sits in the middle — everyone depends on it; it depends on no one.

2 · The dependency rule — the one rule to remember

The single most important idea in this whole codebase:

The Dependency Rule

Dependencies point inward. Outer layers (HTTP) may import inner layers (services, domain). Inner layers must never import outer ones. The domain knows nothing about Tornado, MongoDB, or JSON.

This is what makes the service framework-agnostic. You could throw away Tornado and bolt on FastAPI by rewriting only interfaces/ — the services and domain wouldn't change a line. That testability and replaceability is the entire payoff.

Arrows only ever flow toward the domain. When you read an import that breaks this, you've found a smell.

3 · The folder map

Here is the tree, annotated so you know what each folder is for:

src/
├── server.py            # entry point — starts the Tornado IOLoop
├── bootstrap.py         # composition root — wires every adapter once
├── tornado_app.py       # the route table (URL → handler + injected deps)
│
├── interfaces/          # DELIVERY — the only HTTP-aware layer
│   └── http/
│       ├── tornado/
│       │   ├── handlers/    # base_handler, signup, signin, contact…
│       │   └── schemas/     # marshmallow request/response DTOs
│       └── swagger/         # OpenAPI doc generation
│
├── app/                 # USE-CASES — services orchestrate work
│   ├── base_generic_service.py
│   ├── user_service.py · contact_service.py
│   └── factory/             # builders that wire a service per request
│
├── domain/              # MODELS — pure data + validation
│   ├── base_model.py · base_sql_model.py
│   └── user_model.py · contact_model.py
│
└── infra/               # THE "HOW" — all real-world detail
    ├── adapters/        # wrap pymongo / sqlalchemy / minio
    ├── data/
    │   ├── repositories/    # CRUD per store (mongo, postgres)
    │   └── unit_of_work/    # transaction boundary + its factories
    ├── generator/       # hashing, jwt token, identity (uuid)
    ├── validators/      # query-argument validation
    ├── parser/ · transform/ · builders/
    ├── logging/         # structured logger with request context
    └── constants/       # _string, _url, _type — no magic values
Reading shortcut

When you open an unfamiliar file, first ask "which layer am I in?". That alone tells you what it's allowed to do and what it should delegate elsewhere.

4 · Where the program starts

Three files form the startup spine. Read them in this order:

  1. server.py — the ignition

    Tiny by design. It builds the application and hands it to Tornado's event loop. Nothing business-y happens here.

  2. bootstrap.py — the composition root

    The single place where all infrastructure is created and connected: Postgres engine, Mongo client, MinIO client, logger. It checks each is reachable and fails fast with a ConnectionError if not. After this runs, the app is fully wired.

  3. tornado_app.py — the route table

    Maps each URL to a handler and injects that handler's dependencies (logger, schema validators, the right service factory). This is dependency injection done by hand — no magic.

Composition root, defined

A composition root is the one spot in an app where you assemble the object graph. Keeping it in bootstrap.py means every other file can stay ignorant of how things are constructed — they just receive what they need.

5 · Why bother with all this structure?

Benefit What it buys you
Testability Services take their dependencies as arguments, so tests pass in fakes — no real DB needed for unit tests.
Replaceability Swap MongoDB for another store by writing one new repository + adapter. Services don't notice.
Readability Every concept has exactly one home. New contributors find code by responsibility, not by guessing.
Parallel work One person edits handlers while another edits repositories — they meet only at stable interfaces.

The cost is more files and indirection. For a throwaway script that's overkill; for a service meant to live and grow, it pays for itself quickly.

Check yourself

Which layer is allowed to import tornado?
Only interfaces/ (the delivery layer). If you see Tornado imported inside app/, domain/, or infra/, the dependency rule has been violated.
Where would code that talks to MongoDB live?
In infra/ — specifically an adapter wrapping PyMongo plus a repository that exposes CRUD. Services never touch PyMongo directly.
If you replaced Tornado with FastAPI, which layers change?
Only interfaces/. The whole point of the dependency rule is that services and domain are framework-agnostic, so they stay untouched.
What is the job of bootstrap.py?
It's the composition root: it creates and connects every piece of infrastructure once at startup and fails fast if a dependency is unreachable.
