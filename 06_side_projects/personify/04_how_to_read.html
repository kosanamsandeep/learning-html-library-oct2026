Chapter 4 · Don't Get Lost

How to Read This Codebase

A big DDD tree can feel intimidating. The trick is not to read it folder-by-folder, but to follow one feature end-to-end. This chapter gives you a concrete reading order and a feature trail you can repeat for any endpoint.

In this chapter

  2. Follow one feature: the "sign in" trail
  3. Reading cheats & conventions

1 · The recommended reading order

Open files in this sequence the first time. It goes from the outside in, matching how a request actually travels.

  1. README + docker-compose

    Get the elevator pitch and see which services spin up (app, Postgres, Mongo, MinIO, nginx). You learn the runtime shape before any code.

  2. server.py → bootstrap.py → tornado_app.py

    The startup spine from Chapter 1. The route table is your map: every URL and the handler it points to.

  3. Pick ONE route and open its handler

    e.g. signin_handler.py. Read only its post() — resist wandering.

  4. Jump to the service it calls

    The handler calls self._service.something(...). Open that service method and read the business rule.

  5. Drop into the base service + UoW + repository

    See how _add/_get route through the with unit_of_work block to the repository, then the adapter, then the driver.

  6. Glance at the schema + model

    Open the marshmallow schema and the domain model to see the data shape the whole trail moves around.

The golden rule of code reading

Follow one thread to the end before starting another. Breadth-first reading of a big codebase is how you get lost; depth-first along a single feature is how you build a mental model.

The destination — what sign-in actually does

# app/user_service.py
def loginUserWithCredentials(self, data) -> Union[str, List[str]]:
    _findUser = self.findByUserName(userName=data.username)   # repository read
    if _findUser is not None:
        if HashGenerator.is_valid(_findUser.password, data.password):
            _encode = {FieldNameConstants.USER_ID: str(_findUser._id)}
            return TokenGenerator.encode(data=_encode)       # issue JWT
        _errors.append(MessagesConstants.MSG_INVALID_PASSWORD)
    else:
        _errors.append(f'Account with {data.username} does not exist')
    return _errors

That one method touches the repository (read), the hash generator (verify), and the token generator (sign) — a perfect cross-section of the whole architecture.

3 · Reading cheats & conventions

When you see… It means…
Base* prefix A reusable parent — read it once, then every subclass is just "this + a few methods".
build_*.py / *Factory Object construction — go here to see how something is wired, not what it does.
with self.unit_of_work as _uow You're inside a transaction; commit/rollback is automatic.
self._model_type().dump()/.load() marshmallow (de)serialisation between Python objects and DB/JSON.
infra/constants/_string.py The dictionary of every literal — no magic strings scattered around.
initialize(self, ...) Tornado's DI hook — the handler's dependencies arrive here.
A docstring full of responses: 200/400/500 Swagger/OpenAPI source — the API contract is documented inline.
Use the constants file as an index

Stuck on what a field or message is? infra/constants/_string.py, _url.py and _type.py are effectively the project's glossary. Skimming them early pays off.

4 · Run it yourself

Nothing cements understanding like watching it boot. The repo is container-first:

# bring up app + postgres + mongo + minio (+ nginx)
docker compose up --build

# then open the interactive API docs
# Swagger UI is generated from the handler docstrings
http://localhost:<port>/swagger

# run the test pyramid locally
pytest            # unit + integration + e2e
mypy src          # static type checking
ruff check src    # linting
A powerful exercise

Open Swagger, sign up, sign in, copy the JWT, and create a contact — while watching the logs. You'll see the request-id context, the layer hops, and the status codes you read about in Chapter 2 happen live.

Exact ports, env vars and commands live in the repo's README and compose files — check there, as they may differ from this snapshot.

Check yourself

You want to understand "list contacts". What's your first file, and why?
tornado_app.py to find the route → its handler's get(). Start at the route table and follow the thread inward; don't start by browsing infra/.
You hit a class named BaseUserQueryableRequestHandler. What do you do?
Read the base once to learn the shared skeleton (auth + query-arg validation), then treat every subclass as "that skeleton plus a verb method". You won't re-read the plumbing each time.
Where do you look to learn the exact JSON a request expects?
The marshmallow schema in interfaces/http/tornado/schemas/ for that endpoint — and the Swagger docstring on the handler method.
