Chapter 5 · Where Do You Stand?

Learnings & Self-Assessment

You've seen the architecture, the lifecycle, the patterns, and how to navigate. Now turn it into your skill. This chapter lists what to take away, the caveats a senior eye would flag, and a level-by-level self-check so you can honestly answer "where do I stand?".

1 · What you can learn from this code

Layering with intent

How to split a service into delivery / use-case / domain / infrastructure so each part is independently understandable and testable.

The dependency rule in practice

Keeping the framework at the edge so the core stays portable — a habit that survives long after Tornado is forgotten.

Patterns as vocabulary

Repository, UoW, Factory, Adapter, DI — not as academic trivia but as the actual joints of a working system.

Polyglot persistence

Choosing Postgres for relational users and Mongo for flexible contacts behind one uniform service interface.

Thin handlers, rich services

Pushing logic out of the transport layer so endpoints stay readable and rules stay testable.

Quality as a gate

Tests (unit/integration/e2e), mypy, ruff, and container parity as first-class parts of the project, not afterthoughts.

2 · Best-practices checklist

These are the habits worth copying into your own projects. Tick the ones you already understand well enough to explain to someone else.

  • Single composition root — wire everything in one place (bootstrap.py), fail fast if infra is unreachable.
  • Dependency injection everywhere — pass collaborators in; never new them deep inside business code.
  • Repository per store — a stable CRUD interface that hides the database engine.
  • Unit of Work as a context manager — make the with block the transaction boundary.
  • Generic base classes — write CRUD once, reuse per model with TypeVar.
  • Schema validation at the edge — reject bad input in prepare() before any logic runs.
  • Centralised constants — no magic strings; one glossary file.
  • Structured logging with request context — every log line carries the request id.
  • API versioning — /api/v1 so you can evolve without breaking clients.
  • Docs from code — Swagger generated from handler docstrings stays in sync.
  • Container parity — same compose stack for dev and prod-like runs.
  • Test pyramid — unit + integration + e2e, plus type-checking and linting.

3 · Caveats — what's demo, not production

Reading critically is a senior skill. A learning repo makes simplifications you should be able to spot. Here's what a careful reviewer would flag:

Hard-coded secrets

generator/token.py ships a literal JWT_SECRET = "dummy-secret" and generator/hashing.py uses a fixed salt 'dummy' with only 100 iterations. In production these must come from secrets/config, the salt must be per-user and random, and the iteration count must be far higher (or use a purpose-built password hash like Argon2/bcrypt).

A couple of rough edges

Some __enter__ log lines mix str.format with positional braces (a cosmetic bug), and a few service methods carry TODOs (e.g. scoping a contact query by user id). None break the teaching value — but noticing them is exactly the muscle you're building.

Why caveats are a feature

Being able to say "the architecture is excellent, but the crypto config is demo-grade" is a sign you've moved from following the code to judging it. That's the level this guide is aiming for.

4 · Self-assessment: rate your level

Read each level honestly. Where do you stop being able to do everything described? That's roughly where you stand today.

Level 1 · Aware

You can name the layers

You can point at interfaces / app / domain / infra and say what each is for, and you understand "dependencies point inward". You can find where an endpoint lives.

Level 2 · Tracer

You can follow a request end-to-end

Given an endpoint, you can trace handler → service → unit of work → repository → adapter → DB without help, and explain where validation, auth, and the transaction boundary happen.

Level 3 · Pattern-fluent

You can name and justify the patterns

You can identify Repository, Unit of Work, Factory, Adapter, DI, Generics, Template Method and Strategy in the source, and explain why each is used and what it buys.

Level 4 · Contributor / Critic

You can extend and critique it

You could add a new entity (model + service + factory) reusing the generic base, write tests for it, and spot the demo-grade shortcuts (hard-coded secret, weak hashing) that need fixing for production.

Turn the self-check into action

If you're at Level 2, do the Level 3 work: open each pattern in Chapter 3 and re-find it in the source. If you're at Level 3, attempt the Level 4 exercise below.

5 · Sharpen it further

  1. Trace a second feature unaided

    Pick DELETE /contact/{id} and map every file it touches — no peeking at Chapter 4.

  2. Add an imaginary entity on paper

    Sketch the NoteModel + NoteService + NoteServiceFactory you'd write, and which generic pieces you'd reuse.

  3. Fix one caveat for real

    Move the JWT secret to config and make the password salt per-user. Watch which layers you have to touch — ideally just infra/generator and config.

  4. Explain it out loud

    Teach the architecture to someone (or rubber-duck it). If you can explain the dependency rule and the UoW in your own words, you're solid.

You've finished the guide

You now have the map, the lifecycle, the pattern vocabulary, a reading method, and an honest gauge of your level. That's a genuinely strong understanding of a real DDD service — keep the source open and keep tracing.
