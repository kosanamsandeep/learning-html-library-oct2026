Practice Lab · Think Like an Architect

Architecture Thinking Scenarios

Seventy real-world situations — ten per concept — drawn from many domains (banking, e-commerce, IoT, healthcare, social, logistics). For each, decide where the logic belongs and which pattern applies before you reveal the answer. The goal: make the right architectural call instinctive.

How to practise

Read each scenario and answer out loud (or on paper): Which layer? Which pattern? Why? Only then click “Reveal the answer” to cross-check. If you disagree, re-read the relevant chapter — disagreeing well is itself progress. Don’t rush; reasoning beats recall.

1

Domain Models

Pure data + invariants · no infrastructure · the heart of the system
1Banking

An Account must never hold a negative balance. Where do you enforce “balance ≥ 0” — model, service, or repository?

Reveal the answer & reasoning
Domain model

An invariant — a rule that must always hold — belongs with the data it protects. The model should refuse to enter an invalid state (raise on a debit that would go negative). The service orchestrates the operation; the repository only persists.

Principle: a model guards its own consistency, so no caller can create an illegal object.

2E-commerce

Money values show rounding bugs because prices are passed around as floats. How do you model an amount of money?

Reveal the answer & reasoning
Value object

Introduce a Money(amount, currency) value object in the domain that stores integer minor units (cents) and owns its arithmetic/rounding. It’s immutable and compared by value, not identity.

Principle: wrap primitives that have rules into value objects so the rules live in one place and can’t be bypassed.

3Healthcare

A Patient stores an SSN that must never appear in API responses, but the name is public. How do you keep the secret field from leaking?

Reveal the answer & reasoning
Schema at the edge

The domain model may hold all fields, but what gets serialized is the schema’s job (marshmallow dump/load at the interface layer). Use a response schema that simply doesn’t expose the SSN. Don’t rely on the model’s shape for security.

Principle: separate the persistence/domain shape from the transport DTO so you control exposure per direction.

4IoT

Sensor readings have wildly different fields per device type, while user accounts are rigid and relational. Postgres model or Mongo model for each?

Reveal the answer & reasoning
Choose by shape

Readings = flexible/document → a Mongo model (like ContactModel). Users = strong schema + integrity → a Postgres model (like UserModel). Personify is polyglot for exactly this reason.

Principle: let the data’s shape and consistency needs pick the store; the model abstracts the choice from services.

5Social

Every Post needs created_at / updated_at set on write, and you keep forgetting it in places. Where should timestamping happen?

Reveal the answer & reasoning
One consistent place

Pick a single home: either a base model default or the service on create/update (Personify’s ContactService.addUserContact stamps both). What matters is it’s not scattered across handlers.

Principle: cross-cutting fields need one authoritative write point to stay consistent.

6Orders

Should a new Order get its id from the application (UUID) or from the database auto-increment? Which, and why does it matter?

Reveal the answer & reasoning
App-generated UUID

Generating the id in the app (Personify has an IdentityGenerator) lets you know the id before insert, enables idempotency and cross-store references, and avoids coupling identity to a single DB’s insert mechanism.

Principle: stable, app-controlled identity is friendlier to distributed systems than DB-assigned sequence ids.

7Inventory

A teammate adds Product.reserve_stock() that opens a repository and writes to the DB inside the model. Is that the right place?

Reveal the answer & reasoning
Smell — move it

No. A model must not depend on infrastructure (the dependency rule). Pure behaviour like product.can_fulfill(qty) is fine on the model; anything that touches a repository belongs in a service.

Principle: rich models are good, but “rich” means pure logic, not database access.

8Loyalty

A Customer.tier (Bronze/Silver/Gold) is determined by their points. Store the tier, or compute it?

Reveal the answer & reasoning
Compute (derive)

Derive tier from points via a method/property so there’s one source of truth. Only persist a denormalised copy if you must query/sort by it — and then recompute it whenever points change.

Principle: avoid two fields that can disagree; prefer a single source of truth.

9Logistics

An identical Address block (street, city, zip, country) is needed inside both Customer and Warehouse. How do you avoid duplicating the fields?

Reveal the answer & reasoning
Composition

Model Address once as a reusable value object / embedded model and compose it into both. Duplicating four fields in two models invites drift.

Principle: composition over duplication keeps shared structure in one definition.

10Versioning

An old mobile client still sends a legacy contact JSON shape that no longer matches your model. Where do you translate the old shape into the current model?

Reveal the answer & reasoning
At the boundary

Adapt incoming shapes at the edge — in the schema or a transform / parser in infra (Personify has both folders). Keep the domain model on the latest shape; never pollute it with legacy branches.

Principle: translate at boundaries so the core stays clean and singular.

2

Services / Use-cases

Orchestrate domain + infra · own business rules · framework-agnostic
1Banking

A transfer must debit one account and credit another, all-or-nothing. Which component coordinates it, and how is atomicity guaranteed?

Reveal the answer & reasoning
Service + one UoW

A TransferService use-case wraps both writes in a single Unit of Work so they commit or roll back together. Splitting them across two services with separate transactions risks half a transfer.

Principle: the use-case defines the consistency boundary; the UoW enforces it.

2Auth

Passwords must be hashed before they’re stored. Handler, model, or service?

Reveal the answer & reasoning
Service

The service (Personify’s UserService.createUser) calls the HashGenerator then persists. The handler only shapes HTTP; the model has no infra dependency.

Principle: orchestrating infra helpers around a domain operation is a use-case responsibility.

3E-commerce

Placing an order must (a) save the order, (b) decrement stock, and (c) send a confirmation email. Which of these belong inside the same transaction?

Reveal the answer & reasoning
Separate consistency from side-effects

Save order + decrement stock go in the same UoW (they must agree). The email is a side effect — do it after commit (or via an outbox/queue), never inside the transaction, or a mail failure rolls back a valid order.

Principle: only data that must be consistent shares a transaction; external effects happen after commit.

4Auth

A handler builds and signs a JWT inline before returning it. Is that a problem?

Reveal the answer & reasoning
Move to service

Token issuance is a use-case concern. Personify’s loginUserWithCredentials verifies the password and returns the token; the handler just maps it to a response.

Principle: handlers translate HTTP; decisions and credentials live in services.

5Reporting

A dashboard endpoint needs user data from Postgres and activity data from Mongo in one response. Where do you combine them?

Reveal the answer & reasoning
Service composes repositories

A service may hold multiple repositories / UoWs and stitch their results together. Cross-store coordination is exactly what a use-case is for.

Principle: the service is the only place allowed to know that two stores combine into one answer.

6Accounts

“Username must be unique.” Is that schema validation or service logic?

Reveal the answer & reasoning
Mostly service

Format checks (length, non-empty) belong in the schema. Uniqueness needs the database, so it’s a service rule — Personify lets the DB’s unique constraint fire and catches IntegrityError in createUser.

Principle: rules that need stored data can’t be validated at the edge; they live in the use-case.

7API design

getUserContacts could return ready-made JSON or domain models. What should a service return?

Reveal the answer & reasoning
Domain models

Return List[ContactModel]; the handler/schema does the dump to JSON. If the service returned JSON it would be coupled to the transport.

Principle: keep services transport-agnostic so the same use-case serves HTTP, a CLI, or a worker.

8Payments

“Create payment” may be retried by a flaky client, risking double charges. How do you design the service to be idempotent?

Reveal the answer & reasoning
Idempotency key in the use-case

Accept a client-supplied idempotency key; the service checks the repository for an existing operation with that key and returns the prior result instead of creating a duplicate.

Principle: idempotency is a business guarantee, so it’s designed into the service, not bolted onto the handler.

9SaaS

New rule: VIP users may add unlimited contacts; everyone else is capped at 50. Where does this rule live?

Reveal the answer & reasoning
Service

It needs a count from the repository and the user’s tier — a business rule the service evaluates before calling _add. Not the handler (HTTP) and not the model (no data access).

Principle: policy that depends on stored state is use-case logic.

10Testing

You must unit-test createUser without spinning up a database. What makes that possible here?

Reveal the answer & reasoning
Dependency injection

The service receives its Unit of Work / repository as constructor arguments, so a test passes in a fake. No real DB needed; you assert on behaviour (password hashed, id returned).

Principle: injected collaborators are the seam that makes use-cases unit-testable.

3

Repositories

Collection-like data access · hide the query language · return domain models
1Analytics

You need “users created in the last 7 days.” Add a method to the repository, or build the query in the service?

Reveal the answer & reasoning
Repository method

The repository owns query construction; expose an intent-named method and let the service call it. The service should express what, not how.

Principle: no SQL/BSON leaks into services; query knowledge stays in the repository.

2ORM leak

A repository returns raw SQLAlchemy row objects straight to the service. What’s wrong?

Reveal the answer & reasoning
Leaky abstraction

It leaks the ORM across the boundary, coupling the service to SQLAlchemy. The repository should map rows to domain models (Personify does _model_type().load(...)).

Principle: the repository’s job is to keep persistence types from escaping upward.

3Migration

Leadership wants contacts moved from MongoDB to PostgreSQL. If the repository is well-designed, what has to change?

Reveal the answer & reasoning
Just a new repository

Write a PostgresRepository with the same method names and swap the wiring. Services stay untouched because they depend on the interface, not the engine.

Principle: a stable repository interface makes the storage engine replaceable.

4Side effects

Someone makes the repository’s add() also fire a “welcome” email. Acceptable?

Reveal the answer & reasoning
No — single responsibility

Repositories do data access only. The email is a service-level side effect (and should follow a successful commit). Mixing them makes the repository unpredictable and hard to test.

Principle: one reason to change per class — persistence, not notifications.

5Paging

A handler receives offset and limit for a contact list. Which layer actually applies the pagination?

Reveal the answer & reasoning
Repository

The repository’s get(filter_by, skip_to, limit_by) translates to .offset().limit() (SQL) or Mongo skip/limit — exactly how Personify does it. The handler validates the numbers; the service passes intent.

Principle: turning paging parameters into store-specific calls is the repository’s job.

6Testing

You want fast tests with no database at all. Can you build an in-memory repository?

Reveal the answer & reasoning
Yes — same interface

Implement a dict-backed repository exposing the same add/get/get_by_key/update/remove methods and inject it. The service can’t tell the difference.

Principle: because the interface is the contract, any conforming implementation is substitutable.

7CRM

You need “contacts in city X whose birthday is this month.” Where is that filter compiled?

Reveal the answer & reasoning
Repository compiles it

The service expresses the filter as plain criteria; the repository turns it into binary expressions (Postgres) or a filter dict (Mongo), like Personify’s _compile_filter_by.

Principle: translation of criteria → engine syntax stays inside the repository.

8Reuse

Two different services both need “find by email.” Duplicate the query in each?

Reveal the answer & reasoning
Define once, reuse

Put find_by_email once on the repository (or a shared base) and have both services call it. Duplicating queries invites them to drift apart.

Principle: DRY at the data layer; queries have a single home.

9Leak

A repository adds get_session() so callers can run ad-hoc queries. Good idea?

Reveal the answer & reasoning
No — it breaks the wall

Exposing the session lets callers bypass the repository and couple to the engine + transaction. Expose intent-revealing methods instead; keep the session private.

Principle: an abstraction you can reach around isn’t an abstraction.

10Compliance

Policy changes: deleting a contact should keep the row but mark deleted=true (soft delete). Where does this change, and do callers change?

Reveal the answer & reasoning
Inside the repository only

Change remove() to perform an update (and filter out deleted rows in reads). The service still calls remove; the storage detail stays hidden.

Principle: changing how data is stored shouldn’t ripple into callers.

4

Unit of Work

Transaction boundary · commit on success, rollback on error · per-request scope
1Banking

Two writes must both succeed or both fail. How do you structure the boundary?

Reveal the answer & reasoning
One with block

Wrap both repository calls in a single with unit_of_work as uow:. Commit happens on a clean exit; an exception triggers rollback. The block is the transaction.

Principle: co-locate writes that must be atomic in one UoW scope.

2Code review

A reviewer asks “where do we call commit()?” What’s the answer in this architecture?

Reveal the answer & reasoning
Nowhere explicit

The UoW’s __exit__ commits on a clean exit (Personify’s base UoW does this). Services never sprinkle commit() calls.

Principle: centralising commit/rollback in __exit__ removes a whole class of “forgot to commit/rollback” bugs.

3Scaling

One database session is reused across many unrelated operations in a long request. What’s the risk?

Reveal the answer & reasoning
Fat / stale transaction

Long-held sessions hold locks and accumulate state. Prefer a fresh UoW/session per request scope — Personify builds one per request_id.

Principle: short, request-scoped transactions reduce contention and surprises.

4MongoDB

A Mongo operation inserts a single document. Do you still need commit/rollback?

Reveal the answer & reasoning
No-op, kept for uniformity

A single-document write is atomic on its own, so Personify’s Mongo UoW commit/ rollback are intentionally empty. The pattern stays so services have one uniform interface across stores.

Principle: consistent shape across stores beats special-casing the service code.

5Failure

An exception is thrown after the first of three writes. What happens to the partial work?

Reveal the answer & reasoning
Rolled back

__exit__ sees a non-null exc_type and calls rollback(); nothing persists. Atomicity is preserved automatically.

Principle: the context manager guarantees cleanup on both the happy and sad paths.

6Banking

You must read a balance, then debit based on it, without another request sneaking in. Same UoW or two?

Reveal the answer & reasoning
Same UoW

Do the read and the write inside one transaction so you act on consistent data (and can lock if needed). Reading in one transaction and writing in another opens a race window.

Principle: check-then-act must share a transaction to stay correct.

7Design

Service A opens a UoW, then calls Service B which opens its own UoW. What’s the concern?

Reveal the answer & reasoning
Two boundaries can’t roll back together

Independent nested transactions defeat atomicity. Either pass one UoW/session down, or coordinate at a single use-case so there’s one boundary.

Principle: one logical operation should map to one transaction.

8Wiring

Why does the UoW own the repository rather than the service creating a repository itself? What would break otherwise?

Reveal the answer & reasoning
Shared session

The UoW hands out a repository bound to its session, so all writes land in the same transaction. A separately-created repository could use a different session and escape the boundary.

Principle: repository + transaction must share one session to be atomic.

9Ops

Connections are leaking; sessions never close. Where do you fix the lifecycle?

Reveal the answer & reasoning
UoW __exit__

The UoW should close/clean up after commit/rollback (Personify’s Postgres UoW closes the session on exit). Centralising lifecycle there means callers can’t forget it.

Principle: own the resource’s full lifecycle in one place.

10Batch

An import writes 10,000 rows inside a single UoW. Any concern?

Reveal the answer & reasoning
Boundary too big

One huge transaction means memory pressure and long-held locks. Chunk the work into batches, each its own UoW/commit.

Principle: a transaction boundary can be too large; size it to the real unit of consistency.

5

Factories

Centralise construction · wire the object graph · per-request scope
1Smell

A handler does UserService(logger=…, uow=PostgresUnitOfWork(…)) inline. What’s the better approach?

Reveal the answer & reasoning
Use a factory

Construction logic leaks into the transport layer. A UserServiceFactory.build(scope) hides the wiring; the handler just asks for a service.

Principle: the handler should know what it needs, not how to build it.

2Design

Personify has a service factory and a Unit-of-Work factory. Why two tiers?

Reveal the answer & reasoning
Composable construction

The service factory delegates UoW creation to the UoW factory. Each factory owns one slice of the graph, so wiring stays small and reusable.

Principle: layer your construction the way you layer your runtime.

3Testing

In tests you want services built with a fake UoW, without editing the service. What’s the seam?

Reveal the answer & reasoning
The factory

Provide a test factory (or a fake bootstrap) that builds the service with stubs. The factory is the single place where “real vs fake” is decided.

Principle: centralised construction gives you one place to substitute test doubles.

4Config

A flag chooses Postgres vs Mongo persistence for a feature at runtime. Where does that choice belong?

Reveal the answer & reasoning
In the factory

The factory reads config and builds the matching UoW/repository. Business code receives a ready service and never branches on the store.

Principle: push implementation choices to construction time, out of the use-case.

5Wiring

Personify’s factories take the bootstrap object. Why pass it in?

Reveal the answer & reasoning
Access shared singletons

The bootstrap (composition root) holds the long-lived logger and DB clients. Factories read from it to wire per-request objects, avoiding globals.

Principle: create expensive things once (bootstrap), assemble cheap per-request things in factories.

6Anti-pattern

A teammate proposes a global get_service() callable from anywhere. What’s the downside?

Reveal the answer & reasoning
Service locator

It hides dependencies and makes tests hard (callers reach into a global). Prefer an explicit factory injected into the handler, so dependencies are visible.

Principle: make dependencies explicit; avoid hidden global lookups.

7Scope

Each request builds a fresh service via build(request_id). Why per-request rather than one shared instance?

Reveal the answer & reasoning
Isolation

A fresh service means a fresh UoW/session and no shared mutable state across concurrent requests — avoiding cross-talk and stale transactions.

Principle: request-scoped construction keeps concurrency safe.

8Extending

You’re adding a brand-new NoteService. What construction code must you write?

Reveal the answer & reasoning
A new factory + a route

Write a NoteServiceFactory (reusing a UoW factory) and register the handler in the route table. The generic base service/repo are reused.

Principle: the pattern scales by adding a factory, not editing existing ones.

9Performance

A factory’s build() makes a network call to fetch config on every request. Concern?

Reveal the answer & reasoning
Construction should be cheap

Expensive one-time setup belongs in bootstrap, cached for reuse. A factory called per request must stay fast.

Principle: separate “build once, expensive” from “build often, cheap.”

10Contract

BaseServiceFactory.build() just raises NotImplementedError. Why have it at all?

Reveal the answer & reasoning
Defines the contract

The abstract base fixes the build(scope) signature every concrete factory must honour, so handlers can depend on the abstraction.

Principle: an abstract method documents and enforces a uniform construction interface.

6

Adapters

Wrap third-party drivers · anti-corruption layer · keep vendors at the edge
1Driver

PyMongo calls appear directly inside a repository. What’s the cleaner structure?

Reveal the answer & reasoning
Wrap it in an adapter

Put a PyMongoAdapter exposing your own methods (insert_one, find…); the repository depends on the adapter, not the raw driver.

Principle: insulate the codebase from a vendor’s API surface.

2Storage

You’re migrating object storage from MinIO to AWS S3. If adapters are right, what changes?

Reveal the answer & reasoning
Only the storage adapter

Swap the adapter implementation behind the same interface; repositories and services are untouched (MinIO being S3-compatible makes it even smaller).

Principle: vendor swaps stay contained to one adapter.

3Leak

An adapter returns a pymongo.Cursor up to the repository. Problem?

Reveal the answer & reasoning
Vendor type leak

Returning a driver type re-couples callers to PyMongo. The adapter should return plain data (lists/dicts) so the repository maps to models.

Principle: adapters convert vendor types into neutral data at the boundary.

4Reliability

You need retry-with-backoff on transient DB connection errors. Which layer owns that?

Reveal the answer & reasoning
The adapter

Connection-level concerns (retries, pooling, timeouts) belong with the thing that owns the driver — the adapter. Services and repositories shouldn’t know.

Principle: cross-cutting connection behaviour lives where the connection lives.

5Anti-corruption

A third-party SMS SDK throws its own exception types all over your code. How do you contain it?

Reveal the answer & reasoning
Adapter as anti-corruption layer

The adapter catches SDK-specific exceptions and re-raises your error types, so the rest of the app speaks one vocabulary.

Principle: translate foreign concepts/errors into your own at the edge.

6Resources

Bootstrap creates one Mongo client and shares it with adapters. Why not create a client per request?

Reveal the answer & reasoning
Pooling / singleton

Clients are expensive and manage their own pools. Create once in bootstrap and let the adapter wrap the shared client; per-request clients waste connections.

Principle: share heavyweight connections; don’t rebuild them per request.

7Testing

You want to test a repository without a real database. How does the adapter help?

Reveal the answer & reasoning
Swap a fake adapter

Because the repository depends on the adapter interface, inject a fake adapter that returns canned data. The adapter boundary is your mock seam.

Principle: every clean boundary doubles as a test seam.

8Security

MinIO needs admin rights to create buckets at startup but only limited rights at runtime. One adapter or two?

Reveal the answer & reasoning
Two — least privilege

An admin adapter for setup and an app-scoped adapter for day-to-day use, each with appropriate credentials. Don’t run normal traffic as root.

Principle: separate privileges by purpose to limit blast radius.

9Leak

An adapter exposes get_raw_connection() for “flexibility.” Concern?

Reveal the answer & reasoning
Bypasses the abstraction

Callers can now couple to the driver and dodge the adapter’s guarantees. Expose intent methods, not the raw connection.

Principle: don’t provide escape hatches that undo your insulation.

10Growth

Analytics now needs a ClickHouse column store added. What’s the minimal, non-invasive way?

Reveal the answer & reasoning
New adapter + repository

Add a ClickHouse adapter and a repository implementing the existing interfaces; services consume them unchanged. New tech is additive, not invasive.

Principle: adapters make new infrastructure a plug-in, not a rewrite.

7

Interfaces · DI · Validation

Thin handlers · inject dependencies · validate & auth at the edge
1Smell

A handler creates its own logger and database client inside itself. What’s wrong, and the fix?

Reveal the answer & reasoning
Hard dependencies

Self-created collaborators can’t be swapped in tests. Inject them via initialize() (Personify passes logger, schema validators, and a service factory).

Principle: receive dependencies; don’t manufacture them in the transport layer.

2Validation

Where should the JSON request body be validated? Before or after business logic, and in which layer?

Reveal the answer & reasoning
Schema, in prepare()

Validate with a marshmallow schema at the edge, in prepare(), before any use-case runs. Reject malformed input early with a structured 400.

Principle: fail fast at the boundary so the core only sees clean input.

3Auth

Every protected handler repeats the same JWT-decoding code. How do you remove the duplication?

Reveal the answer & reasoning
Base handler (Template Method)

Put auth once in a base handler’s prepare() (Personify’s _set_authentication_context) and inherit it. One implementation, consistent 401s.

Principle: hoist shared steps into a base; subclasses add only the verb method.

4Routing

You’re adding PUT to an endpoint that already handles POST. How do you avoid an if method == … ladder?

Reveal the answer & reasoning
Strategy via a dict

Add a key to schema_method_validators ({"PUT": UpdateSchema}); prepare() selects the right validator by HTTP method automatically.

Principle: table-driven selection beats branching ladders.

5Smell

A handler contains the SQL to load a user. What rule is broken?

Reveal the answer & reasoning
Layer violation

The transport layer is doing data access. It should call a service, which calls a repository. Handlers map HTTP ↔ use-case only.

Principle: each layer talks only to its neighbour, not past it.

6Observability

Every log line must carry the request id, method, URI, and client IP. Where is that context set?

Reveal the answer & reasoning
Base handler prepare()

Set the log context once at the edge (Personify’s _set_log_context), so every downstream log inherits it. Cross-cutting context is established where the request enters.

Principle: establish request-scoped context at the boundary, not in each function.

7Response

A service returns domain models, but the client needs JSON. Who converts, and where?

Reveal the answer & reasoning
Handler via response schema

The handler calls the response schema’s dump to serialise. The service stays transport-agnostic and reusable beyond HTTP.

Principle: serialisation is a delivery concern, not a use-case one.

8Smell

A handler decides “users may have at most 50 contacts.” Right place?

Reveal the answer & reasoning
Move to the service

That’s a business rule needing stored data — it belongs in the service, not the handler. Handlers translate requests; they don’t own policy.

Principle: keep policy out of transport so it’s reusable and testable.

9Testing

You want to test a handler’s status-code logic without Tornado or a database. What enables it?

Reveal the answer & reasoning
Inject a fake service factory

Because the factory and service are injected, pass a stub service that returns canned results and assert on the chosen status codes. DI makes the handler testable in isolation.

Principle: injection turns even the edge layer into a unit-testable piece.

10Consistency

Error responses look different on every endpoint. How do you make them uniform?

Reveal the answer & reasoning
Shared error schemas + base write_error

Centralise on BadRequestSchema / NotFoundSchema / ServerErrorSchema and a base write_error, so every endpoint emits the same error contract.

Principle: one error shape across the API is part of the public contract.

When you can answer most of these without peeking…

…you’ve reached Level 3–4 on the self-assessment: you don’t just recognise the patterns, you can place new logic correctly under pressure. Revisit the ones you missed, then try inventing your own scenario for a domain you know well — teaching is the final test.

Accuracy note

Answers reflect the architecture and patterns of the cloned Personify-Service snapshot and general DDD/clean-architecture practice. In real projects there are sometimes valid trade-offs — if you can justify a different placement with sound reasoning, that’s a win, not a wrong answer.
