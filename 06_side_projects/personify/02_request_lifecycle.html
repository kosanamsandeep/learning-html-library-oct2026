Chapter 2 · Follow the Request

A Request's Lifecycle

The fastest way to truly understand a layered service is to chase a single request through every layer. We'll trace two real endpoints — POST /signup (a write that hits Postgres) and POST /contact (an authenticated write that hits Mongo) — line by line.

In this chapter
  1. Anatomy of every request
  2. Trace A — sign up a new user
  3. Trace B — create a contact (authenticated)
  4. What happens when things fail
  5. Check yourself

1 · Anatomy of every request

Tornado calls a handler's lifecycle methods in a fixed order. The base handlers hook into initialize() and prepare() so that by the time your post() runs, the request is already authenticated and validated.

  1. initialize(...) — dependency injection

    Tornado passes the args from the route table (logger, schema_method_validators, service_factory). The handler builds its service for this request's scope.

  2. prepare() — the gate

    Runs before the verb method. It sets the log context, authenticates the JWT (for user handlers), and parses + validates the JSON body into a typed payload.

  3. get() / post() — the use-case

    Now the body is trusted. The method simply calls a service and maps the result to an HTTP status + JSON response.

  4. on_finish() / write_error() — cleanup & errors

    Logs the outcome; converts exceptions into structured error JSON via the error schemas.

Why this matters

Because validation and auth live in prepare(), the post() body stays tiny and readable — it never re-checks the token or the schema. Separation of concerns in action.

2 · Trace A — POST /api/v1/signup

A brand-new user posts { "username": "...", "password": "..." }. Here's the journey:

sequenceDiagram autonumber participant C as Client participant H as UserSignUpHandler
(interfaces) participant Sc as SignUpSchema
(marshmallow) participant Sv as UserService
(app) participant U as PostgresUnitOfWork
(infra) participant R as PostgresRepository participant DB as PostgreSQL C->>H: POST /signup + JSON body H->>H: prepare(): set log context H->>Sc: validate(body) Sc-->>H: payload (UserModel) or errors H->>Sv: createUser(payload) Sv->>Sv: hash password (pbkdf2) Sv->>U: with unit_of_work as uow U->>R: repository.add(user) R->>DB: INSERT + commit DB-->>R: new user id U-->>Sv: id (commit on exit) Sv-->>H: UUID H-->>C: 201 Created + X-User-Id header
Each arrow crosses exactly one layer boundary. No layer reaches past its neighbour.

The handler stays thin

# interfaces/http/tornado/handlers/v1/signup_handler.py
async def post(self):
    _status = HTTPStatus.BAD_REQUEST
    _data = None
    _result = self._user_service.createUser(data=self.payload)
    if _result is not None:
        _status = HTTPStatus.CREATED
        self.set_header(GenericConstants.HEADER_USER_ID, str(_result))
    else:
        _data = BadRequestSchema().load(...)   # username already exists
    return self.build_response(status=_status, data=_data)

Notice: no SQL, no hashing, no JSON parsing here. The handler only decides the HTTP shape of the answer. All the work is in the service.

The service owns the rule

# app/user_service.py
def createUser(self, data: UserModel) -> Union[None, UUID]:
    try:
        data.password = HashGenerator.create(value=data.password)  # never store plaintext
        user_id = self._add(data=data)                          # inherited from BaseGenericService
    except IntegrityError as e:        # unique username violated
        self._logger.warning(msg=f'{e}')
        user_id = None
    return user_id

The base service wraps the transaction

# app/base_generic_service.py  (the _add helper)
def _add(self, data):
    with self.unit_of_work as _uow:   # __enter__ opens, __exit__ commits / rolls back
        return _uow.repository.add(data=data)
The key insight

The with block is the transaction boundary. If the body raises, the Unit of Work's __exit__ rolls back automatically. If it succeeds, it commits. You never call commit() by hand — that's the whole point of the pattern.

3 · Trace B — POST /api/v1/contact (authenticated)

Creating a contact is the same shape, with two extra moving parts: a JWT auth check and a different store (MongoDB). Because the handler extends BaseUserRequestHandler, the token is verified in prepare() and the user_id is available before post() runs.

sequenceDiagram autonumber participant C as Client participant H as ContactHandler
(interfaces) participant T as TokenGenerator (JWT) participant Sv as ContactService
(app) participant U as MongoUnitOfWork participant R as MongoRepository participant A as PyMongoAdapter participant DB as MongoDB C->>H: POST /contact + Bearer token + JSON H->>T: decode(token) T-->>H: user_id (or 401 Unauthorized) H->>H: validate body -> payload H->>Sv: addUserContact(user_id, payload) Sv->>Sv: stamp created_at / updated_at Sv->>U: with unit_of_work as uow U->>R: repository.add(contact) R->>A: insert_one(db, collection, dumped) A->>DB: write document DB-->>A: inserted id A-->>H: contact id H-->>C: 201 Created + Location + X-Contact-Id
Same skeleton as sign-up — only the auth step and the concrete store differ. That repeatability is a sign of good design.

Auth happens once, in the base class

# interfaces/http/tornado/handlers/base_user_handler.py
def _set_authentication_context(self):
    _encoded = self._fetch_encoded_bearer_token()      # "Authorization: Bearer ..."
    try:
        decoded = TokenGenerator.decode(value=_encoded)
        self.user_id = UUID(decoded[FieldNameConstants.USER_ID])
    except jwt.exceptions.DecodeError:
        return self._raise_unauthorized_request()        # 401

Every authenticated handler inherits this. No endpoint re-implements token handling — it is written once and reused. That's the Template Method pattern (more in Chapter 3).

The service swaps only the store

# app/contact_service.py
def addUserContact(self, user_id, data):
    data[FieldNameConstants.USER_ID]    = user_id
    data[FieldNameConstants.CREATED_AT] = datetime.utcnow()
    data[FieldNameConstants.UPDATED_AT] = datetime.utcnow()
    return self._add(data=data)   # identical helper, different UoW behind it
The same _add, two databases

Both UserService and ContactService call the inherited _add. The only difference is which Unit of Work was injected at construction time — Postgres for users, Mongo for contacts. The service code is genuinely store-agnostic.

4 · What happens when things fail

Failure Where it's caught Response
Malformed / empty JSON prepare() → schema validate 400 + BadRequestSchema
Missing / bad JWT _set_authentication_context() 401 Unauthorized
Duplicate username UserService catches IntegrityError 400 "account exists"
Bad query args (offset/limit) query-argument validator 400 invalid query
Unexpected exception inside with UoW __exit__ rolls back, then bubbles 500 + ServerErrorSchema

Errors are never bare stack traces to the client — they're shaped by dedicated marshmallow error schemas (BadRequestSchema, NotFoundSchema, ServerErrorSchema), keeping the API contract consistent.

Check yourself

By the time post() runs, what has already happened?
The log context is set, the JWT (if required) is verified into self.user_id, and the JSON body is validated and loaded into self.payload. post() can trust all of it.
Who actually commits the database transaction?
Nobody calls commit() explicitly in the service. The Unit of Work's __exit__ commits on success and rolls back on exception — triggered by leaving the with block.
Why do createUser and addUserContact look so similar despite using different databases?
Both delegate to the inherited _add, which talks to a generic repository behind a generic unit_of_work. The store-specific behaviour is injected, not hard-coded — so the service code is identical in shape.
Where would you add a "password too weak" rule?
In the schema (format validation) and/or the service (business rule) — never in the handler or repository. Handlers shape HTTP; repositories shape storage.
