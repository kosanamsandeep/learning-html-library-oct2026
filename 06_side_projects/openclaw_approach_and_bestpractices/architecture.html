How OpenClaw works under the hood

Architecture Deep Dive

OpenClaw follows a hub-and-spoke model with a central gateway daemon orchestrating sessions, channels, tools, and events. The codebase spans 235,000+ lines in the agent runtime alone, organised into a layered dependency graph with strict module boundaries.

🏗️ Hub-and-Spoke Architecture

The gateway module is the central server process orchestrating all subsystems. It exposes multiple API surfaces — WebSocket JSON-RPC for CLI/TUI clients, an OpenAI-compatible HTTP API, and channel plugin connections.

📨 Auto-Reply Pipeline

When a message arrives from any channel, it flows through a 9-stage pipeline. Each stage can short-circuit with a reply or pass to the next.

Model Selection Cascade

When the agent needs to pick an LLM, it resolves through this cascade:

session override → agent config → defaults → aliases → fuzzy match → allowlist

Auth profiles support fallback chains (e.g., DeepSeek → Qwen → OpenRouter) and OAuth flows for providers like GitHub Copilot and Qwen Portal.

Dreaming Phase

As of v2026.4.15, the dreaming (memory consolidation) phase uses separate storage mode — dreaming blocks go into memory/dreaming/{phase}/YYYY-MM-DD.md instead of polluting daily memory files. This keeps daily logs clean while still capturing reflection.

Sandbox Security Hardening

  • Default sandbox backend: Docker (with SSH and OpenShell alternatives)
  • Bind-mount validation: Paths checked against traversal and symlink escape attempts
  • Capability dropping: NET_RAW and NET_ADMIN removed; no-new-privileges enforced
  • Tool allowlist: Granular per-tool — bash, read, write permitted by default; browser, canvas, cron typically denied in sandbox mode
  • Exec approval modes: off (no approval), allowlist (auto-approve matched), always (approve everything)

⚙️ Configuration Architecture

Configuration lives in ~/.openclaw/openclaw.json (JSON5 format). Loading proceeds as: read → parseConfigJson5() → merge includes → Zod validation → OpenClawConfig object. Key sections cover agents, bindings, session behavior, gateway settings, model definitions, auth profiles, per-channel config, hooks, cron jobs, tools, sandbox, memory, plugins, logging, and approvals. A migration system handles upgrades from older config versions, and env substitution expands ${ENV_VAR} references. Config is cached in memory with chokidar-based hot-reload.
