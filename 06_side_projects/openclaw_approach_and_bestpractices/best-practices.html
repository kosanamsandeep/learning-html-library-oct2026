Best Practices Extracted from OpenClaw

OpenClaw's codebase, architecture, and contribution guidelines encode dozens of engineering best practices — from security-first agent design to monorepo management, from multi-agent routing patterns to sandboxed tool execution. This page extracts the most valuable ones for your own projects.

🔐 Security Best Practices

OpenClaw treats security as a first-class architectural concern, not an afterthought. It's one of the most security-conscious open-source AI projects in 2026.

1. Treat inbound messages as untrusted input

OpenClaw's security guidance explicitly states: "inbound DMs as untrusted input." Every message from every channel is processed through the same security pipeline regardless of source.

3. Multi-layer security model

LayerWhat it protects
Gateway authToken/password, device tokens with scopes, rate limiting, origin checking
Channel allowlistsPer-channel allowFrom sender filtering
Command authorizationOwner-only checks for sensitive commands
Tool policyPer-tool allow/deny/ask with full policy pipeline
SSRF protectionBlocks private IPs, link-local, cloud metadata; covers RFC special-use ranges and IPv6
Content securityExternal content wrapping with boundary markers, prompt injection detection
Secret handlingTiming-safe comparison (crypto.timingSafeEqual), log redaction, permission-hardened storage
Exec hardeningObfuscated command detection, safe-bin trusted directory, shell env sanitization
Sandbox isolationDocker containers with dropped capabilities, no-new-privileges, path validation
Takeaway for your projects: Every AI agent platform should have a minimum of these layers: tool-level allow/deny/ask, prompt injection detection, and sandboxed execution. The rest depends on your attack surface.

🧠 Agent Design Patterns

4. Multi-agent routing with tiered binding

OpenClaw routes messages through a tiered binding match: peer → guild+roles → channel → default. This means you can have one agent for your DMs, a different agent for a specific Discord channel, and a fallback agent for everything else.

Pattern: Bind the most specific agent first, fall back to defaults
  Direct message from Alice  → Agent: "personal-assistant"
  Message in #dev channel    → Agent: "dev-assistant"
  Everything else            → Agent: "default"

5. System prompt composition

Instead of one monolithic system prompt, OpenClaw composes it from multiple sources:

SourceExample fileWhat it contributes
IdentitySOUL.mdPersonality, tone, and character
Behavior rulesAGENTS.mdHard rules, constraints, workflow patterns
SkillsSKILL.mdReusable capabilities the agent can use
ToolsTOOLS.mdAvailable tools and when to use them
MemoryMEMORY.mdLong-term knowledge, past learnings
WorkspaceDirectory contextAvailable files, project structure

Best practice: Separate concerns in your system prompts. Don't mix identity, rules, tools, and memory in one file. Composition makes each part independently maintainable and testable.

6. Session as a first-class primitive

Agents can inspect and interact with other sessions programmatically via tools: sessions_list, sessions_history, sessions_send, sessions_spawn. This enables cross-session coordination — one agent can hand off to another, check what happened in a different conversation, or spawn a sub-session for a focused task.

🛠️ Engineering & Codebase Practices

7. Monorepo with strict module boundaries

OpenClaw uses a pnpm workspace with separate tsconfig files for core, extensions, UI, scripts, and plugin SDK. Import boundary checks are enforced via CI scripts that validate no extension imports directly from another extension.

# Import boundary enforcement scripts:
node scripts/check-src-extension-import-boundary.mjs --json
node scripts/check-sdk-package-extension-import-boundary.mjs --json
node scripts/check-test-helper-extension-import-boundary.mjs --json

8. Security scanning in CI

The project runs Semgrep security scanning (.semgrepignore), oxlint linting (.oxlintrc.json), and pre-commit hooks (.pre-commit-config.yaml) in CI. Every PR is automatically scanned for security patterns before it's reviewed.

9. Plugin SDK pattern for extensibility

Rather than accepting all feature PRs into the core repo, OpenClaw maintains a clear boundary: "Most features are not accepted and should be third party plugins instead." The plugin SDK (tsconfig.plugin-sdk.dts.json) and ClawHub marketplace enable community contributions without bloating the core.

Takeaway: Build your plugin SDK before you need it. The SDK boundary forces API stability and lets the community innovate independently of the core team's velocity.

10. PR standards that scale

OpenClaw's contribution guidelines encode several practices for large-scale open source:

  • One thing per PR — "do not mix unrelated concerns." Keeps reviews focused.
  • PRs must link to an issue — "Visible Closes #<issue> or Related: #<issue>". No drive-by PRs.
  • Max 20 open PRs per author — automated enforcement via r: too-many-prs label.
  • Evidence section required — "Focused tests, CI results, screenshots, recordings, terminal output, redacted logs, and artifact links all count."
  • Author owns bot review conversations — "Resolve the conversation yourself once the code or explanation fully addresses the bot's concern. Do not leave 'fixed' bot review conversations for maintainers to clean up."
  • AI-assisted PRs welcome with transparency — must mark as AI-assisted, include Evidence, and confirm the author understands the code.

🚀 Deployment & Operations Practices

11. Three release channels

ChannelSourceWhen to use
stableTagged releasesProduction — you want reliability
betaPrerelease tagsTesting — you want to preview features
devMoving head of mainDevelopment — you want the latest commits

Switch between channels with openclaw update --channel <name>.

12. Health probes for container orchestration

The gateway exposes four health endpoints: /health, /healthz, /ready, /readyz — making it deployment-ready for Kubernetes and Docker Compose out of the box.

13. Onboarding wizard

The openclaw onboard command is the recommended CLI setup path — it interactively configures the gateway, workspace, channels, and skills. This reduces the "blank slate" problem that kills adoption of self-hosted tools.

14. Config hot-reload

OpenClaw watches config files with chokidar and broadcasts changes to connected clients in real-time. No restart needed after config changes. This is critical for a daemon process that should stay running.

Start small

You don't need all of these at once. The highest-leverage practices to start with:

  1. Tool allow/deny/ask policy — gate what the agent can do
  2. Composable system prompts — separate identity from rules from tools
  3. Plugin SDK pattern — define your extension boundary early
  4. Config hot-reload — essential for daemon uptime
  5. Secret redaction in logs — first security practice to implement
