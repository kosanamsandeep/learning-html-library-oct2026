🛠️ DevOps / SRE Copilot

A copilot that triages incidents: it pulls logs, metrics, and cluster state through tools, correlates the signals against runbooks, proposes a root cause and a fix, and can apply it — only with human approval.

The story — why this copilot exists

It's 3 a.m. A pod is crash-looping, an alert fires, and a sleepy engineer starts the same ritual: check logs, describe the pod, look at recent deploys, grep the runbook. Mean-time-to-resolution bleeds away in context-gathering before anyone even forms a hypothesis.

An SRE copilot does that legwork in seconds: it gathers every relevant signal in parallel, correlates them, and presents a ranked root-cause hypothesis with a suggested fix — turning a 30-minute investigation into a 30-second briefing.

Inspired by: k8sgpt-ai/k8sgpt and robusta-dev/holmesgpt — popular projects that bring LLM diagnosis to Kubernetes and observability.

The triage flow

flowchart TD
    AL["🚨 Alert / on-call asks 'why is checkout down?'"] --> AG["SRE Copilot (agent)"]
    AG --> GATHER["Gather signals in parallel"]
    GATHER --> L["pod logs"]
    GATHER --> M["metrics (CPU/mem/latency)"]
    GATHER --> K["k8s state (events, restarts)"]
    GATHER --> DEP["recent deploys"]
    L --> CORR["Correlate + match runbooks (RAG)"]
    M --> CORR
    K --> CORR
    DEP --> CORR
    CORR --> RC["Ranked root-cause hypothesis + fix"]
    RC --> APPROVE{"Apply fix?"}
    APPROVE -->|human approves| ACT["kubectl rollout undo / scale"]
    APPROVE -->|no| REPORT["Post briefing to Slack"]

Read-only diagnosis is automatic; any change to the cluster goes through an explicit human approval.

The code — read-only diagnostic tools

from langchain_core.tools import tool
import subprocess

def _sh(cmd: list[str]) -> str:
    return subprocess.run(cmd, capture_output=True, text=True, timeout=20).stdout

@tool
def pod_logs(namespace: str, pod: str) -> str:
    """Return the last 200 log lines for a pod."""
    return _sh(["kubectl", "logs", "-n", namespace, pod, "--tail=200"])

@tool
def describe_pod(namespace: str, pod: str) -> str:
    """Show events and status for a pod (restarts, OOMKilled, etc.)."""
    return _sh(["kubectl", "describe", "pod", "-n", namespace, pod])

@tool
def recent_deploys(namespace: str) -> str:
    """List recent rollout history for the namespace."""
    return _sh(["kubectl", "rollout", "history", "deploy", "-n", namespace])

@tool
def search_runbooks(symptom: str) -> str:
    """Find runbook steps matching a symptom (RAG over the ops wiki)."""
    return runbook_retriever.invoke(symptom)

The code — the diagnosing agent

from langgraph.prebuilt import create_react_agent

SYSTEM = (
    "You are an SRE copilot. Investigate the incident using the tools. "
    "Gather logs, pod state, and recent deploys, cross-check runbooks, then "
    "output: (1) most likely root cause, (2) evidence, (3) a recommended fix. "
    "NEVER change the cluster yourself — only recommend. Be concise."
)

sre = create_react_agent(
    "openai:gpt-4o",
    tools=[pod_logs, describe_pod, recent_deploys, search_runbooks],
    prompt=SYSTEM,
)

briefing = sre.invoke({"messages": [("user",
    "Checkout is throwing 500s in namespace 'prod'. What's wrong?")]})
print(briefing["messages"][-1].content)
# → "Root cause: deploy #47 set memory limit too low → pods OOMKilled.
#    Evidence: 'OOMKilled' in describe, restarts=8, deploy 6m ago.
#    Fix: kubectl rollout undo deploy/checkout -n prod"
Diagnosis is safe; action is gated. Reading state can be fully autonomous. Anything that mutates the cluster (rollback, scale, delete) must require explicit human approval — the difference between a helpful copilot and an outage amplifier.

Applying a fix — behind approval

from langgraph.types import interrupt

@tool
def rollback(namespace: str, deploy: str) -> str:
    """Roll a deployment back to its previous revision (needs approval)."""
    ok = interrupt({"action": "rollback", "deploy": deploy, "ns": namespace})
    if ok != "approve":
        return "Rollback cancelled."
    return _sh(["kubectl", "rollout", "undo", f"deploy/{deploy}", "-n", namespace])

Advantages this copilot brings

Advantage Why it matters
Lower MTTR Signal-gathering and correlation happen in seconds.
Less on-call toil The boring investigation is automated; humans decide.
Knowledge capture Runbooks become an active resource, not a dusty wiki.
Consistent triage Every incident gets the same thorough first look.
Junior-friendly Less-experienced engineers get expert-level starting points.

Best practices & guardrails

  • Read-only by default; mutations always require human approval.
  • Scope credentials tightly — a dedicated, least-privilege service account.
  • Time-box and sandbox tool calls so one hung command can't stall triage.
  • Keep humans accountable — the copilot recommends; an engineer owns the action.
  • Log the full investigation for the post-mortem and to improve runbooks.
