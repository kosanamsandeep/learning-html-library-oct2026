📊 Data Analyst Copilot

A copilot that turns a plain-English question into validated SQL, runs it against your warehouse, and returns the answer as a number, a table, or a chart — with the query shown so analysts can trust and reuse it.

The story — why this copilot exists

Every team is "data-driven" until someone needs a number that isn't on a dashboard. Then they file a ticket and wait days for an analyst to write SQL. The analyst, meanwhile, spends their week on trivial one-off queries instead of real analysis.

A data analyst copilot lets anyone ask in English — "What were our top 5 products by revenue last month?" — and get an answer in seconds, backed by the exact SQL it ran. Self-serve analytics, without everyone learning SQL.

Inspired by: vanna-ai/vanna, Canner/WrenAI, and LangChain's SQL agent — leading open-source "chat with your database" projects.

The model can't write correct SQL without knowing your schema — so we retrieve the relevant tables/columns first (schema-RAG), then validate before running.

The code — schema-aware SQL generation

from sqlalchemy import create_engine, text
from openai import OpenAI

engine = create_engine("postgresql+psycopg://readonly:***@db/shop")  # read-only role!
client = OpenAI()

def schema_hint() -> str:
    """A compact description of relevant tables for the prompt."""
    return """
    orders(id, product_id, amount, created_at)
    products(id, name, category)
    """

def to_sql(question: str) -> str:
    prompt = f"""You write PostgreSQL. Use ONLY these tables:
{schema_hint()}
Return a single SELECT statement (read-only). No comments.
Question: {question}"""
    resp = client.chat.completions.create(
        model="gpt-4o", temperature=0,
        messages=[{"role": "user", "content": prompt}],
    )
    return resp.choices[0].message.content.strip().strip("`")

The code — validate, then run safely

import sqlparse

def is_safe(sql: str) -> bool:
    """Allow a single read-only SELECT only."""
    parsed = sqlparse.parse(sql)
    if len(parsed) != 1:
        return False
    stmt = parsed[0]
    banned = {"INSERT", "UPDATE", "DELETE", "DROP", "ALTER", "TRUNCATE"}
    return stmt.get_type() == "SELECT" and not (banned & {t.value.upper() for t in stmt.flatten()})

def answer(question: str):
    sql = to_sql(question)
    if not is_safe(sql):
        raise ValueError("Refusing non-read-only query.")
    with engine.connect() as conn:
        rows = conn.execute(text(sql)).fetchall()
    return sql, rows         # show the SQL alongside results for trust
Two layers of safety, not one. A read-only database role makes destructive queries impossible at the engine; the validator gives a friendly error before they ever run. Never rely on the prompt alone.

Make it learn your data (the Vanna idea)

Generic schema text only goes so far. The strongest NL→SQL copilots train on examples: store your real tables, documentation, and known-good question→SQL pairs in a vector store, and retrieve the most relevant ones into the prompt for each new question.

    DDL["Table DDL"] --> VS[("Training store")]

    PAIRS["Q → SQL examples"] --> VS
    NEWQ["New question"] --> RET["Retrieve similar context"]
    VS --> RET
    RET --> LLM["LLM → SQL"]

More relevant examples in context ⇒ dramatically higher SQL accuracy on your specific schema.

Best practices & guardrails

  • Connect with a read-only role — the single most important safeguard.
  • Validate every query (single SELECT, allow-listed tables) before running.
  • Add LIMIT by default to avoid scanning huge tables.
  • Show the SQL so humans can sanity-check and reuse it.
  • Curate training pairs for your schema — accuracy comes from examples, not cleverer prompts.
