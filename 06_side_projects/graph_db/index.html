What is a graph database in one picture?

A graph database stores data the way you draw it on a whiteboard: nodes (things) connected by relationships (how they relate), each carrying properties. There are no foreign keys or JOIN tables — the connections are the data. 

graph LR
    A(["👤 Alice"]) -- FOLLOWS --> B(["👤 Bob"])
    B -- FOLLOWS --> C(["👤 Carol"])
    A -- LIKES --> P(["🎬 Inception"])
    C -- ACTED_IN --> P
    A -- LIVES_IN --> L(["🏙️ London"])
    B -- LIVES_IN --> L
    classDef person fill:#dbeafe,stroke:#2563eb,color:#1e3a8a;
    classDef thing fill:#ede9fe,stroke:#7c3aed,color:#4c1d95;
    class A,B,C person;
    class P,L thing;

Nodes (circles) + relationships (arrows) + properties = the property graph model. "Who does Alice follow that likes a movie Carol acted in?" is one short query here — and a painful multi-JOIN in SQL.

When should you reach for a graph database?

✅ Great fit

  • Relationships are the question — "friends of friends", paths, networks.
  • Recommendations — "people who bought X also bought…".
  • Fraud / AML rings — find suspicious connection patterns.
  • Knowledge graphs — entities + facts, GraphRAG for LLMs.
  • Network/IT, supply chain, identity & access graphs.

⚠️ Probably not

  • Simple CRUD over flat, tabular records.
  • Heavy aggregation/analytics on huge columns (use a warehouse).
  • Blob/document storage with no meaningful links.
  • Pure key→value lookups at massive scale.
Rule of thumb: if your most valuable questions contain the word "connected", "path", "network", or "related", and SQL would need 3+ JOINs or recursive CTEs, a graph database will be simpler and faster.
