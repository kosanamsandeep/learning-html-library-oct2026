Chapter 08 · Test yourself

Practice tests — prove you're an expert

Three graded rounds against the social + e-commerce dataset from chapter 03. Try each in Neo4j Browser before revealing the answer. Aim to explain why, not just type the query.

Setup: make sure Dataset B from chapter 03 is loaded. If results look off, reset (MATCH (n) DETACH DELETE n;) and re-paste it.

Round 1 Fundamentals & reading data

easy Q1. Return every person's name and city, sorted by city. 
MATCH (p:Person)
RETURN p.name, p.city
ORDER BY p.city;
easy Q2. How many products are in the Tech category? 
MATCH (pr:Product {category:'Tech'})
RETURN count(pr) AS techProducts;
Answer: 3 (Laptop, Phone, Mouse).
easy Q3. List who bought the Laptop. 
MATCH (p:Person)-[:BOUGHT]->(:Product {name:'Laptop'})
RETURN p.name;
Alice and Bob.
easy Q4. What's the difference between CREATE and MERGE?
CREATE always inserts a new node/relationship (can duplicate). MERGE finds a matching pattern and only creates it if it doesn't already exist (idempotent upsert). Use MERGE on a unique key to avoid duplicates.

Round 2 Traversals & aggregation

medium Q5. Average review rating per product, highest first. 
MATCH (:Person)-[r:REVIEWED]->(pr:Product)
RETURN pr.name, avg(r.rating) AS avgRating, count(r) AS n
ORDER BY avgRating DESC;
medium Q6. Suggest friends-of-friends for Carol (2 hops, not already her friend, not herself). 
MATCH (c:Person {name:'Carol'})-[:FRIENDS_WITH]->()-[:FRIENDS_WITH]->(fof)
WHERE fof <> c AND NOT (c)-[:FRIENDS_WITH]->(fof)
RETURN DISTINCT fof.name;
medium Q7. Total spend per person (sum of product prices they bought), highest first. 
MATCH (p:Person)-[:BOUGHT]->(pr:Product)
RETURN p.name, sum(pr.price) AS spend
ORDER BY spend DESC;
medium Q8. List every person and the products they bought as a single list per person. 
MATCH (p:Person)-[:BOUGHT]->(pr:Product)
RETURN p.name, collect(pr.name) AS basket;
collect() rolls grouped rows into a list.
medium Q9. Which people never wrote a review? (Hint: OPTIONAL MATCH.) 
MATCH (p:Person)
WHERE NOT (p)-[:REVIEWED]->()
RETURN p.name;
Dave and Frank (they bought but never reviewed).

Round 3 Recommendations, paths & performance

hard Q10. "People who bought what Bob bought also bought…" — recommend products Bob hasn't bought, ranked by strength. 
MATCH (bob:Person {name:'Bob'})-[:BOUGHT]->(p)<-[:BOUGHT]-(other)-[:BOUGHT]->(rec)
WHERE NOT (bob)-[:BOUGHT]->(rec)
RETURN rec.name, count(*) AS strength
ORDER BY strength DESC;
Bob bought the Laptop; Alice also bought the Laptop and the Graph Book → recommend the Book.
hard Q11. Shortest friendship path from Alice to Frank, returning the names along the way. 
MATCH (a:Person {name:'Alice'}), (f:Person {name:'Frank'})
MATCH p = shortestPath( (a)-[:FRIENDS_WITH*1..6]-(f) )
RETURN [n IN nodes(p) | n.name] AS path, length(p) AS hops;
hard Q12. Products bought by Alice's friends that Alice hasn't bought (a simple recommendation). 
MATCH (a:Person {name:'Alice'})-[:FRIENDS_WITH]->(f)-[:BOUGHT]->(pr)
WHERE NOT (a)-[:BOUGHT]->(pr)
RETURN DISTINCT pr.name;
hard Q13. You added an index on Person.name. How would you confirm a lookup query actually uses it?
Prefix the query with PROFILE (or EXPLAIN) and look at the plan: you want to see NodeIndexSeek rather than NodeByLabelScan + Filter. PROFILE also shows db hits — they should drop after indexing. 
PROFILE MATCH (p:Person {name:'Alice'}) RETURN p;
hard Q14. Conceptual: a teammate wants to store flat sales transactions and run monthly SUM reports. Should they use a graph DB? Why/why not?
No. That's flat, aggregation-heavy, columnar work — a relational DB or data warehouse/OLAP store is the right fit. Graph DBs shine on connected queries (paths, multi-hop relationships, recommendations, fraud rings), not on "SUM a column grouped by month."
