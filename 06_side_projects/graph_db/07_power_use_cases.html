Chapter 07 · Why graphs win

The real power — and when NOT to use it

A graph DB isn't "a better SQL". It's a different shape of database that crushes connected-data problems. Here's the proof, the killer use cases, and an honest list of when to reach for something else.

The core advantage: relationships are first-class

In a relational DB, relationships are inferred at query time by matching foreign keys across tables (JOINs). In a graph DB, relationships are stored on disk as direct pointers. Traversing them is constant-time, no matter how big the database grows.

graph TB
    subgraph Relational["Relational: JOIN cost grows with hops"]
        R1["Users table"] -.->|"scan FK index"| R2["Friends table"]
        R2 -.->|"scan again"| R3["Friends table"]
        R3 -.->|"scan again"| R4["..."]
    end
    subgraph Graph["Graph: follow pointers, O(1) per hop"]
        G1(["Alice"]) -->|pointer| G2(["Bob"])
        G2 -->|pointer| G3(["Dave"])
        G3 -->|pointer| G4(["Frank"])
    end
    classDef rel fill:#fee2e2,stroke:#dc2626,color:#7f1d1d;
    classDef gr fill:#dbeafe,stroke:#2563eb,color:#1e3a8a;
    class R1,R2,R3,R4 rel;
    class G1,G2,G3,G4 gr;

Each extra hop adds an expensive index lookup in SQL, but only a pointer-follow in a graph. Deep queries are where graphs pull ahead dramatically.

Benchmark intuition: the "deep query cliff"

Query depth Relational (JOINs) Graph (traversal)
1 hop ("my friends") Fast Fast
2 hops ("friends of friends") OK Fast
3–4 hops Slow (exploding JOINs) Fast
5+ hops / variable depth Often impractical Still fast

The classic Neo4j "friends of friends to depth 5" demo: relational query takes minutes (or times out) on a million users; the graph returns in milliseconds. The exact numbers vary by data and tuning, but the shape of the curve is the point.

Killer use cases

🛒 Recommendations
"Customers who bought X also bought Y", friend suggestions, content feeds. Collaborative filtering is a 2–3 hop traversal.
🕵️ Fraud detection
Spot rings: shared devices, addresses, or cards linking "unrelated" accounts. Fraud hides in relationships, not rows.
🧠 Knowledge graphs
Connect entities, facts, and ontologies (people, companies, topics). Powers search, reasoning, and data integration.
🤖 GraphRAG
Ground LLMs in a knowledge graph: retrieve connected facts (not just similar text chunks) for more accurate, explainable answers.
🌐 Network & IT ops
Model infra dependencies; answer "if this server dies, what breaks?" via impact traversal.
🚚 Supply chain / routing
Shortest/cheapest paths, bottleneck and single-point-of-failure analysis across a network.
🔐 Identity & access
Who can reach what, through which roles/groups? Permission graphs are naturally hierarchical and transitive.
👥 Social networks
Friendships, follows, communities, influence (PageRank). The original graph use case.

GraphRAG — why it matters for AI

Vector RAG retrieves text chunks that are semantically similar to a question. It misses connections. GraphRAG adds a knowledge graph so the LLM can follow explicit relationships. 

graph LR
    Q["Question"] --> V["Vector search
(similar chunks)"]
    Q --> G["Graph traversal
(connected facts)"]
    V --> M["Merge context"]
    G --> M
    M --> LLM["LLM answer
(grounded + explainable)"]
    classDef step fill:#d4f3e9,stroke:#0f9d77,color:#14241f;
    classDef llm fill:#ede9fe,stroke:#7c3aed,color:#4c1d95;
    class Q,V,G,M step;
    class LLM llm;

GraphRAG = "find similar" + "find connected". The graph supplies relationships a pure vector store can't, improving multi-hop reasoning and letting you cite the path.

Choosing the right database

If your data is… Best fit Why
Highly connected, deep relationships Graph Traversal beats JOINs
Tabular, transactional, fixed schema Relational (Postgres/MySQL) ACID, mature, SQL everywhere
Flexible nested documents Document (MongoDB) Schema-light, fast writes
Simple lookups by key, huge scale Key-value (Redis) O(1) reads, caching
Time-series / huge write volume Wide-column / TSDB Write throughput, retention
Semantic similarity search Vector DB Embeddings, ANN search
Rule of thumb: if your most valuable questions contain the words "connected", "path", "related to", "network", "recommend", or "how are X and Y linked" → graph. If they're "give me row by id" or "sum this column" → probably not.

When NOT to use a graph DB (be honest)

❌ Simple CRUD / flat data. A few tables with rare JOINs? Postgres is simpler and faster to staff.
❌ Heavy aggregation / analytics over columns. "SUM of sales by month" is a job for SQL/OLAP/warehouse, not traversal.
❌ Massive write-only logging / time-series. Use a TSDB or wide-column store built for ingest.
❌ Pure key-value caching. Redis will be cheaper and faster.
⚠️ Tiny app with no relationships. Don't add operational complexity you won't use.
⚠️ Team has zero graph experience & tight deadline. Factor the learning curve.

Polyglot persistence is normal: many systems use Postgres for transactions, a vector DB for search, and a graph DB for the relationship-heavy slice. Pick the right tool per problem, not one DB for everything.

Remember it

Graphs store the JOIN. Relationships are on disk, not computed each query.
Depth is free-ish. Cost scales with the answer size, not the whole database.
Connected questions → graph. Recommendations, fraud, knowledge, paths.
Flat/aggregate questions → not graph. Use SQL, TSDB, key-value, or vector.
