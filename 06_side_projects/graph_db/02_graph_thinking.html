Chapter 02 · Mental model

Think in graphs, not tables

Before any query, rewire how you picture data. The property-graph model has just four building blocks — once they click, Cypher reads like English.

The four building blocks

Node a thing

An entity: a person, movie, product, account. Drawn as a circle. In Cypher: (p:Person).

Relationship a connection

A typed, directed link between two nodes: FOLLOWS, ACTED_IN. In Cypher: -[:FOLLOWS]->.

🏷️ Label — a category

Groups nodes by type: :Person, :Movie. A node can have several labels.

🔑 Property — a key/value

Data on a node or a relationship: name: 'Alice', since: 2019.

Read a pattern aloud: (p:Person)-[:ACTED_IN]->(m:Movie) = "a Person node, connected by an ACTED_IN relationship pointing to, a Movie node." That's the entire idea behind Cypher.

Anatomy of one relationship

graph LR
    A(["Person
name: 'Tom Hanks'
born: 1956"]) -->|"ACTED_IN { role: 'Forrest' }"| B(["Movie
title: 'Forrest Gump'

    classDef person fill:#dbeafe,stroke:#2563eb,color:#1e3a8a;

Both nodes and the relationship hold properties. The arrow direction is part of the meaning (Tom acted in the movie, not the reverse).

Same data, four database models

Imagine "users who follow users, and like movies." Here's how each database family stores it:

graph TD
    subgraph REL["🗄️ Relational (SQL)"]
        T1["users table"] --- T2["follows table
(user_id, follows_id)"]
        T1 --- T3["likes table
(user_id, movie_id)"]
        T4["movies table"]
    end
    subgraph DOC["📄 Document (Mongo)"]
        D1["user doc
{ name, follows:[ids], likes:[ids] }"]
        D2["...but ids point nowhere
you resolve them in app code"]
    end
    subgraph GRAPH["◆ Graph (Neo4j)"]
        G1(["User"]) -->|FOLLOWS| G2(["User"])
        G1 -->|LIKES| G3(["Movie"])
    end

SQL needs join tables; documents need app-side stitching; the graph stores the relationship natively as a first-class, walkable thing.

The decisive difference: JOINs vs traversal

"Who do the people I follow, follow?" (friends-of-friends).

SQL — self-join the join table twice

SELECT DISTINCT u3.name
FROM follows f1
JOIN follows f2 ON f1.follows_id = f2.user_id
JOIN users u3   ON f2.follows_id = u3.id
WHERE f1.user_id = 1;

Cypher — draw the path

MATCH (me:User {id: 1})-[:FOLLOWS]->()-[:FOLLOWS]->(fof:User)
RETURN DISTINCT fof.name;
Why it matters: add a third or fourth hop and the SQL grows another JOIN each time (and slows down as tables grow). In Cypher you just add -[:FOLLOWS]->() — and Neo4j follows pointers in memory ("index-free adjacency"), so deep traversals stay fast regardless of total dataset size.

Pick the right tool — a comparison

Model Stores data as Strength Weak at Example
Relational Tables + foreign keys Structured data, transactions, aggregation Deep/variable relationships (JOIN explosion) PostgreSQL, MySQL
Document JSON documents Flexible schema, nested objects Cross-document relationships MongoDB
Key-Value key → value Blazing simple lookups, caching Any query that isn't "by key" Redis
Wide-column Rows with dynamic columns Massive write scale Ad-hoc joins/relationships Cassandra
Graph Nodes + relationships Connected data, paths, networks Bulk column analytics, plain CRUD Neo4j
It's not graph vs the world. Real systems mix them — e.g. Postgres for orders, Redis for sessions, Neo4j for the recommendation/fraud graph. Use a graph for the connected part of your problem.

Remember it — the whiteboard test

If you can draw your problem as circles and arrows and someone immediately understands it, the graph model fits. Your drawing is your schema. Keep these mnemonics:

  • Nodes are nouns (Person, Movie, Account).
  • Relationships are verbs (FOLLOWS, BOUGHT, TRANSFERRED_TO) — usually UPPER_SNAKE.
  • Properties are adjectives/details (name, price, since).
  • Direction carries meaning — but you can query it either way.
