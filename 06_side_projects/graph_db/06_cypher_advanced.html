Chapter 06 · Cypher

Advanced Cypher & making it fast

Shortest paths, indexes & constraints, query planning with EXPLAIN/PROFILE, and the power tools — APOC and Graph Data Science (GDS). This is what separates "I can query" from "I run graphs in production."

1 · Shortest path

Find the fewest hops between two nodes — the classic graph problem (six degrees of separation, routing, supply chains).

MATCH (a:Person {name:'Alice'}), (f:Person {name:'Frank'})
MATCH p = shortestPath( (a)-[:FRIENDS_WITH*1..6]-(f) )
RETURN [n IN nodes(p) | n.name] AS hops, length(p) AS degrees;
graph LR
    Alice(["Alice"]) ---|FRIENDS_WITH| Carol(["Carol"])
    Carol ---|FRIENDS_WITH| Erin(["Erin"])
    Erin ---|FRIENDS_WITH| Frank(["Frank"])
    classDef person fill:#dbeafe,stroke:#2563eb,color:#1e3a8a;
    class Alice,Carol,Erin,Frank person;

Alice → Carol → Erin → Frank: shortest path of 3 hops. Use allShortestPaths() for every tied-shortest route.

2 · Indexes & constraints — the #1 speed lever

Without an index, finding a node by property scans every node. With one, it's instant. Always index the properties you look up by.

// Uniqueness constraint (also creates an index)
CREATE CONSTRAINT person_name IF NOT EXISTS
FOR (p:Person) REQUIRE p.name IS UNIQUE;

// Plain index for fast lookups / range scans
CREATE INDEX product_category IF NOT EXISTS
FOR (pr:Product) ON (pr.category);

// See what exists
SHOW INDEXES;
Tool Use it for
UNIQUE constraint Stop duplicates + speed lookups on a key (id, email)
Range / B-tree index Equality & range WHERE on a property
Full-text index Searching text inside properties
EXISTS / type constraint Enforce a property is present / typed
Golden rule: index every property used as a starting point in a MATCH or MERGE. The traversal after that is already fast (index-free adjacency).

3 · EXPLAIN & PROFILE — read the query plan

EXPLAIN — shows the plan without running. Free. Check whether it uses an index (NodeIndexSeek) or scans (NodeByLabelScan = slow).
PROFILE — actually runs it and reports db hits per step. Fewer hits = faster. Use to find the bottleneck. 
PROFILE
MATCH (p:Person {name:'Alice'})-[:BOUGHT]->(pr)
RETURN pr.name;

If you see NodeByLabelScan + a big Filter on a property you query often → add an index and re-PROFILE. Db hits should drop sharply.

4 · Subqueries & pattern comprehensions

// CALL subquery: per person, count purchases in an isolated scope
MATCH (p:Person)
CALL (p) {
  MATCH (p)-[:BOUGHT]->(pr:Product)
  RETURN count(pr) AS items, sum(pr.price) AS spend
}
RETURN p.name, items, spend
ORDER BY spend DESC;

// Pattern comprehension: inline-collect related data
MATCH (p:Person {name:'Alice'})
RETURN p.name,
       [(p)-[:BOUGHT]->(pr) | pr.name] AS bought;
Version note: older Neo4j used CALL { WITH p ... }. Newer versions allow CALL (p) { ... }. If one errors, try the other form for your version.

5 · APOC — the "standard library"

APOC (Awesome Procedures On Cypher) adds 450+ helpers: data import/export, graph refactoring, text utilities, batching big writes, and more.

// Run a huge update in safe batches
CALL apoc.periodic.iterate(
  'MATCH (p:Person) RETURN p',
  'SET p.processed = true',
  {batchSize: 1000}
);

// Convenience helpers
RETURN apoc.text.capitalize('alice');

Install APOC by adding the plugin (Neo4j Desktop: one click; Docker: the NEO4J_PLUGINS=["apoc"] env var). Verify with RETURN apoc.version();.

6 · Graph Data Science (GDS) — algorithms at scale

When you need real graph analytics — not just queries — the GDS library runs PageRank, community detection, centrality, similarity, and pathfinding over a projected in-memory graph.

Algorithm Answers
PageRank Who/what is most influential?
Louvain / Community detection What clusters/communities exist?
Betweenness centrality Who are the critical "bridge" connectors?
Node similarity Which nodes behave alike? (recommendations)
Dijkstra / A* Cheapest weighted route 
// Sketch: project a graph, then run PageRank
CALL gds.graph.project('social', 'Person', 'FRIENDS_WITH');
CALL gds.pageRank.stream('social')
YIELD nodeId, score
RETURN gds.util.asNode(nodeId).name AS person, score
ORDER BY score DESC;
Mental split: Cypher = "find patterns." GDS = "measure the whole graph's structure." You'll use both in fraud, recommendations, and knowledge graphs.

Performance checklist

✅ Index/constraint on every MATCH/MERGE start property
✅ Bound variable-length paths (*1..3, never bare *)
✅ PROFILE slow queries; kill NodeByLabelScan
✅ Filter early; carry only needed columns through WITH
❌ Returning entire nodes when you only need one property
❌ MERGE on a non-indexed / non-unique property

hard Find the shortest friendship path between Bob and Erin and list the names along it. 
MATCH (b:Person {name:'Bob'}), (e:Person {name:'Erin'})
MATCH p = shortestPath( (b)-[:FRIENDS_WITH*1..6]-(e) )
RETURN [n IN nodes(p) | n.name];
hard Why is the friend-of-friend query fast in a graph DB even with millions of users?
Index-free adjacency: each node stores direct pointers to its relationships, so traversing a hop is O(1) per neighbor — independent of total DB size. A relational JOIN, by contrast, searches an index across the whole table for every hop.
