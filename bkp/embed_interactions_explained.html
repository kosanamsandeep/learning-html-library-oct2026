Interactions Pipeline

Two Airflow DAGs that upload interaction data to ContentHub and then embed it — with a feasibility analysis of adding parse→summarize→embed.
Python Airflow Upload DAG Embed DAG External APIs

The Two DAGs

Together, these two DAGs form a pipeline that takes "interactions" data (probably user conversations or messages) and makes it searchable via vector embeddings:

⬆️ Upload DAG

askit_monthly_interactions_upload_to_contenthub
Runs daily @ 3:00 AM ET. Uploads interaction records from the previous completed day into ContentHub, organized by month folders. ~350 lines.

🧠 Embed DAG

askit_embeddings_from_interactions
Runs daily @ 4:00 AM ET. Triggers an external embedding service to generate vector embeddings from the uploaded files. ~295 lines.

💡 The schedule is intentional: Upload runs at 3 AM ET (so yesterday's data is available), then Embed runs at 4 AM ET (so it can process what was just uploaded). The hour gap gives the upload time to complete.

Upload DAG — Tasks in Detail

get_token
POST to TOKEN_URL with OAuth2 client credentials grant. Returns the access_token string. This is a @task — the return value is pushed to XCom automatically by the TaskFlow API.
compute_plan
Calls resolve_interactions_plan() which determines the month folder, date range, and 7-day chunks. Takes these inputs:
  • as_of_date — "today" in ET
  • dynamic_enabled — Airflow Variable flag (default true)
  • target_month — for manual backfill (e.g. "may" or "may_2026")
Returns a dict with folder_path, start_date, end_date, chunks.
extract_chunks
Pulls plan["chunks"] — the list of 7-day date range dicts. Each chunk looks like {"folder_path": "...", "start_date": "2026-07-01", "end_date": "2026-07-07"}.
purge_interactions
DELETE request to /bv/v1/purge_data_file with is_delete_all_files: true. Clears the target month folder before re-uploading. Handles several edge cases gracefully:
  • 404 / "folder not found" → skip (nothing to purge)
  • 500 + "error fetching file list" → skip (known backend bug)
  • All other failures → raise
upload_interactions_chunk (mapped tasks)
Uses Airflow's .expand() to create one task per chunk. Each sends a POST to /sn/v1/upload_past_interactions_into_contenthub with the folder path and date range. Timeout: 15 min (configurable, default 900s). This is where the actual interaction data gets sent to ContentHub.

✅ Smart edge-case handling

Purge tolerates missing folders and known backend bugs. Uses chunk_days for configurable granularity. Dynamic mode picks the right month automatically.

❌ No filesystem access

Despite the name "upload", the DAG doesn't read actual interaction files. It sends date ranges to an API — the ContentHub server presumably queries some DB and creates the files internally.

This DAG is simpler — it just triggers an external embedding service with configuration metadata. It does zero data processing itself.

Embed DAG — Tasks in Detail

load_json_config
Reads JSON from Airflow Variable askit_embeddings_config_interactions. Validates required keys (spaceId, flowId, spaceName, userName, userRole). Sets defaults for optional flags. Generates a correlationId (UUID). Pushes to XCom.
validate_core_service
Pings canvasai_core_svc_url/ping with the correlationId header. Just a health check before proceeding.
get_token
Same OAuth2 flow as the upload DAG — client credentials → access_token. Pushes to XCom.
trigger_local_file_embedding
The core action. Builds a payload from the config + token, fires a POST to the embedding service URL. Uses fire-and-forget timeout handling:
  • Connect timeout: 10s
  • Read timeout: 10s
  • On ReadTimeout → log and continue (assume backend accepted it)
  • On ConnectionError → raise (real failure)
# The embed payload sent to the external service:
{
  "spaceId": "...",
  "flowId": "...",
  "spaceName": "...",
  "userName": "...",
  "userRole": "...",
  "isFromDatahub": true,
  "vectorStorageType": "ChromaDB",
  "clearEmbeding": false,
  "clearIndexing": false,
  "runEmbedding": true,
  "runIndexing": false
}

✅ Where files DO exist

ContentHub storage (server-side) — After the upload DAG runs, files live on the ContentHub server in month-organized folders. The embedding service then reads them from there.

❌ Where files do NOT exist

In the Airflow DAGs. Neither DAG reads, writes, or processes file content. They only send metadata (date ranges, folder paths, config flags) to external APIs. The Airflow workers never see the actual interaction data.

🚫 Critical Gap for Your Requirement

To add custom Python parse logic + OpenAI summarization to this pipeline, you would need file content available in the DAG worker's memory/filesystem. Currently it isn't. The upload DAG sends date ranges (not files) to ContentHub, and the embed DAG sends config (not files) to the embedding service.

🛠️ What IS feasible (with changes)

Adding PythonOperator tasks to the embed DAG that:
1. Call ContentHub's API to download files
2. Run custom parse logic
3. Call OpenAI for summaries
4. Generate embeddings libraries (sentence-transformers / openai)
5. Store in ChromaDB via the ChromaDB Python client

🚫 What is NOT feasible

Injecting custom parse/summarize logic into the existing black-box embedding service — you don't control it. And the upload DAG sends no file content, only date ranges.

⚡ The most pragmatic approach: Don't modify either DAG. Build a third DAG (or standalone script) that:
1. Fetches files from ContentHub (maybe via a download API endpoint)
2. Parses + summarizes + embeds locally
3. Writes all three vectors (raw chunks, parsed structure, summary) to ChromaDB
This keeps the existing pipeline untouched and is independently testable.

Final Verdict

📊 Summary Assessment
QuestionAnswer
Does any DAG read file content locally? No.
Is the pipeline entirely external-service-reliant? Yes.
Upload DAG — does it handle file content? ❌ No. Sends date ranges to ContentHub API. The server creates the files.
Embed DAG — does it handle file content? ❌ No. Sends metadata config to a black-box embedding service.
Can you add parse→summarize→embed as new tasks? ⚠️ Yes, but only if you also add file-fetching capability.
Can the existing external services do this? ❌ Unknown — the embedding service is a black box.

✅ What This Pipeline Does Well

It cleanly separates concerns:
• Upload → gets data into ContentHub
• Embed → triggers vectorization
Each DAG has one job. The schedule ensures data is available before embedding runs. Error handling (fire-and-forget, purge edge cases) is thoughtful.

❌ What It Cannot Do (as-is)

• Read or process file content in Airflow
• Run custom Python on interaction data
• Call OpenAI or any LLM
• Store structured + summarized embeddings side by side
These would require significant new code.

🚩 Bottom line: The parse → summarize → embed pipeline you want cannot be dropped into the existing DAGs. Both DAGs are pure orchestrators — they delegate all data work to external services. You'd need to build a data-processing layer (new tasks, a new DAG, or a new service) that fetches files from ContentHub, runs your Python parser, calls OpenAI, and then stores the results. The existing pipeline is a trigger, not a processor.
