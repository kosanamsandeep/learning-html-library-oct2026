E-commerce API — DTO seam, validate-then-mutate

Same DTO pattern as the Go version, but with one extra Rust touch: validate the whole order first, then mutate. If you mutated as you went and the third line failed, you'd have already deducted stock from the first two — the borrow checker can't save you from that, only design can.

The two-pass pattern

// Pass 1: validate every line, accumulate the total.
for line in lines {
    let p = self.products.get(&line.product_id)
        .ok_or_else(|| format!("unknown product {}", line.product_id))?;
    if line.quantity <= 0 || line.quantity > p.stock {
        return Err(format!("bad quantity for {}", line.product_id));
    }
    total_cent += line.quantity * p.price_cent;
}

// Pass 2: now we know everything is valid, mutate.
for line in lines {
    let p = self.products.get_mut(&line.product_id).unwrap();
    p.stock -= line.quantity;
}

This is a transferable design lesson — equally useful in Python. Validate first, mutate later.

What a real Rust app would change

  • Add serde + serde_json in Cargo.toml and #[derive(Serialize, Deserialize)] on the DTOs. The hand-rolled to_json goes away.
  • Add an axum or actix-web handler around the Catalog — same shape, different dispatcher.
