Banking System — inheritance becomes embedding + interfaces

The Python version uses class SavingsAccount(Account) and overrides deposit. Go has no inheritance, so the same problem becomes two ideas working together: an interface for the shared behaviour, and struct embedding for the shared data.

The Go translation

  1. Account is an interface — the contract every account type satisfies.
  2. BaseAccount is a struct with shared fields + a default Deposit and Balance.
  3. SavingsAccount embeds BaseAccount (SavingsAccount struct { BaseAccount }). It gets all fields and methods for free, then overrides what differs.
  4. CheckingAccount does the same and adds an overdraft field.
  5. summarise([]Account{...}) walks any mix of account types — that's polymorphism, just declared explicitly.

The killer detail

type SavingsAccount struct {
    BaseAccount             // embedded — its fields/methods are promoted
}

func (a *SavingsAccount) Deposit(amount int) error {
    a.balanceCent += amount + amount/20  // 5% bonus
    return nil
}

Because SavingsAccount defines its own Deposit, that one is used. Balance() is inherited from the embedded BaseAccount. This is composition, not inheritance — but the day-to-day feel is similar.

What you gain over Python's class hierarchy

  • No deep inheritance trees — Go's design discourages them by making them awkward.
  • The interface stays small (4 methods here). Anyone implementing those 4 is an Account, no registration needed.
  • The compiler enforces the contract. Forget to implement Withdraw on CheckingAccount and the build fails.
