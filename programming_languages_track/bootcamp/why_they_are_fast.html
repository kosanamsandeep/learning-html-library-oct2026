Why are Go and Rust so much faster than Python?

"Faster" isn't a single thing. There are five separate decisions Python made for ergonomics that each cost some performance. Go undoes some; Rust undoes all. Once you understand the five, the speed gap stops being magic.

The five ergonomic-vs-speed trade-offs

Decision Python Go Rust
Compilation Interpreted (CPython bytecode VM) Compiled to native Compiled to native, optimising
Type information Looked up at runtime (every attribute access is a dict lookup) Known at compile time Known at compile time + monomorphisation
Memory layout Everything is a heap-allocated boxed object Structs live on the stack by default; pointers are explicit Same as Go, plus zero-cost abstractions over them
Concurrency One Python thread runs at a time (GIL); asyncio is cooperative Goroutines + M:N scheduler use all cores Threads + async, no GIL
Memory management Reference counting + cycle GC Concurrent tracing GC (sub-ms pauses) Compile-time ownership — no runtime GC at all

Each row is a 2-10× speedup on its own. They compound.

Speed factor 1 — compiled vs interpreted

Python source is compiled to bytecode at import time, then a virtual machine in C executes it instruction by instruction. Every x.y, every +, every for is several CPU instructions of dispatch overhead. Go and Rust compile to native machine code; x.y is one mov, + is one add.

A naive numeric loop in Python is 30-100× slower than the same loop in Go, and 50-200× slower than in Rust. Most of that gap is interpreter dispatch — not algorithmic.

Speed factor 2 — types known at compile time

In Python, obj.method() walks the MRO at runtime: check the instance dict, then the class, then base classes. The interpreter cannot inline anything because the next call could resolve to a totally different function.

In Go and Rust, the compiler knows the exact type. Most calls are direct or virtual through a small vtable. Many become inlined. The CPU branch predictor stays happy.

Rust's special trick: monomorphisation

fn print_all<T: Display>(xs: &[T]) {
    for x in xs { println!("{x}"); }
}

print_all(&[1, 2, 3]);          // monomorphised to print_all_i32
print_all(&["a", "b"]);          // monomorphised to print_all_str

The Rust compiler generates a separate, fully-specialised copy for each type used. That copy can be inlined and aggressively optimised — there's no runtime polymorphism cost.

Speed factor 3 — memory layout

In CPython, even an integer is a 28-byte heap-allocated object: refcount + type pointer + the actual value. A list[int] with a million entries is a million pointers to a million little boxes. Cache behaviour is poor.

In Go and Rust, primitive types are values: 8 bytes for an int64, period. []int64 in Go and Vec<i64> in Rust are contiguous arrays. The CPU cache loves them.

For numeric / bytes-heavy work the layout difference alone is 5-20×. This is why tokenizers (Rust) and polars (Rust) leave their pure-Python predecessors in the dust.

Speed factor 4 — concurrency

Python's Global Interpreter Lock

The GIL makes only one Python thread execute Python bytecode at a time. Multi-threading helps with I/O (the lock is released around blocking calls) but cannot scale CPU-bound work across cores. Workarounds are real but heavy: multiprocessing (separate processes, IPC overhead) or rewriting the hot path in C/Rust.

Note: Python 3.13+ ships an experimental no-GIL build, but it is not the default and most C extensions are not yet ready for it.

Go: goroutines + M:N scheduler

Go's runtime maps thousands of goroutines onto a small pool of OS threads. Each goroutine is ~2 KB of stack (vs ~1 MB for an OS thread). One process can run a million goroutines comfortably.

Rust: threads + async, no GIL

Rust uses real OS threads when you want them and zero-cost futures + an async runtime (Tokio) when you don't. There is no global lock — and the borrow checker statically prevents data races.

Speed factor 5 — memory management

Python Reference counting on every assignment, + a cycle collector. Refcount writes are atomic (under the GIL) — that's part of why removing the GIL is hard. Frees can cascade unpredictably.
Go Concurrent, tri-colour, write-barrier mark-and-sweep GC. Pauses are usually under 1 ms in production.
Rust No runtime GC. The compiler knows exactly when each value goes out of scope and inserts drop() there. Memory release is predictable, deterministic, and free at runtime.
Rust's lack of GC is what makes it suitable for kernels, browsers, and the absolute hot path of inference engines. Go's tiny-pause GC is what makes it perfect for network services.

Where the gap actually shows up

Workload Python Go vs Py Rust vs Py
JSON parsing per request baseline 5-10× 10-30×
HTTP handler hot loop baseline 10-30× 20-50×
Tokenisation of 1 MB text baseline 3-8× 20-100×
Vector similarity over 100k embeddings baseline (NumPy already C) 1-3× 2-10×
Concurrent fan-out to 1000 endpoints baseline (asyncio) 3-5× (less ceremony) 3-8×

Numbers are order-of-magnitude rules-of-thumb from public benchmarks. Your mileage will differ; what won't differ is the direction.

The mental model

  • Python is fast to write. Each line is the slowest, but you write fewer lines.
  • Go is fast to ship. Each line is fast, the compile is fast, the binary is one file.
  • Rust is fast to run. Each line is the fastest possible, with a compiler that pre-checks correctness — at the cost of a steeper learning curve.
The honest take: for most CRUD APIs Python is plenty. The bar isn't "is it faster?" — it's "is the speed bottleneck big enough that it justifies the productivity hit?" For a gateway, a tokeniser, a vector index, the answer is usually yes. For your agent and your evaluation harness, usually no.
