Presence service — heartbeats with a TTL

The green dot next to a user is one of the easiest patterns in system design: each client beats every few seconds; the server keeps "last seen" with a TTL.

The story

Your chat app needs to show who is online. A long-lived TCP connection is brittle (mobile networks drop). The simpler design is short-lived: each client sends a tiny heartbeat over HTTP/WebSocket every ~10s. The server keeps the last heartbeat per user. Anyone whose last heartbeat is within 30s is "online". No background offline check needed — TTL eviction is automatic.

Why heartbeats beat long connections

Approach Pros Cons
Long-lived TCP / WS connections Truly real-time Hard to scale; mobile networks kill connections silently.
Periodic heartbeat (this project) Cheap, stateless, auto-recovers Up to heartbeat_interval seconds of staleness.

Mental model

client beats every 10s
->
server sets last_seen=now
->
is_online? = now - last_seen ≤ 30s

In Redis this is exactly SET user:42:alive 1 EX 30 + EXISTS user:42:alive.

Run it

cd system_design_academy/system_design_case_studies/p3_realtime_presence
python main.py

The simulation runs three users with different heartbeat cadences over 90 fake seconds; you will see bob drop off, carol come online, and alice stay alive.

Interview-ready answer

"I use Redis with a TTL'd key per online user. Each client beats every 10s, server does SET user:<id>:alive EX 30. To list online users I scan or maintain a separate SET that is also TTL-evicted. The design degrades gracefully under partial network failure — there is no long connection to lose."
