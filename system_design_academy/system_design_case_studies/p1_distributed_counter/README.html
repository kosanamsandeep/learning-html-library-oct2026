Distributed counter — make view counts not melt

A YouTube-style view counter can take 100k increments per second on a single hot video. One row in one database cannot keep up. The standard fix is to shard the counter and sum at read time.

The story

A video goes viral. Every play needs to increment the view count. If the counter is a single row, every writer fights for the same lock — throughput collapses. Shard the counter into 16 (or 256) buckets, let each writer pick one at random, and reads simply sum the buckets. Writes parallelise; reads are slightly more expensive but still fast.

Mental model

writer picks random shard
->
increments only that shard
->
reader sums all shards
->
cache the sum for ~1s

The cache means most reads never even hit the shards.

Tradeoffs

Choice Effect
More shards (e.g. 256) Less write contention; read sum is wider.
Random shard pick Even distribution without any coordination.
Cache the read total Hides the sum cost when display rate >> write rate.
Strict real-time count Hard at high scale — accept eventual consistency.

Run it

cd system_design_academy/system_design_case_studies/p1_distributed_counter
python main.py

Eight writer threads each do 50,000 increments. The final total matches exactly, and you can see the per-shard distribution.

Interview-ready answer

"For a hot counter I shard the value across N keys — Redis hash slots or DB rows — and pick a random shard per write. Reads sum all shards and cache the result for a second or two. This trades small read latency for huge write throughput, and the count is eventually consistent which is fine for displays like view counts and likes."
