Saga pattern — distributed transactions without a distributed transaction

A booking touches three services: flight, hotel, payment. There is no two-phase commit across them. The saga pattern runs steps forward and undoes them with compensating actions when a later step fails.

The story

Flight reserved. Hotel reserved. Payment fails. Now what? The user did not get the booking, but you are holding a seat and a room. A saga rolls back: refund (no-op here), release hotel, cancel flight. The user sees a clean failure; nothing is stuck reserved.

Mental model

Step A: reserve flight
->
Step B: reserve hotel
->
Step C: charge card
->
success or compensate in reverse

Orchestration vs choreography

Style How it works When to pick it
Orchestration (this project) One coordinator calls each step and tracks state. Few steps, clear ownership, easy to debug.
Choreography Each service publishes events; others react. Many independently owned services; weaker central coordinator.

Hard truths

Compensations can fail. Refund APIs go down too. Alert humans when a compensation fails — there is no automatic recovery.
Steps must be idempotent. Retries are required, so doing a step twice must equal doing it once.
Order matters. Always compensate in reverse of forward order.

Run it

cd system_design_academy/system_design_case_studies/p4_saga_orchestrator
python main.py

You will see the happy path (all three steps succeed) and the payment-failure path (hotel and flight rolled back).

Interview-ready answer

"I use a saga any time a workflow spans services without a shared transaction — bookings, multi-step checkouts, signup flows. I prefer orchestration when the steps are few and well known, choreography when ownership is spread out. Every step has a compensating action, every step is idempotent, and a failed compensation pages a human because it cannot be auto-fixed."
