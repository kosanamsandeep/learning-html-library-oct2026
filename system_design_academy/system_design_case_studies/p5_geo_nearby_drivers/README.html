Nearby drivers — geohash bucketing for Uber-style dispatch

When the rider taps "ride", you need a list of drivers within 2 km in under 50 ms. A full scan is impossible at city scale. Geohashes bucket the world so you only scan the cells you care about.

The story

Bengaluru has thousands of active drivers. Scanning all of them every time someone opens the app is wasteful. A geohash turns (lat, lng) into a short string like tdr1y. Two locations close to each other share a long prefix — so bucketing drivers by their geohash gives near-constant-time lookup of "everyone in this cell".

Geohash precision vs cell size

Length Approx cell size Use case
4 chars ~ 20 × 20 km City-wide buckets.
5 chars ~ 4.9 × 4.9 km Ride dispatch within a neighbourhood (this demo).
6 chars ~ 1.2 × 0.6 km Walking distance proximity.
7 chars ~ 150 m Pinpoint / IoT.

Mental model

driver pings position
->
geohash(lat,lng,5)
->
map[bucket] = list of drivers
->
rider query → scan center bucket + 8 neighbours

The "+ 8 neighbours" trick handles riders standing right on the edge of a cell.

Production notes

  • Drivers move; you must re-bucket on each location ping (every 5–10s).
  • Use Redis GEO commands (GEOADD / GEOSEARCH) — they use geohashes under the hood.
  • Use the haversine formula (great-circle distance) for the final precise filter — geohash gives "in the right cell", haversine gives "actually within R km".

Run it

cd system_design_academy/system_design_case_studies/p5_geo_nearby_drivers
python main.py

The demo seeds 50 drivers around Bengaluru and queries from MG Road and Indiranagar.

Interview-ready answer

"For 'find nearby X' I bucket entities by geohash prefix. Length 5 gives ~5 km cells which suit ride dispatch. On a query I scan the rider's cell plus the 8 neighbours, then filter with haversine for precise radius. In production this is a Redis GEO key or a quadtree backed by an in-memory index per service node."
