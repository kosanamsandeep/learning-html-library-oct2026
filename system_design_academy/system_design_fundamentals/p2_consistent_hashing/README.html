Consistent hashing — add a server without breaking the cache

If you shard data with hash(key) % N, adding a single server can move nearly every key. Consistent hashing keeps the move small — only the slice owned by the new server changes.

The story

You scale from 3 cache servers to 4 to handle Black Friday traffic. With naive modulo sharding, ~75% of keys change owner — cache miss storm. With a consistent hash ring, only ~25% of keys move. The site stays warm.

Mental model

Hash key to a slot
->
Walk clockwise on the ring
->
First server you meet owns the key

Each server is placed on the ring at many "virtual nodes" so the load distribution stays even. Removing a server only re-maps the keys that fell on its slots.

Why virtual nodes matter

Setup What happens
1 slot per server Unbalanced load; some servers carry much more than others.
~100–200 virtual nodes per server Smooth distribution and small remap when membership changes.

Core code

slot = _hash(key)
index = bisect_right(self._ring, slot) % len(self._ring)
return self._slot_to_node[self._ring[index]]

The ring is just a sorted list of integers; bisect_right gives the next slot in O(log N).

How to run

cd system_design_academy/system_design_fundamentals/p2_consistent_hashing
python main.py

You will see the distribution across 3 nodes, then the small fraction of keys remapped after adding and removing nodes.

Interview-ready answer

"I use consistent hashing whenever I need to shard data across servers that may be added or removed — cache layers, partitioned queues, or session stores. Virtual nodes keep the load even, and only the slice belonging to a changed server is re-mapped, which avoids cache miss storms during scaling."
