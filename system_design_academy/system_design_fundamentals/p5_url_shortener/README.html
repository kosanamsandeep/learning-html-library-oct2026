Fundamentals · Project 5

URL shortener — the classic 5-line system design question

Turn a long URL into a tiny code. Map the code back at read time. Decide what to do about collisions, hot codes, and analytics. Two strategies in one file.

The story

Marketing wants short links for SMS campaigns: 160 characters total, so the URL must be tiny. The system is read-heavy — one POST to create, billions of GETs to follow. Latency on resolve matters more than anything else.

Two strategies

Strategy How it works Good Tradeoff
Hash slice Take first N chars of SHA-256(url) as the code. Same URL → same code. No coordination needed across servers. Collisions need a fallback (lengthen the slice).
Counter + base62 Allocate a monotonic id, encode in base62. No collisions ever. Codes stay short. Needs a global counter (Redis INCR, ticket server, or DB sequence).

Mental model of the read path

GET /abc1234
->
CDN / edge cache
->
Read replica
->
302 redirect

The vast majority of traffic should never hit the database. Cache aggressively; URLs are immutable once created.

Why base62?

62 = 10 digits + 26 lowercase + 26 uppercase. Fits in URL-safe characters. A 7-character base62 code addresses ~3.5 trillion items — enough for any real shortener.

62^7 = 3,521,614,606,208

Run it

cd system_design_academy/system_design_fundamentals/p5_url_shortener
python main.py

You will see the same URL produce the same hash-based code and a new counter-based code, plus a resolve round-trip.

Interview-ready answer

"I default to counter + base62 because collision handling is built in and codes stay short. I generate the counter with Redis INCR or a ticket server, so the API tier stays stateless. The read path goes CDN → read replica; URLs are immutable, so the cache hit rate is very high. If campaigns demand a deterministic code per URL, I add a hash-based path that re-uses an existing record when present."
