Idempotent API — make retries safe with one header

Networks drop responses. Clients retry. Without an idempotency key the customer is charged twice. The fix is small: keep a (key → response) store and replay the first answer.

The story

Your payments API succeeds, but the response is lost in transit. The mobile app retries. Without idempotency, you have just charged the customer twice. With an idempotency key, the server recognises "I already did this work" and replays the original response.

The contract (Stripe-style)

Client picks a UUID
->
Sends as Idempotency-Key header
->
Server: seen this key?
->
Yes: replay. No: do the work, store result.

The client uses the same key for every retry of the same logical request, and a new key for a genuinely new request.

What can go wrong without it

Scenario Without idempotency With idempotency
Server processed, response dropped Client retries → second charge. Server replays original response; no new charge.
Client times out, retries Risk of duplicate work. Server returns the original result quickly.
Same key but different body Hard to detect. Reject with 409 Conflict — body must match.

Run it

cd system_design_academy/system_design_fundamentals/p4_idempotent_api
python main.py

Three "attempts" with the same key produce only one real charge. The second and third attempts return the cached response marked replayed: True.

Production notes

  • Store the key + response in Redis or a dedicated table with a TTL (24h is common).
  • Hash the request body and compare on replay — refuse if a different body uses the same key.
  • Lock the key while the first request is in flight, otherwise two parallel retries can both do the work.

Interview-ready answer

"For any non-GET endpoint that touches money or state, I require an Idempotency-Key. The server stores (key → response) with a 24-hour TTL and replays the original response on retries. I lock the key during the first request and hash the body so the same key with a different payload is rejected — that catches client bugs early."
