Rate limiter — three classic algorithms, one demo

Stripe, Cloudflare, AWS, and almost every public API rate-limits requests. The choice of algorithm controls how the system feels: smooth, bursty, or strict.

The story

Your API got featured on a tech newsletter. Suddenly traffic is 30× normal. Without a rate limiter, one greedy client can starve everyone else. A rate limiter is the polite bouncer at the door — it lets in a fair share and asks the rest to come back soon.

The three algorithms

Algorithm How it works Best for Watch out for
Token bucket Tokens refill at a steady rate up to a max bucket size; each request costs one. APIs that want to allow short bursts but cap sustained rate. Picking a too-big bucket lets one client burst hard.
Sliding window log Store a timestamp per request; count timestamps inside the window. Strict per-second/per-minute fairness. Memory grows with traffic; use approximations at scale.
Fixed window counter One counter per time window; reset at window boundary. Cheap counters when exactness does not matter. Boundary bursts: 2× the limit possible across a window edge.

Mental model

Request arrives
->
Lookup limiter for this key
->
Allow or deny
->
Update internal state

Real systems key the limiter by user id, API key, or IP, and store the state in Redis so multiple servers share one view.

Core code

def allow(self) -> bool:
    now = time.monotonic()
    self.tokens = min(self.capacity, self.tokens + (now - self.last) * self.rate)
    self.last = now
    if self.tokens >= 1:
        self.tokens -= 1
        return True
    return False

Notice the bucket is updated lazily on each request — no background thread needed.

How to run

cd system_design_academy/system_design_fundamentals/p1_rate_limiter
python main.py

You will see the same request pattern hit all three limiters and notice the differences.

Interview-ready answer

"I usually start with a token bucket because it allows short bursts while still capping the long-term rate. If exact fairness across a window matters I move to a sliding window log, knowing it costs more memory. Fixed window counters are cheapest but allow 2× bursts at window boundaries, which I call out explicitly. In production I keep limiter state in Redis with a Lua script so it stays consistent across multiple API servers."
