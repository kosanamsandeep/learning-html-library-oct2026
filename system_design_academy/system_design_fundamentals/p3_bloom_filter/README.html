Bloom filter — answer "have I seen this?" in 10 bits per item

A bloom filter trades a small false positive rate for huge memory savings. Crawlers, key-value stores, and CDNs use them to skip expensive lookups.

The story

You crawl 100 million URLs. Storing them all in a Python set would use gigabytes. A bloom filter sized for that load fits in ~120 MB and answers "have I seen this URL?" in microseconds. The catch: it can say "maybe yes" when the answer is actually no — a false positive. It can never say "no" when the answer is yes.

How it works

k hash functions
->
k bit positions
->
add: set those k bits
->
check: are all k bits set?

If any of the k bits is zero, the item is definitely not there. If all are one, it might be there (or another item set the same bits).

Choosing size and hash count

Inputs Formula What you control
expected items n, target FP rate p size m = -n·ln(p) / (ln 2)^2 Memory the filter uses.
m and n hashes k = (m/n) · ln 2 Lookup speed; usually 5–10.

Code in main.py picks these for you so you only choose n and p.

When to use, when to avoid

Use when a false positive only costs an extra lookup (cache, disk, network) and the real check happens after.
Avoid when a false positive is unsafe — billing, identity, security checks. A "maybe yes" can never be a final answer.

Run it

cd system_design_academy/system_design_fundamentals/p3_bloom_filter
python main.py

The demo inserts 5,000 items and then probes 10,000 unseen items, reporting the observed false positive rate against the 1% target.

Interview-ready answer

"I reach for a bloom filter when I need a cheap 'definitely not seen' check in front of an expensive lookup — disk read, network call, or cache. I never use it as the final source of truth because false positives are baked into the design. I size it from the expected item count and target false positive rate using the standard formula."
