Advanced RAG + Verification Loops

High value The pattern that turns a plain RAG pipeline into a self-checking system — plus the tools (graph databases, AST code indexing, context engineering) that make retrieval both smarter and cheaper.

THINK / KNOW / ANSWER / JUDGE / LEARN

A clean, practitioner-proven RAG architecture with an evaluation loop. If you're building a RAG pipeline with retry logic, this is the formal reference to design against — each stage is independently testable, and JUDGE gives the system a bounded self-correction mechanism.

graph TB Q["User Query"] --> T["THINK
Supervisor — understand intent"] T --> K["KNOW
Retriever — find evidence"] K --> A["ANSWER
LLM — generate using evidence"] A --> J["JUDGE
Evaluator — pass/fail"] J -->|"fail"| K J -->|"pass"| OUT["Final answer"] A --> L["LEARN
Learning Engine —
remember what worked"] L -.-> T
StageComponentJob
THINKSupervisor / RouterClassify intent, decide if retrieval is even needed
KNOWRetrieverFind candidate evidence (hybrid search, rerank)
ANSWERGenerator LLMProduce an answer grounded in the retrieved evidence
JUDGEEvaluatorPass/fail against a rubric (faithfulness, citation validity). Retry or return.
LEARNLearning engineRecord what worked → inform future routing/retrieval
Key discipline: JUDGE must be bounded — a retry budget, not an infinite corrective loop. And LEARN isn't optional: without it, JUDGE failures repeat forever. This is the evaluator-optimiser pattern applied to RAG.

Graph Databases — the "Understanding" Layer

High value The one-liner that frames GraphRAG: "LLMs generate. Vector DBs find. Graph DBs understand how things are connected."

Taxonomy vs Ontology (the key distinction)

TaxonomyOntology
WhatA hierarchy of categoriesEntities + their relationships + rules
ExampleProduct → Electronics → SmartphoneSmartphone compatible_with Charger; Employee works_at Dept
Answers"Is X a kind of Y?""How is X connected to Y?" — multi-hop

In a 5-stage agentic architecture, the knowledge layer is LLM + VectorDB + GraphDB together — vector similarity for "find," graph traversal (Cypher) for "understand how things connect." Popular engines: Neo4j, Amazon Neptune, TigerGraph, JanusGraph.

Relevance: You already use Neo4j + APOC. This is the conceptual map for that exact work — and why a graph query can answer "which policies mention a penalty tied to this clause" that pure vector search can't.

codebase-memory-mcp — AST Knowledge Graphs Verified

Verified via arXiv:2603.27277. The tool indexes an entire codebase (28M lines of Linux kernel in 3 minutes) into an AST knowledge graph so the agent doesn't re-read files.

Facts (corrected from the tweet's overclaim)

  • Uses tree-sitter for AST parsing — supports 158 languages, runs 100% locally as a single static C binary (no Docker / Ollama / API keys).
  • Stores the graph in SQLite; exposes 11–14 MCP tools.
  • Evaluated across 31 real-world repos: 83% answer quality vs 92% for file-exploration, at roughly 10× fewer tokens.
  • The tweet's "99% token reduction" overstates the paper's real "10× fewer tokens" figure — but the core value is real and peer-reviewed.
  • Works with Claude Code, Cursor, Aider, Gemini CLI.
Why this is your single most actionable find: you were already investigating codebase-memory-mcp as RAG for code structure to fight context bloat with Aider + local LLMs. It's real, published, and directly solves that exact problem. Install and test it against a large repo.

Chunking & Retrieval — the discipline that compounds

From the same thread of practitioner knowledge (and consistent with your chatbot design doc):

  • Chunking is experimental, not fixed. Recursive (multiple sizes: 256/32 … 1024/128), semantic (embedding-based boundaries), structure-aware (PDF/Markdown/code), parent-child. Evaluate each against Recall@K and downstream faithfulness.
  • Retrieval is a pipeline, not a single call. Dense + sparse → RRF fusion → cross-encoder rerank → context builder (dedup → merge → token budget → order → provenance).
  • Query transformation — standalone query, rewrite, multi-query, decomposition, HyDE, step-back. Route per query type; never enable all globally.
Why this module's pattern matters together: RAG quality = retrieval quality × grounding enforcement × context budget. THINK/KNOW/ANSWER/JUDGE/LEARN gives you the enforcement; graph DBs and AST graphs give you smarter retrieval; context engineering gives you cheaper retrieval. All three are needed for a production system.
