nanoGPT Explained

Building a Transformer language model piece by piece — learning from Andrej Karpathy's legendary lecture, visualized with every block's "why", "what if", and measurable impact.

Based on Karpathy's "Let's build GPT from scratch"

What is nanoGPT?

nanoGPT is a minimal implementation of the GPT (Generative Pre-trained Transformer) architecture — the same core technology behind ChatGPT. It's just two files of ~300 lines each: one defines the model, one trains it.

Andrej Karpathy built it to show that the Transformer isn't magic — it's a series of simple, composable blocks. Each block adds a capability, and you can see the loss drop and the output improve as you add them.

💡 The Big Idea: Start with the dumbest possible language model (just count which character follows which), then add one Transformer ingredient at a time. Watch the validation loss fall from 2.50 → 1.48 and the text go from random garbage to Shakespeare-sounding prose.

Data & Tokenization

Before we build anything, we need data. Karpathy uses the Tiny Shakespeare dataset — all of Shakespeare's works concatenated into a single ~1 MB file (~1 million characters).

Character-Level Tokenization

We map each character → integer (65 unique characters in Shakespeare). This is the simplest possible tokenizer:

# The entire vocabulary of Shakespeare
chars = sorted(list(set(text))) # 65 characters
vocab_size = len(chars) # 65

stoi = {ch:i for i,ch in enumerate(chars)} # char → int
itos = {i:ch for i,ch in enumerate(chars)} # int → char

encode = lambda s: [stoi[c] for c in s] # "hi" → [46, 47]
decode = lambda l: ''.join([itos[i] for i in l]) # [46, 47] → "hi"

How Training Examples Are Packed

We sample random chunks of text (batch size × block size). Crucially, every prefix is its own training example — in a chunk of 9 characters there are 8 training examples packed in, from context length 1 to block size.

flowchart LR subgraph Chunk["Chunk of 9 characters: [18, 47, 56, 57, 58, 1, 15, 47, 58]"] direction LR C1[18] --> C2[47] --> C3[56] --> C4[57] --> C5[58] --> C6[1] --> C7[15] --> C8[47] --> C9[58] end subgraph Examples["8 training examples packed inside"] direction TB E1["x: [18] → y: 47"] --> E2["x: [18, 47] → y: 56"] E2 --> E3["x: [18, 47, 56] → y: 57"] E3 --> E4["x: [18, 47, 56, 57] → y: 58"] E4 --> E5["...continuing..."] end Chunk --> Examples

🔑 Key insight: Training on all prefixes makes the model robust — during generation, it can start with just one character of context and still predict well.

0 The Bigram Model

The simplest possible language model: predict the next character based only on the current character. No context. No memory. Just "if you see 'q', the next char is probably 'u'".

✅ What it does

Learns that certain characters tend to follow others (e.g. 'q → u', space → capital). Simple, fast, interpretable.

❌ What's missing

No context awareness. Each prediction is blind to everything except the very last character. It cannot know what the sentence is about.

1 Positional Encoding

The first upgrade: tell each token where it is in the sequence. We add a learnable position embedding to each token's embedding.

Without position info, the model treats "the cat sat" and "sat cat the" identically — it's permutation-invariant. Positional encoding breaks this symmetry.

💡 Why this matters for Self-Attention: Attention operates on sets — it has no built-in notion of order. Positional encoding is the only thing telling the model WHERE each token is. Without it, "I love you" and "you love I" look the same to the attention mechanism.

2 Single-Head Self-Attention

The core innovation of the Transformer. Each token looks at all previous tokens and decides how much to listen to each one — in a data-dependent way.

The Math Trick: Weighted Aggregation with Matrix Multiply

Before implementing attention, Karpathy shows a crucial trick: you can compute averages of previous tokens efficiently using a lower-triangular matrix and a single batched matrix multiply.

The Self-Attention Mechanism

Instead of uniform averages, each token emits a Query ("what am I looking for?"), a Key ("what do I contain?"), and a Value ("what do I share?"). Affinity = Query · Key, then softmax, then aggregate Values.

(B,T,T) — data-dependent"] Aff --> Mask["Mask future tokens → -∞

✅ With Self-Attention

Tokens can now look at relevant context. A vowel finds nearby consonants. A pronoun finds its referent. Predictions are context-aware.

❌ Without Self-Attention

Each token predicts in total isolation. The model has no idea what the sentence is about. It's just bigram statistics — no better than counting pairs.

3 Multi-Head Attention

One attention head can only learn one relationship pattern. But tokens need many: "Am I a vowel looking for consonants? Am I a verb looking for a subject? Am I a pronoun looking for a referent?"

Solution: Run multiple attention heads in parallel, each with its own Q, K, V projections. Concatenate their outputs.

✅ With Multi-Head (4 heads)

Each head can specialize: Head 1 tracks vowel→consonant patterns, Head 2 tracks article→noun, Head 3 tracks sentence boundaries, etc. The model builds a rich, multi-faceted representation.

❌ Single Head Only

Only one communication channel. The model must choose: grammar OR syntax OR semantics — it can't do all three. Representations are impoverished.

🎯 Like group convolution: Instead of one giant attention operation (expensive, hard to train), we split into smaller parallel heads that are computationally efficient and learn diverse features.

4 Feed-Forward Networks (Computation)

Attention handles communication between tokens. But after gathering information, each token needs to think — to process what it learned. That's the Feed-Forward Network (a simple MLP applied to each token independently).

✅ With FFN (Computation)

Token gathers info from past, then processes it through a non-linear transformation. "Think before you speak." The inner layer is 4× wider, giving the model room to compute rich features.

❌ No FFN (Computation-less)

Tokens talk to each other but have no capacity to process what they hear. It's like having a meeting where everyone speaks but nobody thinks. The model needs depth of computation, not just breadth of communication.

📊 Performance Improvement
Multi-head only
2.28
+ Feed-Forward
2.24

↓ -0.04 improvement. Small here, but FFNs become critical as models deepen.

🔑 Communicate → Compute pattern: This interleaving of attention (gather) and FFN (process) is the fundamental rhythm of a Transformer. Each block = one round of "talk then think".

5 Residual Connections + Stacking Blocks

Now we want to stack multiple Transformer blocks (communication + computation) to build a deep network. But deep networks are hard to optimize — gradients vanish as they backprop through many layers.

Solution: Residual (skip) connections. Each block forks off from a main "residual pathway", does its computation, and adds back via "+". Gradients flow directly through the additions.

flowchart TB subgraph Deep["Deep Transformer with Residuals"] direction TB Input["x"] --> Add1["✚"] Attn["Multi-Head Attention"] --> Add1 Input --> Attn Add1 --> Add2["✚"] FFN["Feed-Forward"] -.-> Add2 Add1 --> FFN Add2 --> Output["Output + Gradient Super Highway"] end subgraph Gradient["Gradient Flow"] direction LR Loss --> G1["∂Loss/∂Output"] --> G2["✚ splits gradient equally"] G2 --> G3["to FFN (fork)"] G2 --> G4["to Add1 (main path)"] G4 --> G5["...all the way to Input"] end style Add1 fill:#1e293b,stroke:#4ade80,stroke-width:2px style Add2 fill:#1e293b,stroke:#4ade80,stroke-width:2px style Gradient fill:#1e293b,stroke:#fbbf24

✅ With Residual Connections

Gradients flow unimpeded from loss → input via the "super highway" of addition ops. Blocks start near-identity (initialized to contribute almost nothing) and gradually come online during training.

❌ Without Residuals (Naive Stacking)

Gradients must pass through every nonlinearity, causing vanishing gradients in deep stacks. The first few blocks train, but deeper blocks learn nothing. Loss plateaus.

📊 Performance Improvement
Shallow (1 block)
2.24
Deep + Residuals
2.08

↓ -0.16 improvement. Residuals unlock depth — stacking 6+ blocks becomes possible.

🛣️ The Gradient Super Highway: Addition distributes gradients equally to both branches. So gradients from the loss can skip all the nonlinear blocks and flow straight to the input — unimpeded. The residual blocks start "off" and gradually turn on during training.

6 Layer Normalization

Layer Norm stabilizes training by normalizing each token's features to have zero mean and unit variance. Unlike Batch Norm (which normalizes across examples), Layer Norm normalizes across features for each token independently.

✅ With Layer Norm (Pre-Norm)

Applied before each sub-layer (attention/FFN) — the "Pre-Norm" formulation. Normalizes inputs, keeping activations well-behaved. Each token's features have controlled scale, preventing exploding activations in deep stacks.

❌ Without Layer Norm

As the model deepens, activation magnitudes grow uncontrollably. Training becomes unstable — loss spikes, NaNs. The model diverges beyond a few layers.

Modest improvement here, but essential for stability at larger scales.

📐 Pre-Norm vs Original: The original "Attention is All You Need" paper applied Norm after each sub-layer (Post-Norm). Modern practice (and nanoGPT) applies it before (Pre-Norm) — it's more stable and allows larger learning rates.

Complete Decoder-Only Architecture

What we actually built is a decoder-only Transformer (GPT-style), not the full encoder-decoder from the original paper. Here's what that means:

✅ Decoder-Only (GPT)

Only needs the triangular mask — each token sees only past tokens. Perfect for language modeling (predicting what comes next). Simpler architecture, fewer parameters, scales beautifully.

📐 Encoder-Decoder (Original Paper)

Has an encoder (full attention, no mask) to read source text, and a decoder with cross-attention to attend to it. Designed for translation. More complex, more flexible for conditional generation.

🧠 Why GPT works without an encoder: In language modeling, there's no external "source" to condition on — the model just continues the text. The past context IS the conditioning. That's why the decoder-only design is sufficient and has become the dominant architecture.

⚡ Core Concepts Recap

Three essential Transformer ideas that repay re-visiting. Understanding these deeply will make every other LLM paper and implementation click.

Concept 1 · Positional Encoding

Why Positional Encoding Is Needed (Even When Data Is an Ordered List)

🧠 The Core Insight

Your dataset is an ordered sequence — [18, 47, 56] has a clear left-to-right meaning. But the internal math of Self-Attention (Q · Kᵀ) treats tokens as an unordered set. The dot product between two token vectors is the same number regardless of where they sit in the sequence. This is called permutation invariance.

🚫 Without Positional Encoding

"cat eats fish" and "fish eats cat" produce identical attention scores at every position. The model literally cannot tell the difference between subject and object.

flowchart LR subgraph WithoutPE["Attention Without Position — Permutation Invariant"] direction TB W1["Token A: 'cat'
Token B: 'eats'
Token C: 'fish'"] W2["Q·Kᵀ gives same scores
regardless of order"] W3["'cat eats fish' = 'fish eats cat'
to the attention mechanism ❌"] end subgraph WithPE["With Positional Encoding — Order Matters"] direction TB P1["Token A + Pos₁: 'cat'
Token B + Pos₂: 'eats'
Token C + Pos₃: 'fish'"] P2["Q·Kᵀ now sees:
'cat at pos₁' different from
'cat at pos₃'"] P3["'cat eats fish' ≠ 'fish eats cat' ✅"] end style WithoutPE fill:#1e293b,stroke:#f87171 style WithPE fill:#1e293b,stroke:#4ade80

💡 The Solution: We add a learnable position vector (wpe) to each token's embedding vector (wte) right at the input. Now each token carries both what it is and where it is. The attention can distinguish "the dog bit the man" from "the man bit the dog" because the vectors at position 2 and position 4 are different — even if the tokens are the same.

Concept 2 · The Lower-Triangular Trick

Weighted Aggregation (How Tokens Communicate)

🧠 The Problem

In autoregressive generation, token #5 needs to aggregate information from tokens #1–4 (but NOT #6–8). Doing this with nested for loops is too slow on a GPU. We need a vectorized way.

📐 The Math Trick

Multiply the sequence matrix by a lower-triangular weight matrix:
• Zeros in top-right — block future tokens from peeking ahead
• Rows in lower-left — assign weights to current + past tokens
• One batched matrix multiply does all positions at once.

flowchart LR subgraph Triangle["The Lower-Triangular Weight Matrix (T × T)"] direction TB M["[1.0 0 0 0 ]
[0.5 0.5 0 0 ]
[0.33 0.33 0.33 0 ]
[0.25 0.25 0.25 0.25]"] end subgraph Agg["What It Does — Row by Row"] direction TB R1["Row 1: token₁ alone"] R2["Row 2: average(token₁, token₂)"] R3["Row 3: average(token₁, token₂, token₃)"] R4["Row 4: average(token₁, token₂, token₃, token₄)"] end M --> Agg style Triangle fill:#1e293b,stroke:#38bdf8 style Agg fill:#1e293b,stroke:#fbbf24

🔧 Evolution to Self-Attention

This fixed triangular matrix does uniform averaging (weights are all the same per row). Self-Attention replaces those static weights with data-dependent, learned scores from Q·Kᵀ. Now each token can dynamically decide how much to listen to every other token:

"The fox jumps over the lazy dog" → "jumps" might place 60% of its attention on "fox", 10% on "dog", and 30% spread over the rest.

❌ Why Nested Loops Don't Work

A Python for loop over T positions × B batch items would be hundreds of sequential operations. GPUs are designed for massive matrix multiplications — the triangular trick turns a sequential aggregation into a single, highly parallel matmul. This is what makes Transformer training at scale possible.

Concept 3 · KV Cache

Why Only K and V Are Cached (and Q Is Not)

During generation, after predicting token t, we slide to token t+1. We don't want to re-compute projections for every past token. The KV Cache is the optimization that makes this possible.

sequenceDiagram participant Gen as Generation Loop participant Cache as KV Cache (GPU VRAM) participant Model as Transformer Note over Gen: Generating token #5 Gen->>Model: "Here is token #5's embedding" Model->>Model: Compute Q₅ (for token #5 only) Model->>Cache: "Give me K₁₋₄ and V₁₋₄" Cache-->>Model: Returns cached K₁₋₄, V₁₋₄ Model->>Model: Attention(Q₅, K₁₋₄, V₁₋₄) → output token #5 Note over Model: Now compute K₅ and V₅ for the cache Model->>Cache: Store K₅, V₅ Cache->>Cache: Cache now holds K₁₋₅, V₁₋₅ Note over Gen: Generating token #6 — repeat with Q₆

🧠 Why Only K and V Are Cached

Query (Q): Belongs only to the brand-new token being generated. Once token t finishes predicting, its Query is discarded — token t+1 creates its own new Query from scratch.

Keys (K) and Values (V): Belong to all past tokens. Past tokens never change, so their K and V vectors remain constant for the entire generation session. Cache them once, reuse forever.

🔥 The Cost Without KV Cache

Without caching, generating token #100 would re-compute K₁₋₉₉ and V₁₋₉₉ from scratch — 99 unnecessary matrix multiplications. Each new token would cost O(T²) instead of O(T) in attention computation. For a 4096-token context, that's ~16× more compute per token.

💾 Storage vs. Memory — A Key Distinction: The KV Cache lives in fast, scarce GPU VRAM during active generation (because every new token needs to read it instantly). Long-term conversation history sits as lightweight raw text in standard cloud databases or Redis. The KV cache is a runtime optimization, not a persistence strategy. For a 7B model generating 2048 tokens, the KV cache can consume ~1 GB of GPU memory — that's why managing it (cache pruning, sliding window, etc.) is an active research area.

💬 Concrete Example

User prompt: "What is the capital of France?" → model generates "The capital of France is Paris."

Without cache: For the word "Paris", re-run Q/K/V projections for all 7 input tokens + all generated tokens so far from scratch.
With cache: Only compute Q for the current position. Fetch K and V for all prior positions from the cache. ~4× faster generation in practice.

⚡ The operational trade-off: KV Cache trades GPU memory for generation speed. It's why you see "context length" limits on LLM APIs — the KV cache for 128K tokens won't fit on most GPUs without optimization (e.g., Multi-Query Attention, grouped-query attention, sliding window, or offloading).

📈 The Pre-training → Assistant Pipeline
  1. Pre-training (nanoGPT-scale): Train a decoder-only Transformer to predict the next token on a large corpus. Result: a document completer that mimics the training data style.
  2. Supervised Fine-Tuning (SFT): Fine-tune on thousands of high-quality Q&A examples. The model learns the format of being helpful: "question → answer".
  3. Reward Modeling (RM): Humans compare model outputs and rank them. Train a separate model to predict which response humans prefer.
  4. RLHF (PPO): Use reinforcement learning to make the model produce responses that score highly on the reward model. This aligns the model to be helpful, honest, and harmless.

🚀 The key takeaway: The ~600 lines of nanoGPT code you just learned contains the core architecture of ChatGPT. The Transformer blocks, the attention mechanism, the residual connections, the layer norms — it's all the same. What differs is the scale (10M → 175B+ parameters) and the training data (Shakespeare → the internet) and the alignment stage (RLHF).
