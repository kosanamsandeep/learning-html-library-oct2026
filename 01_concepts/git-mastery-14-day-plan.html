Plan overview Read first

This plan assumes you are the only engineer but want to behave like one of 100. To simulate the team you will:

  • Use multiple feature branches in parallel as if different developers opened them.
  • Keep a second clone of the same repo in a sibling folder (call it poc_iq_dev2) and use it to push conflicting work, then resolve as the "other developer".
  • Open and review your own Pull Requests on GitHub the same way a real reviewer would: comment, request changes, then approve.
  • Promote code through dev → qa → main branches the way a release manager would.
Mental model: Git tracks snapshots, not files. A commit is a snapshot + parent pointer. Branches are just movable pointers to commits. Everything else (merge, rebase, cherry-pick, revert) is moving or copying these pointers. Once you internalize that, every command makes sense.

How to use each day

  1. Read the Goal and Why it matters.
  2. Run the Commands block in the listed order.
  3. Read the What if you do it the wrong way box — this is where most team incidents come from.
  4. Tick off the Self-check before moving on.

The big question: how often should I commit?

Do

  • Commit when a single logical change is complete and the code still runs. Could be 1 file or 20 files — size doesn't matter, cohesion does.
  • Use many small commits while you work, then optionally squash them into 1–3 meaningful commits before the PR is merged.
  • Each commit message must explain why, not just what.

Don't

  • Don't make one giant 40-file commit at the end of the day called "updates". Reviewers can't review it and reverting it is dangerous.
  • Don't commit every keystroke either ("fix typo", "fix typo again") on the shared branch — squash those locally first.
  • Don't commit broken or non-compiling code to a shared branch.

Rule of thumb: on your feature branch commit as often as you like (cheap save points). Before merging into dev, curate the history so each commit tells a story a stranger could read in a year.

Week 1 · Foundation Solo fluency

Goal of the week: be unshakeable on the everyday loop — status → diff → add → commit → push → pull, branching, and your first PR.

Day 1~45 min

Identity, config, and reading the repo

Goal: never again be confused about "what state is my repo in?".

Commands

git status              # working tree vs index vs HEAD
git status -sb          # short format with branch info (your alias: git st)
git log --oneline -10
git lg                  # graph of all branches
git diff                # unstaged changes
git diff --staged       # what would be in the next commit
git remote -v
git branch -vv          # local branches + their upstream tracking

Why each matters

  • git status answers "what will git commit include?".
  • git diff --staged is the only truth about what your next commit contains. Always run it before committing.
  • git branch -vv shows which remote branch each local branch tracks. Most "my push went somewhere weird" incidents come from missing this.

Good habit

Run git status before and after every Git command for the first two weeks. Build the muscle memory.

Bad habit

Running git add . and git commit -am "wip" without looking at status. You will eventually commit .env, a 200 MB zip, or a half-broken file.

Self-check: can you explain the three areas (working tree, staging index, HEAD) and which command moves changes between them?

How often to commit (definitive answer)

Situation Commit cadence Why
On your own feature branch Every 15–60 min when a thought is finished Cheap save points; you can rewrite history later.
Before opening a PR Curate to 1–5 meaningful commits via squash/rebase Reviewers read the history, not just the diff.
On dev/main Only via PR merge — never direct commits Direct commits skip CI and review, the two safety nets.

Day 3~60 min

Branching model for a 100-dev team

Goal: understand which branch is for what, and never push to the wrong one.

Recommended model (trunk-based with env branches)

  • main — production. Always deployable. Only updated by release merges or hotfixes. Protected: no direct pushes, PR + approvals required.
  • qa (or staging) — what QA tests. Updated by merging dev at the end of a sprint or candidate freeze.
  • dev (or develop) — integration branch. All feature PRs land here. Must stay green.
  • feature/<ticket>-<slug> — one branch per ticket, short-lived (ideally < 3 days).
  • bugfix/<ticket>-<slug> — non-urgent bug fix, off dev.
  • hotfix/<ticket>-<slug> — urgent production fix, off main, merged into both main and dev.
  • release/v1.4.0 — optional stabilization branch when you need to freeze features but keep fixing bugs for that release.

Setup the three env branches in your lab

git checkout master
git branch -m master main          # rename to industry standard
git push -u origin main
git push origin --delete master    # only after main is set as default on GitHub

git checkout -b dev
git push -u origin dev
git checkout -b qa
git push -u origin qa
git checkout dev
On GitHub: Settings → Branches → set main as default → add branch protection on main and qa: require PR, require status checks, disallow force-push.

Create your first feature branch

git checkout dev
git pull --ff-only
git checkout -b feature/BANK-101-add-leaderboard-projection
# do work, commit, push
git push -u origin feature/BANK-101-add-leaderboard-projection

Good

Short-lived feature branches (< 3 days). Rebased on dev daily so they stay current. Merged via PR and deleted right after.

Bad

A feature/big-refactor branch alive for 6 weeks. By merge time it conflicts with everything and nobody remembers why decisions were made.

Day 4~45 min

Pull vs Fetch — the single most misunderstood pair

Goal: know which to use and why.

Command What it does Touches working tree?
git fetch Downloads new commits from remote into origin/* tracking branches. No. Safe. Always.
git pull = git fetch + git merge (or rebase) of the upstream into your current branch. Yes — can create merge commits or conflicts.
git pull --ff-only Only updates if no local commits would be overwritten by merge; otherwise refuses. Safest "pull" — recommended default.
git pull --rebase Fetches then replays your local commits on top of the new upstream. Keeps history linear, no merge bubbles.

The pro daily routine

git fetch --all --prune         # see what changed everywhere; prune deleted remote branches
git status                       # am I ahead/behind?
git pull --ff-only               # if behind only, fast-forward; else handle explicitly

What if you fetch first

You see exactly what's coming before it touches your code. You can decide merge vs rebase vs reset on a per-branch basis. Zero surprises.

What if you just git pull blindly

If you had un-pushed local commits and the remote also moved, Git creates a merge commit on your branch with a message like "Merge branch 'dev' of github into dev". Multiplied across 100 devs, the history becomes spaghetti and bisecting bugs becomes painful.

Lab exercise (simulate teammate)

# Terminal A (you, in poc_iq)
git checkout dev
echo "// note from dev1" >> docs/styles.css
git commit -am "chore(docs): dev1 note"

# Terminal B (in poc_iq_dev2)
git checkout dev
git pull --ff-only
echo "// note from dev2" >> docs/styles.css
git commit -am "chore(docs): dev2 note"
git push

# Back in Terminal A
git push                          # rejected: remote has new commits
git fetch
git log --oneline --graph --all -10
git pull --rebase                 # replay your commit on top of dev2's
git push
Day 5~75 min

Merge vs Rebase — and when to use each

Goal: pick the right integration strategy without flipping a coin.

Use case Use Why
Updating my private feature branch with latest dev git rebase dev Linear history, easier PR review, no merge noise.
Merging a completed feature into dev Merge (via PR; squash or merge-commit per team policy) The merge point records "this feature landed".
Branch is shared with other developers Merge — never rebase Rebase rewrites history; collaborators' branches break.
Bringing a hotfix from main back into dev Merge Preserves provenance.
Golden rule: never rebase commits that have been pushed to a branch other people use. Rebase rewrites SHAs; their next git pull will explode.

Practical workflow on your feature branch

git checkout feature/BANK-101-leaderboard
git fetch origin
git rebase origin/dev            # replay my commits on top of latest dev
# resolve conflicts if any (Day 8)
git push --force-with-lease      # safe force push: only if remote matches what I expect

--force-with-lease is the pro version of --force: it refuses if someone else pushed to your branch in the meantime, preventing accidental overwrite.

Day 6~45 min

Stash, WIP, and switching context

Goal: never lose work because "I just need to check something on main real quick". 

git stash push -u -m "wip: leaderboard query in progress"
git checkout main                # safe, your changes are stashed
# ... do the other thing ...
git checkout feature/BANK-101-leaderboard
git stash list
git stash show -p stash@{0}      # preview
git stash pop                    # re-apply and drop from stash
# OR
git stash apply stash@{0}        # re-apply, keep in stash
  • -u includes untracked files. Without it, new files are left behind and you may commit them on the wrong branch later.
  • Always give a stash a message (-m). Anonymous stashes pile up and you forget what's in them.
Better than stash for longer breaks: just commit a wip: commit on your feature branch and amend/squash later. Stash is for minute-scale interruptions.
Day 7~90 min

Your first PR end-to-end

Goal: raise a PR a senior reviewer would call clean.

  1. Branch from up-to-date dev: 
    git checkout dev && git pull --ff-only
git checkout -b feature/BANK-110-add-leaderboard-projection
  2. Make small, well-named commits as you work.
  3. Before pushing the final time, sync with dev: 
    git fetch origin
git rebase origin/dev
  4. Run tests locally. Push: 
    git push -u origin feature/BANK-110-add-leaderboard-projection
  5. Open PR on GitHub: base: dev ← compare: feature/....
  6. PR description template (paste this into every PR): 
    ## What
One-paragraph summary of the change.

## Why
Business or technical reason. Link the ticket.

## How
Key design decisions; anything reviewers should look at first.

## Test plan
- [ ] Unit tests added/updated
- [ ] Manual scenario: ...
- [ ] Edge case: ...

## Risk & rollback
Low/Medium/High. To roll back: revert this PR.

Refs: BANK-110
  7. Keep PRs small: aim for < 400 lines changed. Big PRs don't get reviewed, they get rubber-stamped.

Good PR

  • One concern. Clear title. Filled-out description.
  • Green CI before requesting review.
  • Author responds to every comment (even "done").

Bad PR

  • "Misc fixes" title, 38 files, 2,400 lines, red CI, no description.
  • Reviewer closes it or rubber-stamps it. Bugs ship.

Goal of the week: handle conflicts, hotfixes, promotions, releases, and recovery without asking anyone for help.

Day 8~75 min

Merge conflicts — reading them and resolving them

Goal: conflicts become routine, not panic moments.

Anatomy of a conflict marker

<<<<<<< HEAD               ← what is currently in your branch
your version of the line
=======
their version of the line
>>>>>>> origin/dev          ← what is coming from the branch you are merging in

The pro resolution loop

git status                         # lists "both modified" files
git diff                           # see the conflicts
# Open each conflicted file. Decide:
#   keep mine? keep theirs? combine both? rewrite entirely?
# Remove the <<<, ===, >>> markers.
git add <file>                     # mark resolved
git status                         # confirm all resolved
git rebase --continue              # or: git merge --continue
# If you are lost:
git rebase --abort                 # safely back out

Better tools than the markers

git mergetool                      # opens configured 3-way merge tool
git config --global merge.tool vscode
git config --global mergetool.vscode.cmd 'code --wait $MERGED'

VS Code's inline "Accept Current / Incoming / Both" buttons are usually the fastest way.

Ideation: how to think about a conflict

  1. Understand both intents. Run git log -p <file> on both sides. What problem was each change solving?
  2. Pick the right merge, not a syntactic one. Sometimes the answer is neither side as-is, but a new third version.
  3. If unsure, ask the other author. A 2-minute chat beats a 2-hour bug.
  4. Re-run tests after resolving. Conflicts often hide semantic bugs.

Lab exercise — create and resolve a real conflict

# in poc_iq_dev2 (dev2)
git checkout dev && git pull --ff-only
git checkout -b feature/dev2-edit-readme
# edit the SAME line of e.g. docs/index.html
git commit -am "feat(docs): dev2 wording"
git push -u origin feature/dev2-edit-readme
# open PR dev2 → dev, merge it on GitHub

# in poc_iq (dev1), at the same time:
git checkout dev && git pull --ff-only   # now has dev2's change
git checkout -b feature/dev1-edit-readme
# edit the SAME line differently
git commit -am "feat(docs): dev1 wording"
git fetch origin
git rebase origin/dev                    # CONFLICT — resolve it
Day 9~60 min

Cherry-pick and the hotfix flow

Goal: move one specific commit from one branch to another safely.

When cherry-pick is the right tool

  • A bug fix landed on dev but production needs it now without shipping the rest of dev.
  • A useful commit exists on someone else's branch and you only want that one commit.
  • You accidentally committed to the wrong branch and want to move just that commit.

Commands

git log --oneline dev -20          # find the SHA you want, e.g. a1b2c3d
git checkout main
git pull --ff-only
git checkout -b hotfix/BANK-999-null-pointer
git cherry-pick a1b2c3d            # applies that commit here
# if conflicts: resolve, then
git cherry-pick --continue
git push -u origin hotfix/BANK-999-null-pointer
# Open PR hotfix → main, merge, deploy.
# Then forward-merge to keep dev in sync:
git checkout dev && git pull --ff-only
git merge --no-ff main
git push
Don't abuse cherry-pick as a regular promotion mechanism between dev → qa → main. That causes duplicated commits with different SHAs. Use proper merges for promotion; reserve cherry-pick for true one-offs.
Day 10~75 min

Squash, fixup, amend — curating history

Goal: turn 12 messy WIP commits into 1–3 clean ones before merge.

The four tools

Tool What it does When
git commit --amend Modify the last commit (message or contents). You forgot a file or made a typo in the last commit message, and haven't pushed yet.
git commit --fixup <sha> Creates a special "fixup!" commit that rebase -i --autosquash will merge into the target commit. Mid-feature, you spot a bug in commit #3; just fixup it.
git rebase -i HEAD~N Interactive rebase: reorder, squash, fixup, edit, drop commits. Final cleanup before PR.
PR "Squash and merge" GitHub squashes all PR commits into one on the target branch. Team default for feature PRs to dev.

Interactive rebase walkthrough

git log --oneline -8
# pick: 7f3a1b2 wip
# pick: 9c2d4e5 wip more
# pick: 1a2b3c4 actual feature
# pick: 5d6e7f8 fix typo
# pick: 9e0f1a2 fix typo again

git rebase -i HEAD~5
# editor opens; change "pick" to "squash" (s) or "fixup" (f):
# pick   7f3a1b2 wip
# fixup  9c2d4e5 wip more
# squash 1a2b3c4 actual feature
# fixup  5d6e7f8 fix typo
# fixup  9e0f1a2 fix typo again
# Save & close → editor reopens for combined message → rewrite cleanly.

Squash vs Merge vs Rebase-and-merge on GitHub

Strategy Result on dev Best for
Merge commit All feature commits preserved + a merge commit Long-lived feature with meaningful history.
Squash and merge One commit on dev per PR Default for most teams; clean linear dev.
Rebase and merge Feature commits replayed onto dev, no merge commit You want every commit individually but no merge bubbles. Rare.
Never rebase or amend commits that exist on a shared branch (dev, qa, main). Only rewrite history on your own feature branches before they're merged.
Day 11~60 min

Reviewing PRs like a senior

Goal: give reviews that improve code and the author.

Review checklist (use every time)

  1. Does it do what the ticket says? Read the PR description first.
  2. Is it the simplest design that works? Suggest cuts, not additions.
  3. Tests: happy path + at least one edge case + one failure path.
  4. Naming & readability: can a stranger understand this in 6 months?
  5. Security: input validation, secrets, authz checks.
  6. Performance: N+1 queries, unbounded loops, blocking I/O.
  7. Backward compatibility: DB migrations, API contracts, config keys.
  8. Observability: logs, metrics, error messages.

Review tone

Good comment

"nit: could we rename x to balance_after? Makes the call site self-explanatory."

"question: what happens if event.data['amount'] is missing? The .get(..., 0.0) default silently skews the balance."

Bad comment

"This is wrong."

"Why did you do it like this???"

Prefix comments with intent: nit: (optional), question:, suggestion:, blocking:. It tells the author whether they must address it before merge.

Approval gates

  • 1 approval for routine changes.
  • 2 approvals (including a domain owner) for security, payments, schema, infra.
  • CI must be green. No "merging with red tests, will fix later".
Day 12~75 min

Promoting code dev → qa → prod

Goal: a repeatable, boring promotion that anyone on the team can run.

The promotion flow (merge-based, no cherry-picks)

# 1. Cut a release candidate from dev into qa at end of sprint
git checkout qa && git pull --ff-only
git merge --no-ff origin/dev -m "release: promote dev → qa for sprint-14"
git push origin qa
# QA tests on the deployed qa env.

# 2. After QA sign-off, promote qa into main
git checkout main && git pull --ff-only
git merge --ff-only origin/qa     # or --no-ff if you want a merge commit
git tag -a v1.4.0 -m "Release 1.4.0 — sprint 14 features"
git push origin main --tags
# CI/CD deploys main to production.

# 3. Any qa-only fixes get back-merged into dev so dev never drifts behind
git checkout dev && git pull --ff-only
git merge --no-ff origin/qa
git push
Why not cherry-pick selected commits from dev into qa? Because cherry-picked commits have different SHAs than their originals. Git can't tell they're the same change, so future merges between the two branches will conflict in confusing ways. Use cherry-pick only for hotfixes that explicitly need to skip the queue.

Hotfix flow (skips the queue)

git checkout main && git pull --ff-only
git checkout -b hotfix/BANK-999-prod-crash
# fix, commit, PR → main
# after merge to main:
git tag -a v1.4.1 -m "Hotfix 1.4.1"
git push origin main --tags
# Forward-merge the hotfix into qa and dev so they don't lose it:
git checkout qa  && git pull && git merge --no-ff main && git push
git checkout dev && git pull && git merge --no-ff main && git push
Day 13~45 min

Tags, semantic versioning, and release notes

Goal: a release that auditors and on-call engineers can trace.

Semantic versioning MAJOR.MINOR.PATCH

  • MAJOR: breaking change to the public contract.
  • MINOR: backwards-compatible new feature.
  • PATCH: backwards-compatible bug fix.

Commands

git tag                                  # list tags
git tag -a v1.4.0 -m "Sprint 14 release"
git push origin v1.4.0                   # push one tag
git push origin --tags                   # push all tags

# generate a quick changelog between two tags
git log v1.3.0..v1.4.0 --pretty=format:'- %s (%an)'

On GitHub: Releases → Draft a new release → choose tag v1.4.0, paste the changelog, attach artifacts. This is what stakeholders read.

Day 14~75 min

Recovery — reflog, reset, revert

Goal: never fear losing work again. Almost nothing in Git is truly lost for ~90 days.

The three "undo" commands

Command Does what Safe on shared branches?
git revert <sha> Creates a new commit that undoes <sha>. Yes. The only safe undo on main/dev.
git reset --soft <sha> Moves branch pointer back; keeps changes staged. No — rewrites history. Local only.
git reset --hard <sha> Moves pointer back; discards working tree changes. No — destructive. Local only.

Reflog — your safety net

git reflog                          # every HEAD movement in the last ~90 days
# Example output:
# 9e0f1a2 HEAD@{0}: reset: moving to HEAD~3
# 1a2b3c4 HEAD@{1}: commit: feat(projections): leaderboard
# ...
git reset --hard HEAD@{1}           # restore to the state before the bad reset
Lost a commit after a bad rebase? git reflog → find the SHA → git branch rescue <sha>. Done. Crisis over.

Final exercise — break and recover

git checkout -b experiment/recovery
echo "important" > important.txt
git add . && git commit -m "feat: very important work"
git reset --hard HEAD~1             # "oh no"
git reflog                          # find the SHA of "very important work"
git reset --hard <that-sha>         # recovered

Self-check: can you explain in one breath the difference between revert, reset --soft, and reset --hard? If yes — you've graduated.

Concept Deep Dives Reference

Use these whenever you forget the "why" behind a command.

Commit message standard

The 7 rules (Tim Pope / Conventional Commits hybrid)

  1. Separate subject from body with a blank line.
  2. Limit the subject line to ~72 characters.
  3. Capitalize the subject (after the type prefix).
  4. Do not end the subject with a period.
  5. Use the imperative mood ("Add", not "Added" or "Adds").
  6. Wrap the body at 72 characters.
  7. Use the body to explain what and why, not how.

Cheat — types

feat:     new user-facing feature
fix:      bug fix
refactor: code change with no behavior change
perf:     code change that improves performance
docs:     documentation only
test:     adding or fixing tests
build:    build system / dependencies
ci:       CI config changes
chore:    everything else (tooling, housekeeping)
revert:   reverts a previous commit

Branching strategy comparison

Strategy Branches Best for Watch out
Trunk-based (recommended) main + short-lived feature branches; optional qa Continuous delivery, < 1 week cycles Requires strong CI, feature flags for in-progress work
GitHub Flow main + feature branches Web apps with continuous deploy No staging branch — relies on environments
Git Flow (classic) main, develop, release/*, hotfix/*, feature/* Versioned software with explicit releases Heavy; many merge bubbles
Env-branch (your lab) dev, qa, main Mirrors deployment environments Risk of branch drift if promotions aren't disciplined merges

PR playbook — raising and approving

As an author

  • One concern per PR. Split if you wrote "and" in the title.
  • < 400 lines changed where possible.
  • Self-review your own diff on GitHub before requesting reviewers — you will catch 30% of issues yourself.
  • Address every comment. Reply "done", "won't fix because…", or push a commit.
  • Don't force-push after review starts unless asked — it invalidates reviewers' context. Use --force-with-lease if you must.

As a reviewer

  • Review within 1 business day. Latency kills team velocity.
  • Approve OR request changes — never just leave comments and walk away.
  • Be specific. "This will break on null input" beats "looks fragile".
  • Praise good code too. Reviews are mentoring, not gate-keeping.

Merge conflict resolution — the thinking framework

  1. Stop. Don't randomly accept one side. Run git status, list every conflicted file.
  2. Reconstruct intent. For each file: git log -p --all -- <file> to see what both sides were trying to do.
  3. Pick one of three resolutions:
    • Keep mine if their change is obsolete.
    • Keep theirs if yours is obsolete.
    • Synthesize a new version preserving both intents (most common).
  4. Compile and test before git add. A clean merge that doesn't run is worse than no merge.
  5. If the conflict is conceptual, not textual — pair with the other author for 5 minutes. Saves hours.

Escape hatches you should know exist:

git merge --abort        # bail out of a merge, restore previous state
git rebase --abort       # bail out of a rebase
git checkout --ours   <file>    # take current-branch version entirely
git checkout --theirs <file>    # take incoming-branch version entirely
git rerere               # "reuse recorded resolution" — Git remembers your resolutions
                         # enable: git config --global rerere.enabled true

# Save points while working
git add -p                        # stage hunks selectively
git commit -m "feat(scope): ..."

# Sync with dev mid-work
git fetch origin
git rebase origin/dev
git push --force-with-lease       # only on your own branch

# Wrap up before PR
git rebase -i origin/dev          # squash WIP into clean commits
git push --force-with-lease
# Open PR → dev

# Context switch
git stash push -u -m "wip: ..."
git checkout other-branch
# ... later ...
git checkout feature/<...>
git stash pop

# Oh no
git reflog
git reset --hard HEAD@{N}

# Promote
git checkout qa  && git pull && git merge --no-ff origin/dev && git push
git checkout main && git pull && git merge --ff-only origin/qa && git tag -a vX.Y.Z -m "..." && git push --tags

# Hotfix
git checkout main && git pull
git checkout -b hotfix/<ticket>
# ... fix ... PR → main
# back-merge:
git checkout dev && git merge --no-ff main && git push
git checkout qa  && git merge --no-ff main && git push

Mindset shifts that make you a pro

  1. Read before you write. Every Git command should be preceded by git status until it's second nature.
  2. Local history is yours, shared history is sacred. Rewrite freely on your branch; never on dev/qa/main.
  3. Small, frequent, intentional. Small commits, small PRs, frequent syncs. Big-bang anything is a code smell.
  4. Communicate via Git. Branch names, commit messages, PR descriptions are how the team — including future-you — understands the codebase.
  5. Recover, don't panic. git reflog + --force-with-lease make almost every mistake reversible.
