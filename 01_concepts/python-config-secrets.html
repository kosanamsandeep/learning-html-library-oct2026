Operational basics

Good Python applications keep configuration outside code and treat secrets differently from normal settings.

Configuration answers questions such as which port to run on, which database URL to use, and whether debug mode is enabled. Secrets are more sensitive values such as API keys, passwords, tokens, and signing keys.

If configuration is scattered across the codebase or secrets are hard-coded in source files, the app becomes unsafe and hard to deploy across environments.

Simple distinction

  • Config: environment-specific settings
  • Secrets: sensitive credentials and keys
  • Rule: keep both out of hard-coded business logic

Sources

Where configuration should come from

Source Good for Notes
Environment variables Runtime configuration and secrets Common default for containers and cloud platforms
.env files Local development Useful locally, but sensitive files should not be committed
Secret managers Production secrets Best option for serious deployments
Config files Non-sensitive structured settings Useful when human-readable settings need versioned structure

Environment variables

Why environment variables are commonly used

Why they work well

They separate runtime settings from code, work well with Docker and Kubernetes, and let the same code run in dev, test, staging, and production with different values.

What to watch out for

Everything comes in as strings, values may be missing, and secret rotation requires proper operational handling. Validation is important.

Secrets

How secrets should be handled

Good practices

  • Use secret managers or secure environment injection in production.
  • Keep secrets out of source control.
  • Rotate secrets when exposure is suspected or scheduled policy requires it.
  • Limit access to only the services and people that need them.

Bad practices

  • Hard-coding keys in Python files.
  • Printing secrets in logs.
  • Sharing .env files casually over chat or email.
  • Using the same credentials across all environments.

Python pattern

A clean Python configuration pattern

Simple settings object

import os
from dataclasses import dataclass


@dataclass
class Settings:
    app_name: str
    debug: bool
    database_url: str
    openai_api_key: str


def load_settings() -> Settings:
    return Settings(
        app_name=os.getenv("APP_NAME", "my-app"),
        debug=os.getenv("DEBUG", "false").lower() == "true",
        database_url=os.environ["DATABASE_URL"],
        openai_api_key=os.environ["OPENAI_API_KEY"],
    )

Useful rule: load config in one place near startup, validate it early, and then inject the resulting settings object where needed.

Common mistakes

What teams often get wrong

Config access everywhere

When code calls environment variables all over the codebase, configuration becomes hard to reason about and harder to test.

No startup validation

If required config is missing, fail early at startup rather than discovering it halfway through a production request.
