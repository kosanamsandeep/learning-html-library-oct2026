Architecture for maintainability

A scalable Python project structure keeps API code, business logic, data access, and tests separate.

When Python applications grow, the main failure mode is not syntax. It is mixing too many concerns in the same files. Routes start containing business rules, models start calling third-party APIs, and test setup becomes painful.

A clean structure gives every part of the system a clear place. That makes onboarding easier, refactoring safer, and testing much cheaper.

One-line rule

  • Routes: translate HTTP into application calls
  • Services: hold business logic
  • Repositories: talk to storage
  • Tests: verify behavior at different levels
  • BDD features: express user-visible behavior clearly

Suggested layout

A practical project structure for Python applications

Example layout

app/
  api/
    routes/
      users.py
      orders.py
  services/
    user_service.py
    order_service.py
  repositories/
    user_repository.py
    order_repository.py
  domain/
    models.py
    schemas.py
  integrations/
    payment_gateway.py
    email_client.py
  core/
    config.py
    logging.py
    dependencies.py
  main.py

tests/
  unit/
  integration/
  api/

features/
  checkout.feature
  user_signup.feature

steps/
  test_checkout_steps.py
  test_signup_steps.py

Simple mental model: keep the runtime app under app/, test code under tests/, and business-readable BDD scenarios under features/.

Folder responsibilities

What each folder should contain

Folder Purpose Should contain Should avoid
api/routes HTTP entry points Request parsing, response formatting, auth checks Heavy business logic and SQL queries
services Business rules Use-case logic, orchestration, validation flow Framework-specific route code
repositories Persistence access Database queries, storage operations HTTP concerns and unrelated business rules
domain Core data concepts Entities, schemas, value objects, enums Database sessions and external API calls
integrations External systems Adapters for email, payments, LLMs, queues Core domain rules spread across vendor code
core Shared application setup Config, dependency wiring, logging, settings Feature-specific logic

Testing layout

Where tests should live

Unit tests

Put focused service or domain tests in tests/unit. These should be fast, isolated, and mostly free of databases and network calls.

Integration tests

Put repository or external integration tests in tests/integration. These verify real boundaries such as database access, queues, or APIs.

API tests

Put route-level or end-to-end HTTP tests in tests/api. These verify that the service surface behaves correctly from the client perspective.

Useful rule of thumb

Most logic bugs should be caught in unit tests. Integration and API tests should be fewer, more expensive, and targeted at boundary risk.

Behavior files

Where BDD feature files and step definitions should live

Feature files

Store business-readable scenarios in features/. These files describe behavior in Given-When-Then language and should be understandable without reading the application code.

Step definitions

Store the Python glue code in steps/ or a test-specific package. Step definitions connect the natural-language scenario to executable code and assertions.

Minimal BDD example

features/
  login.feature

steps/
  test_login_steps.py

Request flow

How a typical request should move through the app

1. Route receives the request

The route parses input, checks auth, and calls a service method.

2. Service applies business rules

The service validates workflow decisions and coordinates domain behavior.

3. Repository reads or writes data

The repository handles the persistence details and returns data in a useful shape.

4. Route returns the response

The route translates the service result into an HTTP response or serialized output.

What to avoid

Common structural mistakes

Fat route files

  • SQL in route handlers
  • Business rules mixed with HTTP parsing
  • Third-party API calls directly inside endpoints

Ambiguous shared folders

  • Large misc or utils modules that hide unrelated logic
  • Helpers that become a dumping ground
  • Shared code without clear ownership or purpose
