💾 Feature Stores & Caching Strategies

Why feature stores matter, why Redis dominates caching, and how to make LLM apps blazing fast

What is a Feature Store?

A feature store is a centralized repository for storing, serving, and managing ML features (the processed data that models consume). In the LLM world, it stores embeddings, user profiles, context windows, and pre-computed data that your AI app needs repeatedly.

The Core Problem: LLM apps need the same data transformed the same way every time. Without a feature store, you end up recomputing embeddings, re-fetching user context, and duplicating transformation logic across training and serving. Feature stores solve the "train-serve skew" problem and provide a single source of truth for features.

[Raw Data] → [Feature Engineering] → [Feature Store] → [Online Serving (Redis/low-latency)]
↓
[Offline Store (S3/BigQuery)] → [Training]

Why Feature Stores Matter for LLM Apps

  • Embedding Cache: Store pre-computed embeddings to avoid re-embedding the same documents
  • User Context: Store user preferences, history, and personalization features for retrieval
  • Real-time Features: Serve fresh features (last 5 messages, recent activity) at low latency
  • Consistency: Same feature computation in training and serving (no train-serve skew)
  • Versioning: Track feature versions, roll back, audit what was served when

Feature Store Platforms Compared

🍽️ Feast (Open Source)

The most popular open-source feature store. Lightweight, flexible, self-hosted. Defines features in code (infrastructure-as-code for ML features).
Architecture:

Offline store (BigQuery/Redshift/S3) + Online store (Redis/DynamoDB) + Registry (metadata)

Features defined in Python → materialized from offline → served from online store

  • Pros: Free, flexible, GitOps-friendly, many backends
  • Cons: Self-managed infra, no built-in monitoring at scale
  • Best for: Teams who want control, moderate scale, budget-conscious
# Feast: Define and serve features from feast import FeatureStore store = FeatureStore(repo_path="./feature_repo") # Get features for online serving (low-latency) features = store.get_online_features( features=["user_features:embedding", "user_features:last_query"], entity_rows=[{"user_id": "u123"}] ).to_dict()

🚀 Tecton

Enterprise-grade managed feature platform. Built by the founders of Feast. Handles real-time feature computation, streaming features, and complex pipelines automatically.
Key Differentiator:

Real-time feature computation (streaming + batch in one platform), not just storage

Handles time-windowed aggregations (e.g., "count of queries in last 5 minutes") automatically

  • Pros: Managed, real-time streaming, enterprise SLAs, monitoring
  • Cons: Expensive, vendor lock-in, overkill for small teams
  • Best for: Large-scale production apps with real-time requirements

🔮 Vertex AI Feature Store (Google)

Google Cloud's managed feature store. Integrates natively with BigQuery, Vertex AI Pipelines, and GCP ML stack.
  • Pros: Fully managed, BigQuery integration, auto-scaling, IAM security
  • Cons: GCP-only, less flexible than Feast, pricing can grow
  • Best for: Teams already on GCP who need managed ML infrastructure

🏗️ AWS SageMaker Feature Store

Amazon's managed feature store within SageMaker. Online + offline store with tight AWS integration.
  • Pros: AWS-native, auto-scaling, IAM, integrates with SageMaker pipelines
  • Cons: AWS-only, limited customization, can be expensive at scale
  • Best for: AWS-heavy organizations already using SageMaker

Why Redis Dominates LLM Caching

Redis is the go-to cache for LLM applications because of its sub-millisecond latency, rich data structures, and versatility. Here's why:

⚡ Redis for LLM Apps

Redis isn't just a key-value store. It's a data structure server that serves as cache, vector DB, message broker, and session store — all at once.
Why Redis for LLM/AI specifically:

1. Speed: ~0.1ms reads. LLM API calls cost $0.01-0.10 and take 1-10 seconds. Caching saves both.

2. Vector Search: Redis Stack includes native vector similarity search (RediSearch)

3. Semantic Caching: Cache by meaning, not just exact match

4. Session/Memory: Store conversation history with TTL (auto-expire)

5. Rate Limiting: Protect against LLM API abuse with Redis counters

import redis import json import hashlib r = redis.Redis(host='localhost', port=6379) def cached_llm_call(prompt, model="gpt-4o"): # Create cache key from prompt hash cache_key = f"llm:{hashlib.sha256(prompt.encode()).hexdigest()}" # Check cache first cached = r.get(cache_key) if cached: return json.loads(cached) # Cache HIT — saved $$ and time # Cache MISS — call LLM response = openai.chat.completions.create(model=model, messages=[{"role":"user","content":prompt}]) result = response.choices[0].message.content # Store in cache with 1-hour TTL r.setex(cache_key, 3600, json.dumps(result)) return result

LLM Caching Strategies Compared

1️⃣ Exact Match Caching

Cache by exact prompt string (or hash). Simplest approach — if someone asks the exact same question, return cached answer.
How it works:

key = hash(prompt) → value = LLM response

Hit rate: LOW (users rarely ask identical questions)

  • Pros: Simple, zero false matches, fast lookup
  • Cons: Very low hit rate, "What is AI?" ≠ "what is ai?" (unless normalized)
  • Use when: API endpoints with predictable inputs, batch processing

2️⃣ Semantic Caching

Cache by MEANING. Embed the query, find similar cached queries using vector similarity. If similarity > threshold, return cached answer.
How it works:

1. Embed new query → vector

2. Search cache for similar vectors (cosine similarity > 0.95)

3. If found → return cached response

4. If not → call LLM, cache result with embedding

  • Pros: Much higher hit rate, catches paraphrases
  • Cons: Embedding cost, possible false matches, needs tuning threshold
  • Use when: User-facing chatbots, FAQ-style queries, high-traffic apps
# Semantic Caching with GPTCache or Redis Vector from gptcache import cache from gptcache.embedding import Onnx from gptcache.similarity_evaluation import SearchDistanceEvaluation # Initialize semantic cache cache.init( embedding_func=Onnx(), similarity_evaluation=SearchDistanceEvaluation() ) # "What is machine learning?" and "explain ML" now hit same cache!

3️⃣ Prompt-Result Caching (with Context)

Cache based on (prompt + context documents). Same question with different retrieved docs = different cache entry. Critical for RAG apps.
How it works:

key = hash(prompt + sorted(doc_ids)) → value = LLM response

Invalidate when source documents change

  • Pros: Accurate for RAG, respects context changes
  • Cons: Lower hit rate than semantic, needs document tracking
  • Use when: RAG pipelines where accuracy matters, enterprise knowledge bases

4️⃣ KV-Cache (Model-Level)

Not application-level — this is inside the model. LLMs cache key-value attention matrices from previous tokens to avoid recomputation during generation.
How it works:

During token generation, previously computed attention K/V pairs are cached in GPU memory

Prefix caching: If multiple prompts share a prefix, cache that prefix's KV state

  • Pros: Dramatic speedup for long contexts, provider-managed
  • Cons: GPU memory intensive, managed by inference provider
  • Use when: Long system prompts shared across requests (OpenAI does this automatically)

5️⃣ Multi-Layer Caching

Combine multiple strategies in layers. Check exact match first (fastest), then semantic (broader), then call LLM (slowest).
The layers:

L1: In-memory exact cache (dict/LRU) → µs latency

L2: Redis exact match → <1ms latency

L3: Redis semantic cache (vector search) → ~5ms latency

L4: LLM API call → 1-10 seconds, costs $$

  • Pros: Maximum cost savings, best latency
  • Cons: Complex to implement and maintain, cache invalidation challenges
  • Use when: High-traffic production apps where latency and cost matter

📊 Caching Strategy Comparison

Strategy Hit Rate Accuracy Complexity Cost Savings Best For
Exact Match Low (5-15%) Perfect Trivial Low APIs, batch jobs
Semantic High (30-60%) Good (tunable) Medium High Chatbots, user queries
Context-Aware Medium (15-30%) Excellent Medium Medium RAG pipelines
KV-Cache High Perfect Zero (provider) Latency savings Shared system prompts
Multi-Layer Highest (50-80%) Very Good High Maximum High-traffic production

🎯 Decision Framework

Feature Store Selection:

Small team, want control → Feast (open-source, self-managed)

Real-time streaming features → Tecton (managed, streaming-native)

Already on GCP → Vertex AI Feature Store

Already on AWS → SageMaker Feature Store

Caching Strategy Selection:

Just starting out → Exact match with Redis (simple, effective)

User-facing chatbot → Semantic caching (catches paraphrases)

RAG application → Context-aware caching (respects document changes)

High traffic, cost-sensitive → Multi-layer caching

Long shared prompts → Rely on provider KV-cache (automatic)

🧠 Pro Thinker Analysis

Caching is the #1 way to reduce LLM costs in production. A well-implemented semantic cache can cut your LLM API spend by 30-60%. The ROI is massive: Redis costs ~$50/month for most apps; a single LLM call costs $0.01-0.10. If you serve 100K queries/day with 40% cache hit rate, you save 40K LLM calls/day = $400-4000/day saved. Feature stores become critical when your app needs real-time personalization (user embeddings, recent activity, preferences) served at <10ms. Without one, you'll rebuild the same data pipelines repeatedly.
