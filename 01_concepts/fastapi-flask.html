Python web frameworks

FastAPI vs Flask

Flask pioneered micro-framework simplicity in Python. FastAPI builds on modern Python features (type hints, async/await) to deliver automatic validation, documentation, and high performance. Both have clear use cases.

This page covers the strengths of each, when to choose one over the other, and what interviewers expect you to know about building production APIs.

One-line distinction

  • Flask: Battle-tested simplicity, massive ecosystem, synchronous by default
  • FastAPI: Modern, async-first, auto-docs, type-safe, built for ML/AI APIs

FastAPI Advantages

1. Automatic API documentation

FastAPI generates interactive Swagger UI (/docs) and ReDoc (/redoc) automatically from your code. No plugins, no configuration. Type hints become the documentation.

  • Swagger UI: test endpoints directly in browser
  • OpenAPI schema auto-generated
  • Client SDK generation from schema

2. Type-safe request validation

Uses Pydantic models for automatic request/response validation. Invalid input returns clear 422 errors without any manual validation code.

  • Pydantic V2: 5-50x faster validation than V1
  • Nested models, custom validators
  • Automatic type coercion where safe

3. Async/await native support

Built on Starlette and ASGI (Asynchronous Server Gateway Interface). Handles concurrent requests efficiently without threads — critical for I/O-bound ML serving.

  • async def endpoints for non-blocking I/O
  • WebSocket support built-in
  • Background tasks without Celery for simple cases

4. Performance

One of the fastest Python frameworks. Built on Starlette (ASGI) and Uvicorn. Comparable to Node.js and Go for I/O-bound workloads.

  • ASGI > WSGI for concurrent connections
  • Uvicorn with uvloop: near-C-level event loop
  • Benchmarks: 2-3x Flask for concurrent requests

5. Dependency injection system

Declarative dependency injection for database sessions, auth, rate limiting. Dependencies can be nested, cached, and scoped (request, app lifetime).

  • Clean separation of concerns
  • Easy testing with dependency overrides
  • No global state needed

6. ML/AI serving advantages

FastAPI is the de facto choice for serving ML models because of:

  • Async handlers for concurrent inference requests
  • Pydantic for strict input schema validation
  • Background tasks for batch processing
  • WebSocket for streaming LLM outputs
  • Easy Docker + Kubernetes deployment

Flask Advantages

1. Simplicity and minimal boilerplate

A working Flask app is 5 lines. No mandatory project structure, no forced patterns. Perfect for prototypes, internal tools, and learning.

  • Minimal "magic" — easy to understand what's happening
  • Explicit over implicit philosophy
  • Gentle learning curve

2. Massive ecosystem

13+ years of community extensions covering every use case.

  • Flask-SQLAlchemy, Flask-Migrate (database)
  • Flask-Login, Flask-JWT-Extended (auth)
  • Flask-CORS, Flask-Limiter (middleware)
  • Flask-SocketIO, Flask-Mail (features)
  • Thousands of tutorials and Stack Overflow answers

3. Full-stack web development

Flask excels at serving HTML templates, not just JSON APIs. Jinja2 templating, static files, session management — everything for a traditional web app.

  • Jinja2 templates with inheritance
  • Static file serving built-in
  • Session and cookie management
  • Flask-Admin for quick admin panels

4. Battle-tested stability

Flask has been in production at companies of all sizes since 2010. Its API is stable, well-documented, and rarely has breaking changes.

  • Used by Netflix, LinkedIn, Pinterest
  • Mature, predictable release cycle
  • Long-term support and maintenance

5. Flexibility

Flask is truly a micro-framework — it makes no decisions for you. Choose your own ORM, validation library, auth solution, and project structure.

  • No forced project structure
  • Use any database (SQLAlchemy, Mongoengine, etc.)
  • Blueprints for modular applications

6. Synchronous simplicity

For CPU-bound tasks (most ML inference), synchronous code is simpler to reason about. No async/await complexity, no event loop debugging.

  • Easier debugging (straightforward stack traces)
  • No async footguns (forgetting await, etc.)
  • Gunicorn workers for parallelism

When to use which

Choose FastAPI when

  • Building a pure REST/JSON API (no HTML serving)
  • Serving ML models with strict input validation
  • Need auto-generated API docs for team/clients
  • High concurrency with async I/O (database, external APIs)
  • Streaming responses (LLM token streaming via WebSocket/SSE)
  • Microservices communicating via typed contracts
  • Greenfield project with modern Python (3.8+)

Choose Flask when

  • Building a full-stack web app with HTML pages
  • Quick prototypes and internal tools
  • Team is more comfortable with synchronous code
  • Need specific Flask extensions not available elsewhere
  • Legacy codebase already using Flask
  • Simple webhook receivers or internal dashboards
  • Learning web development (simpler mental model)

FastAPI — ML model endpoint

from fastapi import FastAPI, HTTPException
from pydantic import BaseModel, Field
import numpy as np

app = FastAPI(title="ML Prediction API")

class PredictionRequest(BaseModel):
    features: list[float] = Field(
        ..., min_length=1, max_length=100
    )
    model_version: str = "v1"

class PredictionResponse(BaseModel):
    prediction: float
    confidence: float
    model_version: str

@app.post("/predict",
          response_model=PredictionResponse)
async def predict(req: PredictionRequest):
    # Validation is automatic via Pydantic
    result = model.predict(
        np.array([req.features])
    )
    return PredictionResponse(
        prediction=float(result[0]),
        confidence=0.95,
        model_version=req.model_version
    )

# Invalid input → automatic 422 with details

Flask — equivalent endpoint

from flask import Flask, request, jsonify
import numpy as np

app = Flask(__name__)

@app.route("/predict", methods=["POST"])
def predict():
    data = request.get_json()

    # Manual validation required
    if not data or "features" not in data:
        return jsonify(
            {"error": "features required"}
        ), 400

    features = data["features"]
    if not isinstance(features, list):
        return jsonify(
            {"error": "features must be list"}
        ), 400

    if len(features) > 100:
        return jsonify(
            {"error": "max 100 features"}
        ), 400

    result = model.predict(
        np.array([features])
    )
    return jsonify({
        "prediction": float(result[0]),
        "confidence": 0.95,
        "model_version": data.get(
            "model_version", "v1"
        )
    })

# Need flask-restx/flasgger for docs
# All validation is manual

from fastapi.responses import StreamingResponse

app = FastAPI()

async def generate(prompt: str):

        async for token in llm.generate(prompt):
            yield f"data: {token}\n\n"

        token_stream(),

Flask — Streaming (more complex)

from flask import Flask, Response, stream_with_context

app = Flask(__name__)

@app.route("/generate", methods=["POST"])
def generate():
    prompt = request.json.get("prompt")

    def token_stream():
        # Flask streaming is synchronous
        # Blocks the worker for duration
        for token in llm.generate_sync(prompt):
            yield f"data: {token}\n\n"
        yield "data: [DONE]\n\n"

    return Response(
        stream_with_context(token_stream()),
        content_type="text/event-stream"
    )
# Worker is blocked during stream
# Limits concurrency significantly

Performance considerations

FastAPI performance profile

  • Async I/O: Single process handles thousands of concurrent connections
  • Best for: APIs waiting on DB/external calls (I/O-bound)
  • Caveat: CPU-bound work (ML inference) still blocks the event loop unless offloaded to a thread/process pool
  • Solution: Use run_in_executor() for CPU-heavy tasks, or deploy with multiple Uvicorn workers

Flask performance profile

  • Process/thread based: Each worker handles one request at a time
  • Best for: CPU-bound tasks where each request does real computation
  • Scaling: Gunicorn with N workers = N concurrent requests
  • Simple model: No async footguns, predictable memory usage per worker

Production deployment pattern

FastAPI: Uvicorn (ASGI server) + multiple workers, behind nginx/traefik. For ML serving: FastAPI + Ray Serve or Triton for model inference separation.

Flask: Gunicorn (WSGI server) + multiple workers, behind nginx. For ML serving: Flask + Celery for async job processing.

Interview Questions

Q

Why would you choose FastAPI over Flask for a new ML model serving API?

A

1) Automatic input validation via Pydantic prevents malformed requests from reaching model code. 2) Auto-generated docs make it easy for consumers to understand the API contract. 3) Async support handles concurrent inference requests efficiently. 4) Type hints serve as both documentation and runtime validation. 5) WebSocket/SSE support for streaming LLM token generation.

Q

What's the difference between WSGI and ASGI?

A

WSGI (Web Server Gateway Interface) is synchronous — one request per thread/process. ASGI (Asynchronous Server Gateway Interface) supports async/await — one process can handle thousands of concurrent connections by yielding during I/O waits. ASGI also natively supports WebSocket and HTTP/2, which WSGI cannot. Flask uses WSGI; FastAPI uses ASGI.

Q

If ML inference is CPU-bound, does FastAPI's async actually help?

A

Not directly — async helps with I/O waits, not CPU computation. If an async endpoint does CPU-heavy work, it blocks the event loop. Solutions: 1) Use run_in_executor() to offload to a thread/process pool. 2) Separate the inference into a dedicated service (Ray Serve, Triton). 3) Use multiple Uvicorn workers (like Gunicorn + Flask). The async advantage comes from handling request parsing, validation, DB calls, and response formatting concurrently.

Q

How does Pydantic improve API reliability compared to manual validation?

A

1) Single source of truth — the model IS the validation, docs, and serialization. 2) No forgotten edge cases — if a field is defined, it's validated. 3) Clear error messages — tells clients exactly which field failed and why. 4) Composable — nested models, custom validators, computed fields. 5) Performance — Pydantic V2 is written in Rust, faster than manual Python checks. 6) IDE support — type hints enable autocomplete and static analysis.
