Loose coupling in practice

Dependency injection means the code receives what it needs from the outside instead of creating everything internally.

When a service directly creates its database client, email sender, logger, cache, and model client inside the class, the code becomes tightly coupled and hard to test. Dependency injection fixes that by passing dependencies in clearly.

In Python, dependency injection does not require a complicated framework. Often it is just constructor arguments, function parameters, or FastAPI dependencies.

Simple before and after

  • Without DI: service creates its own dependencies
  • With DI: service receives dependencies from outside
  • Benefit: lower coupling, easier testing, easier replacement

Why this matters

Why dependency injection improves Python applications

Testability

You can swap real dependencies for fakes or mocks without changing business logic.

Replaceability

You can change storage, vendors, or model providers with smaller code impact.

Clarity

Dependencies become visible at the edge of the class or function instead of being hidden inside the implementation.

Before and after

Bad coupling vs better injection

Tightly coupled service

class UserService:
    def __init__(self):
        self.repository = PostgresUserRepository()
        self.mailer = SmtpMailer()

    def create_user(self, payload):
        user = self.repository.save(payload)
        self.mailer.send_welcome(user.email)
        return user

This is hard to test because the class decides its own dependencies.

Injected dependencies

class UserService:
    def __init__(self, repository, mailer):
        self.repository = repository
        self.mailer = mailer

    def create_user(self, payload):
        user = self.repository.save(payload)
        self.mailer.send_welcome(user.email)
        return user

This is easier to test because the dependencies can be replaced at construction time.

Framework example

How dependency injection looks in FastAPI

Dependency providers

from fastapi import Depends, FastAPI

app = FastAPI()


class UserRepository:
    def save(self, payload):
        return payload


class Mailer:
    def send_welcome(self, email):
        return None


class UserService:
    def __init__(self, repository: UserRepository, mailer: Mailer):
        self.repository = repository
        self.mailer = mailer


def get_user_repository() -> UserRepository:
    return UserRepository()


def get_mailer() -> Mailer:
    return Mailer()


def get_user_service(
    repository: UserRepository = Depends(get_user_repository),
    mailer: Mailer = Depends(get_mailer),
) -> UserService:
    return UserService(repository, mailer)

Injected route

@app.post("/users")
def create_user(
    payload: dict,
    service: UserService = Depends(get_user_service),
):
    return service.create_user(payload)

The route depends on a service provider, and the service provider depends on lower-level providers. This keeps each layer focused.

Important point: FastAPI dependency injection is mainly for wiring objects and request-scoped resources cleanly. It is not just a convenience feature. It enforces clearer boundaries if used well.

Testing seam

Using fakes and overrides in tests

Fake dependencies

Instead of talking to a real database or external API, tests can pass fake repositories or stub mailers into the service. That makes unit tests fast and deterministic.

FastAPI dependency overrides

FastAPI lets you override dependency providers in tests, so routes can run against safe fake collaborators without changing production code.

Simple override example

def get_fake_user_service() -> UserService:
    return UserService(FakeUserRepository(), FakeMailer())


app.dependency_overrides[get_user_service] = get_fake_user_service

Useful patterns

Dependency injection patterns worth using

Pattern When to use it Why it helps
Constructor injection Services and long-lived objects Makes dependencies explicit at object creation time
Function parameter injection Small utilities and pure functions Keeps dependencies simple without needing classes
Provider functions Framework integration and wiring Separates object construction from business logic
Interface or protocol plus implementation Swappable infrastructure Improves replaceability and testing seams

Common mistakes

What to avoid when using dependency injection

Over-abstracting too early

  • Do not create interfaces for every tiny class from day one.
  • Add abstraction where variation or testing seams are real.
  • Keep the code readable for the next developer.

Hiding dependencies again

  • A service locator can reintroduce hidden global state.
  • Dependencies should still be visible in constructors or provider functions.
  • The goal is clarity, not indirection for its own sake.
