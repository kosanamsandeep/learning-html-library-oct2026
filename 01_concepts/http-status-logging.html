API correctness and observability

HTTP status codes tell clients what happened, and log levels tell engineers how serious it is.

Many backend issues become harder than necessary because applications return vague status codes like 200 for failures or 500 for user mistakes. The same thing happens when everything is logged at the same level. Good systems communicate clearly to both machines and humans.

This page explains the importance of HTTP status codes from 1xx to 5xx, what the major logger levels mean, and how to think about them together in Python applications.

Simple split

  • Status codes: response meaning for the client
  • Log levels: severity and operational signal for engineers
  • Goal: make failures understandable, searchable, and actionable

1xx

Informational responses

What they mean

These status codes mean the request has been received and the communication is continuing. They are uncommon in most everyday REST APIs but still part of the protocol family.

Examples

100 Continue tells the client it can continue sending the request body. 101 Switching Protocols is used when changing protocols, such as HTTP to a WebSocket upgrade.

2xx

Success responses

Code Meaning Typical use
200 OK The request succeeded Normal reads, updates, or calculations
201 Created A new resource was created Create user, order, document, or job
202 Accepted The request was accepted but not finished yet Async jobs, background processing, queued tasks
204 No Content The request succeeded and there is nothing to return Delete operations or updates with no body

Important habit: do not always return 200. Use 201 for creation and 202 for accepted async work when that is what really happened.

3xx

Redirection responses

What they mean

The client needs to take another step, usually by following a different location. These are less common in JSON APIs than in browser-heavy apps, but they still matter.

Examples

301 Moved Permanently, 302 Found, 304 Not Modified, and 307 Temporary Redirect are common redirection-related responses.

4xx

Client error responses

Code Meaning Typical use
400 Bad Request The request is malformed Invalid JSON, missing required input shape
401 Unauthorized Authentication is missing or invalid No token, expired token, bad credentials
403 Forbidden The user is authenticated but not allowed Permission denied
404 Not Found The resource does not exist User id or document id not found
409 Conflict The request conflicts with current state Duplicate user, version conflict, idempotency clash
422 Unprocessable Content The request format is valid but the content fails validation Field-level validation errors in FastAPI or Pydantic
429 Too Many Requests The client is being rate-limited Quota or abuse protection

Rule of thumb

If the client can fix the problem by changing the request, it is usually a 4xx response, not a 5xx response.

5xx

Server error responses

Code Meaning Typical use
500 Internal Server Error Unexpected server-side failure Unhandled exception, broken internal logic
502 Bad Gateway Upstream dependency returned an invalid response Gateway or proxy to another service failed
503 Service Unavailable The service is temporarily unavailable Maintenance, overload, dependency outage
504 Gateway Timeout An upstream service timed out Reverse proxy or upstream service timeout

Important habit: reserve 5xx codes for server-side failures. They should create clear operational attention because they mean the platform, not the user, is at fault.

Logger severity

What the different logging levels mean

Level Meaning When to use it
DEBUG Detailed diagnostic information Variable values, branch choices, request details during development or deep troubleshooting
INFO Normal important application events Service started, job completed, user created, scheduled task began
WARNING Something unusual happened but the app can continue Retry triggered, fallback used, slow upstream, deprecated path called
ERROR A specific operation failed Request failed, job failed, DB query failed, external API error
CRITICAL Severe failure that may stop the service or make it unsafe Service cannot start, config missing, corrupted state, fatal dependency outage

About severe

Some systems or teams say SEVERE informally, but in Python’s standard logging module the common built-in top severity is CRITICAL. In everyday explanation, “severe” usually maps to ERROR or CRITICAL depending on how bad the problem is.

Working together

How HTTP status codes and log levels should work together

Situation Status code Log level Why
User sends invalid payload 400 or 422 INFO or WARNING Client can fix it; this is not usually a server failure
User is unauthorized 401 or 403 INFO or WARNING Security-relevant but not necessarily an app failure
Resource missing 404 INFO Usually normal behavior, not a platform issue
Unexpected exception in request path 500 ERROR The server failed to handle a valid request
Service cannot boot 503 or no response CRITICAL This is a severe platform-level problem

Practical examples

Common API examples to remember

Example

Create user successfully

Best answer

Return 201 Created. Log at INFO if the creation event matters operationally.

Example

Client sends invalid input

Best answer

Return 400 or 422. Usually log at INFO or WARNING, not ERROR.

Example

Database is down

Best answer

Return a 5xx response, often 503 if the outage is dependency-related. Log at ERROR or CRITICAL depending on the blast radius.

Example

Background job accepted

Best answer

Return 202 Accepted. Log initial acceptance at INFO and log failures later at ERROR if processing breaks.
