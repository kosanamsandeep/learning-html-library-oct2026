Big-O — the language of "how fast does this thing scale?"

Every DSA conversation, code review, and interview round uses Big-O as shorthand. Master this one page and the rest of the track makes sense.

The intuition Story

Story: your function works in 0.2 seconds on dev data (1,000 rows). Ships to prod (10 million rows). Times out. The reason is your function was O(n²): 1000² = 1M ops (fast), 10M² = 100 trillion ops (forever). You didn't see a bug because you didn't measure scaling.

Big-O describes how the cost of an algorithm grows as the input size grows. It strips away constants and lower-order terms because at large n only the dominant term matters.

The complexity ladder

Listed from fastest to slowest. Anywhere above O(n log n) is "fast enough for any interview input". Anywhere below is suspicious.

Big-O Name Example operation n=1M, time at 10⁸ ops/sec
O(1) Constant Hash lookup, array index, push/pop on stack 0
O(log n) Logarithmic Binary search, balanced BST operations ~20 ops → instant
O(n) Linear Loop through array, traverse linked list ~0.01 s
O(n log n) Linearithmic Mergesort, quicksort average, heapsort ~0.2 s
O(n²) Quadratic Nested loops, bubble sort, naive pair-checks ~3 hours
O(n³) Cubic Triple-nested loops, Floyd-Warshall ~30 years
O(2ⁿ) Exponential Power set, naive recursive Fibonacci ~age of universe (for n=80)
O(n!) Factorial All permutations Worse than exponential
Heuristic to memorize: at 10⁸ operations/second (a modern CPU), if your input is up to 10⁵, even O(n²) is OK. Up to 10⁶, you need O(n log n). Up to 10⁹ — O(n) or better only.

How to compute Big-O — 4 rules

  1. Drop constants. 5n + 100 is O(n).
  2. Drop non-dominant terms. n² + n is O(n²).
  3. Sequential = add. Loop n, then loop n again → O(n + n) = O(n).
  4. Nested = multiply. Loop n inside loop n → O(n × n) = O(n²).

Practice — classify these

# 1
for x in arr:
    print(x)

# 2
for i in range(n):
    for j in range(n):
        if i == j: print(i)

# 3
for i in range(n):
    print(i)
for j in range(n):
    print(j)

# 4
i = n
while i > 0:
    i //= 2

# 5
def f(n):
    if n <= 1: return 1
    return f(n - 1) + f(n - 1)

Answers: 1: O(n) · 2: O(n²) · 3: O(n) · 4: O(log n) · 5: O(2ⁿ).

Time vs Space complexity

Big-O applies to both time (operations) and space (memory).

Time-Space tradeoff

A hash table lets you check "is x in the array?" in O(1), but costs O(n) extra space. Worth it when reads dominate writes.

Recursion costs stack space

A recursion of depth n uses O(n) call-stack memory even if the function body is tiny. Tail-recursion or iteration avoids it.

Worst / Average / Amortized

  • Worst case — guarantee under any input. Default in interviews.
  • Average case — assumes typical input distribution. Quicksort is O(n log n) average but O(n²) worst.
  • Amortized — average cost per operation over many operations. Dynamic array append is amortized O(1) even though occasional resizing is O(n).

What if you ignore Big-O Bad

  • Code is fast on dev data, dies on prod.
  • You can't compare two solutions in a code review — "which is better?" becomes vibes-based.
  • Interviews are unforgivable about it — failing to state and improve your complexity is usually an instant pass-over.
