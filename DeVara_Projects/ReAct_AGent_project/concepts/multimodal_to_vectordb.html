Pushing tables, images, audio & PDFs to a vector DB — the right way

📖 Story mode — the museum curator and the mixed exhibit

The scene. Curator Anika is unpacking a crate for a new exhibit. Inside: old letters, a few photographs, a sculpture, a printed table of dates, an audio diary on tape, and a short film reel. The museum has one rule: every item on display must have a small white catalog card with a barcode, so a visitor with a phone can scan and search anything. Problem — letters, photos, tape, and film all look nothing alike. How does she give them all the same kind of card?

Her trick: she has different specialists in the back room, each turning their item type into the same shape — a list of 1,536 numbers (an embedding). Once everything is numbers, the barcode printer doesn't care if the item was a tape or a photo.

  • 📜 Letters → the linguist. She chunks each letter into paragraph-sized cards (same as Detective Rao with chunking) and hands each to the text embedder.
  • 📸 Photographs → the art historian. She does two things per photo: (a) writes a one-paragraph caption and embeds that as text, and (b) runs the photo through a CLIP model so visitors can search by “sunset over a bridge” even without a caption. One photo → two cards.
  • 📊 The table of dates → the archivist. She doesn't embed the whole table as one blob. She turns each row into a sentence — “In 1923, the museum acquired the bronze lion from Lyon.” — and embeds the sentence. One row → one card.
  • 🎞️ The film reel → the projectionist. He samples one frame per scene (image embed) and runs the audio through Whisper to get a transcript (text embed). One reel → dozens of cards, timestamped.
  • 📼 The audio tape → the same projectionist's friend. Whisper transcript, chunked into ~30-second windows, each window becomes one text card with a t_start on it.
  • 🗿 The sculpture → the docent. She writes a structured description (material, era, dimensions) and embeds that; the physical object stays in its case but its card lives in the same drawer as everything else.

Every white catalog card carries the same metadata stamp — {exhibit_id, item_id, modality, page_or_timestamp, parent_id} — so a visitor searching “bronze lion 1923” can pull back the letter that mentions it, the photo of it, the row in the table, and the audio clip where the donor talks about it. All four light up in one search.

One-line recall trick: “Different specialists, same white card.” Text, images, tables, audio, video — all of them become a vector + a metadata sticker. The vector DB doesn't know (or care) what the original was.

Rule of thumb: store one vector per self-contained idea, in the same vector space when possible. Use metadata, not separate indexes, to slice across modality / tenant / time.

What goes into ONE row vs many rows

QuestionAnswer
"Do I embed an entire page of text as one vector?"No. Split the page into chunks (say 50), embed each, store 50 rows.
"Do I embed an entire table as one vector?"Optionally yes for the summary, but also embed each row separately so queries like "price of SKU 1234" hit the exact row.
"Do I embed an image as one vector?"Yes — but usually two vectors: one CLIP image vector + one text vector from a vision-LLM caption.
"Can I put text and image vectors in the same DB?"Yes — one collection, metadata field modality tells them apart. Use separate indexes only if the dimensionality differs.

Same rule, more modalities: 1 chunk (text/row/image) = 1 vector = 1 row. Multimodal just means you produce more rows per source — never fewer.
