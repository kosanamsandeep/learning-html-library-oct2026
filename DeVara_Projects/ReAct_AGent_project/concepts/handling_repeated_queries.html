How to handle 20 user queries without paying for all 20

"If a user asks query #1, how do I make sure I'm not redoing the same work on queries #2–20?"

📖 Story mode — the bouncer at Club LLM

The scene. Outside Club LLM there's a velvet rope and a long queue of 20 partygoers. Every time someone gets in, the club's DJ (the expensive GPT-4 inside) has to spin a brand-new track — that costs $$ and 4 seconds. The owner hires four bouncers, standing one behind the other, to stop most people from ever bothering the DJ.
  1. Bouncer 1 — “Same face?” (exact cache)
    He has a Polaroid of everyone who entered today. If your face matches a Polaroid pixel-for-pixel, he waves you through with the same wristband as last time. → InMemoryCache / Redis keyed by hash(query). Zero LLM cost. Misses anything reworded.
  2. Bouncer 2 — “Look-alike?” (semantic cache)
    If you're not in the Polaroid book, she squints: “You look 96% like Priya who came in at 9 pm — close enough.” Same wristband, no DJ needed. → GPTCache / vector similarity on the query embedding. Catches “refund policy?” ≈ “how do I return?”.
  3. Bouncer 3 — “I know the playlist for your vibe” (plan / skill cache)
    If you're brand new but you say “I want 90s hip-hop”, he hands the DJ a pre-written setlist instead of making him compose one. The DJ still plays — but much faster and cheaper. → Cache the plan / tool sequence / retrieved chunks, not the final answer. Saves planning tokens and tool calls.
  4. Bouncer 4 — “Weren't you just inside?” (conversation memory)
    For the same partygoer asking again 30 seconds later, he just lets them back in with their old wristband and tells the DJ “keep playing what they liked.” → Per-session ConversationBufferMemory / LangGraph thread checkpoint. No re-retrieval, no re-planning.
One-line recall trick: “Same face → look-alike → same vibe → same person.” Four bouncers, each looser than the last. By the time query #20 reaches the DJ, only ~3 actually got past all four.

The 4 layers of reuse

flowchart LR Q[Incoming query] --> L1{Exact-match cache?} L1 -- hit --> R1[return cached answer] L1 -- miss --> L2{Semantic cache?
cosine > 0.95} L2 -- hit --> R2[return cached answer] L2 -- miss --> L3{Same intent?
route to memoised plan} L3 -- yes --> R3[reuse plan, only run new steps] L3 -- no --> L4[Full agent run] --> Persist[(cache answer + embedding)] Persist --> R4[return]

Layer-by-layer

LayerWhat it doesCost savedLibrary / pattern
1. Exact-string cacheHash the query & user context; return prior answer if identical.100%Redis / functools.lru_cache / langchain.cache.InMemoryCache
2. Semantic cacheEmbed query, look up nearest prior query; reuse if similarity > threshold.~90%GPTCache, Redis VectorSearch, SemanticCache in LangChain
3. Plan / tool-call memoisationCache the tool calls, not the LLM answer. New query reuses search results, only the final summary is redone.50–80%Custom — wrap each skill with a TTL'd dict keyed by input.

Implementation snippets

Exact-string LangChain cache (1 line)

from langchain.globals import set_llm_cache
from langchain_community.cache import InMemoryCache
set_llm_cache(InMemoryCache())   # identical prompts → no LLM call

Semantic cache via GPTCache

from gptcache import Cache
from gptcache.adapter.api import init_similar_cache
cache = Cache()
init_similar_cache(cache_obj=cache, data_dir="cache_dir")
# every wrapped LLM call now checks embedding similarity first

Skill-level cache (your own)

from functools import lru_cache
@lru_cache(maxsize=256)
def _cached_sql(query: str) -> tuple:
    return tuple(run_sql_sync(query))

Practical advice (the 1 → 20 path)

StepWhat to add when
Day 1Turn on InMemoryCache for the LLM.
~ 100 queriesAdd a semantic cache so paraphrases hit.
~ 1k queriesCache expensive tools (web_search, SQL) with TTL.
multi-tenantScope every cache key by session_id / tenant_id.
10k+/dayMove caches to Redis; add metrics; SLA on cache hit ratio.
In real systems you'll see 60–90% of follow-up queries hit a cache or reuse a prior plan — the agent only does original thinking on the first one.

The vector DB still holds 500 rows (one per chunk) — caching doesn't change that. What caching changes is how often you have to touch those 500 rows. With all 4 layers you'll typically do retrieval against the DB only ~6 times out of 20.
