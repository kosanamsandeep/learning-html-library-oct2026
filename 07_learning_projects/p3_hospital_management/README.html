Why Composition? Object Graph vs Inheritance Data Flow Structure

🤔 Why Composition Over Inheritance Here?

The Golden Rule

Inheritance: "X IS-A Y" (SavingsAccount IS-A Account)

Composition: "X HAS-A Y" (Doctor HAS Appointments)

Ask: "Is a Doctor a Patient?" → NO! So don't inherit. A Doctor HAS patients.

Problems with Inheritance Here

# BAD: What if we tried inheritance?
class Doctor(Person): ...
class Patient(Person): ...

# What about a doctor who is ALSO a patient? 🤯
# Python allows multiple inheritance but it's complex!
# With composition: Doctor HAS health_record (acts as patient when needed)

⚔️ Composition vs Inheritance Comparison

Scenario Inheritance Composition Winner
SavingsAccount → Account IS-A ✓ Possible but overkill Inheritance
Doctor → Hospital "Doctor IS-A Hospital" ❌ Hospital HAS Doctors ✓ Composition
Adding new behavior at runtime Can't change parent Swap components Composition
Deep hierarchy (5+ levels) Fragile, hard to change Flat, flexible Composition
Code reuse Rigid (all-or-nothing) Pick what you need Composition

🔑 The Famous Rule

"Favor composition over inheritance" — Gang of Four (Design Patterns book)

This doesn't mean NEVER use inheritance. It means: when in doubt, compose.

🔄 Sequence: Booking & Completing an Appointment

sequenceDiagram participant Main participant Hospital as HospitalService participant Doctor participant Apt as Appointment participant Patient Main->>Hospital: book_appointment(apt_id, patient_id, doctor_id, time) Hospital->>Hospital: Look up Patient Hospital->>Hospital: Look up Doctor Hospital->>Doctor: schedule_appointment(apt_id, patient, time) Doctor->>Apt: Create Appointment(patient, time) Note over Apt: Appointment now HAS-A Patient reference Doctor->>Doctor: Add to _appointments list Doctor-->>Hospital: Return Appointment Hospital-->>Main: Return Appointment Main->>Hospital: complete_appointment(doctor_id, apt_id, notes) Hospital->>Doctor: Find appointment Doctor->>Apt: apt.complete(notes) Apt->>Patient: patient.add_to_history(notes) Note over Patient: History updated through composition chain!

Key Insight: Information Flows Through Composition

When we complete an appointment, the notes automatically flow to the patient's medical history. The appointment KNOWS about the patient (HAS-A), so it can update the patient directly. No inheritance needed!

🎯 Key Takeaways

  1. HAS-A over IS-A when objects contain/use other objects
  2. Objects are independent - Patient doesn't know about Doctor
  3. Flexible - Add/remove relationships without breaking hierarchies
  4. Multi-level composition scales to complex systems
