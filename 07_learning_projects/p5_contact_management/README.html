📝 Schema = Contract

A schema defines the EXACT shape of data that your system accepts and returns. Think of it as a legal contract: "You send me data in THIS format, I guarantee responses in THAT format."

graph LR A[Client sends JSON] -->|Must match schema| B[ContactSchema.validate] B -->|Valid| C[Create Contact] B -->|Invalid| D[Return ALL errors] C --> E[ContactSchema.serialize] E --> F[Return formatted JSON]

Nested Validation Error Paths

// Input with errors:
{
  "first_name": "",              → "first_name is required"
  "addresses": [
    { "zip_code": "INVALID" }   → "addresses[0].zip_code: invalid format"
  ],
  "phones": [
    { "number": "" }            → "phones[0].number is required"
  ]
}

// All errors returned at once with clear paths!

✅ Validation Layers

graph TD A[Raw Input Data] --> B{Top-Level Valid?} B -->|first_name empty| E[Error: first_name required] B -->|OK| C{Nested Valid?} C -->|bad zip_code| F[Error: addresses.0.zip_code invalid] C -->|OK| D{Cross-Field Valid?} D -->|company but no job_title| G[Warning: job_title recommended] D -->|OK| H[✅ All Valid - Create Contact]
Validation Level What It Checks Example
Field-level Single field rules email must contain @
Nested-level Sub-object rules Each address has valid zip
Cross-field Rules between fields If company given, need job_title
Business-level Domain rules Max 5 addresses per contact

🎯 Key Takeaways

  1. Schema = Contract between your system and the outside world
  2. Nested schemas validate sub-objects independently
  3. Error paths tell exactly WHERE the problem is
  4. Serialize/Deserialize in one place for consistency
