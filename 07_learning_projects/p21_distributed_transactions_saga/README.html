Project 21 simplified

A saga keeps many services consistent without one giant transaction

One order touches the order service, the payment service, the inventory service, and the shipping service. If any one of them fails, you cannot roll back the others with a single database transaction. The Saga pattern coordinates the steps and compensates what already ran.

The story

You book a flight: hold a seat, charge the card, issue the ticket. These are separate microservices, each with its own database. What happens if the seat is held and the card is charged, but the ticket printer is down?

Without a saga

The card is charged, the seat is held forever, and no ticket exists. The customer is angry and the data is inconsistent.

With a saga

The saga notices the failure and runs compensating actions: release the seat and refund the card. The system is back to a consistent state.

The mental model

step 1
→
step 2
→
step 3
⚠
fail
←
undo 2
←
undo 1
Key idea: you cannot roll back remote services together, but you can run compensating actions in reverse order until the system is consistent again.

Why not just use a distributed transaction?

A two-phase commit (2PC) tries to lock all participants until everyone agrees. That works for two databases, but breaks down across services:

  • Locks are held across the network, so latency and lock contention explode.
  • A participant can crash while waiting to commit, blocking everyone.
  • Third-party services (Stripe, Twilio) never join your 2PC.

So modern systems say: don't try to be atomic — accept the temporary inconsistency and guarantee you can fix it. That is the Saga pattern.

Choreography in plain English

Nobody calls the next service. The order service publishes ORDER_PLACED. The payment service listens, charges, and publishes PAYMENT_CHARGED. The inventory service listens, reserves, and so on. The compensation chain works the same way:

inventory fails -> publishes INVENTORY_RESERVED_FAILED
payment listens -> refunds, publishes PAYMENT_REFUNDED
order listens    -> cancels, publishes ORDER_CANCELLED

Every step both does work and publishes its result. Other services just react.

Orchestration in plain English

One object — the saga — holds the list of steps. It calls them in order. If a step fails, it walks the completed steps backward and runs each one's compensating action:

saga.add_step("reserve_inventory", do_reserve, undo_reserve)
saga.add_step("charge_card",       do_charge,   undo_charge)
saga.add_step("confirm_shipment",  do_ship,     undo_ship)

If confirm_shipment fails, compensation runs undo_charge first, then undo_reserve — the exact reverse of execution.

The outbox in plain English

When an order is created, two things must happen: the order row is written and an event is emitted. If you write the row first and the process crashes before emitting, the event is lost forever.

business row
+
outbox row
=
ONE commit
→
dispatcher publishes

The outbox row lives in the same local transaction as the business change, so both succeed or both fail. A background dispatcher then publishes pending rows. If it crashes halfway, a restarted dispatcher picks up where it left off — no events lost, none duplicated.

Idempotency in plain English

A network timeout makes the client retry a charge. Without protection the customer is charged twice. The client sends an idempotency key with the logical payment; the server remembers the key and returns the first result for any retry.

result, replayed = store.execute("idem-PAY-ORD-200", charge)

First call runs charge and stores the result. A retry with the same key is replayed and never runs charge again.

The saga state machine

A saga is always in exactly one state, and only certain transitions are allowed:

PENDING
→
RUNNING
→
COMPLETED
PENDING
→
RUNNING
→
COMPENSATING
→
FAILED
Guarantee: compensation only touches steps that actually completed, each exactly once, in strict reverse order. That is what makes the saga trustworthy enough to run in production.

Interview answer in simple words

Use this when someone asks, "How do you keep multiple services consistent?"

A saga coordinates a business process across services without a distributed transaction. Each step runs a local transaction; if a later step fails, previously completed steps are compensated in reverse order. Sagas can be choreographed — services react to each other's events — or orchestrated — one coordinator drives every step. Reliability comes from a transactional outbox so no event is lost, and idempotency keys so retries never apply an action twice.
