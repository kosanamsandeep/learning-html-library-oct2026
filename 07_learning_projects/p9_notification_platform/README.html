🏭 Factory Pattern Explained

What is Factory Pattern?

Factory Pattern centralizes object creation. Instead of scattering Notification(...) calls everywhere in your code, you delegate creation to a Factory class that knows how to properly construct objects.

❌ Without Factory

# Scattered across codebase
n1 = Notification(
    notification_id=str(uuid4()),
    recipient="x@y.com",
    subject="...",
    body="...",
    channel="EMAIL",
    priority="NORMAL",
    metadata={}
)
# Repeated everywhere, inconsistent

✅ With Factory

# Clean, consistent, validated
n1 = NotificationFactory.create_email(
    "x@y.com",
    "Subject",
    "Body"
)
# Factory handles ID, defaults, validation

🎯 Strategy Pattern Explained

What is Strategy Pattern?

Strategy Pattern defines a family of algorithms (email sending, SMS sending, etc.), encapsulates each one in its own class, and makes them interchangeable. The client code doesn't need to know which algorithm is being used.

❌ Without Strategy

# Giant if/elif chain
def send(notification):
    if notification.channel == "EMAIL":
        # 50 lines of email logic
    elif notification.channel == "SMS":
        # 50 lines of SMS logic
    elif notification.channel == "PUSH":
        # 50 lines of push logic
    # Adding new channel = modify this function!

✅ With Strategy

# Each channel is its own class
strategy = strategies[notification.channel]
result = strategy.send(notification)

# Adding new channel = new class file
# ZERO changes to existing code!

🤝 Factory + Strategy: How They Work Together

1
Client calls service.send_email("to@x.com", "Subject", "Body")
2
Factory creates a properly configured Notification object with generated ID, defaults, and validation
3
Service looks up the registered Strategy for channel "EMAIL" from the strategy registry
4
Strategy (EmailStrategy.send()) executes the channel-specific sending logic
5
Result is returned and logged in history for analytics/retry
sequenceDiagram participant Client participant Service as NotificationService participant Factory as NotificationFactory participant Registry as Strategy Registry participant Strategy as EmailStrategy Client->>Service: send_email("to@x.com", "Sub", "Body") Service->>Factory: create_email("to@x.com", "Sub", "Body") Factory-->>Service: Notification object (with ID, defaults) Service->>Registry: get strategy for "EMAIL" Registry-->>Service: EmailStrategy instance Service->>Strategy: send(notification) Strategy-->>Service: NotificationResult(success=True) Service-->>Client: NotificationResult

🔓 Open/Closed Principle in Action

Adding a new channel (e.g., WhatsApp) requires:

Step Action Files Modified
1 Create WhatsAppStrategy class that extends NotificationStrategy NEW file only
2 Register: service.register_strategy("WHATSAPP", WhatsAppStrategy()) Configuration only
3 Use: service.send(...) with channel="WHATSAPP" None

✅ ZERO modifications to NotificationService, NotificationFactory, or any existing Strategy!

🧠 Key Concepts & Takeaways

Concept Implementation Benefit
Factory Pattern NotificationFactory.create_*() Consistent creation, hidden complexity
Strategy Pattern NotificationStrategy ABC + concrete implementations Swappable algorithms, no if/elif chains
Strategy Registry _strategies: dict[str, Strategy] Dynamic channel selection at runtime
Open/Closed register_strategy() Add channels without modifying existing code
Single Responsibility Each class has ONE job Easy to test, maintain, and understand
Dependency Inversion Service depends on NotificationStrategy ABC Decoupled from concrete implementations
Template Pattern create_from_template() Reusable notification templates
