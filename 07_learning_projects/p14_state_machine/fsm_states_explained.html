How the FSM Sets States and Allows Transitions

This page explains the finite state machine in machine/fsm.py using simple words. Think of the FSM as a strict traffic controller for an order workflow: it knows the current state, listens for events, checks rules, and only then moves to the next state.

State Event Transition Guard Action

One-line summary

A state changes only when you call send(event), a matching transition exists from the current state, and the transition guard allows it.

1. Where is the current state stored?

The machine stores the current state in one private variable: 

self._current_state: str = initial_state

In the order workflow, the machine starts here: 

machine = StateMachine(initial_state="draft", context=context)
Simple meaning: when the order workflow is created, the order starts in draft. Nothing else is the current state until the FSM updates self._current_state.

2. What is a state?

A state is a named stage of the workflow. In this project, states are registered using add_state(StateConfig(...)).

State Meaning Final?
draft Order has been created but not submitted. No
pending_payment Order is waiting for payment. No
paid Payment has succeeded. No
processing Order is being prepared. No
shipped Order has been shipped. No
delivered Order reached the customer. Yes
cancelled Order was cancelled. Yes
refunded Money was returned to the customer. Yes
payment_failed Payment attempt failed. No

3. What is a transition?

A transition is one allowed movement from one state to another, triggered by an event. 

Transition(
    from_state="draft",
    event="submit",
    to_state="pending_payment",
    guard=lambda ctx: ctx["order"].total_amount > 0,
)
draft -- submit --> pending_payment
Simple meaning: if the machine is currently in draft and it receives the event submit, it may move to pending_payment.

4. When is a transition allowed?

A transition is allowed only when both checks pass:

Check Question asked by the FSM If answer is yes
1. Matching transition exists Is there a transition where from_state == current_state and event == event_sent? The FSM continues to guard checking.
2. Guard passes Is there no guard, or does the guard return True? The FSM performs the state change.

Allowed example

Current state is draft, event is submit, and order total is greater than zero.

draft -- submit --> pending_payment

Result: success=True, and current state becomes pending_payment.

5. When is a transition not allowed?

Case A: No transition is defined for that state and event

If the current state is draft and you send ship, the FSM searches for: 

from_state="draft" and event="ship"

No such transition exists, because shipping is only allowed from processing.

Result: success=False, error says no transition exists, and the state stays draft.

Case B: A transition exists, but its guard fails

If the current state is draft and you send submit, a transition exists. But this transition has a guard: 

guard=lambda ctx: ctx["order"].total_amount > 0

If the cart is empty, total_amount is 0, so the guard returns False.

Result: success=False, guard_failed=True, and the state stays draft.

6. What exactly happens inside send(event)?

This is the simple decision flow:

Step What the FSM does Example
1 Looks at the current state. draft
2 Finds transitions matching current state and event. draft + submit
3 If none match, rejects the event. draft + ship is rejected.
4 If a guard exists, runs the guard. total_amount > 0
5 If guard fails, rejects the event. Empty cart cannot submit.
6 Runs old state's on_exit, if configured. Leaving draft.
7 Runs transition action, if configured. Increase payment_attempts.
8 Sets the new current state. self._current_state = transition.to_state
9 Runs new state's on_enter, if configured. Add note: awaiting payment.
10 Stores the result in history and notifies listeners. Audit trail is updated.
Important: the state is actually changed at this line in fsm.py: 
self._current_state = transition.to_state
This line is reached only after a matching transition is found and its guard passes.

7. Allowed and blocked examples from the order workflow

Current state Event sent Allowed? Why? New state
draft submit Yes, if total > 0 Transition exists and guard passes. pending_payment
draft ship No No transition exists from draft using ship. Still draft
pending_payment pay Yes Transition exists and has no guard. paid
paid ship No Must first send start_processing. Still paid
processing ship Yes, if address exists Transition exists and guard checks shipping address. shipped
shipped cancel No Cancellation transitions are only added for draft, pending_payment, paid, and processing. Still shipped
delivered refund Yes A partial refund transition exists after delivery. refunded

8. How to check without changing state

The FSM has helper methods for asking what is possible before sending an event.

Method Meaning Does it change state?
can_send("submit") Returns True if this event can currently transition successfully. No
available_events() Returns all currently allowed events whose guards pass. No
is_in_final_state() Returns True if current state is marked final. No

9. Mental model

For every event, ask these questions in order:

  1. Where am I now? That is current_state.
  2. Is this event listed as a transition from this state?
  3. If yes, does the guard allow it?
  4. If yes, run actions and set current_state to the transition's to_state.
  5. If no, keep the current state unchanged and return a failed result.

10. Tiny example

machine.current_state
# "draft"

machine.send("submit")
# allowed only if order.total_amount > 0
# current_state becomes "pending_payment"

machine.send("ship")
# blocked because there is no pending_payment --ship--> ... transition
# current_state stays "pending_payment"

machine.send("pay")
# allowed
# current_state becomes "paid"
Final takeaway: states are not randomly assigned. They are set only by successful transitions. A successful transition requires the right current state, the right event, and a passing guard if one exists.
