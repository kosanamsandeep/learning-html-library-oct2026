Project 16 simplified

Circuit breaker means: stop calling a service that is already failing

This project looks complex because it teaches four resilience patterns at once. Start with the simplest idea: when an external service is unhealthy, your app should stop hammering it, fail fast, wait a little, then test if it recovered.

The story

Imagine your app calls a payment gateway. On a normal day, every payment request goes through.

One day the payment gateway goes down. If your app keeps sending every request to that broken gateway, three bad things happen:

  • Your users wait longer before seeing an error.
  • Your app wastes threads, connections, and CPU on calls that will fail anyway.
  • The payment gateway gets even more overloaded while it is trying to recover.
Circuit breaker solution: after a few failures, mark the service as unhealthy and reject new calls immediately. After a timeout, allow a small test call. If the test works, resume normal traffic.

The one picture to remember

CLOSED

The circuit breaker is closed, so traffic can pass through to the service. Calls are allowed. Failures are counted.

OPEN

The circuit breaker is open, so traffic is blocked. The service looks unhealthy, and calls are rejected immediately.

HALF_OPEN

The circuit breaker is partly open for recovery testing. Allow a small number of calls to see if the service is back.

breaker CLOSED: send calls
->
too many failures
->
breaker OPEN: fail fast
->
wait timeout
->
breaker HALF_OPEN: test recovery
Important: CLOSED and OPEN describe the circuit breaker, not the payment service. A closed breaker lets requests pass through. An open breaker blocks requests to protect your app.

The core code, simplified

This is the heart of the circuit breaker. Do not start with every stat and listener. Understand this tiny version first:

if state == OPEN:
    reject_request_fast()

try:
    result = call_external_service()
    record_success()
    return result
except Exception:
    record_failure()
    if failures_reached_threshold:
        state = OPEN
    raise

In this project, the real version lives in resilience/circuit_breaker.py inside CircuitBreaker.call(), _on_success(), and _on_failure().

How demo 1 works

main.py creates a fake payment service that fails 100% of the time:

payment = PaymentService(failure_rate=1.0)

Then it creates a circuit breaker that opens after three failures:

cb = CircuitBreaker(
    CircuitBreakerConfig(
        name="payment-gateway",
        failure_threshold=3,
        success_threshold=2,
        timeout_seconds=2.0,
    )
)

The behavior is intentionally simple:

  1. Request 1 fails. Failure count = 1. The circuit breaker is still CLOSED, so calls are still allowed.
  2. Request 2 fails. Failure count = 2. The circuit breaker is still CLOSED.
  3. Request 3 fails. Failure count = 3. The circuit breaker changes to OPEN.
  4. Requests 4, 5, 6, 7, 8 are rejected fast because the circuit breaker is OPEN. They do not call the payment service.

Retry, bulkhead, fallback: the simple version

Retry

Meaning: try again because the error may be temporary.

Example: network blip, temporary timeout, service restart.

Danger: retrying too aggressively can overload the dependency.

Bulkhead

Meaning: give each dependency its own limit.

Example: payment can use 3 slots; inventory can use 5 slots.

Benefit: payment being slow does not block inventory.

Fallback

Meaning: return a safe backup response when the ideal response fails.

Example: show cached inventory or say "payment temporarily unavailable".

Benefit: the app degrades gracefully instead of fully crashing.

Why the stack order matters

In demo 5, the project combines the patterns like this:

1. Bulkhead
->
2. Circuit Breaker
->
3. Retry
->
4. Payment Service
Layer Question it answers
Bulkhead Do we even have capacity to try this call?
Circuit Breaker Does this service look healthy enough to call?
Retry If the first try fails, should we try again gently?
Service Call Actually call payment, inventory, email, database, etc.

Interview answer in simple words

Use this when someone asks, "What is a circuit breaker?"

A circuit breaker protects my system when another service is failing. It starts CLOSED and allows requests. If too many calls fail, it opens and fails fast without calling the broken service. After a timeout, it becomes HALF_OPEN and sends a test request. If the test succeeds, it closes again. This prevents cascading failures and gives the dependency time to recover.
