📦 What is a DTO?

DTO = Courier Box

Imagine you're shipping a product to a customer:

  • Your warehouse has FULL details: cost price, supplier info, shelf location
  • The shipping box (DTO) only shows: product name, price, description
  • The customer doesn't need to know your cost or where you stored it!

Key Principle

Domain Model ≠ API Contract

Your internal representation should NOT be your external interface. They change for different reasons.

Problem Without DTO With DTO
Security Internal fields leaked to client Only safe fields exposed
Validation Invalid data reaches model Caught at boundary
API Stability Model change = API breaks Model change = update mapping only
Flexibility One representation for all Different DTOs for different needs

DTO_Out-->>Service: Safe DTO Service-->>API: Return DTO API-->>Client: 201 Created + safe response end

The Three-Step Pattern

  1. INPUT DTO: Validate what comes IN (CreateProductDTO)
  2. DOMAIN MODEL: Process with full internal data (Product)
  3. OUTPUT DTO: Filter what goes OUT (ProductResponseDTO)

📋 Types of DTOs

Request DTOs (Client → Server)

DTO Purpose Key Feature
CreateProductDTO New product data All required fields, validation
UpdateProductDTO Partial update Optional fields (None = skip)
CreateOrderDTO New order data Nested items validation

Response DTOs (Server → Client)

DTO Purpose Key Feature
ProductResponseDTO Single product view Hides internal fields, adds computed
ProductListResponseDTO Paginated list Includes total_count, page info
OrderResponseDTO Order confirmation Computed total, formatted dates

🆕 New Layer: dtos/

This is the first project with a dedicated DTO layer. It sits BETWEEN the outside world and your domain models, acting as a protective gateway.

🎯 Key Takeaways

  1. DTO = Courier Box — only what's needed for transport
  2. Validate at boundary — catch bad data before it enters the system
  3. Separate input/output DTOs — they have different requirements
  4. from_model() — factory method centralizes conversion
