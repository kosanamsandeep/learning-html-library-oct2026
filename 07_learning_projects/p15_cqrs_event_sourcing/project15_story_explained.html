Project 15 Explained Simply: CQRS & Event Sourcing

This project is a small banking system. The goal is to show how a serious banking-style application can keep a perfect audit trail. Instead of only storing balance = 1450, it stores the full story: account opened, money deposited, money withdrawn, transfer completed, account frozen, and so on.

CQRS Event Sourcing Commands Events DTOs Aggregate Projections Queries

One-line idea

Commands ask the system to do something, events record what actually happened, projections build easy-to-read views, and queries read those views.

1. The project story

Imagine a bank employee named Alice opens an account. Later, Alice deposits money, withdraws money, transfers money, and maybe the account gets frozen for safety.

In a normal CRUD app, the database row may simply say: ACC-001 balance = 1150. But that does not explain how the account reached 1150.

In this project, the system keeps a diary. Every important thing that happened is saved as an event. The current balance is rebuilt from that diary whenever needed.

2. The simplest mental model

Thing Simple meaning Example from this project
Command A request to do something. It is an intention. DepositCommand("ACC-001", 500)
Event A fact that already happened. It is history. MoneyDeposited
DTO A simple data carrier. It holds fields and usually has no business logic. OpenAccountCommand, GetBalanceQuery
Aggregate The business-rule brain for one account. BankAccountAggregate
EventStore The permanent diary of all events. EventStore.append(event)
Projection A read-friendly view built from events. BalanceProjection
Query A request to read information. It does not change anything. GetTransactionHistoryQuery
Handler The class that receives a command/query and performs the correct work. BankCommandHandler, BankQueryHandler

3. Why is it called CQRS?

CQRS means Command Query Responsibility Segregation. In simple words:

Write side

Used when the user wants to change something. It receives commands, checks business rules, and writes events.

Command -> CommandHandler -> Aggregate -> EventStore

Read side

Used when the user wants to know something. It receives queries and reads from projections.

Query -> QueryHandler -> Projection -> Response

Why separate them? Writing needs strict rules and correctness. Reading needs speed and convenient shapes. CQRS allows each side to be designed for its own job.

4. Why is it called Event Sourcing?

Event Sourcing means the source of truth is not the current balance table. The source of truth is the list of events. 

AccountOpened(initial_deposit=1000)
MoneyDeposited(amount=500)
MoneyWithdrawn(amount=200)

Current balance = 1000 + 500 - 200 = 1300
Simple analogy: Your bank statement is the truth. The balance is calculated from the statement. If someone asks, "Why is my balance 1300?", the system can show every event that produced it.

7. Why are commands called DTOs?

DTO means Data Transfer Object. It is a small object used to move data from one layer to another. It does not make decisions. It simply carries information. 

@dataclass
class DepositCommand:
    account_id: str
    amount: float
    description: str = ""

DepositCommand is called a command because it represents the user's intention: "Please deposit this amount into this account."

It is also a DTO because it is just a data packet containing account_id, amount, and description.

8. Command classes and why they exist

Command class User is saying Why this separate class is useful
OpenAccountCommand Open a new account. Clearly carries account opening fields like owner and initial deposit.
DepositCommand Add money to an account. Keeps deposit data separate from withdrawal or transfer data.
WithdrawCommand Remove money from an account. Allows withdrawal-specific validation like sufficient balance.
TransferCommand Move money from one account to another. Needs both source and destination accounts.
FreezeAccountCommand Freeze an account. Carries the account and reason for freezing.
CloseAccountCommand Close an account. Represents a separate business action with its own rules.

9. Why are events separate classes?

Events are not requests. Events are facts. They are named in past tense because they already happened.

Event class Meaning Why it matters
AccountOpened An account was created. Starts an account's event stream.
MoneyDeposited Money was added. Increases balance when replayed.
MoneyWithdrawn Money was removed. Decreases balance when replayed.
TransferInitiated Transfer started from source account. Debits the sender.
TransferCompleted Transfer reached destination account. Credits the receiver.
TransferFailed Transfer failed. Can reverse a debit if needed.
AccountFrozen Account was frozen. Future deposits/withdrawals are blocked.
AccountClosed Account was closed. Marks account as no longer active.
Important difference: DepositCommand means "I want to deposit money." MoneyDeposited means "money was actually deposited." A command can fail. An event is already accepted history.

10. Why is DomainEvent frozen?

@dataclass(frozen=True)
class DomainEvent:
    event_id: str
    event_type: str
    aggregate_id: str
    timestamp: str
    version: int
    data: dict
    metadata: dict

The project uses frozen=True because events should be immutable. Once something happened in the bank, you should not secretly edit history. If a mistake happened, you add another event to correct it.

Field Simple meaning
event_id Unique id for this event.
event_type Name of what happened, like MoneyDeposited.
aggregate_id The account this event belongs to.
timestamp When it happened.
version Event sequence number inside that account's stream.
data The business details, like amount or owner name.
metadata Extra technical details, if needed.

11. The EventStore: the bank diary

EventStore has three main responsibilities:

Part What it does Why it exists
_global_log Stores all events in order. Gives a complete bank-wide audit trail.
_streams Stores events grouped by account id. Quickly rebuilds one account.
_subscribers Stores projections that should hear about new events. Keeps read models updated automatically. 
self._global_log.append(event)
self._streams[event.aggregate_id].append(event)

for subscriber in self._subscribers:
    subscriber.handle_event(event)
Simple meaning: when a new event is appended, it is saved forever and then announced to all projections so they can update their read views.

12. The Aggregate: the business-rule brain

BankAccountAggregate represents one account's business state. It is not loaded from a balance table. It is rebuilt by replaying that account's events. 

events = event_store.get_stream("ACC-001")
aggregate = BankAccountAggregate.from_events(events)

After replaying events, the aggregate knows facts like:

  • account exists or not
  • current balance
  • whether the account is frozen
  • whether the account is closed
  • current version
Why create this class? The aggregate is the place where business rules are enforced before events are created. For example: do not withdraw more than the balance, do not deposit into a frozen account, do not close an account with money still inside.

13. The CommandHandler: the write-side worker

BankCommandHandler receives command DTOs and decides whether they can become events.

1
Receive command. Example: WithdrawCommand("ACC-001", 100).
2
Load account aggregate. It gets events for ACC-001 and replays them.
3
Check business rules. Does account exist? Is it frozen? Is there enough balance?
4
Create event if valid. If rules pass, create MoneyWithdrawn.
5
Append event to store. The event becomes permanent history and projections are notified.

14. Projections: read-friendly views

Raw events are excellent for audit history, but not always convenient for screens. A user may simply want: "show my balance" or "show my last 10 transactions". Projections build these convenient views.

Projection Builds this view Optimized question
BalanceProjection AccountBalanceView What is this account's current balance?
TransactionHistoryProjection TransactionRecord list What transactions happened for this account?
DailySummaryProjection DailySummary What happened today across the bank?
Why projections are called disposable: They are not the source of truth. If a projection is deleted, it can be rebuilt by replaying all events from the EventStore.

15. Read model DTOs

These are also data carrier classes, but they are for responses/read views rather than write requests.

Read model What data it carries
AccountBalanceView Account id, owner name, balance, account type, frozen/closed flags, transaction count.
TransactionRecord Timestamp, event type, account id, amount, description, balance after transaction.
DailySummary Date, total deposits, total withdrawals, total transfers, transaction count, accounts opened.

16. Query DTOs and QueryHandler

Query DTOs represent questions. They do not change the system.

Query class User is asking Projection used
GetBalanceQuery What is this account's balance? BalanceProjection
GetTransactionHistoryQuery Show transaction history for this account. TransactionHistoryProjection
GetAllAccountsQuery Show all accounts. BalanceProjection
GetDailySummaryQuery Show a daily banking summary. DailySummaryProjection
Why a separate BankQueryHandler? It gives the read side one clean entry point. Controllers or UI code do not need to know projection internals.

18. Complete story flow: deposit money

User request:
DepositCommand(account_id="ACC-001", amount=500, description="Salary")

If valid, event created:
MoneyDeposited(aggregate_id="ACC-001", data={"amount": 500, "description": "Salary"})
  1. The user asks to deposit money using DepositCommand.
  2. BankCommandHandler loads ACC-001 from its event stream.
  3. BankAccountAggregate now knows whether the account exists and whether it is frozen or closed.
  4. The handler checks: account exists, not frozen, not closed, amount is positive.
  5. If checks pass, the handler creates MoneyDeposited.
  6. EventStore appends the event.
  7. BalanceProjection increases balance.
  8. TransactionHistoryProjection adds a transaction record.
  9. DailySummaryProjection increases daily deposits.

19. Complete story flow: withdraw money

User request:
WithdrawCommand(account_id="ACC-001", amount=200, description="ATM")

If valid, event created:
MoneyWithdrawn(aggregate_id="ACC-001", data={"amount": 200, "description": "ATM"})

Withdrawal is stricter than deposit because it must check balance.

Rule If rule fails
Account must exist. Returns ERROR: Account not found.
Account must not be frozen. Returns ERROR: Account is frozen.
Account must not be closed. Returns ERROR: Account is closed.
Amount must be positive. Returns ERROR: Withdrawal amount must be positive.
Balance must be enough. Returns ERROR: Insufficient funds.
If a command fails validation, no event is created. This is important: the event store only contains accepted facts, not failed intentions.

20. Complete story flow: transfer money

A transfer touches two accounts. The source account loses money, and the destination account receives money.

sequenceDiagram participant User participant Cmd as BankCommandHandler participant Source as Source Aggregate participant Dest as Destination Aggregate participant Store as EventStore participant Proj as Projections User->>Cmd: TransferCommand(ACC-A, ACC-B, 1500) Cmd->>Source: Rebuild ACC-A from events Cmd->>Dest: Rebuild ACC-B from events Cmd->>Cmd: Validate both accounts and source balance Cmd->>Store: append(TransferInitiated for ACC-A) Store->>Proj: Debit ACC-A in read models Cmd->>Store: append(TransferCompleted for ACC-B) Store->>Proj: Credit ACC-B in read models Cmd-->>User: OK

This project models transfer as two events:

  • TransferInitiated belongs to the source account and debits it.
  • TransferCompleted belongs to the destination account and credits it.

21. What happens when an account is frozen?

FreezeAccountCommand("ACC-X", "Suspicious activity")
-- creates -->
AccountFrozen(aggregate_id="ACC-X", data={"reason": "Suspicious activity"})

Later, when someone tries to deposit or withdraw, the aggregate is rebuilt from events. During replay, it sees AccountFrozen and sets is_frozen = True. Then command validation blocks the action.

This is why event history matters. The current frozen state is not guessed. It is rebuilt from the exact event that froze the account.

22. How projections update themselves

Every projection has a method named handle_event(event). The event store calls this method whenever a new event is appended. 

store.subscribe(balance_projection)
store.subscribe(history_projection)
store.subscribe(daily_projection)

store.append(MoneyDeposited(...))

# EventStore then calls:
balance_projection.handle_event(event)
history_projection.handle_event(event)
daily_projection.handle_event(event)
Event BalanceProjection does HistoryProjection does DailySummaryProjection does
MoneyDeposited Adds amount to balance. Adds deposit row. Adds to total deposits.
MoneyWithdrawn Subtracts amount from balance. Adds withdrawal row. Adds to total withdrawals.
TransferInitiated Subtracts from source account. Adds transfer-out row. Adds to total transfers.
TransferCompleted Adds to destination account. Adds transfer-in row. No transfer total change in this code.

23. Why projections can be rebuilt

Since the event store has the full history, a projection can be recreated from zero. 

fresh_projection = BalanceProjection()

for event in store.get_stream("ACC-TT"):
    fresh_projection.handle_event(event)
Practical benefit: if tomorrow you need a new screen called "Top Customers", you do not need to change old events. You create a new projection and replay the existing events into it.

25. Why not just use one Account class?

For a tiny app, one class may be enough. But this project is teaching architecture used when correctness, audit, and scaling matter.

Separated class Reason for separation
Command DTOs Clearly describe user intentions.
Event classes Clearly describe accepted historical facts.
Aggregate Keeps business rules in one place.
EventStore Keeps the source of truth separate and append-only.
Projections Create fast read models for different screens/reports.
Query DTOs Clearly describe user questions.
Handlers Coordinate work without mixing all responsibilities into one class.

28. Final big picture

  1. User sends a Command because they want to change something.
  2. BankCommandHandler loads the account by replaying events.
  3. BankAccountAggregate knows the current business state and rules.
  4. If rules pass, the handler creates a DomainEvent.
  5. EventStore appends the event permanently.
  6. Subscribed Projections update their read models.
  7. User sends a Query when they want information.
  8. BankQueryHandler reads fast answers from projections.

Final takeaway

Project 15 is not mainly about banking. It is about designing systems where every change is traceable. Commands are requests, events are facts, aggregates protect rules, the event store keeps history, projections create fast views, and queries read those views.
