Project 15: CQRS & Event Sourcing - Banking Ledger

Event Sourcing CQRS Aggregate Root Projections Domain Events

Story: You're building a banking system where every cent must be traceable. Instead of storing "balance = $1,450", you store every event that led to that balance. The complete audit trail is built into the architecture itself.

CQRS: Why Separate Read and Write?

Aspect Write Side (Commands) Read Side (Queries)
Model Event stream + Aggregate Denormalized projections
Optimized for Consistency, validation Fast queries, multiple views
Data shape Normalized (events) Denormalized (pre-computed)
Scaling Scale writes independently Scale reads independently
Schema changes Events are immutable Rebuild projections anytime
Consistency Strongly consistent Eventually consistent

Key Insight: Since events are immutable and ordered, you can rebuild ANY projection at ANY time by replaying events. This means you can add new read models, fix bugs in projections, or migrate schemas without any data loss. It's like git log for your data!

Event Sourcing vs Traditional CRUD

Aspect CRUD (Traditional) Event Sourcing
Storage Current state only All events (history)
Audit trail Separate audit table Built-in (events ARE the trail)
Debugging "What happened?" - Unknown Replay and see exactly
Schema migration ALTER TABLE (risky) New projection (safe)
Time travel Impossible Replay to any point
Complexity Simple Higher (worth it for complex domains)
