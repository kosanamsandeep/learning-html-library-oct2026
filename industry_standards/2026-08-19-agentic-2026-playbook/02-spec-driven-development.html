Spec-Driven Development & GitHub Spec Kit

The most prominent methodology shift of 2026: write the spec first and treat it as the source of truth; the code is what the agent generates from it. It's an old idea (specs aren't new) re-applied to AI agents — and it is being adopted because agents turn vague briefs into confident, expensive guesses.

The problem: the "brilliant intern"

The failure it fixes: hand an agent a vague brief and it fills every gap with plausible-but-wrong guesses — a refund endpoint that reverses payment before checking whether the order shipped. It types fluently but skips edge cases. Field estimates: ~75% of AI-generated code needs rework before merge, and teams without clear specs report ~3x more debugging time. The spec, not a longer prompt, is the bounding box.

StageArtifactWhat it pins down
1 · ConstitutionconstitutionStanding principles that outlive any one feature: scope, stack versions, coding standards, repo structure (e.g. hexagonal), non-negotiables (compliance, security baselines, naming).
2 · Specifyspec.mdWhat to build and why — feature description, user/problem statements, functional & non-functional requirements, scenarios, success criteria. Implementation details are forbidden (no framework or DB names); a checklist fails the spec if any leak in.
3 · Clarifyupdated spec.mdConditional structured Q&A: inserts [NEEDS CLARIFICATION] markers, asks up to 3 questions with suggested answers (scope and security get priority), scans for logical gaps between requirements. Repeats until no new questions.
4 · Planplan.mdSelected stack, architecture, component breakdown, API/data contracts, integration points, deployment, testing approach. Consults the constitution. This is where the how lives — deliberately separate from the spec.
5 · Taskstasks.mdDiscrete agent-executable tasks by user story, with dependency management, parallel markers ([P]), exact file paths, test-first structure, and per-phase checkpoints.
6 · Implementthe codeThe agent executes the task list respecting deps and parallel markers, following TDD. It validates that constitution/spec/plan/tasks all exist before generating code.

Change is a spec edit, not a code patch

The core principle: when requirements change, edit the spec and regenerate the affected tasks — do not hand-patch generated code. Example from the field: a sharing feature changed from per-user to per-team; the team edited the spec and regenerated the affected tasks, keeping the change consistent end-to-end. Some workflows add a convergence/assessment stage — gap-finding, a test gate, diff analysis, and a 4-pillar scored verdict (Spec Compliance · Code Quality · Test Adequacy · Risk & Evidence), passing only when all pillars ≥ 70.

Maturity levels — where to aim

LevelNameModel
1Spec-FirstWrite a spec before prompting; often ephemeral — high drift risk.
2Spec-AnchoredSpec files live in the repo (.speckit/, constitution); agents implement from them — the Spec Kit model.
3Spec-as-SourceSpec is canonical; code regenerates when the spec changes; spec-code alignment is enforced.
4Spec-to-ApplicationSpec is a formal model; code is compiled deterministically (model-to-text), removing the LLM from the generation path — for SOC 2 / HIPAA / DoD reproducible builds.

When to use it — and when not to

Use it when an AI coding agent does the bulk of the implementation and you want control over what it builds — greenfield features and well-scoped, up-front-pinnable changes. Not for pure exploration where requirements are still unknown.
Two failure modes:
  • Automating a broken process — a spec for an already-broken process just makes the agent build the broken thing faster.
  • Vibe-coding without security review — dropping the human review gate reintroduces exactly the unsafe code the spec was meant to prevent.

2026 field reports

  • Thoughtworks Radar (Apr 2026) — "two broad camps are emerging: teams that rely on continually improving coding agents with minimal structure, and those that favor defined workflows and detailed specifications." Spec Kit is on the radar.
  • Brownfield challenges: instruction bloat (growing agent instructions → "context rot") and over-verbose markdown outputs. Fix: extract reusable guidance into skills, customize templates, keep it lean.
  • Independent convergence: major AI vendors reportedly converged on spec-first practice within the same ~18-month window — a rare industry-wide consensus.
Worked example (from the Agent Patterns Catalog): a team's old habit of prompting the agent straight into code "produced plausible files that missed half the edge cases." Adding the constitution → spec → clarify → plan → tasks → implement layer kept the agent bounded and made every claim reviewable before code existed.
