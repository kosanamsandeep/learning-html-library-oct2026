The Verification Funnel

The recurring 2026 thesis: the skill isn't who writes better — it's who can prove it's right. Verification is where the reliable teams win. Two pieces: the Verification Horizon (why every verifier is a compromise) and a cost-ordered funnel (how to actually right-size it).

The Verification Horizon — every verifier is a proxy

The problem: any automatic verifier is a proxy for human intent, and it must balance three requirements that are hard to combine:
  • Faithfulness — how close the verification is to real user intent (a database invariant beats "API returns 200").
  • Robustness — can the agent work around it? Fixed samples can be hard-coded; randomized property tests in isolated permission domains are much harder to game.
  • Scalability — cost and speed to run at high frequency.
VerifierFaithfulRobustScalable
Compile / lint / typesLowHighVery high
Unit testsMediumMediumHigh
Property / fuzz testsMediumHigh (randomized)Medium
Human reviewHighHighLow
Model-as-judgeMediumLow (inherits blind spots, self-preferential)Medium

No single verifier covers all correctness dimensions. That's why the funnel — not the single magic check — is the methodology.

The cost-ordered funnel

graph LR A["compile / parse
cheapest"] --> B["lint + types"] B --> C["unit tests"] C --> D["property / fuzz"] D --> E["integration / E2E"] E --> F["security audit / human
most expensive"]
  1. Run the cheapest checks first — compile, lint, types — to eliminate obvious errors at near-zero cost.
  2. Promote candidates up the funnel — only code that passes an earlier gate spends on the next, more expensive check.
  3. Reserve expensive verification (E2E, security audits, deep review) for the few candidates that make it.
  4. Failures return structured evidence, not a vague score — the agent needs "invariant X violated in file Y under input Z" to actually fix it.
Why this pairs with dynamic workflows: the funnel is the cheap side of correctness; adversarial verification and tournament agents are the expensive side. Right projects use the funnel by default and spend on verification only where stakes justify — see Module 01.

Agentic TDD — a working 8-pass template

A concrete state machine from the 2026 ecosystem that operationalizes the funnel inside a coding agent:

PassStageGate
0Design & contextHuman-approved artifacts
1Contracts & typesTypes compile
2Test generation (Red)Tests fail for the right reason
3Core logic (Green)Tests pass
4RefactorTests still pass
5Observability & logsInstrumentation present
6Security hardeningScan + red-line checks
7Documentation / spec syncSpec and code agree
  • Each pass runs the local test suite and self-corrects up to 3 retries before failing.
  • Each pass commits atomically, so any breakage reverts exactly one step.

Model-as-judge, done defensively

  • Never let the producing agent grade its own output (that's the self-preferential bias from Module 01). Separate producer from verifier.
  • Use adversarial verifiers — prompted to refute, defaulting to "not proven" — rather than "rate this 1–10." Comparative judgment (tournaments) beats absolute scoring.
  • Give the judge structured rubrics and structured output (evidence, not vibes).
  • Remember the horizon: model-as-judge inherits blind spots. Pair it with at least one non-model check at the cheap end of the funnel.
⚠️ The trap: a funnel is only as good as its weakest proxy. If your "verify" is "did the tests pass" and the tests encode nothing about the requirement, you've automated confidence in the wrong thing. Faithfulness first — what would the user actually notice breaking?
