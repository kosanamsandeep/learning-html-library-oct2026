Press Delete: The Ablation Mindset

When a new frontier model ships, Cherny's team deletes over 80% of Claude Code's system prompt. Behaviours tuned for older models frequently don't transfer — they become dead weight.

The core move: stop treating system prompts as permanent code. Treat the model as an organic co-worker — observe its raw behaviour first, then add scaffolding only where it repeatedly stumbles.

Each generation of model can natively do more than the last. Instructions written to correct a weaker model often hobble a stronger one — telling it exactly what to do prevents it from doing what it now could, more flexibly. The default should be less, not more.

The Ablation Practice

Line-by-line ablation of your harness

  1. Delete everything: system prompt, CLAUDE.md, custom skills, hooks.
  2. Test raw performance on a representative task suite.
  3. Re-add one thing at a time, only where the model visibly fails.
  4. Measure each addition's contribution — if a line of instruction doesn't change output quality, it's dead weight.
Cadence: every six months, try deleting your CLAUDE.md, custom skills, and hooks to see what the model can now do natively. Model capability only moves one direction — up — so scaffolding that was essential six months ago is often noise today.

Internal ablation with environment variables

Cherny's team uses flags like claude_code_simple=1 to strip back prompting and tooling internally — isolating exactly what each line of instruction contributes.

# strip prompting/tooling to a bare minimum
claude_code_simple=1

# run the same task with full harness vs stripped
# compare output quality side-by-side

The goal: measure contribution, not assume importance. If output is identical stripped vs full, you've found scaffolding to delete.

Unhobbling & Product Overhang

Product Overhang

The model can do more than your harness lets it express.

Example: limiting an agent to single-line autocomplete when it can write entire functions. Your UI/scaffolding is the bottleneck, not the model.

Fix: give the model simpler, higher-level access — full terminal access, broader tools — rather than rigid, over-specified scaffolding.

Product Underhang

You're forcing a model to do something it isn't capable of yet.

Here the answer is the opposite: you need more scaffolding and a domain-specific harness to compensate.

Diagnose first: which side are you on? Most teams default to over-specifying (underhang thinking) when they actually have overhang — and the over-specification is what's blocking capability.

📌 Takeaway: before you add a prompt line, a skill, or a hook — ask "is this compensating for the model, or constraining it?" If the model has moved past the failure mode, delete the compensation.
