Dynamic Workflows & Massive Orchestration

Through Dynamic Workflows, Opus 5 can orchestrate thousands — even tens of thousands — of agents inside a sandbox. The reference example: rewriting a 100,000-line codebase from Zig to Rust in 11 days.

The "Agentic Algebra"

Cherny's framing for composing agents at scale — three operations:

OperationWhat it doesExample
SequenceStage A must finish before stage BPlan → implement → review → ship
ParalleliseIndependent work runs concurrently100 workers each rewrite 1,000 lines
Fan-out / verifyA large batch executes; a small batch verifies/summarises10 verifiers check 1,000 workers' output
Why the verify batch is small: verification is expensive (it reads all the work). Cherny's team uses one set of agents to perform, a second set to verify/summarise, and a third set to fan out the next stage. The algebra composes.

Test-Time Compute — Spend Scale With Stakes

Dynamic Workflows are a form of test-time compute: the ability to ramp up the number of tokens and agents used for a task based on how hard it is. "Hard" tasks that previous models couldn't handle now get huge compute budgets at inference time.

TaskCompute budget
Trivial replySingle call, no orchestration
Moderate code changeFew agents + test loop
High-stakes rewriteThousands of agents + verify batches + iteration
Economics: scaling test-time compute costs real money — Cherny's long-running experiments burn "practically unlimited" token budgets, sometimes tens of thousands of dollars. Design your workflows to scale compute with stakes, not always to max.

Key Skills to Build

  • Sandbox design — dynamic workflows run agents inside a sandbox (e.g. a Bun runtime); the sandbox provides the environment the model needs to "cook".
  • Idempotent work units — each worker's task must be independently verifiable, so failures can be isolated and re-run without restarting the whole workflow.
  • Merge / integration strategy — how 1,000 parallel workers' outputs integrate without conflicts (the Zig→Rust rewrite had to merge per-module).
  • Progress metrics — you need to know a 100K-line migration is 40% done, not just "running".
