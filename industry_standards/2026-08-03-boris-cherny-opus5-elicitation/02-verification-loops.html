Verification Loops & Goal-Oriented Prompting

"The single most important thing developers get wrong is not making it possible for the AI to verify its own work."

The shift: stop over-specifying the how. Define the task, the guardrails, and the exit criteria (when it should stop). Then hand the model the tools to verify itself.

Why Prescriptive Prompting Backfires

Prescriptive (old)

  • Step-by-step "do A, then B, then C"
  • Detailed implementation instructions
  • Assumes the model can't figure it out
  • Constrains a capable model — "hobbles" it
  • Fragile when the task drifts from the script

Goal-oriented (new)

  • Define the outcome ("what")
  • Define the guardrails (what it may NOT do)
  • Define exit criteria (when it's done)
  • Let the model choose the path
  • Robust to unexpected states
The "ignorant" advantage: sometimes non-coders get better results because they simply ask for the what without getting stuck in implementation details. If you're a senior engineer, your architecture background can actively work against you — you're prone to over-prescribing the how.

Why verification is critical for long-running agents

Long-running agents (days or weeks) are prone to drift — small deviations compound over time until the work is far from the original intent. The antidote is a tangible feedback mechanism the agent feeds back into its own loop:

  • Solid test suites — the agent runs tests and iterates until green.
  • Pixel-perfect comparison — rewrite an app, screenshot original vs rewrite, compare until they match.
  • Compile/type-check gates — for language migrations (e.g. Zig→Rust), each chunk must compile before moving on.
  • Rubric checks — the agent evaluates its own output against a stated rubric.
Rule: verification is not an afterthought — it's the single highest-leverage design decision. If you can't define how the agent will know it succeeded, it can't be trusted to run long.

The Recipe

Give the model three things, not a manual

ElementExample
Task"Rewrite this app's UI in the new design system, preserving all current functionality."
Guardrails"Do not touch the API layer. No external dependencies. Don't rename public exports."
Exit criteria"Done when all 400 tests pass, visual diff < 1% across 50 reference screenshots, and bundle size ≤ current."
Note: this is the difference between "context engineering" (curating what the model sees) and task elicitation (finding the right ask to reveal latent ability). Elicitation sets the frame; the model fills the path.
