Self-Maintaining Infrastructure

Cherny's team uses Loops (local) and Routines (cloud) to have Claude maintain itself — turning engineering drudgery into autonomous background work.

The vision: "have Claude maintain itself." Automated agents handle the drudgery of engineering — dead code, duplicated abstractions, shipping experiments — so the human team focuses on product design and user needs.

Loops vs Routines

🔁 Loops — local

Run on your machine. Good for:

  • Iterative development loops
  • Time-boxed tasks in a session
  • Work that needs your local environment

☁️ Routines — cloud

Run on a schedule in the cloud. Good for:

  • Recurring maintenance that runs independent of you
  • Daily / weekly codebase health
  • Autonomous "ship the completed experiments" jobs

Concrete Routines Worth Building

RoutineWhat it doesCadence
"Abstraction police"Scans for duplicated code and unifies it into shared abstractionsWeekly
Dead code cleanupFinds and removes unused code, unreferenced exports, orphaned filesWeekly
Test generationGenerates tests for untested paths, backfills coverageOn merge
Experiment shippingShips completed experiments that have passed criteria, closes stale branchesDaily
Dependency hygieneFlags outdated / unused dependencies, security patchesWeekly
Key design point: each routine must have a verification loop (Module 02) — the abstraction police shouldn't refactor blindly; it should run the test suite after unifying. Autonomous ≠ unverified.

Why This Redefines the Engineer's Job

When maintenance becomes autonomous, the human engineer's time shifts up the stack:

  • From: fixing bugs, cleaning code, closing PRs
  • To: defining what the system should do, designing architecture, deciding what's worth building, setting the routines themselves

The "abstraction police" decides how to unify duplicate code; a human still decides whether the abstraction is the right one. The drudgery is delegated; the judgment is not.
