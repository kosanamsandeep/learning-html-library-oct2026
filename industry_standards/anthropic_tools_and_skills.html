Tools and skills — the agent-computer interface, and how to teach Claude a workflow

Tools are how an agent acts on the world. Skills are how you teach Claude a repeatable way to do something — packaged as a folder and a Markdown file Claude loads on demand. Both are about the agent-computer interface (ACI): the cleaner the interface, the better the agent behaves.

Part 1 — Designing tools (Anthropic's "prompt-engineer your tools")

Anthropic's engineering team explicitly says: while building their SWE-bench agent, they spent more time iterating on tool definitions than on the overall prompt. Tools are not a side concern.

Five rules for a good tool

  1. Pick a format the model has already seen. Markdown over heavily-escaped JSON. Whole-file rewrites over diffs when diffs require counting lines.
  2. Give the model room to think. Don't force the answer into a single tightly-typed field if intermediate reasoning helps.
  3. Eliminate formatting overhead. No mandatory line counts, no escaping nightmares, no "must end in exactly one newline".
  4. Write tool docs like you would for a junior teammate. Include example calls, edge cases, input format requirements, and clear boundaries against neighbouring tools.
  5. Poka-yoke (mistake-proof) the inputs. Anthropic's example: tools that take relative paths broke when the agent cd'd. Switching to absolute paths fixed it. Choose argument shapes that make the wrong call hard to express.
Test your tools the way you test prompts. Run many example inputs in the workbench, see where the model misuses the tool, and iterate the description until misuse goes away.

Tool docstring template

name: search_orders
description: |
  Search the orders database by customer email or order id.
  USE THIS TOOL when the user asks about a specific order or
  the order history of a known customer.
  DO NOT use this tool to look up products — use product_search instead.

parameters:
  query:
    type: string
    description: |
      Either a customer email (e.g. "ada@example.com")
      OR an order id starting with "ord_" (e.g. "ord_a1b2c3").
      Email lookups return up to 50 most recent orders.
  since:
    type: string
    description: ISO date (YYYY-MM-DD); only orders on or after this date.
    optional: true

example:
  query: "ord_a1b2c3"
  -> returns: { id, status, items[], total_cents, placed_at }

Notice the description tells the model when to use the tool and when not to, names a sibling tool to redirect to, and gives a concrete example. That is more important than the parameter types.

Tool-use evals

Anthropic's ACI advice has a testing consequence: do not evaluate only the final answer. Test whether Claude selected the right tool, formed valid arguments, handled empty results, and stopped before risky actions that need approval.

Check What it catches Useful scorer
Tool selection Using product_search when the user asked about an order. tool_call_match, set_match
Argument shape Invalid ids, missing dates, malformed JSON, or wrong customer identifiers. json_schema_match, regex_match
Tool order Writing to a system before reading policy or asking for approval. trajectory_eval
Grounded answer Confident final text that is not supported by retrieved tool results. contains, llm_judge
Standard loop: run examples in the workbench, inspect tool mistakes, improve the description or argument design, then add the failure case to the eval suite so it stays fixed.

Part 2 — Skills (the new packaged-workflow format)

A Skill is a folder that bundles instructions, scripts, and reference files Claude can load on demand when a task matches its description. Skills make capabilities reusable across Claude.ai, Claude Code, and the API.

Minimum viable skill

my_skill/
└── SKILL.md         ← required, with YAML frontmatter
---
name: pytest-tdd
description: |
  Use this skill when the user asks to add tests, write code TDD-style,
  or fix a failing pytest run. Provides our team's pytest conventions
  (AAA, fixtures over setup, no implementation in tests).
---

# pytest-tdd

When a user asks to add tests:
1. Look at conftest.py for existing fixtures; reuse before adding new ones.
2. Use the AAA structure (Arrange / Act / Assert) with one assert per test.
3. Prefer parametrize over loops.
4. After writing tests, run `pytest -q` and fix until green.

## Examples
- "add tests for `services/orders.py`"
- "TDD a function that validates IBANs"

## Guidelines
- Never edit production code without first writing a failing test.
- Use `tmp_path` for any filesystem touchpoint.

Larger skills can also include Python scripts, reference docs, or sample data inside the folder — Claude reads them when the skill is active.

How skills are activated

User asks something
->
Claude scans skill descriptions
->
Loads matching SKILL.md into context
->
Follows its instructions for that turn

This means the description field is the single most important part of a skill. If it does not clearly say "use this when…" and "don't use this when…", the right skill won't fire.

Anti-patterns to avoid

Vague skill descriptions like "helps with code" — Claude has no signal to pick it.
Mega-tool with 12 modes selected by an enum. Split into separate, narrow tools.
Tool docs that read like API references. Add the when-to-use / when-not-to, not just the type signature.
Silent failure modes. When a tool returns nothing useful, return an explicit hint — "no orders found, try widening the date range" — not an empty list.
