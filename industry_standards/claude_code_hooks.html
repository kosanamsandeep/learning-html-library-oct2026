Hooks — lifecycle automation for Claude Code

Hooks are shell commands that fire at specific points in a Claude Code session — before a file is written, after a command runs, when the session exits. They are the event system of an agentic coding workflow: they let you enforce policy, run checks, and plug into your existing toolchain without changing how you work.

If you know git hooks, you already know the pattern

Git hooks Claude Code hooks
pre-commit — run linter before creating a commit beforeWrite — run a schema check before saving a file
post-commit — notify CI after a commit lands afterCommand — log every shell command to an audit trail
pre-push — block push if tests fail beforeToolUse — require approval for sensitive operations

Just as git hooks let you automate around a version-control action, Claude Code hooks let you automate around an AI coding action — without modifying the AI's behaviour, only its environment.

Every hook, one table

Hook Fires Common uses
beforeRead Before the Read tool opens a file Decrypt an encrypted file on read; block reading of sensitive paths
afterRead After the Read tool returns content Strip secrets from displayed content; log file access
beforeWrite Before the Write tool saves a file Validate file structure; enforce file-naming conventions
afterWrite After the Write tool saves a file Run formatter (ruff, prettier); add to git tracking; notify other systems
beforeEdit Before the Edit tool applies a change Check that the edit doesn't touch a protected region of the file
afterEdit After the Edit tool applies a change Run linter on the modified file; type-check
beforeCommand Before the Bash tool runs a command Block dangerous commands; add env vars; add a permission prompt
afterCommand After the Bash tool exits Parse output for errors; log audit trail; send notifications
preExit When the Claude Code session is about to end Save conversation summary; push WIP branch; clean up temp files
preToolUse (special) Before any tool invocation (advisory permission layer) Add custom permission prompts for certain tools or arguments

Why hooks exist — the four jobs they do

🔒 1. Safety & guardrails

The AI doesn't know your organisation's risk policy. Hooks enforce it mechanically — no "please remember to format" or "don't touch prod."

Example: beforeCommand blocks kubectl delete and DROP TABLE unless the user explicitly types a confirmation token.

⚙️ 2. Quality automation

Instead of reminding the AI to run the linter, make the linter run automatically after every write — the same way your editor does.

Example: afterWrite runs ruff format {file} on every saved Python file.

🧩 3. Toolchain integration

Hooks are the bridge between the AI session and your existing toolchain — git, CI, monitoring, ticketing systems.

Example: preExit runs git add -A && git stash so WIP changes are never lost when a session ends unexpectedly.

📋 4. Observability & audit

Every action the AI takes can be logged, analysed, and reviewed — without training the AI to do its own bookkeeping.

Example: afterCommand writes every command, its exit code, and a timestamp to a session audit log.

Where hooks are configured

Hooks live in settings.json — either user-wide or project-scoped:

File Scope Overrides
~/.claude/settings.json Every Claude Code session, every project Baseline — global hooks (e.g. audit logging)
.claude/settings.local.json This project only, not committed User-wide hooks and project-wide hooks
.claude/settings.json This project only, committed to repo Everything below (shared with the team) 
// .claude/settings.json  (project-scoped, committed)
{
  "hooks": {
    "afterWrite": "ruff format {file}",
    "afterCommand": "echo '[{exit_code}] {command}' >> .claude/audit.log",
    "preExit": "git stash push -m 'claude-wip-$(date +%s)'"
  }
}

How to design hooks — what the industry is learning

✅ DO

  • Keep hooks fast. A hook that takes >2 seconds breaks flow. If it's slow, make it async or skip it (e.g. only run the formatter on files <100 lines).
  • Let hooks fail softly. A failing hook should not block the user's work. Log the failure and move on — unless it's a safety hook, in which case block hard.
  • Scope hooks to file type. afterWrite can check the file extension before running — no point running ruff on a .json file.
  • Test hooks independently. Run the shell command in your terminal first. A broken hook silently fails (hooks are fire-and-forget by design).
  • Log everything. Even if you never read the logs, they're there when you need to answer "what did Claude do?"

❌ DON'T

  • Don't put prompts or decisions in hooks. Hooks are shell glue, not AI logic. If a hook needs to "decide" something, it's too complex — move it to a Skill or script.
  • Don't use hooks as a permission bypass. A hook that auto-approves dangerous commands defeats the purpose. Use preToolUse for conscious escalation, not silent allowance.
  • Don't chain hooks through each other. A hook that triggers another tool call that triggers another hook is a debugging nightmare. Keep the chain flat.
  • Don't hardcode secrets. A committed settings file with an API token in a hook is a credential leak waiting to happen. Use env vars or a secrets manager.

Real-world hook configurations

Pattern 1 — minimal Python shop

{
  "hooks": {
    "afterWrite": "if [[ '{file}' == *.py ]]; then ruff format '{file}'; fi",
    "beforeCommand": "if [[ '{command}' == *git\ push* ]]; then echo 'Pushing — sure? (Ctrl-C to cancel)'; fi"
  }
}

Pattern 2 — audit-heavy compliance environment

{
  "hooks": {
    "beforeCommand": ".claude/hooks/check-allowlist.sh '{command}'",
    "afterCommand": ".claude/hooks/audit-log.sh '{command}' {exit_code}",
    "afterWrite": ".claude/hooks/validate-ownership.sh '{file}'",
    "preExit": ".claude/hooks/session-summary.sh"
  }
}

Pattern 3 — WIP safety net

{
  "hooks": {
    "afterWrite":  "git add '{file}'",
    "preExit":     "git stash push -m 'auto-save-$(date +%s)' 2>/dev/null; echo 'WIP stashed'"
  }
}

Put complex hooks in .claude/hooks/ as executable scripts — keeps settings.json clean and lets you test them in isolation.

Hooks vs Skills vs Workflows — when to use what

Hooks Skills Workflows (multi-agent)
Trigger File/system event (write, command, exit) User slash command or natural-language request User ask or scheduled orchestration
Scope One shell command, fire-and-forget Structured prompt with instructions, examples, tools Multi-agent fan-out with control flow
Autonomy None — runs the command, done Dialog — can converse, use tools, loop Full — orchestrates sub-agents
Best for Linting, formatting, blocking dangerous commands, audit logging Reusable domain tasks (deploy, review, summarise) Large-scale investigations, migrations, multi-perspective reviews
