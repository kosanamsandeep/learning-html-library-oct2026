GitHub · Copilot

GitHub Copilot — pick the right surface, prompt it well, verify the output

GitHub's official guidance reads like an operator's manual rather than a product pitch. The headline points: know what Copilot is good at, pick the right surface (inline vs Chat vs coding agent), give it precise prompts, and always verify.

Where Copilot shines, where it does not

Strong at — repetitive code, tests, debugging syntax issues, regex, comments and explanations of existing code.
Mid — large refactors, code that depends on undocumented internal context, anything where the right answer needs domain knowledge it doesn't have.
Weak at — questions outside coding/tech, replacing your judgement on architecture or correctness, anything that needs ground truth it can't observe.
Mental model: Copilot is a fast junior who can type. You are still the engineer.

Pick the right surface

Surface Use for Avoid for
Inline suggestions Completing snippets, repetitive boilerplate, generating code from a comment, TDD-style nudges. Multi-file work, anything that needs a discussion.
Copilot Chat Q&A about code in natural language, generating larger sections, iterating on a draft, asking it to review code as a "Senior X developer" persona. Things you need to ship without reading.
Coding agent (issues / PRs) Background tasks scoped by a GitHub issue: generate, run tests, open a PR. Anything that touches production secrets or external state without review.

Prompt engineering for Copilot Chat

Three rules from the docs:

  1. Break down complex tasks. "Refactor this 800-line file" is too vague — split it into "extract the storage layer", "rename functions", "add types".
  2. Be specific about your requirements. Say which framework, which version, which style. Vague prompts → average answers.
  3. Provide examples. Sample input, sample output, an existing test, a similar function nearby — these all help Copilot match your codebase.

Then, on top of those, Copilot Chat exposes keywords/skills (like #file, @workspace, /explain) — official guidance is to use them to pin context exactly. Tell Copilot which file, which symbol, which repo to consider.

The verification habit

  1. Understand the suggestion before you accept. Ask Chat to explain the code if anything is fuzzy.
  2. Read for security and maintainability, not just whether it runs.
  3. Run linters, type checkers, code scanners, and your tests. Treat them as Copilot's second pair of eyes.
  4. Pick the best when multiple inline suggestions are offered — cycle through, don't accept the first.
Quote: "Copilot is very powerful, [but] still a tool capable of making mistakes, and you should always validate the code it suggests." That is in the official best-practices page.

Steering toward better outputs

  • Open relevant files — Copilot reads your open editors as context.
  • Close irrelevant files — they pollute context and bias suggestions.
  • Trim chat history — delete dead-end turns; start fresh when the conversation no longer applies.
  • Reword the prompt — when an answer is bad, rephrase or split it. Don't keep retrying the same wording.
  • Give feedback — thumbs up/down on responses trains the system over time.

Custom instructions and AGENTS.md

You can pin team-wide context in your repo so Copilot always knows the rules. Two common files:

  • .github/copilot-instructions.md — repo-wide instructions Copilot reads automatically.
  • AGENTS.md — a community-converging convention for telling any AI coding agent (Copilot, Codex, Claude Code) about your repo: structure, build commands, conventions, where tests live.

Both are picked up by Copilot's coding agent and by the chat surface when present.

How this maps to our SDLC samples

  • claude_code_in_sdlc — same idea on the Claude side: CLAUDE.md + a Skill folder.
  • codex_in_sdlc — same idea on the OpenAI side: AGENTS.md + a small Agents-SDK script.
