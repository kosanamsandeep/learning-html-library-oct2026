Loops — recurring tasks & autonomous iteration

The /loop command lets you run a prompt on a recurring interval — checking deploys, monitoring CI, running periodic evals, or any task that benefits from a "check back later" pattern. Under the hood, it's powered by ScheduleWakeup (dynamic pacing) and CronCreate (fixed-schedule). This page explains both mechanisms and when to use each.

What is a loop?

A loop tells Claude Code: "run this same prompt again after some time." It's like setting a timer that re-engages the agent with the same context — but each iteration sees new information (a deploy that finished, a CI run that completed, new test results).

Key insight: A loop is not a while-loop in code. It's a session-level scheduler. Claude finishes its work, sets an alarm, and the runtime wakes it up later with the same prompt. Between iterations, the system is idle — no tokens consumed, no API calls made.

Two loop mechanisms

Claude Code has two distinct scheduling systems, each suited to different patterns:

/loop (Dynamic pacing) CronCreate (Fixed schedule)
How it's started User types /loop 5m check the deploy Claude calls CronCreate tool, typically from a Skill
Interval Self-decided per iteration (60s–3600s) Standard 5-field cron expression
Persistence Session-only (dies when Claude exits) Can be durable (survives restarts via .claude/scheduled_tasks.json)
Best for Interactive monitoring, ad-hoc polling Production recurring jobs (daily reports, weekly evals)
Prompt source User's natural-language prompt at /loop time Full prompt string passed in the tool call
Note on underlying APIs: /loop uses ScheduleWakeup internally. CronCreate is a separate tool that persists to disk. Both deliver the prompt back to Claude at the scheduled time, as if the user had typed it.

Dynamic pacing — how /loop decides the interval

When you run /loop 5m <prompt>, Claude doesn't just set a 5-minute timer blindly. It considers several factors to pick the actual delay:

unknown timing"]
    B --> E["No specific

    C --> F["Pick 270s

    D --> G["Pick 180s

        I["0s — Cache warm"]

    F -.-> I

The scheduler picks the delay based on what you're waiting for and the 5-minute prompt cache window.

Real-world cadence patterns

Use caseChosen delayWhy
Polling CI pipeline (~8 min) ~270s Check twice before CI finishes. Stays inside the 5-min cache window.
Watching a deploy ~60–120s Deploys are fast (1–3 min). Poll aggressively, burn cache.
Idle heartbeat (no signal) ~1200–1800s No point checking sooner. Pay cache miss once, amortize over long wait.
External queue processing ~180s Unknown timing. Poll at a moderate rate.
Why not 300s exactly? The prompt cache has a 5-minute TTL. If you wake at exactly 300s, you pay the cache miss cost and get no benefit. Better to wake at 270s (still cached) or 1200s+ (amortize the miss over a longer wait).

Durable tasks — CronCreate for production

For tasks that must survive restarts (daily reports, weekly eval runs, hourly monitoring), Claude uses CronCreate which persists to .claude/scheduled_tasks.json. 

flowchart TD
    A[Claude calls CronCreate] --> B{durable?}
    B -->|"No (default)"| C["In-memory only
Dies on exit"]
    B -->|"Yes"| D["Write to
.claude/scheduled_tasks.json"]

    D --> E["Claude exits"]
    E --> F["Claude restarts"]
    F --> G["Read scheduled_tasks.json"]
    G --> H["Missed tasks?
Surface for catch-up"]
    H --> I["Fire on next cron match"]

    C --> J["Session ends
Task lost"]
Durable tasks persist to disk and survive session restarts. Non-durable tasks are lost on exit.

When to use durable

ScenarioDurable?Why
"Remind me in 5 minutes to check X"NoSession-only — if you exit, the reminder was for now anyway
"Every morning at 9am, run the smoke test"YesMust survive restarts; Claude might not be running at 9am
"Check the deploy every 5 minutes"NoYou're actively watching — if you quit, you don't need it
"Run weekly eval report on Monday"YesProduction recurring job. Must fire regardless of session state.
7-day expiry: Recurring durable tasks auto-expire after 7 days. They fire one final time, then are deleted. This prevents orphaned tasks from running forever.

Building loop-based Skills

The most powerful use of loops is in Skills — reusable slash commands that self-schedule. Here's the pattern:

Pattern: babysit-prs

A Skill that checks a PR every 5 minutes until it's merged:

# .claude/skills/babysit-prs/SKILL.md
---
name: babysit-prs
description: Watch a PR until it merges.
---
Check the status of open PRs. If any are mergeable, flag them.
If nothing changed since last check, sleep 5m and re-check.
If all PRs are merged, report done.

Then the user runs: /babysit-prs

Claude runs the check. If not done, it calls ScheduleWakeup(300, "babysit-prs") — which re-invokes the skill. The loop continues until all PRs are merged.

Loop-until-dry pattern: Keep repeating until K consecutive iterations return no new results. This is the standard pattern for open-ended discovery tasks (find bugs, review all files, audit a module).

Practical loop patterns

🔍 CI Watch

/loop 5m "check if CI passed on branch main"

Runs a quick check every 5 minutes. When CI passes, Claude notifies you and the loop stops.

📊 Deploy Monitor

/loop 2m "what's the status of the prod deploy?"

Poll a deploy pipeline aggressively. Reports when it's complete or failed.

🧪 Periodic Eval

/loop 1h "run the eval suite and report regressions"

Long-interval loop for ongoing monitoring during a session.

🤖 Autonomous Bug Hunt

/loop "find bugs in the codebase, keep going until no new findings"

No fixed interval — Claude decides. Runs until K consecutive rounds find nothing new.

Hooks vs Loops — when to use what

Hooks Loops (/loop)
Trigger File event / command event / session exit Time-based (every N seconds/minutes)
Scope One shell command, fire-and-forget Full prompt execution with tool access
Duration Milliseconds to seconds Minutes to hours (across many iterations)
State Stateless — just runs a command Stateful — each iteration sees previous output
Best for Formatting, linting, blocking dangerous commands, audit logging Polling external systems, monitoring, recurring investigation
