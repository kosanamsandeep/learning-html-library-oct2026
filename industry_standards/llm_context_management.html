Platform internals

How do ChatGPT, Claude, and Gemini keep a chat going for months?

You send message #300 in a thread you started weeks ago. Does the platform dump all 299 previous messages into the model every time? If it did, the chat would lag, crash, or hit the model's hard context limit on every turn. Here's how the industry actually solves that — three complementary techniques you'll find in every major platform.

The problem — visible to every user, solved by every platform

Large Language Models have a maximum context window — a hard cap on how many tokens they can process in a single request. Claude 4 Sonnet caps at 200K tokens; Gemini 2.5 Pro can reach 1M; GPT-4o sits around 128K. A single long chat that runs for weeks or months will eventually cross any of these limits if the platform kept appending every message unconditionally.

Worse, even before you hit the cap, resending the entire history on every turn would be prohibitively slow and expensive — you'd wait tens of seconds for response generation to even start while the model re-processes hundreds of thousands of words of preamble.

Platforms solve this with three layers operating together: a speed/cost layer (context caching), a hard-stop layer (sliding window truncation), and a continuity layer (background summarisation / memory). Each does something different; none works alone.

Layer 1 — speed & cost

Prompt Caching (KV cache)

When you send message #300, the platform does not re-run the transformer over messages 1–299. Instead, it keeps the Key-Value (KV) cache for those earlier messages hot in accelerator memory. The model only does a forward pass on your new message, then reads the pre-computed cache to link it to everything that came before.

How it feels to the user: Fast — the first token arrives in roughly the same time on message #1 and message #300. The platform is not secretly re-reading the past.

How the platforms implement it

Platform Feature name How it works Cost savings
Anthropic (Claude) Prompt Caching Any prompt prefix ≥ 1,024 tokens is automatically cached server-side. The KV cache persists between turns with a 5-minute TTL (reset on each new message). Up to 90% off input token costs for the cached prefix; 50%+ latency reduction on cache-hit responses.
OpenAI (ChatGPT) Automatic Prompt Caching Prompts ≥ 1,024 tokens are cached; cache is invalidated after 5–10 minutes of inactivity. Special tokens mark cache breakpoints in the Messages API. 50% discount on cached input tokens; lower latency on cache hits.
Google (Gemini) Context Caching Explicit — you choose what to cache via a CachedContent object. 32-second default TTL; extend to up to 30 days for a storage fee. Up to 76% reduction in input token cost (variable by model size).
Important caveat: Caching is not persistence. When the TTL expires (usually 5–10 minutes of inactivity), the cache is evicted and the next request pays full price and latency. This is why resuming a chat hours later feels slower — the platform re-processes the prefix from scratch.

Why this matters for chat quality

  • Coherence — The model sees the full history on every turn (cache hit), so it can reference a detail from message #12 in message #300.
  • Speed — Cache hits reduce time-to-first-token from "re-process 100K tokens" to "process 500 new tokens".
  • Cost feasibility — Without caching, a multi-month chat could cost more in API compute than the subscription price. Caching makes the business model work.
Layer 2 — the hard limit

Context window cutoff (sliding window)

Caching makes history fast to access, but it doesn't make it fit. If your chat has grown beyond the model's maximum context window (say, 200K tokens for Claude 4 Sonnet), the entire history literally cannot be fed to the model in one go. At that point, platforms switch to a sliding window strategy.

What gets dropped vs. kept

Always kept Dropped first (oldest)
System prompt (model instructions) Early back-and-forth pleasantries
Custom instructions / user preferences Exploratory side conversations in the chat
Memory / knowledge files (see Layer 3) Draft after draft of the same document
Most recent ~10–50 exchanges Long code outputs that were never referenced again
Anthropic's approach: Claude's API supports up to 200K tokens. In the chat product, when a conversation approaches the limit, older messages are gradually trimmed from the top — but the system prompt and any Project knowledge files are pinned and never dropped. Anthropic also offers 1M-token context windows for select models (Claude 4 Opus / extended thinking).
OpenAI's approach: ChatGPT uses a similar sliding window. Older messages are compressed or dropped. The Memory feature (see Layer 3) acts as a safety net — facts extracted from dropped messages survive in a persistent profile.

What the user notices

  • Forgetting: The model no longer remembers the specific wording of an early instruction. It may behave as if the conversation "started over" in tone.
  • Still coherent: The model retains the gist of the recent discussion, so a single session within a long chat still works fine.
  • Silent operation: Platforms rarely announce "I dropped messages 1–150." The user just observes that the model seems to have forgotten something from last week.
Layer 3 — continuity

Background summarisation and persistent memory

The sliding window solves the hard-limit problem, but it introduces a new one: information from early in the chat that the user still considers important (their name, their tech stack, their preferences) gets silently dropped. Platforms fight this with background processes that extract and store facts.

How each platform does it

Platform Feature How it works When it triggers
ChatGPT Memory An invisible extraction layer reads the conversation and writes structured facts into a profile snippet (e.g., "user lives in Chicago, uses Python, prefers concise answers"). This snippet is pinned to the system prompt on every turn. After key information is mentioned; user can also explicitly teach or delete memories.
Claude Project Knowledge / Custom Instructions Project-level knowledge files are pinned at the top of the context window and never evicted. For ad-hoc chats, there is no automatic extraction; users add custom instructions manually. (Third-party tools like Memory Bank or Claude's own "remember" skill fill this gap.) Project knowledge is set at project creation; custom instructions are set in settings.
Gemini Saved Info Users can explicitly save personal preferences and facts. Gemini also automatically extracts key details from conversations into a profile. On user request or automatically when Gemini detects new personal information.
Key insight: Memory is not a compression of the chat — it's a structured extract. The system prompt memory snippet might say "user = Sande · role = dev · prefers Python" — 10 tokens instead of the 5,000 tokens of conversation that revealed those facts. This is dramatically more efficient than trying to re-summarise the entire chat history.

Trade-offs

Pro Con
Facts survive across sessions and even across chats Memory can contain stale or incorrect facts — there's no automatic fact-checking
Uses negligible context-window space (~10–100 tokens per fact snippet) Only captures explicit facts — nuance, tone, and implicit context are lost
User-visible and editable (in most platforms) Users may not realise the model is "remembering" things from old chats

How the three layers work together

No single layer solves the problem. A multi-month chat goes through all three:

Chat age Speed layer (cache) Hard limit (window) Continuity (memory)
First session (< 20 messages) Not needed — history is small enough to process directly Not triggered — well under the context cap Warming up — platform may extract first facts
Growing chat (50–500 messages) ✅ Active — early messages are cached, new messages are fast Not yet — still fits ✅ Active — key facts being extracted
Multi-month chat (500+ messages) ✅ Active — but cache evicts after 5–10 min idle ✅ Triggered — oldest messages are being dropped ✅ Essential — only way the "forgotten" early context survives
After idle period (hours later) ❌ Evicted — next message re-processes from scratch Still in effect — earlier history already dropped ✅ Still there — fact snippets survive eviction

What this means for how you use these tools

For everyday chat users

  • Restate important context periodically — don't assume the model remembers an instruction from message #5 when you're on message #500. A quick "Remember, I need everything in markdown" keeps it fresh in the sliding window.
  • Use Memories / Custom Instructions for things that must never be forgotten — your name, your role, your recurring preferences. These survive window drops.
  • Start a new chat for unrelated topics — a clean context window gives the model full attention on the new task without old history diluting it.

For API developers

  • Leverage prompt caching explicitly — structure your API calls so the stable prefix (system prompt + knowledge) comes first, and the new user message comes last. The cache only works if the prefix is byte-identical across turns.
  • Design for the sliding window — if your agent needs long-term memory, build it yourself (summarisation or RAG), don't rely on the API keeping the full chat history forever.
  • Watch the cache TTL — a 5-minute idle gap evicts the cache. If your users typically wait 10+ minutes between turns, caching won't help them much.

For agent builders

  • Memory is a feature, not a bug — persistent memory (like ChatGPT's) is the same pattern as a "memory bank" for coding agents. The Anthropic workshops call this agents-that-remember: a standalone summarisation loop that extracts and re-injects facts.
  • Explicit summarisation beats implicit sliding — if you control the agent, run a background "compress the conversation so far" prompt every N turns and inject the summary as a system message. This preserves key information far better than waiting for the platform's default windowing behaviour.
