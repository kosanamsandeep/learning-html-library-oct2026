OpenAI Agents SDK — small primitives, large reach

The OpenAI Agents SDK is a production-ready Python package built on three primitives: Agents, Handoffs, and Guardrails. Add Sessions for memory and Tracing for debugging and you have a full agentic platform without learning a new programming model.

The three primitives

Primitive What it is What it replaces
Agent An LLM with instructions and tools. A long system prompt + ad-hoc tool plumbing.
Handoff (agent-as-tool) One agent delegating part of the task to another. A custom orchestrator you would otherwise hand-roll.
Guardrail Validation that runs in parallel with the agent and fails fast. A second LLM call you bolt on later for safety.

The agent loop the SDK manages for you

User input
->
Runner loop
->
Tool / handoff
->
Result back to LLM
->
Final output / next turn

You stop writing the loop. You write the agents, the tools, and the handoff graph; the runner handles tool dispatch, retries, streaming, and tracing.

Hello-world (verbatim shape from the docs)

from agents import Agent, Runner

agent = Agent(name="Assistant", instructions="You are a helpful assistant")

result = Runner.run_sync(agent, "Write a haiku about recursion in programming.")
print(result.final_output)

That's the smallest useful program. Add tools, handoffs, and guardrails as your needs grow.

Function tools — Python decorator turns code into a tool

The SDK auto-generates the JSON schema from the function signature and validates inputs with Pydantic. You write a normal Python function with type hints and a docstring; the model gets a clean tool to call. 

from agents import Agent, function_tool

@function_tool
def search_orders(query: str, since: str | None = None) -> list[dict]:
    """Search orders by customer email or order id.

    USE THIS TOOL when the user asks about a specific order, or
    a customer's order history. DO NOT use it for product lookup.

    Args:
        query: Customer email OR order id starting with "ord_".
        since: Optional ISO date; only orders on or after this date.
    """
    ...

agent = Agent(
    name="SupportAgent",
    instructions="Help customers with order status and history.",
    tools=[search_orders],
)

The docstring is what the model sees as the tool description, so apply Anthropic's "junior-developer docstring" rule here too — when to use, when not to use, and an example.

Handoffs — when to delegate vs orchestrate

Pattern How it looks Choose when
Handoff Agent A passes the conversation to Agent B; B owns the rest of the turn. Distinct skill domains (refund vs shipping vs technical support). Each agent has its own narrow prompt.
Manager (agent-as-tool) A central agent calls specialist agents like tools, then composes the answer. You want one face to the user and the manager owns the final response.

Guardrails — fail fast, in parallel

Guardrails run alongside the agent. If an input is unsafe (e.g. asks for medical advice in a coding bot) or an output violates schema, the run stops before reaching the user.

Why parallel: guardrails do not block your fast path. They only intervene when something is wrong.

Sessions — memory for the run

Sessions are a persistent layer that carries state across turns. The SDK ships several backends: SQLite (default), SQLAlchemy, Redis, MongoDB, encrypted, and an advanced SQLite session for richer history.

This matches the three memory layers we built from scratch in ai_engineering / P3 agent memory — short-term in the buffer, durable facts in the session store, episodic summaries persisted at the end of each run.

Sandbox agents — when the agent needs files

If your agent edits real files (a coding agent, a doc generator), use Sandbox agents. The SDK gives each agent an isolated workspace declared by a manifest, with capabilities (filesystem, shell, memory, skills, compaction) you can explicitly grant.

# conceptual shape — not literal API
manifest = {
    "files": ["./src/**", "./tests/**"],
    "capabilities": ["filesystem", "shell"],
}
agent = SandboxAgent(name="Refactorer", instructions="...", manifest=manifest)

Agents SDK vs the raw Responses API

Use the Responses API directly when… Use the Agents SDK when…
You want to own the loop, tool dispatch, and state. You want the runtime to manage turns, tool execution, guardrails, handoffs, sessions.
The workflow is short-lived and mostly about a single response. The agent must produce artifacts or operate across multiple coordinated steps.
You are building a thin proxy or transformation. You need a real workspace or resumable execution.

Mixed usage is fine — many apps use the SDK for managed flows and call the Responses API directly for low-level paths.

Tracing & evaluation

The SDK has built-in tracing that integrates with OpenAI's evaluation, fine-tuning, and distillation tools. Treat traces as your debugger — when an agent goes off the rails, the trace usually shows exactly which tool call surprised it.
