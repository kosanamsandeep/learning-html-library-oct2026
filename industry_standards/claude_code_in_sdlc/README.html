Drop Claude Code into a real Python repo — CLAUDE.md + a custom Skill + a checked-in workflow

A small, opinionated example of how a working Python team can adopt Claude Code without changing their toolchain. We add three things: a project rulebook (CLAUDE.md), one custom Skill (pytest-tdd), and a tiny demo module the agent can iterate on.

This is a shape sample. We aren't shipping a working CLI here — we're showing the files you commit so Claude Code (or any agent following the same conventions) behaves like a teammate from day one.

Why each file exists

File Purpose
CLAUDE.md Top-level instructions Claude Code injects into every session: project structure, build commands, code style, what to never touch.
.claude/skills/pytest-tdd/SKILL.md A skill with a YAML frontmatter description Claude scans. When a user asks "write tests" or "fix this failing test", this skill activates and Claude follows our conventions.
src/orders.py A small domain module — the agent's playground. Has a function with one bug and one missing feature.
tests/test_orders.py Existing pytest tests. The agent runs these to validate any change.

CLAUDE.md — what we put in it

Claude Code reads CLAUDE.md at the repo root. Keep it short. Include only what the agent cannot infer from looking at the code.

# Project: orders-service

## What this is
A toy order-management library. Pure Python, no framework.

## Build & test
- Python 3.11+
- Install: `pip install -r requirements.txt`
- Run tests: `pytest -q`
- Lint: `ruff check .`

## Conventions
- Type hints on every public function.
- AAA test layout (Arrange, Act, Assert).
- Money is stored as integer cents — never floats.

## Don't touch
- `src/orders.py:LEGACY_PRICE_RULES` — we have a deprecation in flight.

## When in doubt
Ask before changing public function signatures. Open a PR, don't push to main.

The custom skill — pytest-tdd

A skill is a folder with a SKILL.md. The frontmatter description is what Claude reads to decide whether to load it for a turn. Be explicit about when to use and when not to.

---
name: pytest-tdd
description: |
  Use this skill when the user asks to add tests, write code TDD-style,
  or fix a failing pytest run in this repo. Provides our conventions:
  AAA structure, parametrize over loops, integer cents for money.
  DO NOT use this skill for non-pytest test frameworks.
---

# pytest-tdd

When a user asks to add tests:
1. Open `conftest.py` (if any) and reuse fixtures before adding new ones.
2. Use AAA: one test asserts one thing.
3. Prefer `@pytest.mark.parametrize` over loops.
4. Money is integer cents — never floats.
5. After writing tests, run `pytest -q` and iterate until green.

## Examples
- "add tests for `src/orders.py::compute_total`"
- "TDD a discount-code validator"

## Guidelines
- Never edit production code without first writing a failing test.
- Use `tmp_path` for any filesystem touchpoint.
- If a test file does not exist yet, create it under `tests/` mirroring the src path.

How a session actually plays out

  1. Developer types claude in the repo.
  2. Claude Code loads CLAUDE.md automatically and lists discovered skills (including ours).
  3. Developer asks: "Add tests for compute_total covering empty cart, single item, and a discount."
  4. Claude matches the request against skill descriptions, loads pytest-tdd, follows its rules, drafts the tests, runs pytest -q, fixes anything broken, and produces a diff.
  5. Developer reviews and accepts. Claude commits via PR (never to main).
Verify habit: always read the diff before accepting. Treat Claude as a fast junior — let it type, you read.

Adoption checklist for your real repo

  1. Add CLAUDE.md at root with build/test commands and 5 rules. Keep it under one page.
  2. Identify one repetitive task your team does (writing tests, fixing imports, generating CRUD endpoints) and write a skill for it.
  3. Review the first three Claude PRs by hand. Iterate the rules and the skill description until reviews are mostly thumbs-up.
  4. Wire pytest, ruff, and your security scanner into CI — Claude's PRs should pass the same gates a human's would.
  5. Start small. One skill is plenty for the first month.
