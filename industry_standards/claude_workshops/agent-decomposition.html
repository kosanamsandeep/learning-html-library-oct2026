CWC · Workshop 2

Agent decomposition (StockPilot): break the 402-line prompt apart on purpose

A "before" agent has 12 tools, three hard-coded sub-agents, and a 402-line system prompt. Score: 71%. The workshop teaches you to decompose — push procedural know-how into Skills, push numeric work into sandboxed code execution, and keep only one sub-agent for the work that needs an isolated context. Score after: 92%.

1 · What you build

  • agents/before/ — the bloated baseline so you can A/B against it.
  • agents/starter/ — a slim Managed Agent configuration with a focused system prompt and a curated tool list.
  • One or two Skills under .claude/skills/ for repeated procedures (e.g. "compute total return", "produce the standard portfolio summary").
  • One remaining sub-agent for the deep-research task that needs its own context window.
  • An eval suite of 12 tasks — R1–R9 (research) and F1–F3 (financial computation). F1 alone drops from 488 seconds / 102 tool calls to 100 seconds / 3 scripts.

3 · Levers the workshop teaches

The decision framework

Tool call → Skill → Sub-agent. Default to a tool. Promote to a Skill when the same procedure repeats. Promote to a sub-agent only when an isolated context is required.

Smell tests

">2k tokens of data" ⇒ code execution. "Always do X first" ⇒ Skill. "Answer is one number" ⇒ not a sub-agent.

System-prompt diet

Cut from 402 lines to under 60. The cut content moves into Skills that load on demand.

Tool curation

Drop tools that are never selected by the model on the eval set. Each surviving tool gets a sharper description.

Sandboxed code execution

For financial math, the agent writes a small Python script in the sandbox instead of orchestrating many tool calls.

The 12-task eval

R1–R9 cover research breadth; F1–F3 cover financial computation. Each task has a deterministic grader.

4 · Use vs don't use — the trade-offs

Lever If you use it If you skip it
Push procedures into Skills System prompt stays small, the procedure is loaded only when needed, and you can edit it without redeploying the agent. The 402-line prompt grows every sprint, latency climbs, and the agent sometimes ignores steps that "got buried" in the middle.
Sandboxed code execution for numeric work F1: 100 seconds, 3 scripts, deterministic answer. The agent stops orchestrating dozens of calls and just writes the calculation. F1: 488 seconds, 102 tool calls, rounding errors compound, and the bill is ~10×.
One sub-agent (not three) Deep-research lives in its own context, so the main agent isn't drowning in source text. The handoff is one message in, one summary out. Three sub-agents = three places to keep prompts in sync, three context windows to pay for, and the parent agent loses the thread.
Tool curation Cleaner tool descriptions mean the model picks the right one on the first try. Twelve overlapping tools mean the model picks the second-best tool, then a third, then recovers — burning tokens and time.
12-task eval before/after 71% → 92% is a number you can defend in a review. F1's wall-clock drop is the screenshot you put in the deck. "Feels better" is the only evidence, and the team rolls back the next time a refactor regresses something silently.
The lesson: decomposition is subtraction first. Every feature should justify its place by moving a measurable score; if it doesn't, it goes back into a Skill or out of the agent.

5 · Adoption playbook for your repo

  1. Make an "as-is" snapshot of your biggest agent and write down its current eval score.
  2. Run the "smell tests" against every tool and every sub-agent. Anything that fails moves to Skill or code execution.
  3. Cut the system prompt by removing every "always" / "before you do X" sentence and re-homing each one into a Skill description.
  4. Add a code-execution sandbox for any numeric or transform-heavy work.
  5. Keep at most one sub-agent. Justify it in writing.
  6. Re-run the eval. If the score didn't move, you decomposed the wrong thing — and your eval just saved you a release.
