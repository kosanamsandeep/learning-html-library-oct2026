CWC · Workshop 1

Pick the right model: audit your evals, then sweep model × thinking × effort

A two-phase Claude Code workshop. First you fix the eval suite (Claude Code reads a Skill and audits the harness for grader bias, task coverage, and pipeline correctness). Then you sweep across models and reasoning settings and plot pass-rate vs cost vs latency, so the model choice is a finding, not a feeling.

1 · What you build

  • A .claude/skills/eval-audit-and-sweep/ Skill with three files: SKILL.md, audit.md, sweep.md, plus a benchmark-specific tau2-bench.md.
  • A patched llm_agent.py that reads THINKING and EFFORT env vars and forwards them as Claude's thinking and reasoning effort parameters.
  • Three plots — sweep_tokens.png, sweep_cost.png, sweep_latency.png — and a short recommendation paragraph.

The benchmark used in the workshop is a 20-task stratified subset of τ²-bench airline. The same Skill works on any pass/fail eval suite.

No Managed Agent yet — this workshop teaches the measurement layer that every later workshop relies on. The decision the Skill helps you make is: "for this task, which model + reasoning combo gives me the best pass-rate per dollar at acceptable latency?"

3 · Levers the workshop teaches

Skill split (audit vs sweep)

Two separate .md files so Claude Code loads the right one for the phase. Keeps each context small.

Task stratification

Pick a 20-task subset that covers the harness's failure modes rather than running all 100+ tasks.

Grader-bias check

Audit step asks "is the grader scoring the model's answer or the model's politeness?"

Model × thinking × effort grid

The sweep dimension. Each cell of the grid is one full eval run.

Three-axis plot

Pass-rate on Y, cost or latency on X, model as colour. Forces an honest trade-off conversation.

Environment-variable injection

THINKING and EFFORT env vars patched into the agent so the sweep runner doesn't fork the codebase.

4 · Use vs don't use — the trade-offs

Lever If you use it If you skip it
Audit-then-sweep Skill Claude Code loads ~200 lines of expert checklist on demand; the same Skill is reusable across every future eval-driven workshop. You hand-craft prompts each time, the audit drifts, and team members re-discover the same harness bugs.
Stratified 20-task subset One sweep cell completes in minutes, so you can sweep ~10 configurations in a workshop slot. Full benchmark runs take hours per cell, you sweep two configs, and the comparison is too noisy to act on.
Grader-bias audit You catch "the LLM judge prefers verbose answers" before it tells you to pick the wrong model. You spend dollars sweeping against a grader that ranks the wrong thing — the picked model looks great in eval and bad in prod.
Thinking + effort env vars One harness, many runs. The sweep script just sets THINKING=high EFFORT=medium and re-invokes. You copy the agent file per configuration, forget to update one, and the “Opus + high thinking” row is silently running Sonnet.
Three-axis plots (cost & latency) The team sees a Pareto frontier and picks the knee-of-the-curve model on purpose. "Best pass-rate" wins the meeting, then the bill arrives and the SLO breaks.
The lesson: the workshop’s claim is that model picking is a measurement, not a preference — and the cheapest way to make the measurement repeatable is to package it as a Claude Code Skill.

5 · Adoption playbook for your repo

  1. Create .claude/skills/eval-audit-and-sweep/SKILL.md with a short description of when Claude Code should load it ("when the user mentions evals, accuracy, pass-rate, or model selection").
  2. Add audit.md — a checklist that covers task coverage, harness correctness, grader bias, and reproducibility.
  3. Add sweep.md — a checklist that defines the sweep dimensions, what gets logged per cell, and which plots are required.
  4. Patch your existing agent so model name, thinking mode, and reasoning effort are read from env vars.
  5. Run the audit once, fix what it finds, then run the sweep once and commit the plots.
  6. Re-run the sweep whenever a new model drops — the Skill makes that a one-prompt operation.
