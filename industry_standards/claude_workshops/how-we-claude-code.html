CWC · Workshop 3

How we Claude Code: interview → spec → divergent mockups → verified build

The internal Anthropic workflow for shipping AI-assisted products. The trick isn't faster typing — it's three deliberate phases: Claude conducts a spec interview, generates four visually different HTML mockups, then implements one of them as a Vite + React app whose components expose a machine-readable DOM contract so a second Claude run can verify the build.

1 · What you build

  • A short Markdown spec for a bill-splitting app, written by Claude after interviewing you.
  • Four standalone HTML files — each one a deliberately different visual direction.
  • A Vite + React + Tailwind app served by Bun: bun run dev on port :5199.
  • A verifier: bun run verify walks the DOM contract and reports a pass/fail matrix.

3 · Levers the workshop teaches

Interview-driven spec

Claude asks five-to-eight scoped questions before writing a single line of code. The output is a short Markdown doc that becomes the contract for the rest of the work.

Four divergent mockups

Generate four static HTML designs in parallel so you can pick a direction, not iterate from a single mediocre starting point.

HTML before React

Static HTML mockups are throwaway, opinionated, and fast — perfect for design decisions. React comes after the direction is locked.

DOM contract per component

Each React component carries data-* attributes that name its testable behaviour, so a verifier (or a second Claude) can walk the DOM and assert correctness.

Verify matrix

bun run verify emits a per-feature pass/fail. Claude can read the matrix and fix the failing rows.

CLAUDE.md as the workflow ledger

CLAUDE.md records the project conventions and is loaded automatically every time Claude Code opens the repo.

4 · Use vs don't use — the trade-offs

Lever If you use it If you skip it
Interview → spec.md The first commit captures intent. Future Claude runs (or new teammates) re-derive context from the spec, not from memory. You jump to code, then re-explain the brief every session. The spec lives in a Slack thread and rots.
Four divergent mockups (not one) You see what design space looks like before committing. The "winner" is usually a blend of two of the four. You build the first idea Claude suggested. It's competent and forgettable.
HTML mockups before React Cheap, fast, deletable. Designers and PMs can read them. No build step gets in the way. You debate layout inside React, which couples design to state-management plumbing. Iteration slows by 5×.
DOM contract (data-* attributes) The verifier and Claude itself can describe the page in structured terms. Tests are stable against pure-visual refactors. Tests anchor on CSS selectors and break on every style sweep. Claude has to "read" the page to test it, which is brittle.
bun run verify matrix Claude can iterate to green without you watching. Every feature has an obvious "done" signal. "Looks fine on my screen" is the spec, and three Claude turns later you regress the basket calculation.
CLAUDE.md Every Claude Code session starts from the same conventions: port :5199, Bun not npm, the DOM-contract rule. Onboarding takes seconds. Each session re-asks "should I use npm or pnpm?" and sometimes guesses wrong.
The lesson: AI-assisted development isn't "Claude writes code faster" — it's "Claude completes a phase, you review the artifact, then Claude picks up the next phase". The phases give humans the right place to intervene.

5 · Adoption playbook for your repo

  1. Add a CLAUDE.md at the repo root with: dev command, port, package manager, conventions you actually want enforced.
  2. For any new feature, start with: "Interview me, then write spec.md". Do not skip.
  3. Ask for four divergent HTML mockups (not three, not one). Pick one or merge two.
  4. When building, give every interactive component a data-testid / data-state attribute and write a tiny verifier that asserts the spec.
  5. Wire the verifier as the first thing Claude runs after a change. Make passing it the success criterion in the prompt.
