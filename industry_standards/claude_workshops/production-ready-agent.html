CWC · Workshop 8

Deal Desk: a production-ready M&A agent with sub-agents, memory, MCP and Vault

A Next.js chat front-end over a Claude Managed Agent that researches deals end-to-end. A coordinator delegates to four parallel sub-agents, pulls prior-deal lessons from a memory store, reaches Linear through an MCP server whose credentials live in the Vault, and emits a graded investment thesis. The seven API exercises in app/api/ are the production CMA surface you'll re-use everywhere.

1 · What you build

  • A Next.js UI streaming over Server-Sent Events.
  • Seven exercises in app/api/ that wire each CMA capability:
    1. List sessions (sessions.list)
    2. Create session (sessions.create)
    3. Steer (events.send with user.message + user.define_outcome)
    4. Retrieve session
    5. Stream bridge (events.list → events.stream → SSE to the browser)
    6. Confirm gated tool calls (events.send with user.tool_confirmation)
    7. Delete session
  • A coordinator agent + four sub-agents added via enable-multiagent.sh (v2).
  • An idempotent setup.sh that recreates everything except the coordinator (which holds the canonical prompt).

3 · Levers the workshop teaches

Coordinator + parallel sub-agents

One agent decides what to research; four sub-agents do the legwork in parallel and summarise back. Time-to-thesis drops without growing the coordinator's context.

define_outcome events

Beyond just user messages — explicit outcomes the user wants. The agent treats them as a goal stack, not chat noise.

Gated tool confirmation

Some tools (e.g. "post to Linear") emit a confirmation event the UI must approve via user.tool_confirmation. Human-in-the-loop without a custom approval system.

Stream bridge (events → SSE)

Server-Sent Events keep the UI live. The browser sees reasoning, tool calls, and final answers as they happen.

Vault-held MCP credentials

Linear's API key never lives in .env. The Vault hands it to the MCP server at run time.

Idempotent setup script

setup.sh can re-run safely. The one thing it won't overwrite is the coordinator — that's the artifact under version control.

4 · Use vs don't use — the trade-offs

Lever If you use it If you skip it
Coordinator + sub-agents Parallelism without context bloat. Each sub-agent has its own scope; the coordinator synthesises. You pile every research source into the coordinator's context. Latency triples, the model loses focus, and the synthesis quality drops.
user.define_outcome The agent has a structured goal, not just a chat. It can re-prioritise mid-session when the outcome changes. Goals leak into chat messages; the agent treats them like passing suggestions and misses the brief.
Gated tool confirmations Compliance and audit happen for free. The user explicitly approves every externally-visible action. The agent posts to Linear automatically and your legal team has a great morning.
Stream bridge (SSE) The UI feels alive; users see reasoning and can interrupt. You can also log every event server-side. Long synchronous calls; the UI hangs; you lose the ability to gate tools mid-run.
Vault for MCP credentials Rotating Linear's key is a Vault operation. Nothing in the repo ever held the secret. Secrets sit in .env, get committed once by accident, and your DLP scanner opens a ticket like the one this learning path was started by.
Memory store for prior-deal lessons The agent learns "what we noticed in the last three deals" and applies it to the new one. Quality compounds. Each deal starts cold; the same gotchas surprise you every quarter.
Idempotent setup.sh New teammate clones the repo, runs one script, and is at parity with you. Onboarding is a 40-minute README walk; everyone's environment drifts.
The lesson: production-ready isn't a new stack — it's the W4–W7 stack hardened with three things: gated tool calls, secrets in Vault, and an idempotent bootstrap.

5 · Adoption playbook for your repo

  1. For your most-important agent, port the seven API endpoints from W8: list / create / steer / retrieve / stream-bridge / confirm / delete.
  2. Add a user.define_outcome step so the user states the goal explicitly. Surface it in the UI as a goal chip.
  3. Mark every externally-visible tool as gated. Wire user.tool_confirmation to a UI approval flow.
  4. Move secrets out of .env and into the Vault. Anything an MCP needs is a Vault read at run time.
  5. Add a memory store for the one piece of state you keep re-learning. Schedule Dreaming weekly.
  6. Write setup.sh as idempotent. The day someone new joins, you'll be glad.
