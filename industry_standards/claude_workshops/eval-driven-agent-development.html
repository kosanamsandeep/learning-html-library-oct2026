CWC · Workshop 7

Eval-driven agent development: improve a PPTX agent through six measured variants

A Managed Agent that writes .pptx decks is taken from naive to QA-loop across six versions. Every step is justified by a two-layer grader: a deterministic parser reads the underlying pptx XML for structural metrics, and an LLM judge looks at rendered slide images for taste.

1 · What you build

  • Six agent variants under resources/agents/: 00-naive.agent.yaml → 05-qa-loop.agent.yaml (visual, typography, palette, density, QA-loop).
  • A slide creator: src/create-slides.ts.
  • A renderer: render.ts calls a Docker LibreOffice image (cwc-pptx-render) that emits JPGs.
  • A grader: parse-pptx.ts for XML structural metrics + graders.ts for an LLM judge with an explicit rubric.
  • Five tasks in tasks.json — same prompts evaluated against every variant.

3 · Levers the workshop teaches

Two-layer grader

Structural XML checks for "did the deck even parse, are there 8 slides, is there a title?" plus an LLM judge for "is it actually readable?"

Rendered images for the judge

The LLM judge looks at the rendered JPG, not the XML — the way a human would.

Variant-per-file

Each agent version is its own YAML, so diffs are explicit and reviewable in PR.

Baseline command

npm run show-baseline renders the comparison so a reviewer sees the regression / improvement in one screen.

QA-loop variant

The last variant has the agent render its own output, grade it, and iterate before returning — the same loop you just built, but inside the agent.

Dockerised renderer

LibreOffice in a container so every reviewer gets pixel-identical output.

4 · Use vs don't use — the trade-offs

Lever If you use it If you skip it
Structural grader (parse-pptx.ts) Cheap, deterministic, runs on every change. Catches "the agent shipped corrupted XML" in milliseconds. The LLM judge has to do everything, and you pay LLM tokens to discover the file is broken.
LLM judge on rendered images Captures the things metrics can't — taste, hierarchy, balance. The judge sees the slide the way a human would. You optimise the metrics (8 slides, 6 bullets) and ship something technically correct that no executive will read.
Variant-per-file Code review shows exactly what changed between v3 and v4. Rollback is one PR revert. You mutate one YAML in place, can't tell which knob caused the win, and re-discover the same fixes a month later.
Dockerised renderer The reviewer on macOS sees the same pixels as CI on Linux. The grader is reproducible. Fonts and kerning differ per machine; the judge's score depends on whose laptop ran the renderer.
QA-loop variant (self-grading agent) The agent catches its own corrupted XML before returning. Tail-latency goes up, but tail-quality goes way up. The agent ships its first draft. Every nth deck is broken and the user notices first.
The lesson: "eval-driven" means every variant is a hypothesis, every hypothesis is graded, and the grader has both a cheap structural layer and a taste layer. Either layer alone misleads you.

5 · Adoption playbook for your repo

  1. For any generative agent, define the two-layer grader before you ship version 1: structural checks (does it parse?) and a small LLM-judge rubric (is it any good?).
  2. Save each meaningful agent config as its own file (00-naive.yaml, 01-….yaml). Treat the prompt as code.
  3. Render whatever the agent produces into a stable artifact (JPG, HTML, JSON) and grade the artifact, not the intermediate.
  4. Containerise the renderer so every contributor's runs are comparable.
  5. Once the eval is solid, build a self-grading variant: the agent runs its own grader and re-tries once before returning.
