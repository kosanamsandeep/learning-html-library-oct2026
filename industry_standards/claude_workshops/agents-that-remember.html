CWC · Workshop 6

Agents that remember: from goldfish to colleague in 45 minutes

"Arc" is the amnesiac baseline — every session it re-asks who you are. You attach a memory store as a session resource, and the same agent picks up where it left off across runs. Then you run Dreaming over past transcripts to consolidate a better store — Claude reads the history offline and writes a more useful memory back.

1 · What you build

  • An amnesiac agent (Arc) so you can see the baseline pain.
  • A memory-store-attached version of the same agent across two sessions, demonstrating continuity.
  • A Dreaming job that reads the memory store + session history and writes a new, distilled store.
  • CLI familiarity: ant beta:memory-stores, ant beta:dreams.

2 · The stack

Amnesiac baseline (no memory)
→
Memory store attached to session
→
Dreaming pass over history
→
Better memory store, next session

The session-create call accepts a resources array of the form {"type":"memory_store","memory_store_id":"$MEM","prompt":"…","access":"read_write"}. Remember: resources attach at session-create only.

3 · Levers the workshop teaches

Memory store as a typed resource

Not a vector DB, not "context". A first-class resource the agent reads and writes through tool calls.

Attach at session-create

You can't bolt a memory store on mid-session. The constraint forces clean session boundaries.

Access mode

read vs read_write. Useful when one agent owns the store and others only consult it.

Memory prompt

A short string telling the agent how to use this store — e.g. "this is the deal-log; prefer it over your own recall for client preferences."

Dreaming

An offline pass: read a memory store + past sessions, write a new memory store. Turns episodic notes into curated knowledge.

CLI affordances

ant beta:memory-stores to list / inspect; ant beta:dreams to schedule and read dream runs.

4 · Use vs don't use — the trade-offs

Lever If you use it If you skip it
Memory store (vs prompt stuffing) Persistent, queryable, isolated from the context window. The user feels like the agent "knows them" without you paying for the history every turn. You shove everything into the system prompt; latency climbs, tokens climb, the agent forgets the bottom 30% of it.
Attach at session-create Resources are available from event 1. Your UI can show "session is using deal-log v3" before the first message. You attempt to attach mid-session, the API refuses, and you ship a workaround that loses audit trail.
read vs read_write Read-only stores let many sub-agents consult shared knowledge without trampling each other. Everything is read_write, sub-agents overwrite each other, and you can't tell who corrupted what.
Memory prompt The agent knows when to prefer the store over its own recall. Hallucinations on recurring facts drop sharply. The store exists but the agent doesn't consult it. The memory is a file on disk, not a tool.
Dreaming You turn raw transcripts into curated knowledge offline. The next live session loads distilled insight, not a transcript pile. The memory store grows linearly, gets noisy, and the agent's retrieval quality drops over time.
The lesson: memory isn't a vector DB you bolt on — it's a resource the agent's prompt is taught to use, refreshed offline by Dreaming so it stays small and sharp.

5 · Adoption playbook for your repo

  1. Identify the one piece of state your agent re-learns every session (user preferences, deal context, codebase conventions). That's your memory store candidate.
  2. Stand up a memory store with ant beta:memory-stores. Attach it at session-create with a memory prompt that tells the agent when to read and when to write.
  3. Run two sessions a week apart. Confirm the second one starts ahead of the first.
  4. Schedule a Dreaming pass over the accumulated sessions. Diff the new store against the old one — if the new one is shorter and more useful, you've found product fit.
  5. Add an audit view (your CLI or UI) so humans can read and prune the store. Memory you can't read is memory you can't trust.
