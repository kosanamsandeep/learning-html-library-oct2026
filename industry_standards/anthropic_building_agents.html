Building effective agents — start simple, add structure only when it pays off

Anthropic's guidance, distilled. The headline message: most successful production deployments are not sophisticated frameworks. They are simple, composable workflows. Reach for an autonomous agent only when the problem is open-ended and a fixed control flow cannot capture it.

Workflows vs agents (the architectural split)

System Definition When to choose
Workflow LLM and tools orchestrated through predefined code paths. Tasks decompose cleanly. You want predictability, lower latency, lower cost.
Agent LLM dynamically directs its own process and tool use. Open-ended problems where you cannot enumerate the steps in advance.
Default: a single LLM call with retrieval and good in-context examples. Add complexity only when measurements show it improves the outcome.

The augmented LLM — the building block of every agentic system

Every pattern below assumes one thing: an LLM that can retrieve, call tools, and maintain memory. Build that augmented LLM well — clear tool definitions, a clean retrieval interface, an explicit memory layer — before you reach for any pattern.

The five workflow patterns

Pattern Shape Best for
Prompt chaining Step 1 → Step 2 → Step 3, with optional gates between. Tasks that decompose cleanly into fixed steps where you trade latency for accuracy. Example: outline → check → write the doc.
Routing Classify input, dispatch to a specialised handler. Distinct categories that benefit from different prompts or different model sizes (cheap model for easy questions, capable model for hard ones).
Parallelisation Sectioning (split into independent subtasks) or voting (run the same task multiple times, aggregate). Independent subtasks; multi-perspective reviews; guardrails that run alongside the main answer.
Orchestrator-workers A central LLM decides what subtasks exist, delegates to workers, synthesises. Tasks where the subtasks can not be predicted up front (e.g. coding changes that touch an unknown number of files).
Evaluator-optimiser One LLM drafts, another LLM critiques in a loop until the critic is satisfied. Clear evaluation criteria + iterative refinement helps. Translation, search, complex code generation.

Choosing the right pattern — concrete scenarios

Each of the five patterns solves a different class of problem. Here is how to recognise which one you need, with real-world examples.

Pattern You need this when … Sample scenario
Prompt chaining The task has a linear sequence of steps where later steps depend on earlier ones. You are willing to trade a little latency for substantially higher accuracy, because each stage can focus on one concern. Content pipeline with quality gates.
Step 1: An LLM drafts a marketing email from bullet points.
Gate: Is the tone on-brand? If not, loop back to step 1.
Step 2: A second LLM localises the approved draft to three languages.
Step 3: A third LLM extracts SEO metadata from the final text.
Why chaining? Each step needs the output of the previous step. No parallelism is possible. The gate prevents wasted work downstream.
Routing Your inputs fall into well-defined buckets, and each bucket needs different instructions, different tools, or a different model tier. You want one entry point with specialised back-ends. Customer support triage.
The router classifies each incoming ticket: refund, technical, billing, or general.
refund → fast cheap model (only needs policy lookup + template).
technical → capable model with access to logs and debug tools.
billing → capable model that can query subscription data.
general → simple Q&A model.
Why routing? Each category has distinct tools, prompts, and sometimes a different cost ceiling. Routing lets you spend money only where you need to.
Parallelisation The work is embarrassingly parallel — subtasks do not share state — or you need multiple independent perspectives on the same input. Speed (sectioning) or reliability (voting) are your goal. Security review of a PR (voting).
Three independent LLM reviewers each analyse the same diff for vulnerabilities — one focused on injection risks, one on auth logic, one on dependency changes. A fourth LLM aggregates their findings, keeping only issues flagged by at least two reviewers.
Why parallelisation? The three reviews are independent. Running them concurrently gives you the answer in the time of the slowest reviewer, not the sum of all three. Voting reduces false positives.

Dashboards from raw data (sectioning).
A quarterly business report pulls revenue, churn, and NPS data at the same time, each handled by a separate sub-pipeline, then assembled into one slide deck.
Orchestrator-workers The task is complex but its shape is unknown at design time. An orchestrator LLM must decide what subtasks exist, how many workers to spawn, and how to join the results. Autonomous codebase refactor.
The orchestrator receives "Rename the interface PaymentGateway to CheckoutProvider across the entire monorepo."
It first searches the codebase to discover every file that references the old name, then spawns one worker per affected file (the number is unknown until the search finishes). After all workers report, the orchestrator updates the barrel exports and runs the test suite, rolling back any worker whose changes break a test.
Why orchestrator-workers? A prompt chain cannot work here because the set of affected files is discovered dynamically. A router cannot work because the subtasks are all "change references" — they just target different files. The orchestrator adds the synthesis and validation step that makes the result safe.
Evaluator-optimiser You have a clear, measurable quality criterion (a rubric, a test, a style guide) and the output improves through iteration. One-off generation rarely gets it right on the first try. Machine translation with dialect targeting.
A generator LLM translates "The elevator is out of service" from English to Spanish.
The evaluator checks against a rubric: is the register informal (Latin America)? Does it prefer ascensor over elevador (Mexico)? Is the tone courteous but direct?
The evaluator scores the draft. If below threshold, it sends specific feedback back to the generator ("Use ascensor, not elevador; make it imperative tone.") and the generator revises. The loop terminates when the score passes the bar or a max iteration count is reached.
Why evaluator-optimiser? Good translation is hard to nail in one pass. The iterative loop lets you separate the skill of writing from the skill of judging, and the evaluator never gets tired or inconsistent the way a human reviewer would after the 50th translation.
Quick rule of thumb: known fixed steps → chaining. Known categories → routing. Independent work → parallelisation. Unknown shape → orchestrator-workers. Needs iteration → evaluator-optimiser.

Evals before agent complexity

Anthropic's practical standard is measurement-first: start with the simplest prompt or workflow, build a representative eval set, then add routing, tools, memory, or an agent loop only when the evals show a real gain. Evals should cover the decision, the tool path, and the final answer because an agent can sound right while using the wrong evidence or skipping a required tool.

Claude team pattern: use clear success criteria, tool-result ground truth, sandboxed testing, and human checkpoints. For coding agents, automated tests are a strong objective signal, but human review still checks broader design fit.

Common eval scorers

Scorer Use it when Agent example
exact_match The answer must be one exact label, route, enum, or status. Expected route is refunds; any other route fails.
regex_match The output must follow a pattern, but the value can vary. Generated ticket id matches ^TKT-[0-9]{6}$.
contains / not_contains Specific required or forbidden content matters. Answer mentions the refund window and does not invent a fee.
set_match Order does not matter, but the selected items must match. Agent used exactly search_orders and refund_policy.
subset_match Required items must be present; extra acceptable items are okay. Retrieved docs include policy and order history, even if shipping FAQ is also fetched.
json_schema_match The model must return structured data or tool arguments. Router output has route, confidence, and needs_human.
numeric_match The answer is numeric, often with a tolerance. Refund amount is within one cent of the expected value.
semantic_similarity Meaning matters more than exact wording. Summary preserves the core policy even with different phrasing.
llm_judge The quality bar is fuzzy and needs a rubric. A judge model scores groundedness, completeness, and unsupported claims from 1-5.
tool_call_match The agent must call the right tool with the right arguments. For ORD-123, the first lookup calls search_orders with that id.
trajectory_eval The order of actions and recovery behavior matters. Search docs -> inspect policy -> answer with cited evidence; no write tool before approval.

Prefer deterministic scorers first because they are cheap, stable, and easy to debug. Use llm_judge for open-ended quality, but give the judge a tight rubric, pass threshold, and structured output so the eval itself is auditable.

Minimal eval file shape

- name: route_refund_question
  input: "Can I get my money back for order ORD-123?"
  expected:
    route: refunds
    tools: [search_orders, refund_policy]
  evals:
    - type: exact_match
      path: route
      expected: refunds
    - type: tool_call_match
      tool: search_orders
      args_contains:
        query: ORD-123

- name: answer_grounded_in_policy
  input: "What is the refund window?"
  evals:
    - type: contains
      expected: "30 days"
    - type: llm_judge
      rubric: "Answer only from retrieved policy text; penalize unsupported claims."
      pass_score: 4

For production agents, keep a small smoke suite for every deploy and a larger scenario suite for prompt, model, retrieval, or tool-definition changes. Track both final-answer quality and intermediate tool-use quality; the intermediate failures are usually easier to fix.

When (and when not) to use a fully autonomous agent

Use an agent when the number of steps is unknown, the LLM needs to make decisions based on tool outputs, and the environment is trusted enough that you can let the loop run.
Stay with a workflow when the steps are predictable. Workflows are cheaper, faster, and easier to debug.
Avoid an agent when the cost of a wrong action is high (irrevocable writes, real money) and you have not invested in guardrails, sandboxing, and human-in-the-loop checkpoints.

The agent loop, in practice

  1. Receive a goal from a user (or a triggered event).
  2. Plan and call a tool.
  3. Observe the tool result — this is "ground truth" for the next step.
  4. Decide: continue, ask the user a question, or finish.
  5. Always have a stop condition: max steps, time budget, or explicit completion signal.
Quote the post: "Agents are typically just LLMs using tools based on environmental feedback in a loop. It is therefore crucial to design toolsets and their documentation clearly and thoughtfully." Tool design is the bottleneck, not model choice.

Three core principles to design by

  1. Maintain simplicity. Add layers only after evidence that simpler did not work.
  2. Prioritise transparency. Show the agent's planning steps so a human can audit them.
  3. Invest in the agent-computer interface (ACI). Treat tool docs as carefully as you treat human-facing docs.
