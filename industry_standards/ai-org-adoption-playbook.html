1. Multi-Agent Infrastructure

ORG SCALING

How do you support multiple coding agents (Claude Code, Copilot, Codex, Cursor) across different teams without fragmentation?

❝ Working out how to support multiple coding CLIs/agents — GitHub Copilot, Codex, Claude, and whatever comes next. Trying to scale agentic flows across different engineering teams. ❞
📖 The Four-Layer Framework

Each tool has a different interaction model — you can't標準ize on one. Instead, standardize on what the agents consume:

LayerWhat It MeansKey Deliverable
1. Process A shared "AI Coding Manifesto" — when to use autocomplete vs. agent, what needs human review, how to handle secrets in prompts 1-page playbook
2. Tooling "README for AI" — every repo has a context file (CLAUDE.md, cursorrules, copilot-instructions.md) that describes itself Context files + generator script
3. Infrastructure MCP servers for shared services (docs, deploy, schema), central prompt registry, audit trail standard MCP servers + audit hooks
4. Culture Seed teams → extract patterns → publish → scale. Habits, not tools. Lunch & learns + living docs
💡 Key Insight: The Context File as the Single Source of Truth

The highest-leverage practice: one canonical CLAUDE.md per repo, auto-generating tool-specific configs:

Repo Root
├── CLAUDE.md                    ← source of truth (you write this)
├── .github/copilot-instructions.md  ← auto-generated from CLAUDE.md
├── .cursorrules                    ← auto-generated
├── .windsurfrules                  ← auto-generated
└── CODEX.md                        ← auto-generated
Why this works: As new tools emerge ("whatever comes next"), you only update the generator — not every config file. The org standard is "declare in CLAUDE.md, consume everywhere."

2. Supply Chain Security

SBOM + SIGNING

In-depth code reviews to inform SBOMs + cryptographically signed pipelines.

❝ Doing in-depth code reviews to inform SBOMs. Building pipelines and cryptographically signing them. ❞
📖 What Is an SBOM?

SBOM = Software Bill of Materials — a complete inventory of every dependency in your software. Like a food ingredients label for code.

LayerExamplesWhy Track It?
Your codeapp.py, routes.js—
Direct depsfastapi==0.111, react@18.2Known vulnerabilities
Transitive depsurllib3 (dep of requests)Hidden attack surface
Container layerspython:3.12-slimBase image CVEs
CI/CD toolsactions/checkout@v4Pipeline compromise
Log4j test: "Where do we use Log4j?" — orgs with SBOMs answered in hours. Orgs without spent weeks. SBOM = incident response speed.
📖 What Does "Cryptographically Signing Pipelines" Mean?

It means proving that a build artifact came from your legitimate CI pipeline and hasn't been tampered with since building.

TechniqueWhat It DoesTool
Container signingSign image with short-lived key tied to CI identityCosign / Sigstore
Provenance attestationRecord what commit + who triggered the buildSLSA + in-toto
Keyless signingNo shared GPG keys — use OIDC identity from CI runnerSigstore (fulcio)
Pipeline-as-codeCI/CD defined in git, reviewed like code, not click-opsGitHub Actions / GitLab CI
The golden flow: Dev commits → PR review (SBOM checked) → CI builds → CI signs image → Registry stores image + signature → Deploy verifies signature → Only then deploy.

3. Custom Eval Framework

THE MEATIEST PART

Why generic benchmarks fail for org-specific AI evaluation, and how to build your own.

❝ They're inventing new processes to evaluate code reviews against "known bad" internal codebases. Standard benchmarks like SWE-bench don't fit. So they're building their own eval framework. ❞
📖 Why SWE-bench Doesn't Fit
DimensionSWE-bench (generic)Their Need (specific)
Codebase2,300+ bugs from random OSSTheir own internal repos
LanguagesPHP, Python, JS — whatever the OSS usesTheir language stack (maybe just TS + Go)
GoalCan the AI produce a passing patch?Can the AI find the problem in a review?
"Bad" defined asFailing unit testOrg's own anti-pattern catalog
Success metricDid the patch pass tests?Did the AI flag the issue? False positive rate?
DistributionOff-by-one, null pointers, parse errorsSQLi, PII leaks, over-privileged IAM, their specific patterns
Bottom line: If you're evaluating an AI code reviewer against SWE-bench, you're measuring how well it fixes random OSS bugs — not whether it catches your team's recurring security mistake.
📖 The Architecture of a Custom Eval Framework 
┌──────────────────────────────────────────────────────┐
│              Custom Eval Framework                     │
├──────────────────────────────────────────────────────┤
│                                                        │
│  1. BUILD "KNOWN-BAD" CORPUS                            │
│     ├── Historical bugs from your repos                 │
│     ├── Deliberately-seeded anti-patterns               │
│     └── Ground truth annotations (issue + line)         │
│                                                        │
│  2. RUN INFERENCE                                       │
│     ├── Your AI code reviewer scans the corpus          │
│     └── Produces: flagged issues + confidence scores    │
│                                                        │
│  3. SCORE                                               │
│     ├── True Positives: flagged real issues             │
│     ├── False Positives: flagged harmless code          │
│     └── False Negatives: missed actual issues           │
│                                                        │
│  4. ITERATE                                             │
│     ├── What did the AI miss that's obvious to humans?  │
│     ├── Add few-shot examples to the prompt             │
│     ├── Adjust temperature / system prompt / context    │
│     └── Re-run → compare precision/recall vs previous   │
│                                                        │
└──────────────────────────────────────────────────────┘

📚 Key Concepts Glossary

📄 SBOM

Software Bill of Materials — a complete inventory of every dependency, library, container layer, and tool in your software.

Supply chain

🔑 Sigstore / Cosign

Open-source toolchain for signing container images and blobs with ephemeral keys backed by OIDC identity — no long-lived signing keys to steal.

Supply chain

📊 SLSA

Supply-chain Levels for Software Artifacts — a maturity framework (Levels 1–4) for build integrity. Level 4 = fully hermetic + reproducible builds.

Supply chain

🔌 MCP

Model Context Protocol — an open standard for AI agents to call external tools (APIs, databases, services). One server, any agent.

Infrastructure

🧪 SWE-bench

A benchmark of ~2,300 software engineering tasks from real GitHub issues. Measures whether an AI can produce a patch that passes tests.

Eval

🎯 Precision / Recall

Precision = TP / (TP+FP). Recall = TP / (TP+FN). F1 = harmonic mean. Standard eval metrics for classification tasks.

Eval

🔐 In-toto

A framework to sign and verify every step of the software supply chain — "who ran the test step?" "who published the package?" — all cryptographically attested.

Supply chain

🔄 OIDC

OpenID Connect — the protocol behind "keyless signing." Your CI runner gets a short-lived identity token from GitHub/GitLab, which it uses to sign artifacts. No shared secrets.
