🏢 Enterprise Multi-User RAG Chatbot

Full reference architecture: retrieval → fusion → rerank → grounding pipeline, LangGraph orchestration with validation loops, three-layer evaluation, experiment tracking, and FinOps telemetry.

📋 Use Case Overview

What We're Building

A multi-user conversational AI chatbot powered by DeepSeek via API, with persistent sessions, enterprise RAG (retrieve → fuse → rerank), prompt prefix stability, LangGraph orchestration with grounding validation, and three-layer evaluation.

Users authenticate, chat across multiple sessions, retrieve grounded answers from documents with citation validation, and every decision is traceable through experiment-versioned pipelines.

Why This Matters

This is an enterprise-grade reference architecture — not a demo. It includes retrieval sophistication (RRF fusion, reranking, HyDE), context engineering, grounded generation with corrective loops, document-level ACLs, structured-output validation, versioned experiments, and FinOps telemetry. Each component reflects production patterns at companies deploying LLMs at scale.

📌 Scope: Local Docker Compose deployment for learning. K8s/infra-as-code out of scope. UI (Chainlit) is a thin client over FastAPI — zero business logic in the frontend.

🎯 The Problem We're Solving

Scenario

An organisation deploys an AI assistant over internal documents (policies, handbooks, technical docs). Multiple users with different access levels query it simultaneously. Requirements:

  • Persistent chat history — past conversations visible across sessions and days
  • Grounded, verifiable answers — each claim cites a specific document source; citations are validated against retrieved chunks
  • Knowledge isolation — User A can't see documents User B doesn't have access to
  • Measurable quality — retrieval metrics, generation metrics, and system metrics tracked per experiment
  • Cost-efficient — prompt prefix stability measured as FinOps; every component versioned and comparable

Key Challenges

  1. Retrieval quality — dense + sparse fusion with reranking, not just vector search
  2. Context engineering — ordering, dedup, token budget, parent expansion
  3. Verification — post-generation grounding check with corrective loop (bounded retries)
  4. Knowledge isolation — document-level ACL enforced before retrieval results reach the LLM
  5. Evaluation — three independent layers: retrieval IR metrics, generation RAGAS metrics, system performance metrics
  6. Experiment tracking — every component versioned so architecture decisions are evidence-based
  7. Resilience — per-error-class retry, circuit breaker, honest abstention on retrieval failure
  8. FinOps — prompt cache hit ratio, cost/session, cost/query-type tracked as first-class telemetry

What You'll Learn

  • RRF fusion + reranker — industry-standard retrieval pipeline
  • LangGraph stateful orchestration with conditional edges and validation loops
  • Three-layer eval — retrieval IR metrics, generation RAGAS, system perf
  • Post-generation grounding — validate claims, retry bounded loop, abstain
  • Context engineering — token-budget allocation, dedup, parent expansion, ordering
  • Document ACL — metadata-filtered retrieval for multi-tenant knowledge isolation
  • Experiment tracking — versioned models, prompts, chunking, fusion, reranker, eval
  • LLM FinOps — cache hit ratio, cost/session, cost/query-type
  • Structured output — Pydantic schemas for citations + validation against retrieved chunks
  • Index versioning — safe migration between embedding models with shadow/promote

🔒 Document-Level Authorization

Multi-user isolation isn't just about chat history — it's about knowledge isolation. Different users should see different documents.

graph LR User["User"] --> Auth["Authenticate"] Auth --> Roles["Resolve roles / groups / claims"] Roles --> Scope["Allowed document scope"] Scope --> Filter["Metadata filter on retriever
where acl_roles && user.roles"] Filter --> VDB["PGVector + tsvector
(filtered search)"] VDB --> Gen["LLM (only sees authorised chunks)"]
ComponentImplementation
User rolesStored in users.roles (JSON array: ["employee", "manager", "hr"])
Document ACLStored in document_chunks.acl_roles — which roles can see this chunk
Enforcement pointPGVector filter: WHERE acl_roles && user_roles — before retrieval results reach LLM
Reranker awarenessReranker only sees already-filtered candidates — no cross-ACL leakage

🚨 The authorization filter must happen before retrieval results reach the LLM. Never rely on the LLM to "respect" ACLs via prompting — it will fail under prompt injection or reasoning errors. Architectural enforcement at the database query level is the only safe approach.

🧩 Context Engineering (The Missing Component)

Retrieval asks "which information might be useful?" Context engineering asks "what information should the model actually receive, in what form and order?" — this is increasingly a core skill in production LLM systems.

graph LR Raw["Reranked chunks
top 5–8"] --> Dedup["Deduplicate
(exact + near-duplicate)"] Dedup --> Merge["Merge adjacent chunks
from same document"] Merge --> Expand["Parent expansion
if chunk is too narrow"] Expand --> Budget["Token-budget allocation
(respect context window)"] Budget --> Order["Order context
logical flow"] Order --> Provenance["Attach provenance
source, page, score"] Provenance --> Final["Final context → LLM"]
StepWhy
DeduplicateDense and sparse often return overlapping chunks. RRF doesn't dedup. Remove exact and near-duplicate (cosine > 0.95) chunks before spending token budget.
Merge adjacentIf chunks 3 and 4 from the same document are both selected, merge them into a single block. Preserves flow and reduces overhead.
Parent expansionIf a small chunk (e.g. 256 tokens) is retrieved but lacks context, expand to its parent section (512–2048 tokens) — but only within token budget.
Token-budget allocationCap total context tokens (e.g. 75% of DeepSeek's window). Allocate proportionally to chunk relevance scores. Drop lowest-scoring chunks if over budget.
OrderPresent chunks in document-logical order (not score order). The LLM reasons better when it reads content sequentially.
ProvenanceEvery chunk carries its source document, page, section — so the LLM can cite correctly AND you can validate citations post-generation.
📌 Track context_strategy in the experiment registry: Did you use parent expansion? What was the token budget ratio? Ordering strategy? These are independent variables that affect downstream quality.

✅ Structured Output & Post-Generation Grounding

Structured Citation Schema

Don't trust [1], [2] markers just because the model generated them. Define schemas and validate citations against the actual retrieved chunks.

class Citation(BaseModel):
    document_id: str
    chunk_id: str

    quote: str | None

class Answer(BaseModel):
    answer: str

🧩 The 5 Agentic Patterns (Anthropic Industry Standard)

Anthropic's engineering guide defines five fundamental workflow patterns. Our architecture uses two of them in combination — here's why, and where the other three would fit:

PatternShapeUsed Here?Why
Prompt Chaining Step 1 → Gate → Step 2 → Gate → Step 3 ⚠ Partial Our ingestion pipeline is a chain (parse → normalise → extract → chunk → embed), but our chat flow is not — the branches diverge based on intent.
Routing Classify → dispatch to specialised handler ✅ Core Intent Router is the entry point of our LangGraph. It classifies each query as chat, rag, or clarify and dispatches to the correct sub-graph. Textbook routing — cheap classifier, specialised downstream handlers.
Parallelisation Fan-out subtasks → aggregate ✅ Core Dense + sparse retrieval run in parallel via LangGraph fan-out. RRF fusion is the aggregation step. Multi-query also fans out N searches and fuses results.
Orchestrator-Workers Central LLM decides subtasks → delegates → synthesises ❌ Not used Doesn't fit our use case — the RAG flow is well-defined and doesn't need an LLM deciding subtask structure at runtime. ReAct is a simpler alternative for dynamic tool selection.
Evaluator-Optimiser Generate → Evaluate → Loop until pass / exhaust ✅ Core Grounding Check is a textbook evaluator-optimiser loop. Generator produces answer with citations; grounding validator evaluates each claim; loop retries (max 2) on failure. Bounded evaluator-optimiser with clear rubric (citation accuracy) and hard stop.
🎯 Why this combination? Anthropic's guidance: "Start with a single augmented LLM call. Add structure only when evals show it improves the outcome." Routing gives cheap triage for non-RAG queries. Parallelisation keeps retrieval fast. The evaluator-optimiser loop ensures grounded answers. Three patterns, each justified by a specific failure mode. ReAct is kept as a baseline comparison — if it matches our graph's quality at lower latency, we simplify.

📐 Three-Layer Context Management (Platform Industry Standard)

Major platforms (ChatGPT, Claude, Gemini) converge on a three-layer model for managing long conversations. Our architecture maps directly onto it:

LayerPlatform FeatureOur Implementation
① Prompt Caching (KV cache)
Speed & cost		 Claude Prompt Caching (5-min TTL),
OpenAI Automatic Prompt Caching,
Gemini Context Caching		 DeepSeek server-side caching (automatic). We ensure prefix stability so the cache hit rate is maximised. Measured via prompt_cache_hit_tokens in API response.
② Sliding Window
Hard limit		 ChatGPT drops oldest messages,
Claude trims from top,
Gemini truncates history		 History summarisation at 70% of context window: old messages summarised, recent N turns kept verbatim. System prompt and memory facts are pinned and never dropped.

📌 Key insight from the platform analysis: These three layers are independent concerns. Caching speeds up re-reading history (but doesn't make it fit). The sliding window enforces the hard limit (but loses early context). Persistent memory preserves key facts across the sliding window (but only captures explicit information). Each solves one problem; you need all three in production.

📝 Prompt Management Lifecycle

Prompts are not "write once, ship forever." They are the closest thing to code that a non-deterministic system can have — they need versioning, testing, staging, monitoring, and a loop back to the author. This lifecycle is the industry standard endorsed by Anthropic and OpenAI.

graph LR Design["① Design
Authoring + playground"] --> Version["② Version
git-native tracking"] Version --> Eval["③ Evaluate
evals + CI"] Eval --> Deploy["④ Deploy
release + canary"] Deploy --> Monitor["⑤ Monitor
LangFuse + scores"] Monitor --> Iterate["⑥ Iterate
back to ①"]
StageOur Practice
① DesignPrompts are prototyped in the DeepSeek playground or LangSmith Hub. XML-structured format (Anthropic ACI style): <instructions>, <context>, <examples>. System prompts follow a "tone, rules, steps" structure.
② VersionGit-native: prompts stored as markdown files with frontmatter in .claude/prompts/. Each file has name, version, model_target, author, date. Standard PR review and tagging.
③ EvaluateCI runs the eval suite (27 test cases across 3 layers) on every prompt PR. The prompt_version field is logged in every LangFuse span so you can correlate quality changes with prompt changes.
④ DeployAfter merge, the prompt is available at a versioned key. Canary releases via experiment registry — serve prompt v2 to 10% of queries, compare scores, promote if better.
⑤ MonitorLangFuse dashboards track faithfulness, cache hit ratio, and user feedback per prompt version. Alert if scores drop below threshold.
⑥ IterateFlagged interactions feed back into prompt design. Root-cause tags (retrieval / prompt / chunking / model) determine whether the fix is a prompt change or a pipeline change.
📌 Why this matters: Without a lifecycle, you cannot tell whether a quality drop was caused by a prompt change, a model update, or data drift. Every component in our system — prompt, model, embedding, chunking, retrieval strategy — has a version string logged in every LangFuse trace. This is what makes the experiment registry meaningful.

🎯 Eval Scorer Taxonomy (Anthropic Standard)

Anthropic's agent evaluation guide defines a set of standard scorers. Our three-layer eval (retrieval / generation / system) maps onto these scorer types — prefer deterministic scorers first, use LLM judge only for fuzzy quality:

ScorerWhen to UseOur Test Case
exact_matchThe answer must be one exact label, route, or statusT1: Intent Router returns rag for policy question
json_schema_matchStructured output must conform to a schemaT17: Generated Answer has valid citations array matching Pydantic schema
contains / not_containsRequired or forbidden contentT8: Answer contains "remote work policy" and document title
semantic_similarityMeaning matters more than exact wordingT14: Context Precision — retrieved chunks are semantically relevant to query
tool_call_matchAgent must call the right tool with the right argumentsT8: Agent called retrieve_docs with query containing "remote work policy"
trajectory_evalOrder of actions and recovery behaviour mattersT9: Greeting → no retrieval tool called. T17: Hallucination → grounding retry → abstain order
numeric_matchNumeric answer within toleranceCustom: Token counts, cost, latency — check within bounds

⚡ Prefer deterministic scorers first. They are cheap, stable, and easy to debug. Use llm_judge for open-ended quality, but give the judge a tight rubric, pass threshold, and structured output so the eval itself is auditable. Our three-layer eval already follows this — retrieval IR metrics are deterministic, generation metrics use RAGAS (LLM judge), system metrics are numeric.

📊 Three-Layer Evaluation

Evaluating only the final answer hides where the system fails. Split into three independent layers:

🔍 Retrieval

  • Recall@K (K=1,3,5)
  • Precision@K
  • Hit Rate@K
  • Mean Reciprocal Rank
  • NDCG@K

Answers: "Did we find the right documents?"

📝 Generation

  • Faithfulness
  • Answer Relevance
  • Citation Correctness
  • Citation Completeness
  • Hallucination
  • Completeness

Answers: "Did we generate a correct, grounded answer?"

⚙️ System

  • p50 / p95 latency
  • TTFT (time to first token)
  • Tokens / request
  • Cost / request
  • Cache hit ratio
  • Retrieval latency
  • Reranker latency
  • LLM latency
  • Error rate

Answers: "How fast and how expensive?"

🔥 Why three layers? If a user gets a bad answer, is it because (a) retrieval missed the right chunk, (b) the LLM hallucinated despite good context, or (c) the system was too slow and the user left? Three-layer evaluation tells you exactly which component to fix — no guessing.

IR Metric Formulas

// Recall@K = relevant docs in top K / total relevant docs
// MRR = mean of 1/rank(first relevant) across queries
// NDCG = discounted cumulative gain normalized by ideal ranking
// Hit Rate@K = fraction of queries with at least 1 relevant doc in top K

Tooling

  • Retrieval metrics: ranx or custom evaluation script over your test set
  • Generation metrics: RAGAS (faithfulness, answer_relevancy) + DeepEval (hallucination, G-Eval)
  • System metrics: LangFuse spans — extract latency, cost, error rate per trace

Circuit open❌ NoFail fast — return "unavailable" message, don't hit a dead API

Fallback Semantics

  • LLM unavailable → return "The assistant is temporarily unavailable, please retry later."
  • Retrieval unavailable (for a policy question) → abstain. Never ask the LLM to guess when retrieval fails. For a policy question, you want "Knowledge service unavailable" — not a hallucinated policy.
  • Reranker unavailable → fall back to RRF-ranked results without cross-encoder scoring.

💰 Prefix Stability as FinOps

DeepSeek's server-side prompt caching is automatic. Your job is to maximise cache hit ratio through prompt construction, and measure the savings as FinOps.

Prompt Construction Rules

  1. Fixed ordering from token 0: system_prompt → stable_RAG_context → summarized_old_history → recent_N_turns → new_user_message. Variable content always last.
  2. No timestamps or request IDs in the prefix. Anything before the stable content breaks the cache for everything after it.
  3. Session state (Redis) decides prompt shape (full vs summarised), not cache control.
  4. Ground truth from API response: prompt_cache_hit_tokens and prompt_cache_miss_tokens tell you whether your strategy is working.

History Summarization — Corrected Logic

Don't use inactivity as the trigger. Separate three concerns:

ConcernTriggerAction
Context managementConversation token estimate > threshold (70% of window)Summarize old history, keep recent N turns verbatim
Redis session stateSliding TTL (1 hour inactivity → evict)Controls hot session metadata, not cache
Provider prompt cachingAutomatic server-side (DeepSeek manages)Measured via API response — you only control prefix stability
