HLD Fundamentals — latency, throughput, scaling

Vocabulary you must own

Term Plain meaning Unit / typical value
Latency How long one request takes. ms; aim < 200 ms p99 for web APIs.
Throughput How many requests/sec the system handles. req/sec (QPS).
Concurrency How many requests are in flight at once. ≈ throughput × avg latency.
Availability Fraction of time the system is reachable. 99.9% = ~9 hrs downtime/year; 99.99% = 52 min/year.
Durability Probability a stored item won't be lost. S3: 11 nines.
Consistency All readers see the same value. Strong / eventual / read-your-writes.
Partition tolerance System keeps working if the network splits. Required for any multi-node system.
p50 / p99 / p99.9 Latency at the 50th / 99th / 99.9th percentile. Tail latency > average latency in importance.
SLA / SLO / SLI Promise / target / measurement. SLA = contract; SLO = internal goal; SLI = the metric.
QPS Queries per second. Used for back-of-envelope.
Hot key / hot shard One key or partition gets disproportionate traffic. Most common cause of "scaling broke".
Back-pressure Mechanism to slow producers when consumers can't keep up. Bounded queues, rate-limits, circuit breakers.

Numbers every senior engineer carries in their head

Jeff Dean's "latency numbers" — memorize the orders of magnitude.

Operation Time
L1 cache reference ~0.5 ns
L2 cache reference ~7 ns
Main memory reference ~100 ns
Read 1 MB sequentially from memory ~250 µs
SSD random read ~150 µs
HDD seek ~10 ms
Round trip same DC ~0.5 ms
Round trip CA → Netherlands ~150 ms
Read 1 MB over network ~10 ms (1 Gbps LAN)

Takeaway: network is 200× slower than RAM, disk is another 100× slower. Every architecture choice flows from this hierarchy.

Vertical vs Horizontal scaling

Vertical (scale up)

Bigger machine. 2 CPU → 64 CPU.

Pros: easy, no code change, single source of truth.

Cons: hard ceiling (biggest machine on the market), single point of failure, expensive.

Horizontal (scale out)

More machines. 1 server → 100 servers behind a load balancer.

Pros: ~unlimited ceiling, fault tolerant.

Cons: requires stateless services, distributed coordination, more moving parts.

Modern default: design for horizontal scaling from day one, even if you deploy only one instance. Switching from vertical to horizontal later is a rewrite; the other way around is a deployment change.

Stateless services — the magic that enables horizontal scaling

Story: a session is kept in server memory on web-1. Load balancer routes the next request to web-2 — and the user is logged out. Now you either pin users to a server (sticky session = single point of failure) or you fix the design.

The fix: move state out of the service. Session in Redis. File uploads in S3. Long-running counters in the database. The web tier becomes pure functions of (request → response). Any instance can serve any request.

Once stateless: add instances when traffic spikes, drop them when it falls. This is what auto-scaling assumes.

The bottleneck principle

A system is only as fast as its slowest component, and only as available as its least available component.

When designing, ask: "where will this break first?"

  • 10 web servers + 1 DB → DB is the bottleneck. Adding web servers helps nothing until you scale the DB.
  • Fast app + slow third-party API → tail latency dominated by them. Add a cache / circuit breaker / async pattern.
  • Plenty of CPU, but a single Redis instance → that Redis is your bottleneck. Shard it.

This is also why scaling is iterative: fix one bottleneck, the next one appears.

Back-of-envelope estimation

Every HLD round starts with capacity numbers. Practice the math; it's the same shape every time.

Example: Twitter feed

  • 300M monthly active users → assume 100M daily.
  • Each user reads feed 20× / day → 2B reads/day → ~23k reads/sec average, ~70k peak (3× average is a safe peak multiplier).
  • Each user posts 0.1 tweets/day → 10M tweets/day → ~120 writes/sec average, ~400 peak.
  • Read:Write ratio ≈ 200:1 → optimize the read path heavily (caching, fanout-on-write).
  • Each tweet ~280 bytes + 200 bytes metadata = 500 B → 5 GB/day → ~2 TB/year.

These numbers drive every design choice: 200:1 read:write means you precompute feeds; 70k QPS means you must horizontally scale the read API; 2 TB/year means a single instance can hold a year of data if hot — but you'll still shard for parallelism.

Cheat formulas

  • Daily active ≈ 30–40% of monthly.
  • Peak QPS ≈ 3× average.
  • Average / day → /sec: divide by 86,400 ≈ ÷ 100,000 for quick math.
  • 1 modern CPU core ≈ ~1k–10k simple HTTP req/sec.
