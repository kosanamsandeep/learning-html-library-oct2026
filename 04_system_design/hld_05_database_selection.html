The single most expensive decision in any system

Choosing the right database — a story-first guide

"Which database should I use?" is the question every senior engineer is paid to answer well. Pick wrong and you'll spend the next 18 months migrating, firefighting, or watching latency graphs climb. Pick right and the database disappears — it just works.

This page walks the entire database landscape, tells you why each one exists, when to pick it, and what specifically goes wrong when you pick the wrong one. Plain words, real stories, decision diagrams.

1 · The mental model — every database is a tradeoff

Every database makes a deal with you. It says: "I will be amazing at X, decent at Y, and terrible at Z." Your job is to know which X you need today, which Y you can live with, and which Z would kill you.

The three big axes are:

  • Shape of data — rows? documents? graph? key-value? time-stamped points?
  • Access pattern — read-heavy or write-heavy? known queries or ad-hoc? joins or single lookups?
  • Consistency vs scale — do you need strict ACID, or can you trade some consistency for massive horizontal scale?
Story: A startup builds their MVP on MongoDB because "it's flexible". Six months later they need a report that joins users, orders, payments, refunds, and shipping. Mongo can do it, but the query is 300 lines of $lookup pipeline and takes 40 seconds. The same query in PostgreSQL is 8 lines of SQL and runs in 80 ms. The team migrates. Cost: 4 engineer-months. Lesson: "flexible schema" is not a free lunch — joins, transactions, and reporting are why relational databases exist.

4 · Relational / SQL — PostgreSQL, MySQL

PostgreSQL · MySQL · MariaDB · Oracle · SQL Server

Rows in tables. Relationships via foreign keys. Queries in SQL. ACID transactions out of the box.

Why they exist: Most business data is relational — orders belong to customers, line items belong to orders, payments link to both. Relational DBs model this naturally and let you ask any question after the fact with SQL.

Strengths:

  • ACID transactions — money moves correctly, no half-updates.
  • Joins & aggregations — "show me revenue by region by month" is a one-line query.
  • Mature ecosystem — every ORM, BI tool, and migration framework speaks SQL.
  • Constraints — the database itself stops bad data (foreign keys, unique, check constraints).

Weaknesses:

  • Vertical scaling has a ceiling — really big instances cost a lot.
  • Sharding across many machines is doable but operationally painful.
  • Schema migrations on huge tables can be scary (locks, rewrites).

Concrete "use it when" examples

  • E-commerce: orders, customers, inventory, payments. You need "did the order get placed AND inventory get decremented AND payment captured" to all succeed or all fail. That's exactly what ACID is for.
  • Banking / Fintech ledger: double-entry accounting. PostgreSQL or Oracle. Always.
  • SaaS app with tenants, users, projects, tasks: classic relational shape.
  • Anything that will need reporting / BI later — and almost everything needs that eventually.

✅ Use SQL when

  • Entities have clear relationships.
  • You need transactions (money, inventory, bookings).
  • You don't yet know all the queries you'll need.
  • Strong consistency matters.
  • Data fits in < ~10 TB (most apps do for years).

❌ Avoid when

  • You're storing 500 GB of raw IoT readings per day → wide-column or time-series.
  • You need sub-millisecond key lookups at huge QPS → Redis or DynamoDB.
  • You're doing graph traversal 6 hops deep → graph DB.
  • You need full-text search with ranking and typo tolerance → search engine.

💥 What goes wrong if you skip SQL when you needed it

Scenario: A team picked MongoDB for an online food-delivery ordering system. Order, restaurant, driver, customer, payment all became separate collections.

What broke:

  1. A driver picked up an order, but a network blip caused the order status to update without the payment hold being placed. No transactions across collections — money was lost on hundreds of orders before they noticed.
  2. The finance team asked for "revenue per restaurant per day, after refunds". The query needed 4-way $lookup joins. Ran for 12 minutes and timed out.
  3. Schema drifted — some orders had price, newer ones had totalPrice, oldest ones had amount. No constraint caught it.

Cure: migrated core entities to PostgreSQL. Kept Mongo only for the restaurant menu catalog (truly variable shape). Outage rate dropped 90%.

✅ Story: when SQL was the obvious right pick

Stack Overflow runs on a single primary SQL Server with read replicas. ~5,000 QPS, hundreds of millions of rows, a few hundred GB. They've been on this stack for a decade. Boring SQL handles it because reads are cacheable and writes are bounded. Most "we need NoSQL because we'll be huge" stories never grow that big.

5 · Document DB — MongoDB, Couchbase, DynamoDB (document mode)

MongoDB · Couchbase · Amazon DocumentDB

Stores JSON-like documents. No fixed schema. Query by any field. Scales horizontally by sharding.

Why they exist: Some data is genuinely nested and varies in shape — product catalogs where every category has different attributes, CMS articles with embedded blocks, event payloads from third-party APIs.

Strengths:

  • Flexible schema — add a field without a migration.
  • Documents map naturally to JSON used by APIs and front-ends.
  • Horizontal scaling via sharding is built in.
  • Single-document writes are atomic.

Weaknesses:

  • Multi-document / multi-collection transactions exist but are slower and discouraged.
  • Joins ($lookup) are limited and slow.
  • "Flexible schema" almost always becomes "no schema discipline" — bugs follow.

Concrete "use it when" examples

  • Product catalogs where each category has unique attributes (a phone has RAM and camera MP; a book has ISBN and page count).
  • CMS / blog platforms where each article is a tree of typed blocks (text, image, embed).
  • Logging / event sinks where the payload shape is owned by many producers.
  • Per-user settings / profiles where the document is read or written in full and never joined.
  • Game state snapshots stored as one document per player.

✅ Use Mongo when

  • Each record is naturally a self-contained document.
  • You read/write the whole document at once.
  • Schema legitimately varies across rows.
  • You need easy horizontal scaling out of the box.

❌ Don't use when

  • Data has many cross-entity relationships.
  • You need multi-document transactions (money!).
  • You'll need ad-hoc analytical queries with joins.
  • You haven't honestly justified why SQL wouldn't work.

💥 What goes wrong when you use Mongo as default

An analytics SaaS stored "users", "workspaces", "dashboards", "widgets", "permissions" all in Mongo. Six months in:

  • Permission checks need to join user → workspace → dashboard → widget. Every page load fires 4 round-trips to Mongo.
  • A bug duplicated a workspace ID across two users. No foreign-key constraint caught it. Customers saw each other's dashboards.
  • Adding "soft delete" required a script that touched every collection. No unified WHERE clause.

Cure: moved relational entities to PostgreSQL with proper FKs. Kept Mongo for dashboard layout JSON (truly document-shaped).

6 · Key-Value — Redis, DynamoDB, Memcached

Redis · Memcached · DynamoDB · KeyDB

Get / set by key. Sub-millisecond. In-memory (Redis) or on-disk (DynamoDB).

Why they exist: Many lookups are "give me the value for this key, fast". A database engine designed only for that is orders of magnitude faster than a general-purpose SQL DB.

Why Redis specifically: not just a cache. It's a Swiss-army knife with built-in types: strings, hashes, lists, sets, sorted sets, streams, pub/sub, geo, HyperLogLog. That's why it shows up in 9 different roles in modern systems.

The 8 roles Redis plays in production

  1. Cache — sit in front of PostgreSQL, store hot rows for 60s. Reduces DB load 10–100x.
  2. Session store — login cookies, JWTs, OAuth state. Stateless app servers + Redis = horizontal scaling.
  3. Rate limiting — INCR with TTL. "Allow 100 req per minute per IP" is 3 lines.
  4. Leaderboards — sorted sets. Top 10 players in O(log n).
  5. Distributed locks — SETNX with TTL.
  6. Job queue — lists with LPUSH/BRPOP, or Streams for richer semantics.
  7. Pub/Sub — fan-out events to many subscribers.
  8. Real-time counters — page views, likes, "users currently online".
flowchart LR
    User[👤 User] --> App[App server]
    App -- "1. check cache" --> Redis[(Redis)]
    Redis -- "hit ⚡" --> App
    App -- "2. on miss" --> DB[(PostgreSQL)]
    DB -- "row" --> App
    App -- "3. set with TTL" --> Redis
    App -- "response" --> User

Cache-aside pattern — the most common Redis use. Cuts SQL load by an order of magnitude on read-heavy endpoints.

✅ Use Redis / KV when

  • Sub-ms latency required.
  • You always look up by a known key.
  • Data fits in RAM (Redis) or you need infinite scale (DynamoDB).
  • Need pub/sub, locks, queues, or sorted leaderboards.

❌ Don't

  • Use Redis as the only store for important data — RAM-based, memory limits.
  • Run ad-hoc queries — there's no query planner.
  • Store huge values (> few MB).
  • Treat it as your source of truth for ledger / finance data.

💥 Story: when Redis was the wrong choice

A team built a "messages" feature backed only by Redis. It worked great until a memory eviction policy kicked in and silently deleted older chats. Customers lost months of conversation. Lesson: Redis is a cache, not a database of record unless you configure persistence (AOF) carefully and budget for memory.

✅ When Redis was the obvious right pick

Twitter's tweet timeline cache, Stack Overflow's hot-questions cache, GitHub's rate limiter, almost every login session in modern web apps. All Redis. Anywhere you said "this needs to be fast and the data is short-lived", Redis is the answer.

7 · Wide-Column — Cassandra, ScyllaDB, HBase

Cassandra · ScyllaDB · HBase · BigTable

Rows keyed by a partition key, distributed across many machines. Write-optimized. Single-digit-ms reads if the query matches the partition design.

Why they exist: Some workloads write so much data that no single machine can keep up — IoT telemetry, ad-tech impressions, social-feed inboxes, game telemetry. Wide-column DBs are designed to absorb millions of writes per second by spreading them across hundreds of nodes.

Concrete use cases

  • Netflix viewing history — every "you watched X for Y seconds" event.
  • Apple iMessage delivery state.
  • Discord messages — billions of messages, scaled by channel ID.
  • IoT sensor streams — fleet of trucks reporting GPS every second.
  • Ad-tech impression / click logs.

✅ Use when

  • Massive write throughput (10k+ writes/sec sustained).
  • Data is append-mostly, rarely updated.
  • You can design queries up front around a partition key.
  • You need active-active multi-region with tunable consistency.

❌ Don't

  • Need ad-hoc queries — Cassandra punishes queries that don't match its partition key.
  • Need joins or strong transactions — you won't get them.
  • Have a small team — operating Cassandra well is a job.

💥 The classic Cassandra anti-pattern

A team picked Cassandra "to scale". Their data model: one big table, queried multiple different ways. They used ALLOW FILTERING on every query. Latency was 8 seconds per page. They needed to either redesign every query (which means a new table per query in Cassandra) or move to a more flexible DB. In Cassandra you design the schema around the query, not the data.

8 · Graph — Neo4j, Amazon Neptune, ArangoDB

Neo4j · Amazon Neptune · ArangoDB · TigerGraph

Nodes and edges. First-class traversal. Made for "find me X that is connected via Y to Z".

Why they exist: Some questions are about relationships, not entities. "Friends of friends who like jazz". "All accounts that share a device with this fraudulent account, up to 5 hops". In SQL these are self-joining nightmares; in a graph DB they're one-line queries.

flowchart LR
    A((Alice)) -- FRIEND --> B((Bob))
    B -- FRIEND --> C((Carol))
    C -- FRIEND --> D((Dan))
    A -- LIKES --> J[Jazz]
    D -- LIKES --> J
    B -- LIKES --> R[Rock]
    C -- LIKES --> J

"Find friends-of-friends of Alice who like Jazz." In Cypher (Neo4j) that's one line: MATCH (a:Person {name:'Alice'})-[:FRIEND*2..3]-(p) -[:LIKES]->(:Genre {name:'Jazz'}). In SQL it's three self-joins per hop.

Real-world graph use cases

  • Social networks — LinkedIn "people you may know".
  • Fraud detection — PayPal, banks: "does this account share a device, address, or beneficiary with a known fraudster within 4 hops?"
  • Recommendation engines — "users like you also bought…"
  • Knowledge graphs — Google's, Wikidata, internal enterprise knowledge bases, GraphRAG for LLMs.
  • Network & IT topology — "if this switch dies, what services go down?"
  • Identity / access management — "which permissions does this user inherit through which groups?"

✅ Use a graph DB when

  • The questions are about paths and connections, not entities.
  • You traverse 3+ relationships in a single query.
  • Relationships are first-class objects (typed edges with properties).

❌ Don't

  • Use it as your primary store for typical CRUD — overkill.
  • Pick it just because you have "users with friends" — that's still SQL territory until you actually do traversals.

💥 Story: fraud system without a graph

A fintech tried to do fraud detection in PostgreSQL. The "are these two accounts linked via shared devices, IPs, or beneficiaries within 5 hops" query needed recursive CTEs that timed out. They missed real fraud rings until they moved to Neo4j — the same query then ran in 200 ms and caught $4M in attempted fraud per month.

9 · Search — Elasticsearch, OpenSearch, Solr

Elasticsearch · OpenSearch · Solr · Meilisearch · Typesense

Inverted index. Designed for full-text search with ranking, typo tolerance, faceting, and aggregation.

Why they exist: SELECT * FROM products WHERE name LIKE '%nike%' is slow on big tables and can't rank by relevance, handle typos, or boost recent items. Search engines are designed exactly for this.

When to add Elasticsearch

  • E-commerce search with filters (size, color, brand, price range) and "did you mean".
  • Log search at scale — ELK / OpenSearch stack. Grep across billions of log lines.
  • Application search — Slack message search, GitHub code search, Jira issue search.
  • Aggregations / analytics dashboards over event data, when queries are predictable.

✅ Use search engines when

  • Users type free-text queries.
  • You need ranking, typo tolerance, synonyms.
  • You need fast faceted filtering on many fields.

❌ Don't

  • Use Elasticsearch as the source of truth — sync from your SQL DB into it.
  • Use it for transactional updates — it's eventually consistent.

10 · Time-Series — InfluxDB, TimescaleDB, Prometheus

InfluxDB · TimescaleDB · Prometheus · QuestDB · VictoriaMetrics

Append-only, time-keyed data. Heavily compressed. Built-in downsampling, retention policies, and time-window queries.

Why they exist: A general DB will store a billion (time, metric, value) rows but query them slowly and waste 10x the disk. Time-series engines compress like crazy and answer "average CPU per minute over last 24h" instantly.

Use cases

  • Server metrics — CPU, memory, latency. Prometheus + Grafana.
  • IoT — sensor readings, smart-home telemetry.
  • Financial tick data — stock prices, FX rates.
  • Application performance monitoring — Datadog, New Relic.
Tip: If you're already on PostgreSQL, TimescaleDB is a Postgres extension that gives you time-series performance without adopting another database. Best of both worlds for small teams.

11 · Vector — Pinecone, Weaviate, Milvus, pgvector

Pinecone · Weaviate · Milvus · Qdrant · pgvector · Chroma

Stores high-dimensional vectors (embeddings) and finds nearest neighbors in milliseconds. The backbone of every modern RAG / LLM app.

Why they exist: Asking "find documents semantically similar to this question" requires comparing 1536-dim vectors. SQL DBs can't index that. Vector DBs use HNSW, IVF, or product-quantized indexes to do it at scale.

Use cases

  • RAG over docs for LLMs (ChatGPT-on-your-docs).
  • Semantic search — "find articles about renewable energy" returns docs even if the word "renewable" isn't in them.
  • Recommendations — "users with similar embedding profiles".
  • Image / audio similarity — reverse image search, song matching.
  • Anomaly detection — items far from any known cluster.
Start small: if you're under ~1M vectors, pgvector (PostgreSQL extension) is plenty. Reach for dedicated Pinecone / Milvus when you cross 10M+ vectors or need very low p99 latency.

12 · Object Storage — S3, GCS, Azure Blob

Amazon S3 · Google Cloud Storage · Azure Blob · MinIO

Cheap, durable, virtually infinite storage of files. Pay per GB and per request. 11 nines of durability.

Why they exist: Storing images, videos, PDFs, backups, ML model artifacts in a relational DB blows up the DB and costs a fortune. Object stores are 10–100x cheaper per GB and don't slow down with size.

Pattern: never store binary blobs in your main DB

Upload to S3, store the S3 URL in PostgreSQL. Every modern app does this — user avatars, document uploads, ML datasets, video transcodes, daily DB backups.

💥 Story: PDFs in PostgreSQL

An insurance startup stored claim PDFs as bytea columns. The claims table grew to 800 GB in 8 months. Every backup took 6 hours. Replication lagged constantly. Cure: moved PDFs to S3, stored URLs in Postgres. Table shrank to 4 GB. Backups now take 5 minutes.

13 · NewSQL / Distributed SQL — Spanner, CockroachDB

Google Spanner · CockroachDB · YugabyteDB · TiDB · Aurora

Speak SQL. Look like PostgreSQL. Scale horizontally across regions like NoSQL. Keep ACID transactions.

Why they exist: NoSQL gave up SQL to get scale. NewSQL gives you both — at the cost of higher latency per query and operational complexity.

Use cases

  • Global apps that need strongly consistent writes across continents (Spanner powers Gmail, Google Ads).
  • Companies that outgrew a single-master PostgreSQL but don't want to fragment into NoSQL.
Reality check: 99% of apps never need NewSQL. PostgreSQL with read replicas + good caching handles way more traffic than people assume. Reach for Spanner / Cockroach only when you've actually hit the wall.

15 · Horror stories — wrong choice, real cost

💥 #1 — "MongoDB will scale, we'll figure out joins later"

SaaS team chose Mongo for everything. After 18 months: 60% of engineering time spent on data-consistency bugs and slow reports. Migration to PostgreSQL took 4 months and froze the roadmap.

💥 #2 — "Redis is so fast, let's just store users there"

Used Redis as primary store. A memory eviction policy silently dropped user records under load. Lost ~3% of users' settings. Cost: refunds, churn, emergency restore from a 2-day-old backup.

💥 #3 — "Cassandra so we can scale"

Pre-product-market-fit startup chose Cassandra at 0 users. 6 months later: couldn't change query patterns without rewriting every table. Migrated to PostgreSQL. Ironic ending: they never crossed 50 QPS.

💥 #4 — Storing 4K videos in PostgreSQL

EdTech put lesson videos as bytea. DB grew to 2 TB; nightly pg_dump took 14 hours and blocked the box; replicas lagged 6 hours. Cure: S3 + CloudFront. Backup time: 8 minutes.

💥 #5 — "We'll do search with LIKE '%query%'"

Marketplace with 5M listings used SQL LIKE for search. Every search scanned the whole table. p95 latency: 9 seconds. Users left. Adding Elasticsearch dropped p95 to 80 ms.

💥 #6 — Fraud detection in SQL with recursive CTE

Bank wrote a 5-hop "linked accounts" query as a recursive CTE in PostgreSQL. Each run took 90 s on production-sized data, locking parts of the table. Moving that single workload to Neo4j made the query 250 ms and uncovered $4M/month in fraud they had been missing.

💥 #7 — Metrics in PostgreSQL

App stored every API call as a row in a requests table. 200M rows in a month. Queries for "p99 latency last 24h" took minutes. Disk filled up. Moving to Prometheus / Timescale reduced storage 30x and made the queries instant.

💥 #8 — Embeddings in a JSON column

RAG side-project stored 1536-dim embeddings as JSON in PostgreSQL and did cosine similarity in Python after loading all rows. At 200k docs, each query took 12 seconds. Switching to pgvector with an HNSW index: 40 ms.

💥 #9 — Storing every user setting per-key in DynamoDB

Mobile app stored each setting as a separate item keyed by user#setting. Reading all settings on app launch fired 30+ requests. Cost ballooned. Cure: store all of a user's settings as one item (a document), or move to a per-user document in MongoDB.

💥 #10 — Single Elasticsearch cluster as source of truth

A logs SaaS made Elasticsearch the only store for customer logs. A bad shard allocation caused a few hours of writes to be lost during a rolling restart. Customers noticed missing logs. Lesson: ES is great for search; pair it with a durable store (S3, Kafka topic) you can replay from.

16 · Polyglot persistence — combining databases

Real systems rarely use one database. They use the right tool per workload, with one store designated as the source of truth and the others as derived views kept in sync via events / CDC.

CDC (Change Data Capture) lets you treat one DB as the truth and feed all the specialized stores from a Kafka stream. This is the standard modern pattern.

Rule: exactly one source of truth per piece of data. Everything else is a cache or a projection that can be rebuilt.

Three rules to remember

  1. Default to PostgreSQL. If you can't articulate why something else, use it.
  2. Pick by access pattern, not by hype. Ask "how will this be queried?" before "which DB is cool?"
  3. One source of truth per fact. Caches and search indexes are projections — be ready to rebuild them.
