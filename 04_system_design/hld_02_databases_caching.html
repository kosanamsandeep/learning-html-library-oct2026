Where the data lives — and how to keep it fast

Databases & Caching — the storage layer in HLD

Pick the wrong storage and no amount of clever code will save you. Pick the right one and most of your performance problems disappear. This page covers the four decisions every HLD answer must address: SQL vs NoSQL, indexes, sharding & replication, and caching strategies.

SQL vs NoSQL — when to pick which

Trait SQL (RDBMS) NoSQL
Schema Strict, defined upfront Flexible, per-row
Joins First-class Rare / discouraged
Transactions ACID across rows & tables Usually single-row only
Scaling Vertical first; horizontal harder Horizontal native
Sweet spot Money, orders, anything multi-entity with strong invariants High write throughput, denormalized read models, flexible JSON
Examples PostgreSQL, MySQL, SQL Server DynamoDB, Cassandra, MongoDB, Redis

NoSQL sub-types

  • Key-Value (Redis, DynamoDB): O(1) get/set by key. Sessions, caches, leaderboards.
  • Document (MongoDB): JSON docs by key, secondary indexes on fields. Product catalogs, user profiles.
  • Wide-column (Cassandra, BigTable): trillions of rows, designed for time-series / event logs.
  • Graph (Neo4j): relationships are first-class. Social graphs, fraud detection.
  • Search (Elasticsearch, OpenSearch): inverted index for full-text queries.
Industry rule of thumb: start with PostgreSQL unless you can articulate a specific reason another store fits better. Most "we need NoSQL for scale" early decisions become regret stories.

Indexes — the cheapest 100× speedup

An index is a sorted side-structure (typically a B-tree) that lets the DB find rows without scanning the whole table.

With an index on users.email

Query: WHERE email = 'a@b.com' → O(log n) via B-tree.

10M rows ≈ 23 hops.

Without

DB does a full table scan: O(n).

10M rows ≈ 10M comparisons → seconds per query → outage at any real traffic.

Costs

  • Every INSERT/UPDATE/DELETE updates the index too → writes get slower.
  • Each index uses disk + RAM (the hot pages live in buffer pool).
  • Composite index on (a, b, c) helps queries filtering by a, or a + b, or a + b + c — but not by b alone.

Rule: index every column you frequently filter or join on; drop unused indexes.

Replication — fault tolerance + read scaling

Replication = keep N copies of the data on different nodes.

Topologies

  • Single-leader (primary / replica): all writes go to primary; async stream to replicas. Most common (Postgres, MySQL).
  • Multi-leader: writes accepted on multiple nodes (e.g., multi-DC active-active). Conflict resolution required.
  • Leaderless: any node accepts any write; quorum-based reads reconcile (Cassandra, DynamoDB).

What it buys you

  • Fault tolerance: lose a node, others keep serving.
  • Read scaling: send read queries to replicas. Writes still bottleneck on primary.
  • Geographic latency: put replicas closer to users.

What it costs

  • Replication lag. Replica might be 500 ms behind primary. "I just wrote a comment and it's not in my feed" — classic bug.
  • Conflict resolution (multi-leader / leaderless).

Sharding — write scaling when one machine isn't enough

Sharding = split the data horizontally across N machines by a shard key. Each shard owns a slice of the keyspace.

Shard key strategies

Strategy How Watch out
Hash-based shard = hash(user_id) % N Even spread; range queries become scatter-gather. Resharding is hard.
Range-based Users A–F → shard 1, G–M → shard 2… Range queries are local. Hot ranges create hot shards.
Geo-based Shard by region Latency wins; cross-region queries painful.
Consistent hashing Place shards on a ring; only neighbors affected when adding nodes Required for cache clusters & many NoSQL stores.
Hot-shard story: Twitter sharded by user_id. Then Justin Bieber became 1% of all traffic. His shard burned. Lesson: any time you have celebrities (or "celebrity keys"), have a strategy: read replicas of that shard, cache, or split that user across multiple shards.

Caching strategies

A cache is a faster, smaller copy of slower data. Memory is ~200× faster than disk; a 90% cache hit ratio can reduce backend load by 10×.

Pattern How Use when
Cache-aside (lazy load) App checks cache; on miss queries DB and writes to cache. Default for read-heavy apps.
Read-through Cache library transparently loads from DB on miss. Same as cache-aside but hidden behind a library.
Write-through Every write goes to cache and DB synchronously. Need strong consistency between cache & DB.
Write-behind (write-back) Write to cache; flush to DB asynchronously. Very write-heavy; tolerate small data loss window.
Refresh-ahead Cache proactively refreshes hot keys before they expire. Predictable hot keys; latency-critical.

Eviction policies

LRU (least recently used) is the default and works well 90% of the time. LFU (least frequently used) better for skewed access. TTL (time to live) absolutely necessary on any cached entry that can become stale.

Cache invalidation — the hard problem

"There are only two hard things in CS: cache invalidation and naming things." — Phil Karlton. He wasn't joking.
  • On write: invalidate (delete) the cache entry, don't update it. Update under concurrency causes stale-vs-new races.
  • Use short TTLs (~minutes) as a safety net for any cache.
  • Version your cache keys when the data shape changes — easier than mass-flushing.

CDN — caching at the edge

A CDN (Content Delivery Network) is a globally distributed cache for static assets and increasingly for API responses. Cloudflare, Akamai, CloudFront.

What if you use a CDN: users in Mumbai download a JS bundle from Mumbai (5 ms) instead of Virginia (200 ms). 95% of your image/JS/CSS traffic never touches your origin.

What if you don't: every static request hits your servers and your bandwidth bill. Your latency is dominated by physics (speed of light × half the globe).

Anti-patterns interviewers love to call out

  • "Just add a cache" without thinking about invalidation. Stale data is worse than slow data in finance / healthcare.
  • Cache stampede: 1000 clients hit an expired key simultaneously, all miss, all hammer the DB at once. Fix: request coalescing or jittered TTL.
  • N+1 queries: fetch a list, then one query per item. Pre-join or batch.
  • Unbounded query (no LIMIT): works on dev with 100 rows, falls over on prod with 100M.
  • Sharding too early when a single Postgres would have handled it for years.
