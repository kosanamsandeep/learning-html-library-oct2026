The four classic LLD interview problems

LLD Case Studies — walked end-to-end

Each case study follows the same 5-step recipe: clarify → identify nouns → identify behaviors → wire relationships → call out tradeoffs. Practice this recipe; it works for any problem an interviewer can throw at you.

Cases

  1. The 5-step recipe
  2. Parking Lot
  3. Elevator System
  4. Library Management
  5. ATM Machine
  6. Common takeaways

The 5-step recipe

  1. Clarify requirements. Functional (what it does) + non-functional (scale, latency, concurrency). Ask 3–5 questions before writing anything.
  2. Identify the nouns. They usually become classes.
  3. Identify the verbs. They become methods on those classes.
  4. Wire relationships. Composition, association, inheritance, multiplicities.
  5. Call out tradeoffs. "I chose X because… I'd switch to Y if…". This is what separates senior from junior answers.

Parking Lot

Clarify

  • Multi-level lot? Yes, 4 floors.
  • Multiple spot sizes? Compact, regular, large, EV.
  • Pricing? Hourly, varies by spot type.
  • Payment? Cash + card + UPI.
  • Capacity? ~1000 spots; 100 entries/min peak.

Nouns → classes

ParkingLot, Floor, ParkingSpot, Vehicle, Ticket, EntryGate, ExitGate, Payment, PricingStrategy.

Class skeleton

class VehicleType(Enum): CAR, BIKE, TRUCK, EV
class SpotType(Enum):    COMPACT, REGULAR, LARGE, EV

class Vehicle:
    plate: str; type: VehicleType

class ParkingSpot:
    id: str; type: SpotType; floor: int; is_free: bool
    def assign(self, vehicle): ...
    def release(self): ...

class Floor:
    number: int; spots: list[ParkingSpot]
    def find_free_spot(self, type: SpotType) -> ParkingSpot | None: ...

class ParkingLot:                                    # facade
    floors: list[Floor]
    def park(self, vehicle: Vehicle) -> Ticket: ...
    def unpark(self, ticket: Ticket) -> Payment: ...

class Ticket:
    id: str; spot: ParkingSpot; entry_time: datetime

class PricingStrategy(ABC):                          # Strategy pattern
    def price(self, ticket: Ticket, exit_time): ...

class HourlyPricing(PricingStrategy): ...
class FlatDayPricing(PricingStrategy): ...

class PaymentProcessor(ABC):                         # DIP
    def charge(self, amount, method): ...

Sequence — happy path

Driver → EntryGate.scan(plate)
        → ParkingLot.park(vehicle)
            → Floor.find_free_spot(spot_type)
            → spot.assign(vehicle)
            → Ticket(id, spot, now())
        ← Ticket returned, gate opens

Driver → ExitGate.present(ticket)
        → ParkingLot.unpark(ticket)
            → PricingStrategy.price(ticket, now())
            → PaymentProcessor.charge(amount, method)
            → spot.release()
        ← receipt, gate opens

Tradeoffs an interviewer wants to hear

  • "I used Strategy for pricing so we can switch from hourly to dynamic without touching ParkingLot." (OCP)
  • "Spot search per floor is O(n). At 1000 spots that's fine; at 100,000 I'd maintain a per-type free-list / min-heap on each floor."
  • "Concurrency: two drivers at the gate could be assigned the same spot. I'd put the spot assignment under a lock or use compare-and-set in DB."
  • "Failure: payment failure shouldn't release the spot. Use a state machine on Ticket: ISSUED → PAID → RELEASED."

Elevator System

Clarify

  • How many elevators? 4 cars, 20 floors.
  • External (hall) buttons + internal (cabin) buttons? Yes.
  • Optimization goal? Minimize average wait time.

Nouns → classes

Building, Elevator, ElevatorController, Request (Hall / Cabin), Direction (UP/DOWN/IDLE), State (MOVING/STOPPED/MAINTENANCE).

Class skeleton

class Direction(Enum): UP, DOWN, IDLE
class State(Enum):     MOVING, STOPPED, MAINTENANCE

class Request:
    floor: int; direction: Direction        # hall request
    # OR target_floor: int                  # cabin request

class Elevator:
    id: int; current_floor: int
    direction: Direction; state: State
    requests: SortedSet[int]               # next stops
    def add_request(self, floor: int): ...
    def step(self): ...                    # move one floor per tick

class DispatchStrategy(ABC):               # Strategy
    def pick_elevator(self, elevators, request) -> Elevator: ...

class NearestCarStrategy(DispatchStrategy): ...
class GroupControlStrategy(DispatchStrategy): ...

class ElevatorController:                  # facade
    elevators: list[Elevator]
    strategy: DispatchStrategy
    def request(self, hall_request): ...
    def press_floor(self, elevator_id, target): ...

State machine for one elevator

IDLE ── request arrives ──▶ MOVING
MOVING ── reached target floor ──▶ STOPPED (open doors, 3s)
STOPPED ── more requests? ──▶ MOVING
STOPPED ── no requests ──▶ IDLE
ANY ── fault ──▶ MAINTENANCE

Tradeoffs

  • "Nearest car" minimizes wait for a single rider but causes thrashing under high load; "group control" reserves elevators per direction batch.
  • I/O concern: the controller is the producer; each elevator runs its own loop (thread / actor). Communication via thread-safe queues.
  • Edge: emergency stop, fire mode (recall to ground), VIP override.

Library Management System

Clarify

  • Multiple copies per book? Yes — copy is a distinct entity.
  • Reservations / holds? Yes.
  • Fines for late return? $0.50/day after due date.

Class skeleton

class Book:               # title-level metadata
    isbn: str; title: str; authors: list[str]

class BookCopy:           # the physical item
    id: str; book: Book; status: CopyStatus  # AVAILABLE/LOANED/RESERVED/LOST

class Member:
    id: str; name: str
    loans: list[Loan]; reservations: list[Reservation]
    def can_borrow(self) -> bool: ...        # max 5 active loans

class Loan:
    copy: BookCopy; member: Member
    issued_at: datetime; due_at: datetime; returned_at: datetime | None
    def fine(self) -> float: ...

class Reservation:
    book: Book; member: Member; placed_at: datetime

class Library:                                  # facade
    catalog: Catalog
    def borrow(self, member, isbn): ...
    def return_copy(self, loan): ...
    def reserve(self, member, isbn): ...
    def search(self, query) -> list[Book]: ...

class Catalog:
    def by_isbn(self, isbn): ...
    def search(self, query): ...                # full-text / index

Tradeoffs

  • Distinguish Book (catalog entry) from BookCopy (physical item). Confusing them is the #1 modeling mistake interviewers look for.
  • Fines via Strategy: FineStrategy can be flat, tiered, or waived for certain member types.
  • When a copy is returned and someone has reserved it, fire an OnHold event (Observer) so the reserver is notified.

ATM Machine

Clarify

  • Operations? balance check, withdraw, deposit, transfer.
  • Authentication? card + PIN, max 3 tries.
  • Hardware abstraction? Yes — same software for different ATM models.

Class skeleton

# Hardware abstractions (DIP) — software depends on these, not concrete drivers
class CardReader(ABC):    def read_card(self): ...
class Keypad(ABC):        def read_pin(self): ...
class CashDispenser(ABC): def dispense(self, amount): ...
class DepositSlot(ABC):   def accept(self): ...
class Screen(ABC):        def show(self, msg): ...

class Card:
    number: str; expiry: date

class Session:                              # one user's visit
    card: Card; account: Account
    def authenticate(self, pin): ...

class Transaction(ABC):                      # Command pattern
    def execute(self): ...
    def rollback(self): ...

class WithdrawTx(Transaction): ...
class DepositTx(Transaction): ...
class TransferTx(Transaction): ...

class BankService(ABC):                      # remote bank API
    def get_balance(self, acc): ...
    def debit(self, acc, amount): ...
    def credit(self, acc, amount): ...

class ATM:
    state: ATMState
    hw: dict   # card_reader, keypad, dispenser, …
    bank: BankService
    def run(self): ...

State diagram

IDLE ── card inserted ──▶ AUTHENTICATING
AUTHENTICATING ── 3 wrong pins ──▶ CARD_RETAINED ──▶ IDLE
AUTHENTICATING ── pin ok ──▶ MENU
MENU ── choose op ──▶ TRANSACTING
TRANSACTING ── done ──▶ MENU
MENU ── eject ──▶ IDLE

Tradeoffs

  • Command pattern on transactions: makes them undoable, logable, retriable.
  • Hardware as abstract base classes means the same software supports new ATM models — only new driver classes are added (OCP).
  • Network failure during withdraw: don't debit account if dispense failed. Implement idempotent debit(tx_id, …) so retries are safe.

Common takeaways across all four

  1. Strategy appears everywhere: pricing, dispatch, fines.
  2. State machine appears anywhere with a lifecycle: ticket, order, elevator, session.
  3. Facade at the entry point: ParkingLot, Library, ATM, ElevatorController.
  4. DIP at integration boundaries: payment processor, bank API, hardware drivers — define the interface in your code, not in their SDKs.
  5. Concurrency + idempotency deserve at least one sentence in every answer. Interviewers reward it.
