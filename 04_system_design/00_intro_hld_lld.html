What is System Design — and why are there two of them?

"System design" is an umbrella term. In product-company interviews and on the job, it splits cleanly into two skills. They use different vocabularies and they're judged differently.

The story Why this matters

Scene: Your interviewer says "design a parking lot". You start talking about load balancers and Redis. They get confused and end the round. Different interviewer, different day, says "design Instagram". You start drawing classes for Post and User. They get confused and end the round. Same skill, wrong layer.

This is the whole reason we separate Low-Level Design (LLD) from High-Level Design (HLD). Each answers a different question:

  • LLD — "What are the objects in this system and how do they collaborate?" Output is a class diagram and method signatures.
  • HLD — "What are the services in this system, what data store does each use, and how does traffic flow?" Output is a boxes-and-arrows architecture diagram.

Side-by-side comparison

Dimension Low-Level Design (LLD) High-Level Design (HLD)
Unit of thinking Class, method, attribute Service, datastore, queue, network
Output artifact UML class diagram, sequence diagram, code skeleton Architecture diagram, capacity estimates, data model sketch
Typical question "Design a parking lot / elevator / chess game" "Design Twitter / WhatsApp / Uber for 100M users"
Time scale 1 machine, in-process objects Many machines, network in between
Key concepts OOP, SOLID, design patterns, polymorphism, state machines Scalability, sharding, caching, replication, CAP, consistency, latency budgets
Failure modes interviewers test for God classes, tight coupling, missing abstraction, leaky interfaces Single point of failure, hot shards, unbounded queues, missing back-pressure
Where it shows up at work Code reviews, refactoring, adding a new feature to a service RFCs, architecture reviews, new service kickoff, scaling incidents

What if you only learn one?

Only HLD, no LLD

You can draw any famous system on a whiteboard, but every PR you raise gets review comments about god classes, missing interfaces, and untestable code. You can't actually build the things you design. You get hired at senior level then struggle in sprint work.

Only LLD, no HLD

Your code is beautiful in isolation. But you suggest a single-database design that falls over at 10× current traffic, or you propose a synchronous call where the right answer is a queue. You stall at the IC3/SDE2 level because architecture rounds keep blocking you.

You need both. Interviews test them in separate rounds; real jobs require you to fluidly zoom in and out across them.

How a senior engineer actually thinks Industry framing

  1. Clarify the problem. What are the functional and non-functional requirements? What's the scale (QPS, users, data size)?
  2. Estimate. Back-of-envelope: how many requests/sec? how much storage/day? how much memory for a cache?
  3. Pick the high-level shape (HLD). Which services, which data stores, where does the cache go, do we need a queue.
  4. Zoom into the risky service (LLD). Sketch the classes / domain model for the part that's most likely to evolve.
  5. Discuss tradeoffs. What did you optimize for? What did you give up?
  6. Identify failure modes. What breaks first? How do you detect it? How do you recover?

This 6-step loop is the same whether you're in an interview or in a real architecture review meeting. Internalize it; you'll never freeze again.
