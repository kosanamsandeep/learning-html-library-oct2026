The five canonical interview problems

Famous System Designs — URL Shortener, Twitter, WhatsApp, Uber, YouTube

Every one of these uses the same primitives (LB, cache, DB, queue, sharding, CDN) wired differently. Learn one and the next is 50% easier.

The HLD interview recipe

  1. Functional requirements — what does it do? (Bullet list, 3–5 items.)
  2. Non-functional requirements — scale, latency, consistency, availability targets.
  3. Capacity estimation — QPS, storage/day, bandwidth, memory for cache.
  4. High-level architecture — boxes and arrows: clients, LB, services, stores, queues.
  5. Data model — the 2–3 tables that matter.
  6. Deep dive into the bottleneck — usually one part: feed generation, geo-search, video upload pipeline.
  7. Tradeoffs and failure modes — what breaks first, how you detect, how you recover.

Each case below uses this recipe so you can pattern-match in your own answers.

URL Shortener (TinyURL / bit.ly)

Functional

  • POST a long URL → get a 7-char short URL.
  • GET short URL → 301 redirect to long URL.
  • Click analytics (optional).

Non-functional

  • Read:write ratio ~100:1.
  • 500M new URLs/month → ~200 writes/sec; 50B redirects/month → ~20k reads/sec.
  • Redirect p99 latency < 100 ms (it's a click).
  • 5 years retention → ~30B URLs; ~500 bytes each → ~15 TB.

Design

[client] → [CDN] → [LB] → [redirect svc] ──┐
                                            ├→ [Redis cache] ── miss ──┐
                                            │                          ▼
                                            └→ [shorten svc]          [URL DB] (sharded by short_id)
                                                  │
                                                  └→ [ID generator] (counter shards or base62 hash)

Short ID generation — the deep dive

Approach Pros Cons
Hash long URL → base62 Stateless, deterministic Collisions need handling.
Auto-increment counter → base62 No collisions; predictable Counter is a SPOF; predictable IDs leak business metrics.
Counter sharded (each shard gets a range of IDs) Scales; no SPOF Complexity.
Snowflake-style 64-bit ID Time-ordered, globally unique Longer than 7 chars unless re-encoded.

Tradeoffs

  • Redirect path is 99% cache hits (Redis), so it's microseconds.
  • Sharding by short_id spreads load evenly; range queries don't matter.
  • Analytics → write events to Kafka, batch process — keep redirect path tiny.

Twitter Newsfeed

The core question

How do you show a user the most recent tweets from the 500 accounts they follow, in < 100 ms, at hundreds of thousands of QPS?

Two extreme approaches

Pull (fan-out on read)

On feed request: query "tweets where author in (my_followees) order by time".

Simple. Writes are cheap. But each feed read = 500 lookups + a sort.

Breaks at scale.

Push (fan-out on write)

On tweet write: insert into the personal feed cache of every follower.

Read = trivial cache fetch. But Justin Bieber tweets → 100M cache writes.

Breaks for celebrities.

Hybrid (the real answer)

  • Push for normal users (median followers ~200).
  • Pull for celebrities (defined as > 1M followers). At read time, merge pushed-feed + celebrity-pull.

Architecture

[client] → [LB] → [feed svc] ── reads ──▶ [Redis: per-user timeline]
                       │
                       └── reads celebrity tweets ──▶ [tweet DB]

[write] → [tweet svc] ──┬─▶ [tweet DB]            (source of truth)
                        │
                        └─▶ [fanout worker] (Kafka) ─▶ writes to each follower's Redis timeline
                                                       (skips if author is "celebrity")

Tradeoffs

  • Eventual consistency: a tweet may take a few seconds to appear in followers' feeds. Acceptable.
  • Storage: each tweet × N followers in cache is huge — TTL old timelines, only keep the active users hot.
  • Sharding: tweets by tweet_id (hash); timelines by user_id (hash).

WhatsApp / Chat System

Functional

  • 1:1 messaging, group chats, online presence, last-seen, delivery receipts.
  • End-to-end encryption (signal protocol — out of scope here).

The key abstraction — long-lived connections

WhatsApp keeps a persistent WebSocket (or XMPP) connection per online user. Each connection lives on a "chat server". A user is always associated with exactly one chat server while online.

[mobile app] ── WebSocket ──▶ [chat-server-N]
                                    │
                                    ├─▶ [presence service: Redis] (user → chat-server-N)
                                    ├─▶ [message store: Cassandra]  (sharded by conversation_id)
                                    └─▶ [Kafka] (for notifications, analytics)

Sending a message

  1. Alice's app sends msg(to=Bob) over her WebSocket to chat-server-3.
  2. Server persists message to Cassandra.
  3. Server looks up Bob in presence service → "Bob is on chat-server-7".
  4. Server forwards message to chat-server-7 which pushes it down Bob's socket.
  5. If Bob is offline: push via APNs/FCM; on next login, server delivers backlog.

Group chats

Repeat step 3–4 for each member. Group of 256 = 256 routes. Fan-out lives on the sender's server.

Tradeoffs

  • Online presence: cheap because of the persistent connection — heartbeat every 30s refreshes the entry; expire after 60s.
  • Read receipts: just ack messages back, fan out the same way.
  • Storage: messages stored in Cassandra (write-heavy, time-series friendly).

Uber Dispatch

Functional

  • Match rider to nearby driver.
  • Track driver location in real time.
  • ETA + price estimate.

The hard part — geo-search at scale

1M drivers send location updates every 4 seconds → 250k writes/sec. For each ride request, find drivers within 5 km. Naive "scan all drivers" is dead on arrival.

The trick — geo-sharding with QuadTree / S2 / Geohash

The world is divided into a hierarchical grid of cells. Each driver lives in the cell covering their current GPS coordinate. To find drivers near a point, you query that point's cell + neighbors.

[driver app] → [location svc] → [Redis Geo / Cassandra by geo-cell]
                                            ▲
[rider app] → [match svc] ──── query cell + 8 neighbors ──┘
                       │
                       └─▶ [pricing svc, ETA svc]

Architecture pillars

  • Per-city sharding. A driver in Bangalore never matches with a rider in NYC. Each city is its own deployment.
  • WebSocket from drivers. Constant location stream; persistent connection avoids HTTP overhead.
  • Kafka backbone. Location updates fan into matching, analytics, fraud detection separately.
  • Surge pricing = real-time stream processing over the demand /supply ratio per cell.

YouTube — upload, encode, serve

Functional

  • Upload videos.
  • Transcode to multiple resolutions + bitrates.
  • Serve to billions of viewers globally.
  • Recommendations, comments, likes (out of scope here).

Upload + encode pipeline

[creator] → [upload svc] → [S3: original.mp4]
                              │
                              └─▶ [Kafka: video.uploaded]
                                        │
                                ┌───────┼───────┬───────┐
                                ▼       ▼       ▼       ▼
                            [encoder] [encoder] [encoder] [encoder]   (workers, autoscaled)
                                │       │       │       │
                                ▼       ▼       ▼       ▼
                            [S3: 1080p] [720p] [480p] [240p]
                                │
                                ▼
                          [metadata DB updated: status = READY]
                                │
                                ▼
                          [CDN warmup for popular regions]

Serving

[viewer] → [edge CDN] ── 99% hit ──▶ video chunk
                ▲ miss
                │
       [origin storage: S3] (cold)

Most bytes never touch YouTube's origin — they're served from CDN PoPs near the viewer.

Tradeoffs

  • Adaptive bitrate (HLS / DASH) so the player switches resolution based on bandwidth — small chunks (~10s) per resolution.
  • Hot videos pre-warmed to CDN; long tail served from origin on first hit.
  • Storage cost is enormous; tiered storage (S3 → Glacier for cold).

Common follow-up: design the recommendation pipeline

  • Batch: Spark job nightly trains a recommendation model from watch-history.
  • Online: at request time, fetch top-N candidates from a feature store; re-rank with a smaller online model.
  • Feature store: precomputed per-user / per-video features in Redis-like store.

Closing — the pattern across all five

  1. Read/write ratio determines whether you precompute (Twitter) or query on the fly (URL shortener).
  2. Geographic concerns drive sharding (Uber by city, YouTube via CDN).
  3. Async queues decouple the slow path (encoding, fanout, analytics).
  4. Cache is always the answer to "make reads faster".
  5. Every answer ends with: "what breaks first, how do we detect it, how do we recover".
