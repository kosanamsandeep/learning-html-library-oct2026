Load Balancers — the front door

A load balancer sits in front of your service pool and distributes incoming requests across instances. Without one, you can't scale horizontally.

L4 vs L7

Layer Sees Examples When
L4 (TCP) IPs, ports — no HTTP knowledge AWS NLB, HAProxy TCP mode Raw TCP services, ultra-low latency.
L7 (HTTP) URL path, headers, cookies NGINX, AWS ALB, Envoy Routing by path (/api/orders → orders svc), TLS termination, sticky sessions.

Algorithms

  • Round-robin — simple, ignores load.
  • Least connections — sends to instance with fewest in-flight. Good default.
  • Weighted — for heterogeneous instance sizes.
  • Consistent hashing — sticky-by-key (e.g. always send user X to the same cache node).
The load balancer itself is a SPOF unless you run it in active-active with DNS or anycast in front. AWS ALB does this for you; self-managed setups need it explicit.

Message Queues — decoupling producer from consumer

A queue lets one service produce events and another consume them at its own pace.

Synchronous (no queue)

OrderService.place() calls payment, inventory, email, analytics one after another. Total latency = sum of all. Email service down → order fails.

Async (with queue)

OrderService.place() writes an OrderPlaced event to a queue and returns to the user. Email, analytics, warehouse consume independently. Email down → message sits in queue, retried later.

Tools by mental model

Tool Model Use when
Kafka Distributed log; consumers track their own offset; messages retained for days Event streaming, audit trail, multiple consumers need the same events.
RabbitMQ Classic queue with ack/nack, exchanges, routing Task queues; rich routing rules.
AWS SQS Managed queue, FIFO or standard Default for AWS workloads; no ops.
Redis Streams Lightweight log inside Redis Already using Redis; lower scale.

Delivery guarantees

  • At-most-once: message may be lost; never duplicated.
  • At-least-once: never lost; may be duplicated. → consumers MUST be idempotent.
  • Exactly-once: rare and expensive (transactional outbox + dedup).
Idempotency is non-negotiable in any async architecture. Tag each message with an event_id; consumer dedups by storing seen ids.

Microservices — when and when not

Microservices = split your app into small services, each owning one bounded context, each deployable independently.

When microservices help

  • Multiple teams (50+ engineers) — each owns a service.
  • Different scaling needs per domain (recommendations is GPU-heavy; catalog is read-heavy).
  • Different tech stacks per problem (Python ML, Go gateway, Java legacy).

When they hurt

  • 10-person team — coordination overhead exceeds the gain.
  • Shared database across services (you've made a "distributed monolith", worst of both worlds).
  • Synchronous chains of 5+ calls — latency and failure compound.

2024 industry pulse: "Modular monolith first; extract services when you have a reason". Many famous teams (Shopify, GitHub) run modular monoliths successfully at huge scale.

API Gateway — the single front door for microservices

Sits in front of all internal services. Responsibilities:

  • Authentication / authorization
  • Rate limiting
  • Request routing (path-based)
  • Request/response transformation
  • Logging, metrics, tracing
  • SSL termination

Examples: Kong, AWS API Gateway, Envoy, NGINX. Without one, every microservice re-implements auth and rate limits.

CAP theorem — pick two (kind of)

In a distributed system you can guarantee at most two of:

  • Consistency — every read sees the latest write.
  • Availability — every request gets a (non-error) response.
  • Partition tolerance — the system keeps working if the network splits.

P is not optional — networks fail. So in practice you choose CP or AP:

Class Behavior on partition Examples
CP Reject requests rather than return stale data HBase, MongoDB (with majority writes), ZooKeeper, etcd
AP Keep accepting requests; reconcile later Cassandra, DynamoDB (default), CouchDB

How to pick: ask "which is worse — a wrong answer or no answer?"

  • Money / inventory / medical → CP (no answer is safer).
  • Social feed / shopping cart / "people you may know" → AP (some staleness OK).

Consistency models — finer than C / not-C

  • Strong consistency — reads see the latest committed write. Expensive coordination.
  • Eventual consistency — given no new writes, all replicas eventually converge.
  • Read-your-writes — you always see your own latest write (even if others don't yet). Cheap UX win.
  • Monotonic reads — once you see version N, you never see < N again.
  • Causal consistency — operations causally related to each other are seen in the same order everywhere.

Most user-facing systems use eventual + read-your-writes: cheap, scalable, users don't notice replication lag because they always see their own actions instantly.

Observability — the three pillars

  • Logs — discrete events. Structured JSON, searchable (ELK, Loki).
  • Metrics — time-series numbers. RED (Rate, Errors, Duration) for services; USE (Utilization, Saturation, Errors) for resources. Prometheus + Grafana.
  • Traces — follow one request across services. OpenTelemetry, Jaeger, Tempo.

If your HLD answer doesn't mention these, the interviewer will assume you've never run a service in production.
