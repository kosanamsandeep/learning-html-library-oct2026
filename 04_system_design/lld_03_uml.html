Just enough UML to communicate, no more

UML — the parts that actually appear on whiteboards

You don't need to memorize all 14 UML diagram types. In real interviews and PRs, three diagrams cover 95% of cases: Class diagram, Sequence diagram, and State diagram.

1. Class diagram — "what objects exist and how are they wired"

Use it when designing static structure. Each box = a class. Lines = relationships.

Box notation

┌──────────────────────────┐
│       Account            │  ← class name
├──────────────────────────┤
│ - id : str               │  ← attributes (- private, + public, # protected)
│ - balance : float        │
├──────────────────────────┤
│ + deposit(amt) : void    │  ← methods
│ + withdraw(amt) : void   │
│ + balance() : float      │
└──────────────────────────┘

Relationship arrows you need

Arrow Meaning Example
──▷ (hollow triangle) Inheritance ("is-a") SavingsAccount ──▷ Account
┄┄▷ (dashed triangle) Implements interface EmailNotifier ┄┄▷ Notifier
──◆ (filled diamond) Composition (owns, dies with) Order ◆── OrderLine (order owns lines)
──◇ (hollow diamond) Aggregation (uses, outlives) University ◇── Student
───▶ (open arrow) Association (knows about) Order ───▶ Customer
┄┄┄▶ (dashed open) Dependency (uses temporarily) OrderService ┄┄▶ Logger

Multiplicities

  • 1 — exactly one
  • 0..1 — zero or one (optional)
  • * or 0..* — many
  • 1..* — one or more

Example: Order 1 ───▶ * OrderLine means one order has many lines.

Worked example — a tiny banking system

┌──────────────┐         ┌───────────────┐
│  Customer    │ 1     * │   Account     │
│──────────────│─────────│───────────────│
│ - id         │ owns    │ - id          │
│ - name       │         │ - balance     │
└──────────────┘         │ + deposit()   │
                         │ + withdraw()  │
                         └───────┬───────┘
                                 △  (is-a)
                ┌────────────────┼────────────────┐
                │                │                │
        ┌───────┴──────┐  ┌──────┴───────┐  ┌─────┴────────┐
        │ Savings      │  │ Checking     │  │ Credit       │
        │ + interest() │  │ + overdraft()│  │ + limit      │
        └──────────────┘  └──────────────┘  └──────────────┘

2. Sequence diagram — "what happens, in what order, when X is called"

Use it when explaining a flow: a use case end-to-end across multiple objects.

Client          OrderService     PaymentSvc    Inventory      EmailSvc
  │                  │                │            │              │
  │ place(order) →   │                │            │              │
  │                  │ reserve(items) →            │              │
  │                  │  ←── ok        │            │              │
  │                  │ charge(amount) →            │              │
  │                  │  ←── success    │           │              │
  │                  │ commit_reserve  →           │              │
  │                  │ send_confirmation ─────────────────────────→
  │  ←── orderId     │                │            │              │
  • Vertical lines = lifelines (one per object).
  • Horizontal arrows = messages (calls).
  • Time flows top → bottom.
  • Dashed arrows = returns.

3. State diagram — "what states can this thing be in, and how does it move"

Use it for any entity with a lifecycle: Order, Subscription, JIRA Ticket, Job.

        (start)
           │
           ▼
       ┌────────┐  place_order   ┌────────┐
       │ DRAFT  │ ─────────────▶ │ PLACED │
       └────────┘                └───┬────┘
                                    │ ship
                                    ▼
                                ┌────────┐
                                │SHIPPED │
                                └───┬────┘
                                    │ deliver
                                    ▼
                                ┌─────────┐
                                │DELIVERED│  (end)
                                └─────────┘
       (from anywhere) ── cancel ──▶ CANCELLED

This diagram answers a question interviewers love: "what's the invariant — can an Order go from DELIVERED back to PLACED?" If your design allows nonsense transitions you have a bug.

How to draw under interview pressure

  1. Names first. Drop the boxes for the major nouns in the problem statement.
  2. Relationships next. One pencil pass to connect them. Don't worry about arrow types yet.
  3. Methods third. Only the methods you'll actually call in the use case.
  4. Multiplicities last. Add 1, *, 0..1 at the end — they catch design bugs.

Final tip: tools like draw.io, Lucidchart, Mermaid render the same shapes from text. For PR descriptions, embed a Mermaid classDiagram block — reviewers love it.
