LLD foundations

OOP & SOLID — the only foundation that matters for LLD

SOLID and OOP are the two halves of Low-Level Design. OOP gives you the vocabulary (class, object, inheritance, polymorphism). SOLID gives you the discipline — which classes to create, what each one should do, and how to keep them changeable without rewriting the world.

OOP — the four pillars, in plain English

Story: You build a banking app. Without OOP, every function takes 12 parameters: account_id, balance, owner, type, frozen, transaction_count, …. Add one field and 80 functions break. With OOP, you bundle them into an Account object and the world stops shaking when a field changes.
Pillar One-line definition Banking example
Encapsulation Bundle data + behavior; hide internals. account.deposit(100) instead of account.balance += 100.
Abstraction Expose what, hide how. Caller sees transfer(from, to, amt); doesn't know about ledgers, locks, retries.
Inheritance "Is-a" relationship; share common behavior. SavingsAccount is-a Account; gets deposit/withdraw for free.
Polymorphism One interface, many implementations. account.calculate_interest() works for any subclass.

Encapsulation — what if you skip it

No encapsulation

account.balance -= 100   # ← caller manipulates state directly
# What if balance goes negative? No one validates.
# What if you want to log every withdrawal? Search the codebase.

With encapsulation

class Account:
    def __init__(self, owner):
        self._balance = 0           # _ = "internal"

    def withdraw(self, amount):
        if amount > self._balance:
            raise InsufficientFunds()
        self._balance -= amount
        self._log("withdraw", amount)

Inheritance vs Composition — the 2024 industry stance

Prefer composition over inheritance. Inheritance is rigid: once SavingsAccount extends Account, changing the parent ripples into every child. Composition (one class holds another) is flexible and testable.

Inheritance — fragile

class PremiumSavings(SavingsAccount):
    def calculate_interest(self):
        return super().calculate_interest() * 1.5

If SavingsAccount changes its formula, PremiumSavings silently behaves wrong.

Composition — flexible

class Account:
    def __init__(self, interest_strategy):
        self._interest = interest_strategy

    def calculate_interest(self):
        return self._interest.compute(self._balance)

Swap the strategy at runtime. Test the strategy in isolation. No hierarchy to maintain.

SOLID — the five principles

SOLID is a checklist. When a class feels wrong, run through it and one of the five will tell you why.

Letter Principle One-line test
S Single Responsibility "What's the one reason this class would change?"
O Open/Closed "Can I add a new variant without editing existing code?"
L Liskov Substitution "Can I swap a subclass for the parent without surprises?"
I Interface Segregation "Is every method on this interface useful to every implementer?"
D Dependency Inversion "Does high-level code depend on abstractions, not concretes?"

S — Single Responsibility Principle

"A class should have one, and only one, reason to change."

Violates SRP

class Invoice:
    def calculate_total(self): ...
    def save_to_db(self): ...
    def send_email(self): ...
    def render_pdf(self): ...

Four reasons to change: pricing rules, DB schema, email template, PDF layout.

Respects SRP

class Invoice:                # domain
    def calculate_total(self): ...

class InvoiceRepository:      # persistence
    def save(self, invoice): ...

class InvoiceMailer:          # notification
    def send(self, invoice): ...

class InvoicePdfRenderer:     # rendering
    def render(self, invoice): ...

What if you don't follow SRP? The class becomes the merge-conflict magnet of the codebase — three developers editing it for unrelated reasons every sprint. Tests touch four concerns and break for the wrong reasons.

O — Open / Closed Principle

"Software entities should be open for extension, closed for modification." New behavior arrives as new code, not edits to existing tested code.

Closed for extension

class AreaCalculator:
    def area(self, shape):
        if shape.type == "circle":
            return 3.14 * shape.r ** 2
        elif shape.type == "square":
            return shape.side ** 2
        # adding triangle? edit this file
        # adding hexagon?  edit this file again

Open for extension

class Shape(ABC):
    @abstractmethod
    def area(self): ...

class Circle(Shape):
    def area(self): return 3.14 * self.r ** 2

class Square(Shape):
    def area(self): return self.side ** 2

# adding Triangle = NEW file, no edits

What if you don't follow OCP? Every new feature is a regression risk because you touched code other features depend on. Tests get re-run for the wrong files; production bugs appear in untouched-looking code.

L — Liskov Substitution Principle

"Subtypes must be substitutable for their base types without breaking the program."

Classic violation: Square extends Rectangle. Sounds OK — a square is a rectangle, right? But Rectangle lets you set width and height independently; Square can't. So set_width(5); set_height(10); assert area == 50 fails for squares. Inheritance hierarchy lies.

Test you can apply: read the parent class's method contracts (what does it promise, what does it require?). If the subclass weakens promises or strengthens requirements, it violates LSP.

Violates LSP

class Bird:
    def fly(self): ...

class Penguin(Bird):
    def fly(self):
        raise NotImplementedError("can't fly")

Now any function def make_fly(b: Bird) crashes when handed a Penguin.

Respects LSP

class Bird: ...                    # only common stuff
class FlyingBird(Bird):
    def fly(self): ...
class SwimmingBird(Bird):
    def swim(self): ...

class Penguin(SwimmingBird): ...

I — Interface Segregation Principle

"Clients should not be forced to depend on methods they do not use." Many small focused interfaces > one fat interface.

Fat interface

class Worker(ABC):
    def work(self): ...
    def eat(self): ...
    def sleep(self): ...

class HumanWorker(Worker): ...
class RobotWorker(Worker):
    def eat(self):  raise NotImplementedError  # forced
    def sleep(self): raise NotImplementedError # forced

Segregated interfaces

class Workable(ABC):
    def work(self): ...
class Eatable(ABC):
    def eat(self): ...
class Sleepable(ABC):
    def sleep(self): ...

class HumanWorker(Workable, Eatable, Sleepable): ...
class RobotWorker(Workable): ...

D — Dependency Inversion Principle

"Depend on abstractions, not concretions." High-level policy (your business logic) should not import low-level details (your database, your email vendor).

Tightly coupled

class OrderService:
    def __init__(self):
        self.db = MySQLConnection(...)
        self.mailer = SendGridClient(...)

    def place(self, order):
        self.db.insert(order)
        self.mailer.send(order.email, "Thanks!")

To unit test: spin up MySQL + SendGrid in CI. Painful and slow.

Inverted dependencies

class OrderRepository(ABC):    # abstraction
    def save(self, order): ...
class Mailer(ABC):
    def send(self, to, msg): ...

class OrderService:
    def __init__(self, repo: OrderRepository, mailer: Mailer):
        self.repo, self.mailer = repo, mailer
    def place(self, order):
        self.repo.save(order)
        self.mailer.send(order.email, "Thanks!")

In tests: inject fake implementations. In prod: inject real ones. Service code never changes.

This is the principle behind dependency injection frameworks (Spring, FastAPI's Depends, NestJS).

Code smells SOLID detects

Smell SOLID hint Fix
Class > 500 lines SRP Split by responsibility.
Long if/elif chain on a type OCP Polymorphism or Strategy pattern.
raise NotImplementedError in subclass LSP/ISP Wrong inheritance hierarchy or fat interface.
Tests need a live DB / network DIP Inject a repository abstraction.
"And" in class name (UserAndOrderService) SRP Split.

Daily checklist before merging a PR

  1. Each new class has a one-sentence purpose I can write down. (SRP)
  2. I added a new variant by writing a new class, not editing an old one. (OCP)
  3. Any subclass I added passes every test the parent passes. (LSP)
  4. Every method on the interface is used by every implementer. (ISP)
  5. My business class takes its dependencies via the constructor, not imports them. (DIP)
