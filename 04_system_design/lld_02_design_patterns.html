Industry-standard solutions to recurring problems

Design Patterns — the 12 that come up in every interview

A design pattern is a named shape for solving a problem you'll meet again. Patterns give your team a shared vocabulary: when you say "let's use a Strategy here", everyone knows the structure without you drawing it.

The Gang of Four catalogued 23 patterns. In practice, ~12 carry 90% of the value. Those are here, grouped by intent.

Creational patterns How objects are made

These patterns hide the "new" keyword. They decouple what object is created from how it's created. Useful when construction is complex or when the exact type isn't known until runtime.

Singleton

Intent: exactly one instance of a class, globally accessible.

Use when: shared resource manager (logger, config, connection pool).

class Logger:
    _instance = None
    def __new__(cls):
        if cls._instance is None:
            cls._instance = super().__new__(cls)
        return cls._instance

With Singleton

One logger across the app; one config read from disk; one connection pool — saves memory and avoids inconsistency.

Without (or overused)

Without: multiple loggers fight over a file handle. Overused: singletons are global state in disguise. Hard to test (can't swap). Often a Singleton should just be a dependency-injected regular object.

Industry pulse: singletons are out of fashion; prefer "create one and pass it around" via dependency injection.

Factory Method

Intent: a method that returns one of several related concrete types, letting subclasses decide which.

class Notification(ABC):
    def send(self, msg): ...

class EmailNotification(Notification): ...
class SmsNotification(Notification): ...
class PushNotification(Notification): ...

def notification_factory(channel: str) -> Notification:
    return {
        "email": EmailNotification(),
        "sms":   SmsNotification(),
        "push":  PushNotification(),
    }[channel]

What if you use it

Caller says "give me a notifier for SMS" and doesn't know about TwilioClient. Swap the SMS provider tomorrow — caller code unchanged.

What if you don't

Every call site has an if channel == "sms". Add WhatsApp in 2 years — touch 40 files.

Abstract Factory

Intent: a factory of factories. Produces a family of related objects that go together.

Real example: a UI toolkit that renders Buttons + Checkboxes + TextFields consistently per OS. WindowsFactory.button(), WindowsFactory.checkbox() vs MacFactory.button(), MacFactory.checkbox().

Use sparingly — only when you truly have multiple families that must stay consistent. Otherwise plain Factory Method is enough.

Builder

Intent: construct complex objects step by step. Useful when the constructor would need 10 parameters with sensible defaults.

pizza = (PizzaBuilder()
         .with_size("large")
         .add_topping("mushroom")
         .add_topping("olive")
         .with_crust("thin")
         .build())

With Builder

Reads like English. Optional params don't pile up. Each with_* can validate independently.

Without

Pizza("large", ["mushroom", "olive"], "thin", True, False, None, "marinara") — readers guess what arg 5 means.

Structural patterns How objects are composed

Adapter

Intent: make an existing class fit an interface you control.

Story: your code calls payment.charge(amount). You sign with a new vendor whose SDK exposes vendor.process_payment_v2(amt_in_cents). Don't rewrite your codebase — write a VendorAdapter that translates one call into the other.

Adapter is the most common pattern in the real world because every team integrates third-party SDKs.

Decorator

Intent: add behavior to an object without changing its class.

class Coffee:
    def cost(self): return 5

class WithMilk:
    def __init__(self, coffee): self.c = coffee
    def cost(self): return self.c.cost() + 1

class WithSugar:
    def __init__(self, coffee): self.c = coffee
    def cost(self): return self.c.cost() + 0.5

drink = WithSugar(WithMilk(Coffee()))   # cost = 6.5

What if you instead used inheritance? You'd need CoffeeWithMilk, CoffeeWithSugar, CoffeeWithMilkAndSugar, … a class explosion. Decorator composes at runtime.

Facade

Intent: a single simple entry point to a complicated subsystem.

Example: OrderFacade.place(order) internally calls inventory check, fraud check, payment, shipping, email. Callers see one method.

Most service classes in real codebases are facades over their domain.

Proxy

Intent: stand in front of an object to add behavior without the caller knowing — caching, lazy-loading, access control, logging.

Examples in the wild: ORM lazy-loading (a relation is a proxy until you touch it), HTTP caches, Spring AOP, RPC client stubs.

Behavioral patterns How objects communicate

Strategy

Intent: a family of interchangeable algorithms; pick one at runtime.

class PricingStrategy(ABC):
    def price(self, items): ...

class RegularPricing(PricingStrategy):
    def price(self, items): return sum(i.price for i in items)

class BlackFridayPricing(PricingStrategy):
    def price(self, items): return sum(i.price for i in items) * 0.6

class Cart:
    def __init__(self, strategy): self.strategy = strategy
    def total(self): return self.strategy.price(self.items)

What if you don't? A giant if season == "black_friday" inside Cart. Every new sale is a code change to Cart (OCP violation). Hard to A/B test pricing.

Observer (Pub/Sub)

Intent: one-to-many notifications. The subject doesn't know who's listening.

Example: when OrderPlaced fires, the email service, the analytics service, and the warehouse service all react — independently, in their own classes. OrderService doesn't import any of them.

Every event-driven architecture, Kafka consumer, GUI event listener is Observer.

State

Intent: an object's behavior changes based on its internal state, but without sprawling if/elif.

Example: an Order behaves differently in DRAFT, PLACED, SHIPPED, DELIVERED, CANCELLED. Each state is its own class with allowed transitions.

See 07_learning_projects/p14_state_machine/ for a worked example.

Chain of Responsibility

Intent: pass a request through a pipeline of handlers; each decides whether to handle or pass on.

Example: middleware in FastAPI / Express. Request → Auth → RateLimit → Logging → Route. Each layer decides to block, transform, or forward.

When NOT to use a pattern Important

Story: a junior dev reads the GoF book and applies all 23 patterns to a 200-line CLI tool. The result is unreadable and untestable. Patterns are answers, not requirements.
  • Don't introduce a pattern before the problem appears. YAGNI (You Aren't Gonna Need It).
  • Don't use Singleton just to avoid passing an argument.
  • Don't use Abstract Factory for a single family.
  • Don't use Observer where a direct call would do.

Rule: when you've written the same if/elif for the third time, then reach for a pattern. The third repetition is what tells you it's a pattern, not the first.
