01Foundations of Data Systems

How a single-machine data system works end to end: what makes an application reliable, scalable and maintainable; how to choose a data model; how storage engines and indexes work under the hood; and how to evolve data formats as your application changes.

Part I · Foundations CHAPTER 01

Reliable, Scalable and Maintainable Applications

The three goals every data system should optimise for — and how to measure them.

Reliability Scalability Maintainability

# Reliability — "continuing to work correctly, even when things go wrong"

A system is reliable if it keeps delivering the expected service despite faults. The key distinction: a fault is one component deviating from its spec; a failure is the whole system stopping service. Reliability is about tolerating faults so they never escalate into failures.

Hardware faultsRandom & uncorrelated (disk, RAM, network). Handled with redundancy — replicas, spare machines, RAID.
Software errorsSystematic bugs, e.g. a runaway process or cascading failure. Harder — no redundancy fixes a bad bug; need isolation, timeouts, careful rollout.
Human errorsThe leading cause of outages. Mitigate with training, sandboxes, good monitoring, and fast rollback.

# Scalability — describing load, then coping with it

Scalability is the ability to keep performing well as load grows. First describe load with load parameters (requests/sec, read/write ratio, cache hit rate, fan-out), then describe performance.

Latency percentilesThe mean is a poor "typical" value. Use p50 (median), p95, p99, p999 — thresholds below which that fraction of requests fall.
Tail at scaleOne slow call can stall an entire end-user request (head-of-line blocking). High percentiles matter disproportionately; average percentiles are meaningless.
Scale up vs outVertical (bigger machine) vs horizontal (more machines); elastic (auto) vs manual scaling for predictable load.

# Maintainability — the three design principles

  • Operability — operations teams can keep the system healthy: visibility, monitoring, good default behaviour.
  • Simplicity — manage complexity with good abstractions, so new engineers can understand it.
  • Evolvability — making change easy: adapt to new requirements without rewriting everything.

Key terms

fault vs failure
component deviates from spec vs the whole system stops providing its service
load parameter
a number that captures load, e.g. tweets/sec, followers per user, cache hit rate
fan-out
delivering one new item to many recipients' caches
percentile (p95)
95% of requests are faster than this latency
SLO / SLA
service-level objective / agreement: e.g. median < 200 ms, p99 < 1 s, uptime ≥ 99.9%
redundancy
duplicated hardware to lower the chance of failure
From the book Twitter, Nov 2012: 4,600 tweets/sec average (12k+ peak), 300k home-timeline reads/sec. A tweet to an average account (~75 followers) becomes 75 cache writes — so 4.6k writes/sec becomes ~345k writes/sec. Hard disks: MTTF ~10–50 years ⇒ a 10,000-disk cluster should expect ~1 disk failure per day. Amazon specs services at the 99.9th percentile; a 100 ms latency increase cut sales ~1%; config/operator errors caused most outages, with hardware only 10–25%.
  • Work at write time (fan-out, fast reads) vs work at read time (JOIN on read) — Twitter chose writes because reads outnumber writes ~65:1.
  • Hardware redundancy protects against hardware faults but does nothing for software bugs.
  • Scaling up vs scaling out; elastic auto-scaling vs manual scaling for predictable load.

Data Models and Query Languages

The data model you pick shapes what problems you can express easily.

Relational vs Document Query languages Graph models

Data models are layered: bytes on disk → data structures → the data model → how your application sees the data. History: the hierarchical model couldn't express many-to-many, so the relational model (Codd, 1970) won; then NoSQL split into document stores (self-contained docs) and graph databases (everything possibly related). No single model fits every use case.

# Relational model vs document model

Relational (SQL)Tables, rows, columns, joins. Handles many-to-many via normalised foreign keys. Strict schema.
Document (NoSQL)Self-contained JSON-like documents — good locality, no joins, schema-on-read. Suits mostly-one-to-many / tree data.
Impedance mismatchThe awkward fit between objects in your code and relational rows. JSON reduces it for hierarchical data.

# Declarative vs imperative query languages

Declarative (SQL, Cypher, MongoDB's aggregation pipeline) says what you want and lets the system decide how — good for parallelism and reuse. Imperative says how, step by step. MapReduce sits in between: declarative at the framework level, with imperative map/reduce functions inside. 

// MongoDB's MapReduce for a URL-counting job (book fig 2-5)
db.observations.mapReduce(
  function map() { emit(this.month, this.num); },
  function reduce(month, nums) { return Array.sum(nums); },
  { out: "monthly-sales" }
)

# Graph-like data models

When relationships are the point (social networks, recommendation, fraud detection), use a property graph: vertices and edges with labels and key-value properties, queried declaratively. Triple-stores express the same idea as (subject, predicate, object) triples queried with SPARQL. 

// Cypher — declarative graph query on the example below
MATCH (person) -[:BORN_IN]-> () -[:WITHIN*0..]-> (loc {name: "United States"})
RETURN person.name
From the book The marine-biologist shark-count query (count per month) is expressible in SQL, MapReduce and the aggregation pipeline — the "moral": NoSQL keeps reinventing SQL. Schema-on-read (structure implicit until read) vs schema-on-write (enforced at write, like static typing) is a key flexibility trade-off.
  • Document locality (whole doc stored together, fast) vs needing joins/references across documents (doc model's weakness).
  • Schema flexibility / schema-on-read (easy evolution) vs enforced schema (integrity, clarity).
  • Normalised (no duplication, but joins needed) vs denormalised (fast reads, duplication to manage).
Part I · Foundations CHAPTER 03

Storage and Retrieval

How databases actually store and find your data: LSM-trees, B-trees, and columnar storage.

Storage engines OLTP vs OLAP Columnar storage

Storage engines split into OLTP (many small lookups, disk seek is the bottleneck) and OLAP / data warehouses (few huge scans, disk bandwidth is the bottleneck). OLTP engines come from two schools: log-structured (LSM) and update-in-place (B-tree).

# LSM-trees — append-only, merge in the background

Start with an append-only log + in-memory hash index (Bitcask). Evolve to SSTables (sorted string tables — keys sorted, so a sparse in-memory index suffices) and merge them into an LSM-tree: writes land in an in-memory memtable that flushes to an SSTable; a background compaction merges segments and discards stale values. Bloom filters skip disk reads for keys that are absent.

B-trees — update in place

The other school keeps keys in fixed-size pages (traditionally 4 KB) updated in place, with a write-ahead log (WAL) for crash recovery. Balanced, height O(log n), one key lives in one place. Rule of thumb: LSM is faster for writes, B-trees for reads; LSM compaction can cause latency spikes at high percentiles.

# Transaction processing vs analytics

OLTP is user-facing, keyed lookups, write-heavy. OLAP runs big analytical scans over most of the dataset. The data warehouse holds a copy of the data loaded by ETL, usually in a star schema: one central fact table (events) surrounded by dimension tables ("who, what, where, when"); a snowflake schema is a further-normalised star.

# Column-oriented storage

Instead of storing each row together, store each column's values together so a query reads only the columns it needs. Enables compact encodings — bitmap encoding plus run-length encoding — and multiple sort orders. Precomputed aggregates can be accelerated with data cubes, but cubes can't answer questions about dimensions they don't include.

From the book Memtables flush at "typically a few megabytes". B-tree pages are "traditionally 4 KB". Big enterprises (Apple, Walmart, eBay) hold tens of petabytes, mostly in fact tables. Sorted/run-length-compressed columns can shrink to a few KB even with billions of rows (Vertica uses multiple sort orders).
  • LSM vs B-tree: write throughput vs read performance and predictability; keys copied in many SSTables (LSM) vs one location (B-tree).
  • Append-only sequential writes vs update-in-place pages with WAL overhead.
  • Row-oriented (OLTP) vs column-oriented (OLAP) layout.
  • Precomputed cubes (fast, inflexible) vs raw data (flexible, slower).
Part I · Foundations CHAPTER 04

Encoding and Evolution

Turning data into bytes — and staying compatible as your schema changes.

Encoding formats Schema evolution Modes of data flow

# Formats for encoding data

Two goals: backward compatibility (new code reads old data) and forward compatibility (old code reads new data) — both needed for rolling upgrades. Formats span language-specific serialisation, textual JSON/XML/CSV, and schema-driven binary formats (Thrift, Protobuf, Avro).

Protobuf / ThriftFields are identified by numeric tags. The tag is the meaning: renaming a field is fine, changing a tag breaks old data; never reuse a tag.
AvroTag-free. Writer's schema and reader's schema are resolved at read time by field name — order-independent.
Language-specific formatsConvenient and fast, but single-language and fragile — deserialising untrusted data is a security risk.

# Schema evolution

Protobuf/Thrift: added fields must be optional or have defaults; a required field can never be removed. Avro: you may only add/remove fields that have defaults; null needs an explicit union type; renaming uses aliases (backward- but not forward-compatible). Avro's tag-free approach means schemas can be generated dynamically (e.g. exported from a relational schema) with no manual tag bookkeeping.

# Modes of data flow

Compatibility must hold wherever data flows: through databases (writer encodes, reader decodes), through services / REST / RPC, and through asynchronous message passing (message brokers or actors).

From the book The record with userName "Martin", favoriteNumber 1337, interests [daydreaming, hacking] encodes to 81 bytes (JSON) → 66 (MessagePack) → 59 (Thrift binary) → 34 (Thrift compact) → 33 (Protobuf) → 32 (Avro). Twitter returns tweet IDs twice — as number and string — because JSON numbers lose precision above 2^53.
  • Human-readable textual (JSON/XML) vs compact efficient binary (Thrift/Protobuf/Avro).
  • Protobuf/Thrift tags: stable and compact, but tags must be managed manually; Avro's tag-free scheme is dynamic-schema friendly but resolves at read time.
  • Binary formats save bandwidth/storage but need decoding to be human-readable.

Part II · Distributed Data CHAPTER 05

Replication

Keeping copies of the same data on multiple machines — and what consistency you sacrifice.

Leaders & followers Replication lag Multi-leader Leaderless

# Leaders and followers

Single-leader replication: all writes go to one leader, which streams changes to followers via a replication log; reads may hit any replica. Used by PostgreSQL, MySQL, MongoDB, Kafka. Replication can be synchronous (a follower confirms before commit — no data loss, but a slow follower blocks writes) or asynchronous (fast, but committed writes can be lost on leader failover). Practical systems use semi-synchronous: one sync follower, the rest async.

# Problems with replication lag

With async replication, a follower can be briefly behind. Three classic consistency models protect users:

Read-your-writesA user always sees their own writes — route reads to the leader, or exclude followers more than ~1 minute behind.
Monotonic readsReads never go backwards in time for one user — don't let a user bounce between an old and a new replica.
Consistent prefix readsState makes causal sense — e.g. you never see an answer before its question.

# Multi-leader replication

Writes accepted at several leaders (e.g. one per datacenter). Enables multi-datacenter writes and offline operation, but creates write conflicts that must be resolved: last-write-wins (LWW) forces an arbitrary order and silently discards concurrent writes; safer options merge concurrent values tracked with version vectors, or use CRDTs that auto-merge.

# Leaderless replication (Dynamo-style)

The client sends each write to several nodes and reads from several in parallel. With n replicas, require w write acks and r read acks; w + r > n guarantees at least one up-to-date replica is read. Convergence happens via read repair and anti-entropy. Sloppy quorums + hinted handoff raise write availability when home nodes are unreachable.

From the book Common config: odd n (3 or 5), w = r = (n+1)/2 rounded up. A read-heavy workload may use w = n, r = 1 — fast reads, but one failed node blocks all writes. Setting up a follower = consistent snapshot + catch-up position in the leader's log (PostgreSQL LSN, MySQL binlog coordinates).
  • Sync replication (no data loss, but blocks on a slow follower) vs async (available, but may lose recent writes on failover).
  • Single-leader (easy to reason about) vs multi-leader / leaderless (more robust, but weaker consistency and conflict handling needed).
  • Strict quorum (stronger guarantee, lower availability) vs sloppy quorum (higher write availability, weaker guarantee).
Part II · Distributed Data CHAPTER 06

Partitioning

Splitting a dataset that no longer fits one machine into shards — evenly, and without hot spots.

Key partitioning Secondary indexes Rebalancing & routing

# Key-range vs hash partitioning

Key-rangeKeys sorted; each partition owns a contiguous range. Efficient range scans, but hot spots when adjacent keys are hot (e.g. all writes go to "today").
Hashhash(key) decides the partition. Even load, but destroys ordering — range queries become inefficient. Cassandra/MongoDB use MD5; Voldemort uses FNV.
Compound keysA hybrid: one key part picks the partition, another provides sort order within it.

# Partitioning and secondary indexes

  • Document-partitioned (local index) — cheap writes, but queries are scatter/gather across all partitions.
  • Term-partitioned (global index) — reads served from one partition, but a write touches several index partitions.

# Rebalancing and request routing

Avoid hash mod N — most keys move whenever N changes. Instead use a fixed number of partitions per node, or dynamic split/merge of ranges (HBase splits partitions over 10 GB by default). For routing, clients can contact any node (which forwards), use a routing tier, or be partition-aware; ZooKeeper tracks partition→node assignments (used by HBase, SolrCloud, Kafka, Espresso).

From the book Fixed-partition example: a 10-node cluster split into 1,000 partitions (~100 per node), moving whole partitions on add/remove. Range partitioning: BigTable, HBase, RethinkDB, MongoDB < 2.4. Hash partitioning: Cassandra, DynamoDB, Riak, Voldemort.
  • Range (efficient range queries) vs hash (even load, no range queries).
  • Document-partitioned secondary index (cheap writes, expensive reads) vs term-partitioned (cheap reads, expensive writes).
  • Fixed partitions (operationally simple, caps max nodes) vs dynamic partitioning (flexible, more complex).
Part II · Distributed Data CHAPTER 07

Transactions

Making the app pretend that concurrency problems and faults don't exist — and what that costs.

ACID Isolation levels Serializability

# The slippery concept of a transaction

AtomicityAll-or-nothing: an aborted transaction writes nothing.
ConsistencyApp-level invariants hold (the least well-defined of the four).
IsolationConcurrent transactions don't interfere.
DurabilityCommitted data survives crashes (WAL, replication).

# Weak isolation levels

Databases default to levels weaker than serializable. Read committed prevents dirty reads and dirty writes (a popular default). Snapshot isolation (MVCC) reads a consistent snapshot: readers never block writers and vice versa, and it prevents read skew — but not lost updates or write skew.

The six race conditions serializability prevents

  • Dirty read — reading another transaction's uncommitted write.
  • Dirty write — overwriting another's uncommitted write.
  • Read skew — seeing inconsistent state across reads.
  • Lost update — a concurrent read-modify-write cycle overwrites another's write.
  • Write skew — acting on a premise stale by commit time (two on-call doctors both deciding to go off-call).
  • Phantom — a write that changes the result of another transaction's search.

# Three ways to implement serializability

Actual serial executionRun transactions one thread at a time (VoltDB, Redis, Datomic). Simple, but single-core throughput and requires short transactions as stored procedures.
Two-phase locking (2PL)Shared/exclusive locks held until commit; index-range locks stop phantoms. Correct but poor performance, deadlocks, unstable latency.
Serializable snapshot isolation (SSI)Optimistic: let transactions run, abort any whose execution wasn't serializable at commit (detects stale reads and writes that affect prior reads).
From the book Alice's $500 + $500 accounts: a $100 transfer observed mid-way shows only $900 total (read skew). SSI first described in 2008; serializable in PostgreSQL since 9.1; FoundationDB uses a similar algorithm. 2PL used by MySQL (InnoDB) and SQL Server serializable.
  • Weak isolation (good performance, but the app handles race conditions manually) vs serializable (correct, slower).
  • 2PL (correct, slow/unstable under contention) vs serial execution (simple, single-core bound) vs SSI (near-snapshot performance, but aborts under high contention).
Part II · Distributed Data CHAPTER 08

The Trouble with Distributed Systems

Unreliable networks, unreliable clocks, and the truth problem — why distributed systems are hard.

Partial failures Unreliable networks Unreliable clocks Truth & lies

# Faults and partial failures

A distributed system never fails all at once — any node can be slow, unresponsive, or dead. A timeout cannot distinguish "packet lost", "delayed" or "still processing". There is no shared state, so nodes must agree over an unreliable network.

# Unreliable networks

Packets may be lost or arbitrarily delayed; the reply can be lost even when the message was delivered. Real networks have unbounded delays (bounded-delay "synchronous" networks are expensive), so algorithms lean on timeouts — which are guesses.

# Unreliable clocks

Time-of-day (wall) clocksNTP-synced, can jump forward/back, ignore leap seconds. Dangerous for ordering decisions.
Monotonic clocksMeasure durations only; always move forward; meaningless across machines (CLOCK_MONOTONIC, nanoTime).

Process pauses (stop-the-world GC, scheduling) can pause a node so long it's declared dead and later "resurrects" — hence leases and fencing tokens to block stale actions.

# Knowledge, truth and lies

A node cannot trust its own judgment — truth is decided by the majority. Byzantine faults (nodes that deliberately lie) require a supermajority (> 2/3) and are impractical in datacenter systems, where nodes are assumed "unreliable but honest". Algorithms must match the real system model, not a tidy theoretical one.

From the book Google assumes 200 ppm clock drift ≈ 6 ms drift with 30 s resync, or 17 s drift with daily resync. NTP over the internet: minimum error ~35 ms, occasional spikes around a second. Byzantine tolerance: with 4 nodes, at most 1 may malfunction. A Gigabit NIC can "limp" at 1 kilobit/s (driver bug) — a degraded-but-alive node.
  • Bounded-delay networks give guarantees but are expensive and under-utilise hardware; most systems choose cheap and unreliable.
  • Timeouts: too short → false suspicions and churn; too long → slow failure detection.
  • Byzantine fault tolerance is impractical for datacenters; assume honest-but-fallible nodes instead.
Part II · Distributed Data CHAPTER 09

Consistency and Consensus

From linearizability to total order broadcast, distributed transactions, and consensus algorithms.

Linearizability Ordering guarantees Consensus

# Consistency guarantees and linearizability

Linearizability makes replicated data behave like a single atomic copy: each operation appears to take effect at one point between its start and end, and reads see the latest write. Cost: Attiya & Welch proved response time must be at least proportional to network-delay uncertainty. Causality ("happens-before") is weaker but needs far less coordination, captured by version vectors or Lamport timestamps. Lamport timestamps give a total order consistent with causality, but can't decide concurrency — which motivates consensus.

# Ordering guarantees

Total order broadcast (a.k.a. atomic broadcast) = reliable delivery + totally ordered delivery to all nodes — equivalent to a replication log and to repeated rounds of consensus, and the basis of state-machine replication (every replica applies the same writes in the same order).

Distributed transactions: two-phase commit

2PC: a coordinator asks each participant to prepare; on unanimous "yes" it decides commit — participants may not abort after "yes". If the coordinator crashes after votes, in-doubt participants wait indefinitely (no termination). Not to be confused with two-phase locking.

# Fault-tolerant consensus

Consensus properties: agreement, integrity, validity, termination. Requires a majority quorum and assumes crash-stop, no Byzantine faults. Algorithms: Viewstamped Replication, Paxos (via Multi-Paxos), Raft, Zab. A leader needs a majority for every decision, so only the majority side of a partition can make progress. Coordination services like ZooKeeper and etcd expose total order broadcast, linearizable compare-and-set, locks/leases, fencing tokens and group membership.

From the book Majority math: 3 nodes tolerate 1 failure; 5 nodes tolerate 2. Linearizable CAS can be built from a replicated log: append the intent, wait for delivery, and check the first claim wins. ZooKeeper's zxid doubles as a fencing token. Raft edge case: one consistently unreliable link can bounce leadership forever so the system never makes progress.
  • Linearizability (easy to reason about, slow under high network delay) vs causal consistency (faster, but can't implement uniqueness).
  • Consensus gives safety + fault tolerance but needs majority quorums, is effectively synchronous replication, and only the majority side progresses.
  • Prefer a proven coordination service (ZooKeeper) over writing your own consensus — implementing it correctly is very hard.

Part III · Derived Data CHAPTER 10

Batch Processing

Bounded input, terminating job: Unix philosophy → MapReduce → dataflow engines.

Unix philosophy MapReduce Joins Dataflow engines

# Batch processing with Unix tools

Batch jobs read a bounded input, produce output derived from it, and terminate. The Unix philosophy — do one thing well; compose small tools; uniform interface of files/pipes — is the seed of everything that follows. The canonical example: count URL frequencies in a web log. 

# count URL frequencies (book fig 10-1)
cat /var/log/nginx/access.log |
  awk '{print $7}' |
  sort |
  uniq -c

# MapReduce and distributed filesystems

Write two stateless callbacks: map (emit a key/value per record) and reduce (combine values sharing a key). The framework shuffles and sorts all key/value pairs by key between the phases. On top of a distributed filesystem (GFS/HDFS): shared-nothing, blocks replicated for fault tolerance, a central NameNode tracks placement, and data locality matters.

# Joins

  • Sort-merge join (reduce-side): both inputs partitioned and sorted by join key; the reducer merges them.
  • Broadcast hash join (map-side): the small input is loaded as a hash table into every mapper of the large input.
  • Partitioned hash join (map-side): both inputs share the same partitioning, hash-joined per partition.

# Beyond MapReduce: dataflow engines

Spark, Tez, Flink (rooted in Dryad, FlumeJava) pipe data between operators, avoiding the sort + materialise-to-disk step unless needed, keep more in memory, and recompute lost data on failure. Declarative APIs with query optimisers (Hive, Spark DataFrames, Impala) converge with MPP databases while keeping the flexibility to run arbitrary code.

From the book HDFS deployments at the time of writing: tens of thousands of machines, hundreds of petabytes. Mapper output goes to the mapper's local disk, then partitioned/sorted/merged into a configurable number of reducer partitions. Because failed tasks are retried and their partial output discarded, the visible result appears as if every record was processed exactly once.
  • MapReduce materialises intermediate state to the distributed filesystem (easy recovery, but slow even with no failures) vs dataflow engines that keep data in memory (faster, but recompute more on failure and need deterministic operators).
  • Sorting is expensive — dataflow engines skip it unless required.
  • The restricted model (stateless callbacks, no side effects) buys strong reliability but sacrifices expressiveness.
Part III · Derived Data CHAPTER 11

Stream Processing

The same work as batch, but continuous — on an unbounded input that never ends.

Event streams Brokers CDC & event sourcing Exactly-once

# Transmitting event streams

Event streams — user activity, sensor readings, market data — are unbounded inputs, so a stream job never completes. The streaming equivalent of a filesystem is the message broker.

# Two kinds of brokers

AMQP / JMS styleEach message to one consumer, individual acks, messages deleted after ack — good as async task queues.
Log-based (Kafka, Kinesis)Messages kept on disk; all messages in a partition delivered in order to one consumer; progress tracked by checkpointed offsets; replayable.

# Databases and streams: CDC & event sourcing

Change data capture (CDC) extracts a database's changelog (Databus, Debezium, Maxwell, Bottled Water) so derived systems stay in sync. Log compaction keeps only the latest value per key — a compacted topic is effectively a full copy of the database. Event sourcing stores application state as an append-only log of immutable events; state is derived by deterministic replay.

# Processing streams, windows, and exactly-once

  • Stream joins: stream-stream (match two events within a window), stream-table (enrichment), table-table (two changelogs → a materialized view).
  • Time: distinguish processing time from event timestamps; out-of-order stragglers complicate event-time windows.
  • Exactly-once: microbatching (Spark Streaming, ~1 s), periodic checkpointing (Flink barriers), atomic commit of output+state+offset (Cloud Dataflow), or idempotent writes (offset stored with the value).
From the book Kafka benchmark cited in the book: ~2 million writes/second on three commodity machines. Flink writes periodic rolling checkpoints to durable storage, triggered by barriers in the stream. Twitter's stream-table example: home timelines as the join of tweets and follows. Samza / Kafka Streams replicate operator state to a log-compacted topic.
  • AMQP/JMS brokers (simple task queues, delete-after-ack) vs log-based brokers (ordered, replayable — right for streams and derived data).
  • Microbatching (simpler, ~1 s latency, processing-time windows) vs continuous checkpointing (lower latency, more complexity).
  • Exactly-once via idempotence (cheap, but needs ordered replay and determinism) vs atomic commit (correct, but coordination overhead).

The Future of Data Systems

Integrating many specialised systems — and unbundling the database.

Data integration Unbundling Responsibility
Source note Chapter 12 is the book's synthesis chapter. This summary is reconstructed from the published book's known content (the supplied PDF's text extraction ends at Chapter 11's references); the page-level detail is faithful in substance, but verify specifics against your copy.

# Data integration — the two strategies for keeping systems in sync

No one system fits all problems, so applications combine databases, caches, search indexes, analytics and ML tools — the hard part is keeping them consistent. Kleppmann frames two fundamental strategies:

  • Distributed transactions — synchronous coordination: atomicity and linearizability, but expensive and fragile.
  • Derived data — one system of record, every other system a derived view updated asynchronously from a change log.

# Unbundling the database

A single database is internally a composition of indexes and materialized views. Unbundling re-implements this by composing separate specialised products connected by asynchronous streams — e.g. Twitter combines MySQL (system of record), Redis (cache), Lucene (search) and analytics. The application code that consumes the change log and updates derived systems is itself the derivation function maintaining those views.

Write path vs read path

Separate the write path (updating derived state from the log) from the read path (serving queries from that state) — a clean way to optimise caching, materialized views, and offline-capable clients. A search index or a cache can be rebuilt from scratch by consuming a log-compacted change stream from offset 0.

# Doing the right thing

The book closes on responsibility: predictive analytics and algorithmic decisions affect people's lives. Designers are responsible for algorithmic accountability, fairness and bias awareness, privacy, and guarding against surveillance. Technology is not neutral — and the engineer chooses the consequences.

From the book A search index, a cache, and an analytics column store are each a materialized view of the same system of record. Validation must happen before a command becomes an immutable event — consumers can't reject an already-written event; a tentative-event-then-confirm pattern allows asynchronous validation (e.g. reserving a unique seat).
  • Distributed transactions (strong atomicity/linearizability, but coordination cost, availability risk, poor scaling) vs derived data (cheap, scalable, asynchronous, but only eventual consistency — and uniqueness/multi-object writes need care).
  • Monolithic database (simpler integrity guarantees, one vendor) vs unbundled systems (best tool per job, but you own the glue code, schema changes and constraint enforcement).
  • Prediction, personalisation and tracking trade off against privacy, fairness and accountability — these are design choices, not givens.
The arc of the book: foundations → distributed data → derived data. If you remember one idea, make it this — decouple the write path from the read path, and treat every system of record as a stream.

Dates and claims were verified against public sources (linked at the bottom) in mid-2026; specific product facts may drift after that. It is a snapshot of where the field stands, not an exhaustive survey.

# Storage & retrieval (Ch 3) — the lakehouse, in-process OLAP, vector indexes

The biggest structural change since 2017 is the collapse of the warehouse / lake / engine distinction into open table formats over object storage, plus a new family of in-process and vector engines the book could only gesture at.

Lakehouse & open table formatsDelta Lake (Databricks, 2019), Apache Iceberg (Netflix → Apache, 2018) and Apache Hudi (Uber, 2017) bring warehouse-grade ACID, versioning, time travel and schema evolution to Parquet files on S3. Databricks popularised the "lakehouse" term in 2020; Iceberg became the de facto standard — Snowflake and AWS now support it natively, and Databricks acquired Tabular (its creators) in June 2024.
In-process OLAP: DuckDBDuckDB (SIGMOD 2019, v1.0 in June 2024) is "SQLite for analytics" — a vectorised columnar engine that queries Parquet/CSV directly, no server. DuckDB Labs (2021) and MotherDuck (2022) industrialised it. It validates Ch 3's OLAP story while inverting the assumption that analytics must be distributed.
Real-time columnar: ClickHouseOpen-sourced by Yandex in 2016, ClickHouse became the default for real-time analytics and observability — billions of rows/sec per server, C++, no JVM, shard/replica scale-out.
Vector indexes — a new storage tierEmbeddings created demand for similarity search: pgvector (HNSW index in v0.5.0, Aug 2023), Milvus, Qdrant, Weaviate, Pinecone. Graph-based ANN (HNSW) is the modern extension of Ch 3's "other indexing structures" — a whole new index type for ML workloads.

Encoding & schemas (Ch 4) — columnar interchange as the new "schema"

Apache Arrow (2016) standardised an in-memory columnar layout with zero-copy exchange between engines; Parquet (2013) is its on-disk counterpart. Query engines (DuckDB, Polars, DataFusion, pandas) now share one memory layout. Meanwhile open table formats made schema evolution a first-class, versioned operation — the Ch 4 lesson ("schemas are about compatibility over time") is now enforced by the storage layer itself.

# Consensus & the cloud (Ch 5, 6, 9) — distributed SQL and storage/compute separation

Distributed SQL went mainstreamCockroachDB (Raft, PostgreSQL-wire, serializable isolation), TiDB (Raft, MySQL-wire, TiFlash columnar HTAP), YugabyteDB, and Google Spanner (public on GCP since 2017) productised Ch 9's Paxos/Raft + serializable-snapshot ideas. Raft, not Paxos, won the implementation race.
Kafka deleted ZooKeeperKRaft (KIP-500, 2019 → production in Kafka 3.3, 2022 → ZooKeeper fully removed in Kafka 4.0, March 2025) replaced the ZooKeeper that Ch 9 discusses as the coordination service. Kafka 4.0 also added a new consumer-rebalance protocol (KIP-848) and "queues" semantics (KIP-932).
Storage/compute separation became the cloud defaultAWS Aurora (log-based storage, 6-way replication with 4/6 quorum) and Neon (serverless Postgres; pageserver + Paxos-based safekeepers; scale-to-zero; code-like branching) make compute stateless and elastic. Snowflake/BigQuery do the same at warehouse scale — Ch 6's partitioning story, now at the architectural level.
Serverless & autoscalingDatabases now scale to zero and resume on demand (Neon), or autoscale within a pool — an operational evolution of Ch 1's "approaches for coping with load".

# Streaming & CDC (Ch 5, 11) — Flink rises, brokers evolve, CDC becomes standard

Apache Flink became the strategic stream engineConfluent acquired Immerok (Jan 2023) and bet on Flink SQL; ksqlDB is effectively in maintenance mode. Flink's watermarks, externalised state, and true event-time won over library-based approaches for serious stateful pipelines.
Brokers diversifiedRedpanda (C++/Seastar, Raft-based, Kafka-API compatible, source-available BSL) targets lean ops and low latency; Apache Pulsar (BookKeeper-based compute/storage separation) targets multi-tenant and long-retention use cases.
CDC is now standard practiceDebezium (3.0, Oct 2024; moved to the Commonhaus Foundation in 2025) is built into Confluent, AWS MSK and most modern stacks. Ch 11's "databases as streams" thesis — change data capture plus the outbox pattern — is a commodity every team reaches for.
Object-storage tieringKafka 4.0's diskless topics (KIP-1150) let brokers serve from object storage — the streaming-log equivalent of Ch 3's "keep everything in memory" pushed to cheap tiers.

# Ch 12's vision, supercharged by AI

The book's closing thesis — unbundle the database; treat every system of record as a stream; derive everything else — turned out to describe the 2020s. Two developments extended it:

  • Data mesh (Zhamak Dehghani, Thoughtworks, 2019): domain-oriented decentralised ownership, data as a product, a self-serve platform, and federated governance — the organisational answer to the integration problem Ch 12 poses.
  • The AI convergence: RAG made vector stores a new derived-data tier on top of the system of record; GraphRAG (Microsoft, open-sourced July 2024) added knowledge-graph retrieval; Model Context Protocol (Anthropic, Nov 2024) became the standard for agents to talk to data systems; "context engineering" replaced prompt stuffing. LLMs are the new consumers of your change logs.
